# Data model

Money uses C# decimal and PostgreSQL numeric(18,2). API money is a canonical dot-decimal string with the currency in a sibling field, as a lowercase ISO 4217 code such as `eur`. Amounts exceeding the column's range or using grouping separators are rejected. Money rounds to two places with midpoints away from zero (`Money.Round`), so 0.125 becomes 0.13 and -0.125 becomes -0.13. Browser numbers are used for display/charts; persisted values go through validated decimal strings.

Accounts have a starting balance in their main currency. Balances are computed per currency from the starting balance, transactions, both transfer directions and both sides of currency conversions; nothing is a stored running total. `currentBalance` is those balances valued in the account's main currency at the newest rate, and `reportingBalance` is the same in the reporting currency. Transactions carry account, date, flow type, amount, description, source and optional bank reference. The amount is positive except for a refund, an expense whose amount is negative (see [Refunds](#refunds)). Split transactions use TransactionLine rows; editing replaces the lines physically, because the new set is what takes their place, while deleting the transaction leaves them alone so that restoring it brings its categories back.
`TransactionLine.Position` (`integer`, from 0) is the line's place in the request that wrote it, and every read orders a transaction's lines by `Position` then `Id`, so the lines come back in the order they were entered. The `OrderTransactionLines` migration of 2026-10-01 added it as generated, with every existing line at 0 and no backfill, so the old lines keep the `Id` order they were read in before, an arbitrary but fixed order. Other owned entities normally use soft deletion and timestamps.

Storage is single-sided on purpose: a transaction names one account and its category, a transfer and a conversion carry both of their sides, an investment entry carries its cash leg, and `AccountMovements` computes the balances. That is double-entry in all but storage, because a transaction's other side is its category. The member export's `ledger.beancount` writes the other sides out as a balanced Beancount journal and asserts the app's balances in it, which gives the proof double-entry is for without rewriting every reader of these shapes; see [Data export per user](features/data-export-per-user.md#double-entry-journal) and the [decision](decisions/exports.md).

Soft deletion is now reversible for the records whose delete touches nothing else. `DeletionEntry` is the trash row: an `OwnableEntity` holding the `Kind` (stored as its name), the `EntityId` of the deleted record, the `Description` it read by at the time (at most 200 characters), `DeletedAt`, a nullable `RestoredAt` and a nullable `CompanionId` for the fee transaction a currency conversion takes with it. Indexes on (UserId, DeletedAt) and (Kind, EntityId) serve the list and the restore lookup. Each feature's `DeleteAsync` writes the entry through `IDeletionRecorder` in the same `SaveChanges` as the soft delete, so one cannot exist without the other; the recorder leaves `DeletedAt` unset and `AppDbContext.ApplyEntityRules` stamps it with the save's own clock reading, the same instant it writes into the deleted row's `UpdatedAt`, and a cascade such as a conversion's fee gets no entry of its own. Restoring flips `IsDeleted` back and stamps `RestoredAt`, again in one save. Seventeen kinds are covered — transaction, transfer, conversion, budget, goal, asset, debt, recurring entry, investment entry, category, tag, categorization rule, household, attachment, CSV import mapping, split expense and settle-up payment.
Category, tag, categorization rule, household and, since 2026-10-01, the ungroup of a transaction group also clear foreign keys, remove join rows or un-share records, so their delete writes one `DeletionChange` row per row it rewrote: the entry id, a `Kind` naming what was done (`TransactionCategory`, `LineCategory`, `RecurringBillCategory`, `Budget`, `TransactionTag`, `RuleTag`, `AccountShare`, `CategoryShare`, `TagShare`, stored as its name) and the `RowId`, with (DeletionEntryId, Kind, RowId) as the primary key and a cascading foreign key to the entry. The previous value is implied by the entry, so it is not stored. A restore puts back only the recorded rows that are still in the state the delete left them in. Archiving an account stays its own named operation. The 30-day retention window is both a read filter and, since 2026-09-23, a sweep: `RetentionJob` hard-deletes the entries and their changes past the window, and the records thirteen of the seventeen kinds point at, taking dependent rows and attachment files with them.
Categories, tags and households are left soft-deleted because restricting foreign keys still point at them, and attachments stay with `RetentionJob`. Both the filter and the sweep read the cutoff from `DeletionEntry.WindowStart`, so the job cannot take a row the trash still offers; the reasoning is in [Trash and undo](features/trash-and-undo.md).

`AuditEvent` is the household activity log: one row per thing a person did to a record shared into a household, written from the `SaveChangesAsync` override of `AppDbContext` out of the change tracker, in the same save as the change. It is a plain class — no owner column, no soft delete, no query filter — holding the `HouseholdId` (cascading foreign key), the `ActorUserId` (restricting foreign key to the user), since 2026-10-01 `ViaToken`, the name of the personal API token the change came through or null (at most 60 characters), `OccurredAt`, the `Action` and `EntityKind` stored as their names, a nullable `EntityId`, the `Description` it read by at the time (at most 200 characters), a nullable `Count` for an import or bulk edit, and `Changes`, a `jsonb` list of at most 12 `{field, from, to}` display strings, each value cut to 120 characters. Indexes on (HouseholdId, OccurredAt) and OccurredAt serve the read and the prune. A transfer between two households writes a row in each; personal records write none; an import or bulk edit writes one summarising row per household. `RetentionJob` deletes rows older than 400 days (`AuditEvent.RetentionDays`). Details in [Audit log](features/audit-log.md).

Transactions have a unique account/import-reference index, including soft-deleted rows, an account/date index that serves the account filter of the ledger and the balance queries, and the `TransactionTags` index on (TagId, TransactionId) that serves the tag filter, which becomes one `EXISTS` subquery per chosen tag rather than a lookup per row; investment entries have the same pair, and transfers are read by user and date or through their two account foreign keys, so they need no further index. TransferImports retains immutable bank-entry receipts for imported/matched transfers and a unique account/reference. A transfer takes at most one receipt per account: a second bank entry of the same account that points at an already matched transfer is refused with `import.transferAlreadyMatched`, while the entry of the other account still matches it. A receipt also fixes part of its transfer against later edits: the date, the receipt's account staying on its side of the transfer, and the amount on that side; the description, the other account and, between currencies, the other amount stay editable. Broker deposits and withdrawals carry the same receipt on the brokerage account. Normal transaction import history and transfer receipts are checked together. Imports serialize per target account with a PostgreSQL transaction advisory lock.

A `Tag` is the second way to classify a transaction and is built from the same pieces as a `Category`: it is an `OwnableEntity` that implements `IShareable`, so it gets the owner column, its restricting foreign key and the shareable query filter with the active-household narrowing without any code of its own. It stores a name of at most 50 characters, the scope and the optional household, and nothing else — no icon and no flow type, because a tag answers "what was this payment for" rather than "what kind of spending was it", and the same tag is meaningful on income and on an expense. The name is unique per owner ignoring case, checked in `TagService` with a case-insensitive comparison and answered with 409 `conflict.duplicate`, and backed by a unique index on (UserId, Name) filtered to `IsDeleted = false`, so the exact duplicate of a race is refused by the database and a deleted name becomes free again.

`TransactionAttachment` is a file attached to a transaction: an `OwnableEntity` whose `UserId` is the uploader and whose `CreatedAt` is the upload time, holding the `TransactionId` (restricting foreign key), the sanitized `FileName` (at most 120 characters, shown only, never a path), the `ContentType` detected from the file's first bytes (at most 60), `SizeBytes` and the lowercase hex `Sha256` (`character(64)`). The bytes live in the attachment directory under the row's id, not in the database. Its query filter is its own rather than the owner filter: an attachment is visible when it is not deleted and its transaction is, so it follows the account's sharing and the active household, a household member sees the files another member uploaded, and deleting or archiving hides the files with the transaction without touching them. One index on (TransactionId, CreatedAt) serves the list and the ledger's count. A transaction holds at most ten files of at most 10 MB. Details in [Attachments](features/attachments.md).

A `Debt` can carry its repayment terms in five columns added on 2026-09-21: `LoanAmount` (numeric(18,2)), `FirstPaymentDate` (date), `TermMonths` (integer, 1 to 600), `MonthlyPayment` (numeric(18,2)) and `AmortizationType` (integer, `Annuity` = 0 by default, `Linear` = 1). The first four are nullable, so a debt stored before has no terms and no schedule; `TermMonths` and `MonthlyPayment` are never both set. The repayment schedule is computed from them on request by `Common/Amortization/AmortizationCalculator` and is not stored, and `OutstandingAmount` stays the recorded balance that net worth subtracts, unless the debt tracks its payments.

`Debt.TracksPayments` (boolean, false by default) and the `DebtPayments` table were added by the `AddDebtPayments` migration of 2026-09-27. A `DebtPayment` is an `OwnableEntity` owned by the debt's owner: `DebtId`, `TransactionId`, `Kind` (integer, `Regular` = 0, `Extra` = 1) and an optional `Principal` (numeric(18,2), in the debt's currency) typed from the bank statement. A unique index on `TransactionId` (where not deleted) lets a transaction pay at most one debt. Both foreign keys cascade, overriding the Restrict convention, so the retention purge of a debt or a transaction takes its links with it; a soft delete on either side leaves the link, and the balance skips it. Unlinking deletes the row for good. `RecurringBill.DebtId` is a nullable foreign key with delete behaviour `SetNull`, set only on the expense shape, so purging a debt does not block on the entries that paid it. The tracked balance is derived on read by `Common/Amortization/DebtBalance` and never stored. See [Debt amortization](features/debt-amortization.md#tracking-payments).

`TransactionTag` is the many-to-many row between `Transaction` and `Tag`: the two ids are its primary key and there is a second index on (TagId, TransactionId) for the ledger filter and the report breakdown. Like `TransactionLine` it is a plain class rather than an `EntityBase`, so it has no timestamps, no soft deletion and no query filter; it is only ever reached through a transaction or a tag, and both of those are filtered. Split lines carry no tags: a tag describes the payment, the split divides it between categories, and putting tags on both would let one amount count twice under the same tag. A transaction carries at most ten tags, which is also the cap on the ledger's tag filter.

`DuplicateDismissal`, added by the `AddDuplicateDismissals` migration of 2026-10-01, is the "keep both" answer to a [possible duplicate](features/transactions.md#possible-duplicates): `TransactionId` and `OtherTransactionId`, the two rows of the pair, are its primary key, each a foreign key to `Transactions` with delete behaviour Cascade, and `OtherTransactionId` has its own index for the reversed lookup. Like `TransactionTag` it is a plain class with no owner, no timestamps, no soft deletion and no query filter: the duplicates query reads it only beside two transactions it can already see, so a pair kept by one household member is kept for everyone who sees the shared account. Deleting a transaction leaves the row, so restoring it from the trash restores the answer; the retention purge removes it with the transaction through the cascade. It is not audited and not in the trash.

A `CategorizationRule` is an `OwnableEntity` and deliberately not an `IShareable`: it is a personal habit rather than a household fact, so the plain owner filter is its whole visibility story and nobody but the owner can list, edit, reorder, delete or run it. It stores a name, a 0-based `Position` that is kept dense per owner, the condition (`Match` of `Contains`, `StartsWith` or `Exact`, plus a `Pattern` of at most 200 characters), the optional narrowings (`AccountId`, `MinAmount`, `MaxAmount`) and the optional `CategoryId` it sets; the tags it adds live in `CategorizationRuleTags`, a plain join row of (RuleId, TagId) built exactly like `TransactionTag`, cascading from the rule and restricted on the tag. A rule has to set a category, a tag, or both, and at most 100 rules belong to one user. Positions are renumbered 0, 1, 2 inside the same database transaction whenever a rule is moved or deleted, so a gap or a tie is not representable. The index on (UserId, Position) serves the only read there is, the ordered list. What a rule reaches is a separate question from who owns it: a run evaluates through the account-filtered transaction query, so a rule of one member does touch a shared account's rows, the same way that member could have set the category by hand.

`SuggestedRuleDismissal`, added by the `AddSuggestedRuleDismissals` migration of 2026-09-29, is the only row rule suggestions write; the suggestions themselves are computed on every read and never stored. It is an `OwnableEntity`, personal like the rules, holding `Key`, the normalized description of at most 200 characters, and `CategoryId`, a foreign key with delete behaviour Restrict. A filtered unique index on (UserId, Key, CategoryId) where `IsDeleted = false` keeps one row per pair per person, as in `SubscriptionDismissal`; the service looks for the row first, so dismissing twice is a no-op. A category is soft-deleted, so its dismissals simply stop mattering and never block the delete. See [Categorization rules](features/categorization-rules.md#suggested-rules).

Accounts, Categories, Tags, Budgets, Goals, RecurringBills, Assets and Debts carry owner, Personal/Shared scope and optional household (the `ShareAssetsAndDebts` migration of 2026-09-30 added the two columns to assets and debts, with an index and a restricting foreign key). An asset's valuations and a debt's recorded balances and payment links follow their parent: `DebtPayment` is visible when its debt is. HouseholdMembership assigns Owner/Member independently from application Admin/Member roles. Transaction visibility follows the account. Transfer visibility follows either endpoint; mutation requires both, and an update that changes an account requires the new account as well. Notifications, net-worth snapshots and month closes remain personal.

A request can narrow that visibility to one household. No column stores the choice: `ICurrentUser` gained an `ActiveHouseholdId` that the HTTP implementation reads from the validated `X-Active-Household` header, defaults to "no household" everywhere else, and that the shareable query filter appends to as "the record is personal, or its household is the active one". Everything that hangs off an account — transactions, transfers, conversions, investment entries — narrows with it, because those filters already ask whether the account is visible. The filter narrows and never widens: the membership condition that was there before still has to hold, so a household the caller is not a member of stays invisible whatever the header says.

Deleting a categorization rule takes its `CategorizationRuleTags` rows with it and renumbers the rules below it; the transactions it filled in earlier keep their category and their tags, because a rule writes once and owns nothing afterwards. Deleting a category unsets category references in transactions, split lines and bills, and retires dependent budgets. Those two, a tag delete and deleting a household are the deletes that rewrite other rows; each records the ids it rewrote as `DeletionChanges`, which is what makes them restorable. Deleting a tag is the same rule applied to the join table: its `TransactionTags` rows are deleted outright inside one database transaction and the tag is then soft-deleted, while the transactions themselves — their amounts, categories, split lines and dates — are untouched. The join rows are deleted rather than soft-deleted because the pair of ids is the whole record and a retired pair would only add a condition to every filter query. Archiving an account hides its transactions through the account visibility filter, and nothing else: no foreign key is cleared and no row is rewritten, so restoring it only sets `IsDeleted` back and everything hanging off it is visible again. The one column that can change while it is archived is its sharing, because removing its owner from the household or deleting the household makes it personal exactly as it does an active account. A transfer's visible side continues to contribute to the balance of its remaining visible account.

A net-worth snapshot is unique per user/local date. Reads and the hourly job update today's value under a per-user lock. The reliability migration retains the latest row if older concurrent reads created duplicate daily snapshots. Historical points represent observations on those dates, not a reconstruction of days when the application was off. Snapshot columns are numeric(18,2) like every money column; when a total of the day does not fit, the totals are still answered and no snapshot is written for that read. Goal amounts are never negative: the target is above zero and the current amount is zero or more.

A goal also stores where its progress comes from: `Funding` (manual or account), a nullable `FundingAccountId` pointing at an account with delete behaviour Restrict, and `FundingSharePercent`, a whole percentage from 1 to 100 that defaults to 100. A manual goal keeps the account empty and reports the stored `CurrentAmount`. A funded goal keeps the account set and reports that share of the account's reporting balance, computed while the request is answered from the same balance service the accounts endpoints use, clamped at zero and never written to a column; its `CurrentAmount` stays as it was and is ignored, which is what lets an edit move a goal between the two modes without losing the typed amount. Because archiving an account is a soft delete and the row stays, the foreign key never blocks it: the account simply drops out of the query filter, and the goal answers a null progress instead.

A budget stores its category, its limit, a `Period` (`Monthly`, `Weekly`, `Quarterly` or `Yearly`, held as the integer the enum declares, with `Monthly` pinned at 0 so rows written before periods existed keep their meaning) and `RolloverEnabled`, added with a default of false so those same rows behave exactly as before. It stores no dates: the window it is read against is derived from the period and from today in the installation time zone, and for a weekly budget from `InstanceSettings.FirstDayOfWeek`, by `BudgetWindow` in the domain. A category may hold one budget per period, checked in the service rather than by a unique index, and the carry a rollover budget shows is recomputed on each read by walking back at most twelve windows, never past the window that holds the budget's `CreatedAt`. `CategoryAttribution` carries the transaction date for this, so one query over the whole walked span is bucketed per window in memory.

RecurringBill stores what a confirmation writes, kind, optional amount/account/category, cadence, NextDueDate, reminder lead days and active state. `Shape` (`Expense`, `Income` or `Transfer`) is an integer with `Expense` pinned at 0, so every row written before shapes existed still means what it meant. `ToAccountId` is a second nullable account with delete behaviour Restrict, set only by a transfer, where `AccountId` is the account the money leaves and `ToAccountId` the account it arrives in; an expense or an income leaves it empty and a transfer leaves `CategoryId` empty. The table keeps its name: renaming it would mean a migration that no backup taken by an older version could be restored into, since a backup file names the tables it carries. Confirmation carries ExpectedDueDate; a per-entry database lock and date concurrency token prevent duplicate occurrence posting. `MatchKey`, a nullable string of at most 200 characters added on 2026-09-26, is the normalized bank text the entry's charges carry; it is normalized again on save, stored as null when empty, and when it is null the entry's normalized name stands in for it, both in the price-rise check and in subscription detection's coverage check. See [Unusual amounts](features/unusual-amounts.md).

`SubscriptionDismissal` is the only row subscription detection writes. It is an `OwnableEntity` and not an `IShareable`, so the plain owner filter is its whole visibility story: a dismissal is one person's judgement about one group, and two members of a household may disagree about a payment on the account they share. It stores nothing but the group — `AccountId` with delete behaviour Restrict, and `Description`, the normalized description at most 200 characters long — and never the transactions that produced the group, which is what makes a dismissal survive a new payment arriving in it. A filtered unique index on (UserId, AccountId, Description) where `IsDeleted = false` keeps one row per group per person and lets a group be dismissed again after a row is deleted; the service looks for the row first, so dismissing twice is a no-op rather than a conflict. Nothing else references the table and detection itself writes nothing at all. Backups need no change: `BackupDatabase.ReadShapes` enumerates the tables from the EF model rather than from a list, so a new table is carried the moment it is mapped.

Notification is the shared row every producer writes: owner, `Type` (`BillDue`, `BudgetWarning`, `BudgetExceeded`, since 2026-09-26 `UnusualAmount`, `UnusualAmounts` and `RecurringPriceRise`, since 2026-09-27 `MonthReadyToClose` and since 2026-09-29 `MonthlyDigest`), a `Title` that names the thing the notification is about, a plain-text `Message`, `RelatedType` and `RelatedId` pointing at the row that caused it, the channel and the read flag. It also stores `Payload`, a nullable `jsonb` column holding a `NotificationPayload` record — `DueDate`, `ThresholdPercent`, `Period`, `Shape`, for the unusual-amount and price-rise kinds `TransactionId`, `BillId`, `Amount` and `TypicalAmount` (decimal strings), `Factor`, `Count` and `Currency`, for the month-end reminder `Month` (the first day of the month), and for the monthly digest `Month` and `Digest`, a nested `MonthlyDigestPayload` record (`Currency`; `Income`, `Expense` and `Net` as decimal strings; `KeptPercent`; up to three `Movers` of `{ Name, Amount, Previous }`; `Uncategorized`, `Unusual`, `UnconfirmedRecurring`, `AccountsNeedingAttention` and `Closed`), each optional and each filled only by the kinds that need it — so the client localizes the sentence from typed values instead of parsing text. The column is nullable because bill reminders written before it existed carry the ISO due date in `Message`; `NotificationMapper` reads that date back into the payload for those rows, which is why the migration adds a column and rewrites nothing. `RelatedId` is a bare `Guid?` with no foreign key, so a notification outlives the bill, budget or transaction it came from; `RelatedType` is `Budget`, `RecurringBill` or `Transaction`.

UserSessions holds one row per signed-in browser: the user, the SHA-256 hash of the current refresh token, the hash of the token it replaced together with the time of that rotation, the security stamp the session was issued under, whether the cookies persist, an absolute expiry, the first 256 characters of the `User-Agent` header sent at sign-in (null when there was none) and `LastSeenAt`, which is set at sign-in and on every refresh token rotation. The user agent and the three times are what the profile's list of signed-in browsers shows; the hashes and the stamp are never returned by the API. The previous hash is accepted for 30 seconds after the rotation so that two tabs refreshing at once both succeed; presented later it counts as a stolen token and the row is deleted. Rows are also hard-deleted on logout, when the user signs another browser out or signs out everywhere else on the profile, on a renewal that finds the session expired, the stamp changed or the user deactivated, and when the user next signs in after they expire or their stamp changes; deleting a user cascades. All of those need that user to come back, so since 2026-09-23 `RetentionJob` sweeps daily for every user at once: a row whose `ExpiresAt` has passed, or whose stamp no longer matches the one on `AspNetUsers`, is deleted whether or not anybody signs in again. The table is not owner-filtered because it is read before a request is authenticated: the refresh endpoint finds the row from the cookie, and the bearer handler checks on every request that the row behind the access token still exists. It is left out of backups, so the new columns need nothing there.

`PersonalApiTokens`, added by the `AddPersonalApiTokens` migration of 2026-09-29, holds one row per [personal API token](features/personal-api-tokens.md): `Id`, `UserId` (cascading foreign key to `AspNetUsers`, indexed), `Name` (max 60), `Prefix` (`character(8)`, unique, the public part of the token in clear), `SecretHash` (`character(64)`, the SHA-256 of the secret part as hex), `Access` (`TokenAccess` stored as its name, `Read` or `ReadWrite`, not null, default `Read`, added by `AddTokenWriteAccess` of 2026-10-01), `CreatedAt`, `ExpiresAt` and `LastUsedAt`, null until the first use and moved at most once a minute. Like `UserSessions` it is a plain class in `Infrastructure/Auth` with no owner filter, because the handler reads it before the request is authenticated; the service filters by the caller itself. Revocation, deactivation, an administrator's password reset and `--recover-admin` hard-delete rows, `RetentionJob` deletes rows 30 days after they expired. Since 2026-10-01 it is transient like `UserSessions`: backups leave it out and a restore ends every token.

`ApiIdempotencyKeys`, added by the same `AddTokenWriteAccess` migration, remembers the `Idempotency-Key` of a token `POST` or `PATCH` for 24 hours: `TokenId` (cascading foreign key to `PersonalApiTokens`) and `Key` (at most 64 characters) as the primary key, `RequestHash` (`character(64)`, the SHA-256 of the request), `StatusCode` and `Body` (`jsonb`), both null while the first request runs, `Location` and `CreatedAt`. `IdempotencyMiddleware` writes it with single statements outside the endpoint's transactions; like `UserSessions` it is transient, left out of backups and the member export, and `RetentionJob` deletes rows older than a day. `Transaction.Source`, stored as its number, gained `Api` (2) the same day for rows a token created; a bank import that links such a row sets it to `Imported`. See [Personal API tokens](features/personal-api-tokens.md#writing-with-a-token).

## Currency

`Money` is an amount plus a `Currency`. On `Account.StartingBalance`, `Transaction.Amount`, `Transfer.Amount`, `Transfer.ReceivedAmount`, `CurrencyConversion.FromAmount` and `CurrencyConversion.ToAmount` it is mapped as an EF Core complex property onto two columns, the numeric amount and a three-letter uppercase code. Since 2026-09-22 `Asset.CurrentValue` and `Debt.OutstandingAmount` are mapped the same way, and since 2026-09-29 `SharedExpense.Amount` and `Settlement.Amount`: an asset or a debt takes the reporting currency of the day it is created and keeps it through later edits, and a debt's `LoanAmount` and `MonthlyPayment` are bare amounts in that currency. A net worth snapshot stores its four totals as bare amounts with the `Currency` they were taken in. The migration that added these columns gave existing rows the installation's reporting currency. Budgets and goals keep a bare amount meant in the reporting currency; a recurring entry's amount is a bare amount in the currency of the account it posts to. Split lines share their transaction's currency.

`Transaction.ReportingAmount` is the amount in the reporting currency, fixed when the transaction is created or edited using the rate for its date. Every income, expense, budget, trend and breakdown total sums this column, so past periods do not move when rates change. Split lines take a proportional share of it. Account totals, the dashboard balance and net worth are different: they value what is held today, so they use the newest rate.

`CurrencyConversion` belongs to one account and records the amount sold, the amount bought, the date and an optional `FeeTransactionId` pointing at the expense transaction created for the fee. It is visible to anyone who can see the account. An update keeps the account and rewrites the rest; the fee transaction is created, updated or soft-deleted in the same save, and its `ReportingAmount` is taken again at the rate for the new date. A conversion with `ImportRef` set came from a broker and is read-only.

`ExchangeRate` has the key (Date, Currency) and stores units of that currency per one euro, as published by the European Central Bank. Any pair is derived by crossing through the euro. `ManualExchangeRate` has the same key and shape and holds the rates an administrator entered by hand; on a date that has both, the hand rate wins, and deleting it brings the synced one back. Neither table has an owner, soft delete or `UpdatedAt`; saving or deleting a hand rate revalues the rows that depend on it, as the [multi-currency feature](features/multi-currency.md#rates-entered-by-hand) describes. The reporting currency is part of the installation settings. It is one value for the whole installation because shared budgets and categories would otherwise have no single meaning. Changing it revalues every stored `ReportingAmount`, soft-deleted transactions and investment entries included, at the rate for each row's date, inside the same database transaction as the settings update. Including the deleted rows is what lets a restore from the trash bring back an amount in the currency the installation is reporting in now. Every row whose `ReportingAmount` the change rewrites gets a new `UpdatedAt`: the foreign-currency rows through the change tracker, and the rows already in the new currency through their `ExecuteUpdate`, which touches only those whose amount actually differs. The same change sets `UnusualCheckedAt` back to null on every transaction, so the unusual-amount verdicts are taken again in the new currency.

## Installation settings

`InstanceSettings` is a single row with Id 1: installation name, the feature switches as a `FeatureFlags` complex property (one boolean column each), reporting currency, the enabled currency codes as a comma-separated string, exchange-rate sync flag, default language, IANA time zone, first day of the week, default account id and default page size. Until the row exists, values come from `App:ReportingCurrency`, `App:ExchangeRates:Enabled`, `App:DefaultCulture` and `App:TimeZone`, so an upgraded installation behaves as before. An empty currency list means every currency.

The same row also holds the mail server: `SmtpEnabled`, `SmtpHost`, `SmtpPort` (default 587), `SmtpEncryption` (`StartTls`, `SslOnConnect` or `None`, stored as its name; `StartTls` is the enum's zero value, so a request that leaves it out gets TLS rather than plain text), `SmtpUserName`, `SmtpProtectedPassword`, `SmtpFromAddress` and `SmtpFromName`. The migration gives existing installations `SmtpEnabled` false, port 587 and `StartTls`, so the enum column never reads back an empty string. `SmtpProtectedPassword` holds ciphertext from `IDataProtectionProvider.CreateProtector("JxFinance.Smtp.Password")`, exactly like `BrokerConnection.ProtectedToken`: it is stored, it travels inside a backup and it is readable only where the data protection keys are the same, and no API response ever carries it — `SmtpSettingsResponse` answers `hasPassword` instead. `InstanceSettingsSnapshot` exposes all of it as an `SmtpSettingsSnapshot` whose `IsConfigured` is what decides whether anything is queued at all.

`DiscordEnabled`, a boolean defaulting to false since the `AddDiscordNotifications` migration of 2026-09-26, is the installation's permission to post to Discord at all. It is in `InstanceSettingsSnapshot` and in the public settings as `discordEnabled`.

## Email

`EmailMessages` is the outbox: `Id`, `Kind` (`PasswordReset`, `EmailVerification`, `BillReminder` or, since 2026-09-27, `Notification`, stored as its name), the recipient address and name, the subject and the plain-text body, an optional `DedupeKey` with a unique index filtered to non-null values, `CreatedAt`, `NextAttemptAt`, a nullable `SentAt`, an `Attempts` counter and the last error. There is a second index on (`SentAt`, `NextAttemptAt`), which is how `EmailOutboxJob` finds what is due. ## Discord

`DiscordWebhook` is an `OwnableEntity` with its own id type, `DiscordWebhookId`, one per user through a unique index on `UserId` filtered to rows not deleted: `ProtectedUrl` (max 1000, ciphertext from the Data Protection purpose `JxFinance.Discord.Webhook`, blanked when the webhook is removed), `IsEnabled`, `Types` (a `jsonb` list of `NotificationType` values as camel-case strings), `LastDeliveredAt`, `LastError` (max 500) and `DisabledByDiscordAt`, set when Discord answers that the webhook no longer exists. `ProtectedUrl` is a concurrency token, so the outbox job's outcome for a URL the owner has since replaced or removed is dropped rather than written over the new state. It is not registered in the audit collector. It travels inside a backup like the SMTP password, readable only under the same key ring.

`DiscordMessages` is the Discord outbox, shaped like `EmailMessages` and plain in the same way — no owner base class, no soft deletion, no query filter: `Id`, `UserId`, `NotificationType` (stored as its name, max 40), `Content` (the finished text, max 2000, Discord's limit), an optional `DedupeKey` (max 200, unique, filtered to non-null values), `CreatedAt`, `NextAttemptAt`, a nullable `SentAt`, `Attempts` and `LastError`, with indexes on (`SentAt`, `NextAttemptAt`) and on `UserId`. It stores the user rather than the URL, so the webhook is looked up when the post is sent. `DiscordMessage.MaxAttempts` is 5; every row is deleted a week after it was queued, sent or not. `AspNetUsers` carries `EmailNotificationTypes` since 2026-09-27, a `jsonb` list of `NotificationType` names (camelCase strings) defaulting to `[]` — the kinds of notification the user also wants by email. ## Unusual amounts

`Transactions` gained six nullable columns in the `AddUnusualAmounts` migration of 2026-09-26: `UnusualCheckedAt` (null means the row still has to be evaluated), the verdict `UnusualBasis` (`Payee` or `Category`, stored as its name, max 20), `UnusualTypicalAmount` (numeric(18,2), the median in the reporting currency), `UnusualFactor` (numeric(9,2)) and `UnusualSampleSize`, all null when the row is usual, and `UnusualDismissedAt`, set when someone marks the row "Not unusual" and kept across edits. ## Transaction groups

The `AddTransactionGroups` migration of 2026-10-01 added the `TransactionGroups` table and `Transactions.GroupId`. A `TransactionGroup` is an `OwnableEntity` with its own id type `TransactionGroupId` and `Name` (varchar 120, `TransactionGroup.NameMaxLength`), indexed on `UserId`; like every owned table it gets the restricting foreign key to its owner. The `ShareTransactionGroups` migration of 2026-10-02 made it `IShareable` with `Scope` (integer, default personal) and `HouseholdId` (indexed, restricting foreign key to `Households`), so the shareable filter shows a shared group to the members of its household and a personal one to its owner alone. `Transactions.GroupId` (`TransactionGroupId?`) is a foreign key with `ON DELETE SET NULL` and the partial index `IX_Transactions_GroupId` where it is not null. A member of a personal group must be a transaction its owner entered, and a member of a shared group a transaction on an account shared with its household. ## Spreading over months

The `AddTransactionSpread` migration of 2026-09-30 added `Transactions.SpreadMonths` (`smallint`, nullable, check constraint `CK_Transactions_SpreadMonths`: null or 2 to 36) and `Transactions.SpreadUntil` (`date`, nullable, the date of the last monthly slice), with `CK_Transactions_SpreadUntil` requiring that both are null or neither is, and the partial index `IX_Transactions_Spread` on (AccountId, SpreadUntil) where `SpreadMonths` is not null, next to the (AccountId, Date) indexes. `AppDbContext.ApplyEntityRules` sets `SpreadUntil` from `Date` and `SpreadMonths` when a transaction is added or either of them changes, the way it sets `PayeeKey`; nothing else writes it. The monthly slices are never stored. The same migration added `RecurringBills.SpreadMonths` (`smallint`, nullable, `CK_RecurringBills_SpreadMonths`), copied onto the transaction a confirmation writes. `TransactionTag`'s relationship gained the `Transaction.Tags` navigation, the only navigation on a transaction, which the slice loader uses to read tag ids in the same query; it changes no column. See [Transactions](features/transactions.md#spreading-over-months) and [architecture](architecture/transactions.md#spread-rows).

The `AddSpreadDirection` migration of 2026-10-02 added `Transactions.SpreadDirection` and `RecurringBills.SpreadDirection` (`integer`, not null, default 0: `Forward` is 0 and `Backward` is 1; `Forward` on a row that is not spread) and `Transactions.SpreadFrom` (`date`, nullable, the date of the first monthly slice). `ApplyEntityRules` sets `SpreadFrom` with `SpreadUntil`, and also when `SpreadDirection` changes. The migration changes no rows and adds no check constraint for `SpreadFrom`, because the spread rows it finds have none yet: `SpreadFromBackfill.RunAsync`, called by `ApplyMigrationsAsync` at every start after `DebtBalanceBackfill`, sets `SpreadFrom` to `Date` on spread rows where it is null, deleted ones included, with one `UPDATE` past the change tracker, so `UpdatedAt` and the activity log stay as they were and a closed month shows no drift. Every row it fills is forward, since nothing could be spread backwards before the column existed. A member download from before the migration imports its spread rows without `SpreadFrom`, and the next start fills them.

`Transactions.PayeeKey` (varchar 200, nullable) was added by the `AddTransactionPayeeKey` migration of 2026-09-29. It holds `SubscriptionDescription.KeyOf(Payee, Description)`, the normalized `Payee` when something is left of it and otherwise the normalized `Description`: null means not computed yet, and an empty string means the row has no key, because it has neither or nothing is left after normalizing. `AppDbContext.ApplyEntityRules` sets it when a tracked transaction is added and when its `Description` or `Payee` is modified; no `ExecuteUpdate` writes either, and `AppDbContextTests` checks the add and edit paths. The migration changes no rows. `PayeeKeyBackfill.RunAsync`, called by `ApplyMigrationsAsync` at every start right after `MigrateAsync` (and so by `--seed-demo` too), reads the id, payee and description of up to 1,000 rows whose key is null, deleted rows included, normalizes them in C# and writes the page with one `UPDATE … FROM unnest(ids, keys)`, until none is left, and logs the count once. Writing past the change tracker keeps `UpdatedAt` and the audit log unchanged, so a closed month shows no drift. A partial index `IX_Transactions_PayeeKeyPending` on `Id` where the key is null serves that query. The report and the ledger's `payee` filter are bounded by account and date and use the (AccountId, Date) index; an index on (AccountId, PayeeKey) is for when an all-dates payee filter turns out slow. Any change to `Normalize` ships with a migration that sets `PayeeKey` back to null, and the next start recomputes it. Backups carry the column like any other. See [Reports](features/reports.md#expense-by-payee).

## Refunds

A refund is a `Transaction` of type `Expense` whose `Amount` and `ReportingAmount` are negative. No column or check constraint was added for the sign: both are `numeric(18,2)` without one, and only the validators and the import decide that a negative amount is allowed on an expense and nowhere else. Split lines stay positive, because a refund cannot be split.

`Transactions.RefundOfTransactionId` (`uuid`, nullable), added by the `AddTransactionRefunds` migration of 2026-09-29, names the purchase a refund returns money for. It is a self-referencing foreign key to `Transactions` with delete behaviour `SetNull`, overriding the Restrict convention, so the retention purge of a purchase, which is an `ExecuteDelete`, clears the pointer in the database instead of being blocked by it. A soft-deleted purchase leaves the pointer in place; the query filter hides the purchase, so the refund answers `refundOf` null and a restore brings the link back. The partial index `IX_Transactions_RefundOfTransactionId` where the column is not null serves the ledger's "Refunded" total, one grouped query over the page's ids. The migration changes no rows. Backups carry the column, and the restore defers foreign keys, so the order of the rows in the file does not matter. See [Transactions](features/transactions.md#refunds).

## Household settle-up

The `AddSettleUp` migration of 2026-09-29 adds three tables. `SharedExpenses` holds one split per transaction: an `OwnableEntity` whose `UserId` is the payer, implementing `IHouseholdScoped`, with `HouseholdId` (restricting foreign key), `TransactionId`, the copied `Date`, `Description` (at most 200 characters, cut with an ellipsis from the transaction's 500) and `Amount` with its `Currency`, and `Method` (integer, `Equal` = 0, `Shares` = 1, `Exact` = 2). The foreign key to the transaction cascades, overriding the Restrict convention, so the retention purge of a transaction takes its split; a soft delete of the transaction leaves the split, and the balances skip it while the transaction is deleted. A unique index on `TransactionId` filtered to `IsDeleted = false` lets a transaction be split once, and an index on (HouseholdId, Date) serves the list. `SharedExpenseShares` is a plain class like `TransactionLine`, with (SharedExpenseId, UserId) as its primary key, a cascading foreign key to the split, a restricting one to `AspNetUsers`, an optional whole `Weight` for the Shares method and the stored `Amount` (numeric(18,2), in the split's currency); the amounts of a split always add up to its amount, allocated by largest remainder. Editing a split updates, adds and removes share rows in place; deleting it leaves them, so a restore brings them back.

`Settlements` holds the recorded payments: an `OwnableEntity` whose `UserId` is who recorded it, implementing `IHouseholdScoped`, with `HouseholdId`, `FromUserId` and `ToUserId` (restricting foreign keys to `AspNetUsers`), `Amount` with its `Currency`, `Date`, an optional `Note` (at most 200) and an optional `TransferId`. The transfer foreign key is `SetNull`, so purging a transfer clears the link, and a unique index on `TransferId` filtered to `TransferId IS NOT NULL AND IsDeleted = false` lets a transfer settle one payment. An index on (HouseholdId, Date) serves the list. Balances are never stored; they are derived on read per household and currency. `AuditEntityKind` and `TrashKind` gained `SharedExpense` and `Settlement`, stored as their names. Backups carry the three tables through the model with no code of their own, and `UserExportTables` classifies them. See [Household settle-up](features/household-settle-up.md).

## People outside the household

The `AddContacts` migration of 2026-10-01 adds four tables for [money with people outside the household](features/money-with-people.md). `Contacts` holds a member's people: an `OwnableEntity` with its own id type `ContactId` and a `Name` of at most 100 characters, under the ordinary owner filter and deliberately not `IShareable`. `ContactSplits` holds one split per transaction: an `OwnableEntity` whose `UserId` is the payer, with `TransactionId` (cascading foreign key, as on `SharedExpenses`), the copied `Date`, `Description` (at most 200) and `Amount` with its `Currency`, `Method` (the household split's `SplitMethod`), and the member's own part as `OwnWeight` (Shares only) and `OwnAmount`, both null when the member takes no part. Its unique index on `TransactionId` is filtered to `IsDeleted = false`; a transaction split with a household is refused in code, through `SplitRules.IsSplitAsync`, since the two tables cannot share an index. `ContactSplitShares` is a plain class with (ContactSplitId, ContactId) as its primary key, cascading foreign keys to the split and to the person, an optional `Weight` and the stored `Amount`; the member's part plus the shares add up to the split's amount. `ContactPayments` holds the payments: an `OwnableEntity` with `ContactId` (cascading foreign key), `Direction` (integer, `ToContact` = 0 when the member paid, `FromContact` = 1 when the person paid), `Amount` with its `Currency`, `Date` and an optional `Note` (at most 200), with an index on (ContactId, Date). The cascades let the retention purge of a person take their shares and payments in the database. Backups carry the tables through the model, and `UserExportTables` and `MemberImport` export and import all four.

## Reconciliation

`AccountReconciliation`, added by the `AddAccountReconciliations` migration of 2026-09-29, is a bank statement's balance on a date: an `OwnableEntity` implementing `IAccountScoped`, with its own id type `AccountReconciliationId`, holding `AccountId` (a restricting foreign key), `Currency`, `Date`, `Balance` (a decimal in that currency) and `Source` (integer, `Manual` = 0, `Statement` = 1). A unique index on (`AccountId`, `Currency`, `Date`), since the `AddReconciliationCurrency` migration of 2026-10-01 which replaced the one on (`AccountId`, `Date`), keeps one per account, currency and date, and saving again on a date in that currency updates that row. `Balance` and `Currency` are plain columns rather than a `Money` because EF Core cannot index a complex property's column; the columns kept their names and data. The account-scoped query filter makes it visible to whoever sees the account and hides it with an archived account. It is never soft-deleted: a delete is `ExecuteDelete`. It is not in the trash, not registered in the audit collector, and the ledger balance and the difference are never stored, only computed on read. `UserId` is whoever recorded it first. Backups carry it like every mapped table. See [Reconciliation](features/reconciliation.md).

## Month-end close

`MonthClose` is an `OwnableEntity` with its own id type, `MonthCloseId`, added by the `AddMonthClose` migration and reshaped by `SimplifyMonthClose`: `Month` (`date`, the first day of the month), `HouseholdId?` (the active household the close was taken under, null for "Everything"; a restricting foreign key), `ClosedAt`, `Note?` (max 1000) and `Snapshot`. A unique index on (`UserId`, `Month`, `HouseholdId`) with nulls not distinct keeps one close per user, month and scope; it is not filtered on `IsDeleted`, because a close is never soft-deleted: reopening hard-deletes the row with `ExecuteDelete`. Only the plain owner filter applies, so a close is personal even when every row it summarises sits on a shared account. It is not in the trash and not registered in the audit collector.

`Snapshot` is a `MonthCloseSnapshot` record stored as `jsonb` through a `JsonSerializer` value converter, like `Notifications.Payload`: `ReportingCurrency`, `TotalIncome`, `TotalExpense`, `Net`, `TransactionCount` (transactions dated in the month, investment entries not counted), the `Income` and `Expense` breakdowns as lists of `{categoryId, syntheticGroup, name, amount}` exactly as the report summary answered them, and `RowIds`, the ids of every transaction and investment entry dated in the month at the moment of closing. Re-closing replaces it whole. `SimplifyMonthClose` rewrote closes taken before it, turning the per-row entries into `rowIds` and dropping the net worth figure, and removed the `IsDeleted` filter from the unique index. See [Month-end close](features/month-end-close.md).

## Investments

`Security` is installation-wide reference data with no owner: symbol, name, ISIN, exchange, type, currency, the broker's contract id, and the last known price with its date. Symbol plus currency is unique. Because the row is shared, writes are split by who may make them: any signed-in user can add a security, only an administrator can change symbol, name, ISIN, exchange, type, currency or the broker contract id, and the last price with its date can be set by an administrator or by a user who has an open position in that security on an account visible to them. A broker import writes securities and prices under its own rules and is not subject to this. Since the `AddMarketPrices` migration of 2026-09-30 a security also has `PriceSource` (`None`, `Eodhd` or `Kraken`, stored as its name, default `None`), `PriceSymbol` (at most 32 characters, required by the check constraint `CK_Securities_PriceSymbol` whenever the source is not `None`), and the result of the last fetch, `PriceSyncedAt` and `PriceSyncError` (at most 200 characters). The `AddSecurityPriceQuoteCurrency` migration of 2026-10-01 adds `PriceQuoteCurrency` (three letters, nullable): the currency EODHD quotes the mapped listing in, stored by the first fetch so a restart does not spend a search call again. Only an administrator sets the source and symbol; changing either clears the fetch result and the quote currency. The member export leaves out all three fetch columns. See [Live security prices](features/live-prices.md).

`SecurityPrice` is the price history of a security: security id, date and price to eight decimals, with the security id and the date as the primary key, so there is one price per security and date. Like `Security` it has no owner and is installation-wide; it is a plain row without soft delete, removed with its security. Every write of a price goes through `SecurityPriceBook`: the set-price operation, a security created or updated with a price, and the mark price of each open position in an Interactive Brokers report. Since 2026-09-30 each row also has `Source` (`Manual`, `Broker`, `Feed` or `File`, stored as its name, default `Manual`, which every older row received), and a price file import and the daily fetch write through the same book. Writing a date that already has a row replaces its price and source, except that a `Feed` price never replaces a row of another source and then leaves the last price alone. `Security.LastPrice` and `LastPriceDate` stay as the denormalized newest point: they move only when the written date is the same as or later than the current one, and deleting a point sets them to the newest remaining point or to empty. Trade prices are never recorded as prices of the day. The migration that added the table copied every existing last price into one row per security. Dates between points have no row, and a valuation uses the latest point on or before its date; the daily fetch fills weekdays only for held, mapped securities, and every day for those priced by Kraken. The portfolio value over time is computed from this table and the ledger on request and is not stored; net worth snapshots remain the only stored value series.

`AssetValuation` is the value history of an asset, added on 2026-09-27: asset id, date, value in the asset's currency and an optional note of at most 200 characters, with the asset id and the date as the primary key. It is a plain row without soft delete, removed by a cascade when the purge deletes its asset for good, so an asset in the trash keeps its valuations. Every write goes through `AssetValuationBook`, and `Asset.CurrentValue` and `AsOf` stay as the denormalized newest valuation, moved and restored exactly like a security's last price; the last valuation of an asset cannot be deleted. `Asset.Depreciation` is an optional complex property on four nullable columns — `Depreciation_StartDate`, `Depreciation_StartValue`, `Depreciation_LifeMonths` and `Depreciation_ResidualValue` — that are all set or all empty. The value of an asset on a date is computed from its valuations and its depreciation when it is read and is never stored. The migration that added the table copied every asset's `CurrentValue` and `AsOf` into its first valuation. See [Net worth](features/net-worth.md#asset-value-history).

`DebtBalanceEntry` is the history of a debt's recorded outstanding amount, added by the `AddDebtBalanceEntries` migration of 2026-10-01: debt id, date, amount in the debt's currency and an optional note of at most 200 characters, with the debt id and the date as the primary key. Like `AssetValuation` it is a plain row without soft delete, removed by a cascade when the purge deletes its debt, so a debt in the trash keeps its balances. Every write goes through `DebtBalanceBook`, and `Debt.OutstandingAmount` and `AsOf` stay as the denormalized newest balance; the last balance of a debt cannot be deleted. The migration changes no rows: `DebtBalanceBackfill.RunAsync`, called by `ApplyMigrationsAsync` at every start after `PayeeKeyBackfill`, inserts one balance from `OutstandingAmount` and `AsOf` for every debt, deleted ones included, that has none. See [Net worth](features/net-worth.md#debt-balance-history).

`InvestmentTransaction` belongs to an account and is visible to whoever can see that account. It holds the type (buy, sell, dividend, withholding tax, interest, fee, split, symbol change, merger, spin-off), date, quantity and price to eight decimals, the fee, a signed `CashAmount` in its own currency (negative when cash left the account, fees included), `ReportingAmount` frozen at the rate for the date like `Transaction.ReportingAmount`, a source, and the broker's id in `ExternalId`, unique per account. A split stores the ratio in `Quantity`, as new shares per old share, and moves no cash; a split imported from Interactive Brokers has `ExternalId` `ibkr:ca:<action id>`. Since 2026-10-02 (migration `AddSymbolChanges`) a corporate action that moves a holding names the security it moves to in `RelatedSecurityId`, a nullable foreign key to `Securities`; a symbol change stores the shares moved in `Quantity` and moves no cash. A merger (migration `AddMergers`) stores the shares given up in `Quantity`, the shares received in `RelatedQuantity` (`numeric(20,8)`, 0 for other types) and the cash received as its `CashAmount`, and, when paid in both, the percentage of the cost carried into the new shares in `CostShare` (`numeric(9,6)`, null when not set or not applicable). A spin-off stores the parent in `SecurityId`, the new security in `RelatedSecurityId`, the shares received in `RelatedQuantity`, 0 in `Quantity` and the parent's cost moved to the new security in `CostShare`, null until it is set. Within one day the replay applies splits and corporate actions first, then buys, then sells, because trades on the day a split takes effect are already in new shares. Holdings, cost basis and gains are never stored: `Portfolio.Positions` replays the entries first in, first out.

Account balances add the sum of `CashAmount` per currency to the existing movements. `AccountResponse.HoldingsValue` is the market value of open positions at the newest exchange rate, and `ReportingBalance` includes it, which is how the dashboard total and net worth pick up investments with no change to the snapshot table. Changing the reporting currency revalues `InvestmentTransaction.ReportingAmount` together with transactions. Reports and the dashboard sum that `ReportingAmount` for dividend, interest, withholding tax and fee entries while the `Investments` feature is on; no table or column was added for it, and the entries still have no category.

`BrokerConnection` is owned by one user and unique per account: Flex Query id, the token protected with ASP.NET Data Protection, an optional funding account, an enabled flag, and the time and error of the last sync. `CurrencyConversion.ImportRef` and the existing `TransferImport` receipts deduplicate imported currency trades and deposits.

## Model configuration and migrations

`AppDbContext.ConfigureConventions` maps the value types once: every `IStronglyTypedId<TSelf>` struct is stored as a uuid through `StronglyTypedIdConverter<TId>`, `Money` properties that are not complex properties are stored as numeric(18,2) through `MoneyConverter`, and `Currency` is stored as its three-letter code. Every `decimal` column takes numeric(18,2) from the same place, so a money-shaped column says nothing about its precision; only the columns that differ state one (prices and quantities use eight decimals, the interest rate uses 5,2). A nullable id or amount needs nothing extra. Each entity has an `IEntityTypeConfiguration<T>` class under `Infrastructure/Data/Configurations`, loaded with `ApplyConfigurationsFromAssembly`; the context adds the restricting `UserId` foreign key to every `OwnableEntity`, the restricting `HouseholdId` foreign key to every `IShareable` and `IHouseholdScoped`, and the query filters, where an entity that implements `IAccountScoped` is visible through its account and one that implements `IHouseholdScoped` through a living household the caller is a member of. A configuration declares an index only when the convention would not create it anyway: EF indexes every foreign key by itself, so the explicit ones left are the composite and the filtered ones, plus `IX_Tags_UserId`, which the convention skips because the filtered unique index on (UserId, Name) appears to cover it.

The `jsonb` columns are mapped two ways. `AspNetUsers.DashboardLayout` and `AuditEvents.Changes` are complex types written by EF itself — `ComplexProperty(...).ToJson()` and `ComplexCollection(...).ToJson()`, with `HasJsonPropertyName` giving each member the camelCase name the web serializer used before — so no converter, no value comparer and no serializer options of their own. `ToJson()` is left to pick the column type; naming it `jsonb` explicitly makes the reader fail to materialise. `Notifications.Payload` keeps its `JsonSerializer` converter because EF would store a different document: it writes every null member out, where the payload omits them, and it has no camelCase string enums. `DiscordWebhooks.Types`, `AspNetUsers.EmailNotificationTypes`, `MonthCloses.Snapshot` and `CsvImportMappings.Columns` use the same kind of converter, each with a value comparer (the two kind lists share `StoredAsJson` in `NotificationTypeConfigurationExtensions`); the snapshot's comparer compares the serialized text, so a re-close that replaces the record is saved.

Migrations are never squashed or renamed. A backup records the id of the newest migration in the running application (`BackupDatabase.CurrentMigration`, read from the assembly because startup applies every migration) and `BackupService` compares it with the running application, so rewriting history would make existing backups unrestorable. To keep the folder small instead, the `*.Designer.cs` file of every migration except the newest has an empty `BuildTargetModel`; the attributes that carry the migration id remain. The generated idempotent script was identical before and after that trim. The cost concerns `dotnet ef migrations remove`, which rebuilds the model snapshot from the designer of the migration before the one it removes. A freshly added migration can still be removed, because the newest committed migration keeps its full designer, but removing further back would produce an empty snapshot; an old migration is never removed anyway because deployed databases have applied it. Once a new migration has shipped, the designer of the one before it can be emptied the same way.
