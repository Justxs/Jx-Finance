# Architecture and deployment

The browser requests `/api` on the same origin. Vite proxies that path during development; Caddy proxies it to the API in Compose. Endpoints validate and delegate to feature services. Services use AppDbContext directly. Domain types have no framework dependencies, enforced by architecture tests. Generated client code is isolated under frontend/src/api/generated.

EF query filters enforce visibility. Administrative/background operations that bypass filters constrain their queries explicitly. Financial writes use decimal values, and repeat-sensitive operations use transaction-scoped PostgreSQL advisory locks. The net-worth scheduler creates a separate context per user so ordinary ownership filters still apply.

Startup applies pending EF migrations directly, then initializes first-run data. Schema changes are versioned. Database dump, backup scheduler and restore functionality were removed by request on 2026-09-05. The API image does not install PostgreSQL client tools.

## Table filtering and sorting
Every table header carries its own controls: clicking a column name sorts by it and toggles direction on a second click; a filter icon beside the name opens a popover with that column's filter. The sort arrow shows the current field and direction, and the filter icon is highlighted while that column is filtered. `ColumnHeader` composes the two; `ColumnFilter` is the popover shell and `TextColumnFilter` wraps it for the text case. Popovers use the shadcn `Popover` on Base UI, shared with `DatePicker`.

All filtering and sorting happens on the server. `GET /api/transactions`, `/api/accounts` and `/api/users` each take their filters plus `sort` and `direction`; all are optional, and the service applies the default order when they are absent. Transactions sort in SQL, including correlated subqueries for category and account name. Accounts and users are unpaged, so their services filter in SQL and then sort the mapped responses — current balance and active status are computed rather than stored, so they cannot be ordered in the query itself.

Dates filter as one range, not two fields. `DateRangePicker` shows the selected span on a single control and takes the two ends from one calendar: the first click sets the start, the second sets the end, and a click before the current start becomes the new start instead. It backs the transactions date column and the reports range, both of which still write `dateFrom`/`dateTo` separately to the URL and the API. It shares its month grid with `DatePicker` through `Calendar` and `lib/calendar.ts`; the single-date picker renders as a range whose ends are the same day.

Filter and sort state lives in the route's search params for all three tables, so a view is shareable by URL and survives reload. Transaction filters also reset paging and feed the CSV/PDF export links. Text filters keep a local draft and debounce for 300 ms with `useDebouncer` from TanStack Pacer (`@tanstack/react-pacer`), because each committed change is a navigation. Pacer is the project's standard for debouncing and throttling; do not hand-roll timers.

An empty result distinguishes the two causes: `filters.noMatches` when filters are applied, the table's own empty copy otherwise.

## Frontend loading and failure states
Queries use TanStack Query's suspense hooks, so components read `data` directly and never branch on status. Loading and failure are handled by position in the tree instead: `QueryBoundary` pairs a `Suspense` fallback with an error boundary wired to `QueryErrorResetBoundary`, so its retry re-runs the failed queries rather than only re-rendering. The query client sets `throwOnError` so a failed fetch reaches that boundary.

Boundaries sit at two levels. One wraps `<Outlet />` in the root layout and covers whole-page queries, falling back to `RoutePending`. Finer ones wrap the sections that load independently — the dashboard sections, the net-worth sections, transfers, imports — so one slow request does not blank unrelated content. The sidebar and notification bell render outside the outlet and carry their own.

Two queries stay on the non-suspense hooks because they are conditional, and `useSuspenseQuery` accepts neither `enabled` nor `placeholderData`: the root layout's profile lookup, disabled on the login and setup routes, and the import transfer picker.

`useSuspenseQuery` accepts no `placeholderData`, so keeping previous rows on screen through a filter or sort change is done with `useDeferredValue` instead, in `useDeferredParams`.

Relying on the router's `startTransition` alone does not work here, and the reason is worth recording. TanStack Router publishes search params through `useSyncExternalStore`, and React deliberately renders external-store updates synchronously to avoid tearing — the transition does not defer them. The new params therefore reached the query on a synchronous render, the query suspended with no cached data, and the boundary dropped to its skeleton: every filter change looked like a full page reload.

`useDeferredParams` breaks that chain. The synchronous render still uses the previous params, so the query stays resolved and nothing unmounts; React then re-renders with the new params in a transition, and a transition *is* allowed to suspend without hiding revealed content. The flag it returns is exact staleness — old data on screen, new data in flight — and drives the `.is-stale` dim.

It defers `JSON.stringify(params)` rather than the params object. `useDeferredValue` compares by identity, so deferring an object that is rebuilt each render never settles and spins. Deferring a string derived from the values cannot, regardless of what the router or the compiler does with object identity.

Background refetches (the window-focus refetch is on) have no indicator at all. They replace data the user is already reading, so signalling them only produces flicker on every refocus.

Mutations still report progress on the control that started them, since they are not queries. `Button` takes a `pending` prop that disables the button, sets `aria-busy` and renders a spinner; icon-only buttons swap their icon for the spinner. That spinner is the only one in the application. Row-level actions scope pending state to the affected row by comparing `mutation.variables` with the row id. Where the affected control is not a button (a role dropdown, a notification about to disappear) the row dims instead. Optimistic transaction rows stay dimmed until the server confirms them.

## Frontend file layout
Every component lives in its own folder named after it, holding the component, its `*.stories.tsx`, any helper used only by that component, and an `index.ts` that re-exports the folder. This applies to `src/components`, `src/components/ui` and each `src/features/<feature>`. Import the folder, never the file: `@/components/ui/button`, `@/features/transactions/transactions-table`. Files inside one folder import each other with `./name`.

A component that only one non-page sibling uses moves into that sibling's folder: `split-lines-editor` sits in `transaction-form/`, `member-row` and `add-member-form` in `household-card/`, the column hooks and `table-features` in `transactions-table/`, `date-range-presets` in `report-filters/`. Pages never absorb their children, so a feature stays a flat list of page, section, table and form folders. Stories that show several components together live in `src/storybook/showcase`.

The shadcn CLI still writes flat files such as `src/components/ui/tooltip.tsx`. After `shadcn add`, move the file into `ui/tooltip/`, add the `index.ts`, and add its story.

## UI components
`src/components/ui` holds shadcn/ui components generated with the `base-nova` style, which builds on Base UI (`@base-ui/react`) instead of Radix. Add or refresh one with `shadcn add <name> --overwrite`; the CLI shells out to npm, which cannot install into a nub project, so install any new dependency with `nub add` first. Generated files import `cn` from `@/lib/utils`. Local changes to generated files are deliberate: `Button` has a `pending` prop, `Dialog` close labels are translated, and `Table` has no scroll container because every table sits in its own labelled, focusable scroll region. `sonner.tsx` is hand-written because the shadcn version depends on `next-themes` and the app has its own theme store.

Three wrappers keep call sites short: `Modal` (titled dialog with a scrolling body), `SelectField` (Base UI select driven by an `options` array and a plain `onChange(value)`), and `ConfirmDeleteDialog` (alert dialog in front of every delete). `DatePicker` and `DateRangePicker` combine `Popover` with the shadcn `Calendar` (react-day-picker, date-fns locale by language, weeks start on Monday) and keep ISO `yyyy-MM-dd` strings as their value. The generated `Calendar` contains the only `useEffect` in the frontend; it moves focus for day-picker keyboard navigation and is left as generated.

Every field control (`Input`, `SelectTrigger`, the date picker triggers) shares one look: 36px tall, `border-input`, `bg-muted/40` that turns to `bg-background` on focus, 17px text below the `md` breakpoint so iOS does not zoom and 15px above it. Default buttons are 36px, `sm` 32px, `lg` 40px. The destructive button is solid rather than tinted so it keeps contrast in dark mode. `SelectField` wraps the Base UI root in its own element because Base UI renders a hidden form input beside the trigger, which would otherwise pick up the parent stack spacing.

## Visual system
`PRODUCT.md` records who the product is for and `DESIGN.md` records the visual system, "The Household Ledger"; both sit at the repository root and are the reference for any new screen. The short version: the page is paper and content sits directly on it. A section opens with an ink rule (`.section` with a `.section-title`), rows are separated by hairlines (`ul.rows`), and a lead total carries a double rule (`.figure` with `.total-rule`). `.card` is kept for objects that really are separate: the sign-in and setup forms, dialogs and popovers. Page content is never boxed and boxes never nest.

Type is self-hosted: Source Serif 4 for page titles, the wordmark and lead figures, Source Sans 3 for everything else. The variable woff2 files (Latin and Latin Extended, which covers Lithuanian) are vendored in `src/assets/fonts` with their OFL license and declared in `src/fonts.css`. They are vendored rather than imported from a package because nub keeps packages in a store outside the project, which the Vite dev server refuses to serve as raw assets. The fonts are bundled by Vite and served from the same origin, so the Content-Security-Policy is unchanged and no third-party request is made. Tailwind's `text-xs`, `text-sm` and `text-base` are raised by one pixel in `global.css` because Source Sans runs smaller than Segoe UI. Serif figures need `lining-nums` next to `tabular-nums`; the `.figure` and `.page-title` classes already apply it.

Color is semantic. `text-income` and `text-expense` are the money text colors and hold AA contrast in both themes; `secondary` and `destructive` remain the fill colors for meters, chart bars and destructive buttons. Signed amounts carry "+" or "−" so direction never depends on color. Lists, meters and charts do not use a palette to tell rows apart. `Tag` replaces every hand-written pill and `Meter` every progress bar; neither is rounded.

Color palettes are a per-browser choice, separate from light/dark. `stores/theme-store.ts` keeps the palette in `localStorage` (`jx-palette`) and sets `data-palette` on `<html>`; `public/theme-init.js` applies it before first paint. The default palette, `ledger`, sets no attribute. Each palette (`plum`, `sepia`, `graphite`) overrides only the neutral and primary tokens in `global.css`, for light and dark; the values are the ledger tokens with the OKLCH hue rotated and lightness kept, so every contrast ratio matches the default. Income, expense, secondary and destructive colors never change with the palette. `PalettePicker` (`components/palette-picker`) is a native radio group shown on Settings and Profile; its swatches carry their own `data-palette`, which is why the dark selectors also match `.dark [data-palette]` descendants.

Typeface and text size follow the same per-browser pattern: `jx-font` sets `data-font` and `jx-text-size` sets `data-text-size` on `<html>`, both applied by `theme-init.js`, and the defaults (`ledger`, `default`) set no attribute. Tailwind `font-sans` and `font-serif` resolve to `--font-body` and `--font-display`, which each `[data-font]` block redefines: `sans` and `serif` use one Source family for both roles, `system` uses the device fonts, and `inter`, `hyperlegible` (Atkinson Hyperlegible Next), `plex` (IBM Plex Sans with Plex Serif 600 for display) and `editorial` (Inter with Newsreader for display) use extra self-hosted families. Their `woff2` files, latin and latin-ext subsets taken from the Fontsource packages, sit in `src/assets/fonts` beside one `OFL-*.txt` license per family and are declared in `fonts.css`; a browser downloads a family only when it is used, so the extra files cost nothing until someone opens the picker or chooses that option. Text size changes the root `font-size` (93.75% or 112.5%); every size and control height is in `rem`, so the whole interface scales. `FontPicker` (`components/font-picker`) sits under `PalettePicker` on Settings and Profile, and each typeface option carries its own `data-font` so it previews itself.

The desktop shell has no top bar. Notifications, language, theme and the collapse control live in the sidebar foot, and `NotificationBell` takes `placement="above"` there so its panel opens upward. Below the `md` breakpoint a compact header and a scrolling navigation strip take over. Navigation items are grouped by job with a gap between groups instead of labels. The language control shows the current language code and names the language it switches to; flags are not used because a flag stands for a country, not a language.

Tables have no surrounding box. The `Table` primitive supplies the muted header text, the ink header rule and `px-3` cells, and each table's scroll region is pulled out with `-mx-3` so cell text aligns with the page edge while row hover still has room.

## Brand assets
The mark is a single vector path, the ledger bird, kept in `frontend/scripts/brand/bird.svg`. `scripts/brand/build.mjs` reads that path, measures its bounding box in headless Chromium and writes `src/components/brand/mark-paths.ts`, which the `BrandMark` component and every static asset share. `favicon.svg` carries a `prefers-color-scheme` rule so the bird stays legible on dark browser chrome; the PNG and ICO files are screenshots of the same SVG on a navy tile, taken with the Playwright already installed for tests, and the ICO container is assembled in the script, so the generator needs no extra dependency. From `frontend/` run `node scripts/brand/build.mjs`; it also copies the favicon to `.storybook/public`. If the mark changes, regenerate all of them together so the favicon, the manifest icons and the in-app logo cannot drift. Storybook uses the same favicon and a branded manager theme (`.storybook/manager.ts`, `.storybook/manager-head.html`). The manifest is covered by the existing Content-Security-Policy because `default-src 'self'` applies to `manifest-src`.

## Accessibility conventions
Row actions name their row: `aria-label` and `title` read "Edit: Maistas", not "Edit", so a screen reader list of buttons is usable. `ConfirmDeleteDialog` takes `itemLabel` and shows what is about to be deleted above the warning; every call site looks the label up from the list it already has. `FieldError` takes an `id`, and each control points at it with `aria-describedby` while the field has an error. A `SelectField` without a visible `Label` must be given `aria-label`.

Money direction never depends on color. `SummaryStats` items take `sign` (`"+"`, `"−"` or `"auto"`), and tables prefix signed amounts the same way. Charts are wrapped in an element with `role="img"` and a label, format their axis with `useAxisMoney` (compact euro amounts in the active locale) and do not animate, because Recharts animation ignores `prefers-reduced-motion`.

Controls are 36px for the desktop bookkeeping session and grow to 44px on touch devices through `pointer-coarse:` variants on `Button` and the column filter trigger. Under reduced motion view transitions keep a 100 ms cross-fade and drop all movement, so state changes stay visible without sliding.

`QueryBoundary` takes `errorFallback` for places where the default sentence does not fit; the notification bell uses it to stay an icon (`NotificationBellUnavailable`) instead of breaking the sidebar foot. `Pagination` renders nothing when there is a single page. Dialog overlays are a flat scrim without blur, in line with the paper surfaces.

Category rows on the dashboard and in reports link to the transactions list filtered by that category and date range, so a total can always be traced to its rows.

## Transactions and import workflow
The transactions page reads three things from the same filter set: the paged list, `GET /api/transactions/summary` for the totals line, and the export links. The summary runs through `useDeferredParams` like the list and has its own `QueryBoundary`, so it dims with the rows and a slow summary never blocks the table. Every mutation that changes the list also invalidates the summary.

Row selection is rendered by the table itself, not by a column definition, because `FlexRender` remounts cell contents on each render and a remounted checkbox loses keyboard focus. Selection state is stored together with the current filter, sort and page key, which clears it on any of those changes without an effect. Bulk recategorize calls `POST /api/transactions/bulk-category`; the toolbar offers only categories whose type matches every selected row and disables itself on a mixed selection, which mirrors what the server accepts. Split rows cannot be selected.

"Save and add another" keeps the dialog open, resets the form but keeps type, account and date, and returns focus to Amount through a ref. The add dialog is opened by the `new` search param so the `n` shortcut and the button share one path; the param is stripped before the deferred params are computed so opening the dialog does not dim the rows. Below `md` the page renders `TransactionsList` instead of the table and moves filters and sort into `TransactionsFiltersDialog`; both layouts share one data source, one pagination and the same handlers, and the switch is CSS only.

Import has its own route, `/import`, with an optional `accountId` search param. Review helpers live in `preview-rows.ts` and are pure (selection summary, select-all, bulk apply, recall), which is what `preview-rows.test.ts` beside it covers. Category recall is one query for the latest 200 transactions, the API's page-size clamp, matched on exact description and type; it is recall, not the out-of-scope rules feature, and older history is not consulted.

## Keyboard shortcuts
`lib/shortcuts.ts` owns the key map and is the single source for both the handler and the help popover, so the two cannot drift. Key matching is done by TanStack Hotkeys (`@tanstack/react-hotkeys`), the project's standard for keyboard shortcuts: single keys are registered with `getHotkeyManager()` and the `g` sequences with `getSequenceManager()`. `app.tsx` calls `registerShortcuts` once at module scope, the same way it registers the session-expired listener, because the project does not use effects; that is why the managers are used directly instead of the `useHotkey` hooks. The library matches modifiers exactly and skips inputs, selects and editable elements. Registrations turn off the library's `preventDefault` and `stopPropagation` so the handler can first apply the app's own guards and only then prevent the default. The handler ignores repeated keydowns, events already handled, events from elements with a combobox or textbox role, events while a dialog is open, and everything on the sign-in and setup routes.

`n` opens the add-transaction dialog by navigating to `/transactions?new=true`; the route owns the `new` search param, so the dialog state is a URL like every other view state. `/` clicks the element marked `data-shortcut="search"` when the page has one and otherwise goes to the transactions list. `g` followed by a letter within 1.2 seconds navigates (`d` dashboard, `t` transactions, `i` import, `a` accounts, `c` categories, `b` budgets, `o` goals, `l` bills, `w` net worth, `r` reports, `h` households). `?` toggles the help popover in the sidebar foot; its open state lives in a small TanStack Store so the key handler and the popover share it without an effect. `toHotkeySteps` maps each entry of the key map to library hotkeys (`?` becomes `{ key: "?", shift: true }` because the typed hotkey strings exclude shifted punctuation); `shortcuts.dom.test.ts` covers that mapping, the ignore rules, the sequence timeout and the registered handlers against a real DOM.

## Forms
Forms use TanStack Form 2 (`@tanstack/react-form@alpha`). Each form passes one zod schema as `validators: [{ run: schema, triggers: ["change"] }]`; submit runs it again. Render props read `field.value`, `field.errors[0]?.message` and `field.meta`, not `field.state`. Lists use `form.ArrayField` with `pushValue` and `removeValue`. In alpha.2 an `ArrayField` re-renders only when the array length changes, not when its errors change, so an error attached to the array path itself (the split total mismatch on `lines`) is rendered through a nested `form.Field name="lines"`. Remove that wrapper once the library subscribes array fields to their meta. The package-update workflow re-pins the `alpha` tag after `nub update --latest`, because `latest` still points at 1.x.

### Shared field components and server errors
`src/components/form` builds on TanStack Form composition: `useAppForm` exposes field components (`TextField`, `MoneyInputField`, `MoneyAmountField`, `SelectFieldControl`, `DateField`, `CheckboxField`) and `SubmitButton`. A field component takes `id`, `label`, optional `hint` and derives the error id, `aria-invalid`, `aria-describedby` and the `FieldError` itself, so a form declares one element per field. Blocks with their own layout (split lines, the conversion rate line, currency lists) stay hand-written inside the same form. Schemas are composed from the builders in `src/lib/validation.ts` (`requiredText`, `optionalText`, `requiredValue`, `positiveMoney`, `password`, ...), which pair each rule with its translated message; length limits come from the generated zod constants.

A form submits through `submitToServer` with `mutateAsync` (a parent that owns the mutation returns the promise from its `onSubmit` prop). When the API answers with field entries, `serverFieldErrors` places each one on the field whose name equals the entry's JSON path (`amount`, `lines[1].amount`), where it renders through the same `FieldError` and aria wiring as a client error and clears on the next edit; `FormError` lists only the entries that match no field.

## Developer tooling
`just` lists every recipe. `just setup` prepares a checkout (generated `.env`, packages, tools, hooks, `.local/api-debug.env` for the VS Code debugger) and ends with `just doctor`, which checks tool versions, that Docker runs, and the known broken global `node` shim that makes git hooks exit with 127. `scripts/dev.ps1` keeps `dotnet watch` in the same terminal as Vite, so a compile error or a crash is visible, and starts Vite only after `/health` answers; it fails with a message when the API exits during startup.

Data: `just seed <email>` runs the API with `--seed-demo`, which fills an existing user that has no accounts with six months of deterministic EUR data (`DemoDataCommand`); it refuses a user that already has accounts. `just db-reset` asks for confirmation, removes the dev database volume and starts an empty PostgreSQL. `just migrate-add|remove|list|script` wrap the pinned `dotnet-ef` local tool, and `DatabaseToolingTests` fails when the model has changes without a migration.

Build rules live in `backend/Directory.Build.props` (warnings are errors, `latest-recommended` analyzers, code style enforced in the build) and `backend/Directory.Packages.props` (every NuGet version in one place); `.editorconfig` holds the C# style rules and the few analyzer rules that are switched off, with a wider exemption for the test project and none for migrations, which are treated as generated code. `global.json` pins the SDK feature band. The API Dockerfile copies these files before `dotnet restore`, otherwise the image build would use different rules than the local build.

Checks: `just check-fast` needs no Docker (backend format and build, frontend types, lint, format, unit and DOM tests); `just check` adds backend tests, contract drift and the app and Storybook builds. lefthook formats and lints staged frontend files, fixes whitespace in staged C# files (`dotnet format whitespace`, a few seconds; the full style rules run in the pre-push backend build and in CI) and validates the commit subject as a conventional commit (`scripts/check-commit-message.mjs`); before a push it type-checks, runs `vitest related` for the pushed files and builds the backend. CI (`.gitea/workflows/ci.yaml`) first detects which areas changed and skips the backend or frontend job when its area is untouched; it uploads test results, coverage and, on failure, the Playwright report.

`just new-endpoint` and `just new-component` scaffold a backend slice and a frontend component with story and test; `docs/13. Adding a feature.md` walks through the whole path.

## Frontend tests
Vitest has three projects. `unit` (node) and `dom` (jsdom) are what `nub run test` runs. `storybook` runs every story, including its `play` function, in headless Chromium through `@storybook/addon-vitest` and Playwright (`just test-stories`, about eight minutes); a story is therefore a test, and a selector that no longer matches fails CI instead of rotting. Only the Vitest plugin is used; the addon is deliberately not registered in `.storybook/main.ts`, because its in-browser test panel spawns a second test runner from the dev server that timed out on this setup and the command line covers the need. `.storybook/preview.tsx` starts the MSW worker itself (`startMockWorker`, up to three attempts) because `worker.start()` occasionally never resolved in a fresh iframe, switches the locale in an awaited loader, and raises the `findBy*` timeout to five seconds for parallel runs. `just e2e` starts a throwaway Compose project (`docker-compose.e2e.yml`: project `jx-e2e`, port 8089, own volumes, no database or API ports published), runs the Playwright smoke tests in `frontend/e2e` against it (first-run setup, closed setup, refused login, account form, ledger and balance, sign out) and removes it; it never touches the dev database. `just e2e-install` downloads the Chromium build both need.

Translation keys are typed: `src/i18next.d.ts` registers `locales/en/common.json` as the resource type, so `t("…")` only accepts existing keys and a key held in a variable is typed `TranslationKey`. `locales.test.ts` fails when English and Lithuanian differ in keys or in the placeholders of a text.

Vitest runs the frontend tests; `nub run --cwd frontend test` runs them once, `test:watch` watches and `test:coverage` writes a V8 coverage report. Tests sit beside the file they cover. `vitest.config.ts` is separate from `vite.config.ts` so a test run never regenerates the route tree, and it keeps the React Compiler preset so components are tested as they ship.

Of the unit and DOM projects, `*.test.ts` runs in plain Node and is for pure logic (validation, calendar, cash effect, import preview rows, report presets). `*.test.tsx` and `*.dom.test.ts` run in jsdom with `src/test/setup.ts`, which loads the jest-dom matchers, stubs `matchMedia`, and after each test unmounts, clears `localStorage`, resets the theme attributes and returns i18n to English. Anything touching `window`, `document`, `localStorage` or a React hook belongs in the jsdom project; the split exists because creating a jsdom environment per file is the slowest part of a run.

Stores read `localStorage` when their module loads, so their tests seed storage, call `vi.resetModules()` and import the store dynamically. `src/test/query.tsx` gives hooks and components a fresh `QueryClient` seeded with settings and currencies and a `fetch` that never resolves, so a test states the loaded data it needs and nothing reaches the network. Text from `Intl` goes through `plain()` before comparison because locales use non-breaking spaces. Time zone tests set `TZ` through `vi.stubEnv` and build their dates inside the test. Exit animations do not run in jsdom, so behaviour that only exists while a dialog closes stays a Storybook concern.

Covered: `src/lib`, `src/api/client.ts` (money normalization, session refresh, problem details), stores, the settings and formatter hooks, the pure feature helpers, and the shared components with behaviour of their own (pagination, error state, query boundary, confirm delete, money field, meter, the theme, language and palette controls, sidebar visibility). Pages, forms and tables are exercised through Storybook stories and their play functions instead.

## API contract and generated client
The backend is the single source of the contract. `OpenApiExtensions` builds the document; `OperationNames.Shorten` strips the `Endpoint` class suffix from every operation id, so an endpoint class `GetAccountsEndpoint` becomes operation `GetAccounts`. `ArrayWrappers.Inline` replaces every array wrapper schema with an inline array, so TypeScript sees `AccountResponse[]` rather than a named `IReadOnlyListOfAccountResponse`, and `SchemaVariants.Collapse` merges per-operation copies of one request type; a backend test fails if a schema name contains `__op` or a collection prefix. On the Orval side `operationName` in `orval.config.ts` drops the `Get` prefix of GET operations, giving `useAccountsSuspense`, `getAccountsQueryKey` and `getAccountsMockHandler` instead of `useGetAccounts…` and `getGetAccounts…`; mutations keep their verb (`useCreateAccount`).

Only what the app uses is generated: suspense hooks for every query, plain `useQuery` hooks only for the operations listed in `plainQueryOperations`, MSW handlers without faker response factories (stories always pass an override), and zod schemas for request bodies and responses only. The zod project reads the spec through the `forValidation` input transformer in `orval.config.ts`, which only affects `src/api/schemas`: it gives every `format: decimal` schema a pattern (digits, optional dot and up to eight decimals), so the generated schema rejects `12,50` or text, and it adds a synthetic `GET /__contract/problem-details` operation because Orval emits zod only for success responses; that yields `ProblemDetailsResponse`, which the fixture contract test uses to check every problem fixture, including that each `code` is a published `ErrorCode`. The synthetic path never reaches the client or the MSW handlers. Generated folders are marked `linguist-generated` in `.gitattributes` so reviews collapse them.

`frontend/orval.config.ts` runs two Orval projects over `frontend/openapi.json`:

| Output | Content | Committed |
| --- | --- | --- |
| `src/api/generated/<tag>/<tag>.ts` | fetch functions, query keys, query/suspense/mutation hooks, one file per OpenAPI tag | yes |
| `src/api/generated/<tag>/<tag>.msw.ts` | typed MSW handler factories (`getAccountsMockHandler`) with path, method and success status from the spec | yes |
| `src/api/generated/model` | request and response types | yes |
| `src/api/schemas/<tag>/<tag>.zod.ts` | zod schemas and constraint constants (`createAccountBodyNameMax`) | yes |

App code imports hooks from the `@/api/generated` barrel and types from `@/api/generated/model`. The barrel deliberately has no `.msw` exports; stories and tests import a handler from its own file (`@/api/generated/accounts/accounts.msw`) so faker and msw never reach the production bundle. Generated code is formatted by the Orval `afterAllFilesWrite` hook (oxfmt) and is excluded from lint, not from formatting.

Regenerate with `just gen`. It runs the API with `--export-openapi-docs true`, which writes `backend/JxFinance.Api/wwwroot/openapi/v1.json` and exits before migrations, so neither a database nor a running server is needed, and copies the result to `frontend/openapi.json`. That file is the one committed copy of the contract: Orval reads it, and the backend test `OpenApi_document_matches_the_approved_contract` compares it semantically (ignoring `servers` and formatting) with what the running API serves, so there is no separate snapshot to refresh. CI runs the identical export, then fails when `git status` shows any change (including new untracked files) to `frontend/openapi.json`, `src/api/generated` or `src/api/schemas`. The export and the EF recipes build in Release so they work while `just dev` holds the Debug output.

`src/api/client.ts` is the Orval mutator. Every failed request throws an `ApiError` (a real `Error` subclass carrying `status`, `title`, `detail` and per-field `errors`). The file exports `ErrorType`, which Orval picks up, and `query-client.ts` registers `defaultError: ApiError`, so `error` on every query and mutation is typed as `ApiError` without casts; use `isApiError` when the value comes from somewhere untyped.

### Route loaders and optimistic updates
Every route has a `loader` that warms the page's primary queries through `warm` in `src/lib/route-prefetch.ts`, a non-awaited `prefetchQuery` with the generated `get…SuspenseQueryOptions`. Loaders never await and never throw, so navigation is not blocked and `QueryBoundary` still owns error display; with `defaultPreload: "intent"` the data is usually cached before the click. The query client reaches loaders and `beforeLoad` gates through router context. Loader and component must build identical query keys, so params derived from search state or settings live in small `*-queries.ts` files used by both; `route-prefetch.test.tsx` mounts the real route tree and asserts each endpoint is requested once.

`src/lib/optimistic.ts` provides `optimisticUpdate`, `optimisticRemoval` and `optimisticPagedRemoval`, which return the `onMutate` and `onError` pair for a generated mutation hook: cancel in-flight reads, rewrite the cached list, roll back on failure. They are used for creating a transaction, deleting rows from lists and marking notifications read. Refreshing afterwards is not their job.

### Cache invalidation
Components do not call `invalidateQueries` after a mutation. `src/api/invalidation.ts` holds the only map from mutation to the query roots it makes stale, and the `MutationCache` built by `createMutationCache` applies it in `onSettled` for every mutation, wherever it was triggered. A root is the URL in a generated query key; invalidating `/api/accounts` also covers `/api/accounts/{id}` and any parameterised variant. Storybook uses the same cache, so stories behave like the app. `invalidation.test.ts` enumerates every generated `get*MutationKey` and fails until a new mutation is either given a rule or listed in `mutationsWithoutInvalidation`. Optimistic updates (`onMutate`, rollback) stay in the component that owns them.

### Error codes
Every failure carries a stable code from the closed set in `Common/Errors/ErrorCodes.cs`: each FluentValidation rule sets one (the shared `CommonRules` and `DecimalRules` extensions set it for you, and `ValidatorErrorCodeTests` fails on a rule without a published code), JSON binding failures map to `decimal.malformed` or `request.malformed`, and service failures return a `DomainError(code, message)` whose code also decides the HTTP status. The OpenAPI `ErrorCode` enum is built from the constants by reflection, so Orval emits an `ErrorCode` union; `errors[].code` is never null and a top-level `code` covers problems without entries. The English `reason` stays as a fallback only.

On the frontend `serverErrorText` in `src/lib/form-server-errors.ts` is the single place that turns an entry into text: it looks up `serverErrors.<code>` in the locale files and falls back to `reason`. `server-error-codes.test.ts` fails when a published code lacks an English or Lithuanian translation, or when a translation exists for a code the API dropped, so adding a code on the backend is: constant, `just gen`, two translations.

Money, prices and quantities are `decimal` in every backend DTO and a JSON string on the wire (`"42.50"`), so nothing passes through floating point. The property carries `[property: Money]` (two decimals, written `0.00`) or `[property: Quantity]` (up to eight, written `0.########`); both attributes derive from `JsonConverterAttribute` and live in `Common/Json` next to their converters. The converters read only a JSON string in invariant culture with a dot separator, so `"12,50"`, grouping, `NaN` and bare numbers fail during binding; FastEndpoints reports that as a 400 problem whose `errors` entry is named after the JSON path (`amount`, `lines[1].amount`), which keeps per-field form errors working. Sign, scale and range rules are the shared FluentValidation extensions in `Common/Validation/DecimalRules.cs` (`IsPositiveMoney`, `IsNonNegativeQuantity`, ...). Request fields where zero is a valid value are `[JsonRequired]`, because a missing non-nullable decimal would otherwise bind as 0. `decimal? InterestRate` on debts is a plain JSON number and carries no attribute.

The same attributes drive the contract: a schema transformer in `OpenApiExtensions` describes such a property as `type: string, format: decimal`. `orval.config.ts` walks every request body in the spec and writes the names of those properties to the generated `src/api/generated/decimal-fields.ts`; the mutator in `client.ts` normalizes exactly those fields (trim, decimal comma to point) before sending, so a user typing `12,50` sends `12.50`. There is no hand-kept list on the frontend: a new money field needs the attribute, then `just gen`.

### Validation limits
Form schemas stay hand-written because they validate form state (strings, localized messages), not request bodies, but the numeric limits and patterns come from the generated zod constants rather than being retyped, so a limit changed in a backend validator reaches the form on the next `just gen`.

## Storybook
Every component file has a colocated `*.stories.tsx`, and `src/storybook/pages.stories.tsx` renders the real route tree at each path, so the whole app can be reviewed with `nub run storybook` (port 6006) without the API, a database or a login. CI runs `nub run build-storybook`, which fails when a story no longer compiles. A new component ships with its story.

`src/storybook/fixtures/<tag>.ts` holds typed, deterministic mock data (fixed ids, dates around 2026-09-18) and `src/storybook/handlers/<tag>.ts` mocks that tag's endpoints with MSW; both folders mirror `src/api/generated/<tag>` and their `index.ts` re-exports the public names, so stories keep importing `@/storybook/fixtures` and `@/storybook/handlers`. `fixtures.contract.test.ts` parses every response fixture through the generated zod response schema, which catches what the TypeScript types cannot (uuid, date and enum formats, length limits), and fails when a new fixture export is neither checked nor listed as exempt. Handlers mock every API endpoint, building each handler from the generated factory in `src/api/generated/<tag>/<tag>.msw.ts` so path, method, success status and response type come from the spec; error responses throw a `Response` from the override (`failWith`, `failWithStatus`, `found`), pending states pass the never-resolving `pending` override, and the few responses the factories cannot express (CSV and PDF export, the blanket error and loading sets) reuse the generated method and path through `onRouteOf`. It also exports `emptyHandlers`, `errorHandlers`, `loadingHandlers` and `unauthenticatedHandlers`; a story picks one with `parameters: { msw: { handlers: emptyHandlers } }`. When an endpoint is added or its shape changes, update both files. The worker script lives in `.storybook/public`, not in `public`, so it never reaches the production bundle.

`src/storybook/decorators.tsx` wraps each story in a fresh query client, a toaster and an in-memory TanStack router that registers the real paths with their search schemas, so components calling `useSearch({ from: "/transactions" })` work; `parameters: { route: "/transactions?type=expense" }` sets the starting URL. Page stories opt out with `parameters.providers = "none"` and use `AppAt`, which mounts the generated route tree and presets the auth gate. The toolbar switches light and dark theme and English and Lithuanian. `.storybook/main.ts` drops the TanStack Router Vite plugin so Storybook never regenerates the route tree. Stories that need an interaction to reach a state use a `play` function; on TanStack Form fields use `fireEvent.change`, because `userEvent.type` followed by submit clears the value.

## Motion
Motion is limited to four things, all built on view transitions: changing page, table rows changing in place, a list row being added, removed or moved, and a section replacing its skeleton. Durations are 120 to 240 ms with an exponential ease-out, and nothing animates on its own.

The page change is driven by the router, not by React. TanStack Router publishes location through `useSyncExternalStore`, and React renders external-store updates synchronously even inside `startTransition`, so a React `ViewTransition` around `<Outlet />` never activates on navigation; an earlier version of this page relied on that and silently stopped animating. Instead the router is created with `defaultViewTransition` set to `pageViewTransition` from `lib/page-transition.ts`, which asks the router to wrap the commit in `document.startViewTransition` with the type `page`, and only when the pathname changed. Sorting, filtering and paging are navigations too, but they only change search params, so they return `false` and the page does not fade on every keystroke. The element around `<Outlet />` has the class `page-transition`, and `global.css` gives it `view-transition-name: page` only while `:root:active-view-transition-type(page)` matches, so it is not captured during any other transition. `::view-transition-old(page)` and `::view-transition-new(page)` give it a short fade and slide. The Storybook router in `src/storybook/decorators.tsx` uses the same option so page stories behave like the app.

Everything else uses React's `ViewTransition`, which needs the update to be a React transition. Query results arrive through an external store as well, so lists pass their data through `useDeferredValue` before rendering: the deferred render is a transition, and that is what lets a row animate. Defer the query's `data` itself and apply `?? []` afterwards; deferring a fresh array literal never settles. `RowTransition` (`components/row-transition`) wraps a list row and carries the classes `row-in`, `row-out` and `row-move`: a new row fades and drops in, a removed row fades out, and the rows below slide to their new position. `QueryBoundary` wraps its fallback and its content in boundaries with `reveal-out` and `reveal-in`, so a section cross-fades from its skeleton instead of snapping. Both content boundaries carry `update="none"` so they are captured only when they appear or disappear, never when something inside them changes. The boundary around `<Outlet />` passes `reveal={false}` because the page transition already covers it.

Each table then carries its own `ViewTransition` around its scroll container, so sorting and filtering cross-fade the rows alone; the reports results block has the same treatment. The names are per-owner (`transactions-rows`, `accounts-rows`, `users-rows`, `report-results`) so two can never claim one name.

Two rules keep those scoped transitions from spilling over the rest of the page.

`:root` is given `view-transition-name: none`. Without it the browser captures everything unnamed into a default `root` group and cross-fades it, so any one scoped transition repainted the entire page — picking a date in a column filter looked like a full reload. Opting the root out means only explicitly named elements animate and the rest of the DOM updates in place. Do not "fix" this by putting `animation: none` on `::view-transition-old(root)`: the old snapshot then sits at full opacity above the new content for the group's duration, freezing the page instead of skipping it.

The scoped boundaries carry `enter="none" exit="none"` so they are named only while their content changes in place. Without this, a table's boundary would also be captured whenever its whole section appears, animating twice.

Dialogs, popovers and select menus are Base UI components rendered through a portal, so `ViewTransition` does not capture them. They animate with the `data-open` and `data-closed` classes that shadcn ships, driven by `tw-animate-css`; Base UI keeps the element mounted until the exit animation ends, so no manual close delay is needed. `#root` sets `isolation: isolate` so portalled layers always stack above page content.

Tooltips use the Base UI `Tooltip` wrapper in `components/ui/tooltip` instead of the native `title` attribute. `Button` takes a `tooltip` prop (and `tooltipSide`), which every icon-only action uses with the same text as its `aria-label`; other elements (sort and filter header buttons, collapsed sidebar links, checkboxes, the icon picker, drill-down category links) are wrapped in `<Tooltip content={...}>`. An empty `content` renders the child untouched. Disabled controls do not receive pointer events, so their tooltip goes on a wrapping `span`. A single `TooltipProvider` in `app.tsx` shares the 400 ms open delay, so moving between adjacent actions shows the next tooltip instantly. Native `title` remains only on truncated text, where it reveals the full value.

Reduced motion is handled in two places: the `*` rule covers dialogs, popovers and menus, and a separate rule covers the view-transition pseudo-elements, which `*` does not match.

## Authentication
Sign-in creates a `UserSessions` row with a 1-day or 30-day absolute expiry and issues two HttpOnly, SameSite=Strict cookies: `jx_access`, a 10-minute JWT built with FastEndpoints.Security (`JwtBearer.CreateToken`), and `jx_refresh`, an opaque token scoped to `/api/auth/refresh` whose SHA-256 hash is all the database keeps. The bearer handler reads the JWT from the cookie, so no token is ever reachable from JavaScript. `POST /api/auth/refresh` rotates the refresh token and issues a new access token without extending the session's expiry; the frontend fetch client calls it once on a 401 and retries the request.

Each request still validates the security stamp and lockout status (`JwtCookieAuthentication`), and a token whose user id claim is missing or not a GUID fails authentication with 401 rather than reaching the ownership filters as an empty user. Role changes/deactivation therefore invalidate access and refresh tokens at once. Own-password and 2FA changes re-issue the initiating session's tokens with the new stamp (`ISessionService.RenewAsync`). FastEndpoints' `RefreshTokenService` is not used: it carries tokens in the request and response body and slides the refresh expiry, which contradicts both the cookie transport and the absolute session lifetime. First-run setup is serialized. 2FA setup/disable requires the current password, and setup refuses to expose a key for an already-enabled authenticator.

The Compose API persists Data Protection keys and the JWT signing key (`jwt-signing.key`, generated on first start unless `App:Jwt:SigningKey` is configured) in `auth_keys`. Protect that volume as sensitive deployment data. The production overlay enables secure cookies. API/database development ports bind only to loopback; the frontend bind address is configurable.

## Containers
`docker compose up -d --build` runs PostgreSQL, API and frontend. The API healthcheck checks PostgreSQL connectivity. Services restart unless stopped. The production overlay uses Caddy internal TLS, persistent Caddy state, and SITE_ADDRESS; install/trust its root certificate on authorized client devices and map the hostname to the private server address. Do not bypass browser certificate interstitials.

The API container runs as the non-root `app` user and the image pre-creates `/keys` owned by it. An `auth_keys` volume created by an older root image keeps root ownership; fix it once with `docker compose run --rm --no-deps --user root --entrypoint chown api -R app:app /keys`, otherwise key persistence fails and sessions reset on restart.

Caddy sends a Content-Security-Policy on the static site only, not on `/api/*`. Scripts are limited to same-origin files, which is why the theme bootstrap lives in `public/theme-init.js` rather than inline in `index.html`. Inline styles stay allowed because the chart and toast libraries set style attributes.

Run a single API instance for this release. Configure the private interface deliberately when enabling remote access. Environment-specific secrets remain in the ignored .env.

## Recovery command
`docker compose run --rm --no-deps -it api --recover-admin admin@example.com`

This requires an existing administrator and interactive password entry. It resets the password, clears lockout and 2FA, invalidates recovery codes, and revokes sessions. It does not create users or change application records. The database must already be migrated. The host command was tested against a disposable administrator; the container invocation still requires validation on a working Docker host.

## Background work
Bills are checked immediately at startup and every 15 minutes. Notifications deduplicate per bill/local day under a database lock. Unconfirmed bills retain their due date and can remind again the next day. Net worth refreshes immediately and hourly for active users. Exchange rates sync at startup and every six hours. Missed historical observations are not fabricated. Neither job sends email.

`.gitea/workflows/update-packages.yaml` runs every Monday at 05:00 UTC and on manual dispatch. ## Recurring bill schedule
A bill stores `AnchorDay`, the day of month the user picked. Monthly, quarterly and yearly advances clamp the anchor to the length of the target month, so a bill on the 31st lands on 28 February and returns to 31 March. The anchor is reset only when an update changes `NextDueDate`. Weekly bills ignore it.

## Shared category deletion
Any household member can rename a shared category, but only its owner can delete it. Deletion clears the category from every member's transactions, split lines and bills and soft-deletes its budgets, bypassing visibility filters so no dangling references remain.

## Transaction summary and bulk recategorization
`GET /api/transactions/summary` and the list, CSV and PDF endpoints all build their query through the one `Filtered` method in `TransactionService`, which takes `ITransactionFilter`; both request types implement it, so a filter cannot mean different things in the totals and in the rows. A split transaction that matches a category filter through one of its lines counts with its whole amount, exactly as the list shows it, not with the matching line's share.

`POST /api/transactions/bulk-category` is all-or-nothing: it loads every listed id through the visibility filter, fails with `not_found` if any is missing, and writes all changes in a single `SaveChanges`. Transactions have no edit rule beyond visibility, matching `PUT /api/transactions/{id}`, so `forbidden` never applies, and like that endpoint it takes no advisory lock because repeating it is harmless. Split transactions are rejected rather than having their lines rewritten, since a split's categories live on its lines. The category check is the same `ValidateCategoryAsync` used by create and update, run once per transaction type present in the batch.

## Multi-currency

Rates come from `IExchangeRateProvider`. The shipped implementation, `FrankfurterRateProvider`, reads ECB reference rates from `App:ExchangeRates:BaseUrl` (default `https://api.frankfurter.dev/v1/`); `App:ExchangeRates:Enabled` only seeds the automatic-sync setting on a new installation; after that the administrator's switch decides, and Sync now always fetches. `ExchangeRateSyncJob` runs at startup and every six hours and fetches from the day after the newest stored rate, or the last 30 days on an empty table.

`ExchangeRateService.GetForDateAsync` answers with the newest stored rates on or before the date, because the ECB publishes nothing on weekends and holidays. If nothing is stored within five days of the date it fetches the ten days ending there on demand, which is how back-dated transactions get historic rates without a full history download. `ExchangeRateFetchLog` stops a failing range from being retried more than once per fifteen minutes. Future dates use today's rates. If the newest rate is still more than five days older than the date, writes in a foreign currency fail with a validation error instead of freezing a stale value. Read-side totals leave a currency without a rate out, and the net worth snapshot is skipped for that day so an understated total is never stored. Fetched rates are inserted with `ON CONFLICT DO NOTHING` outside the change tracker, so concurrent fetches cannot collide and a fetch never flushes the caller's pending changes. Money rounds half away from zero everywhere through `Money.Round`. A split transaction's reporting value is shared across its lines in proportion, with the last line taking the remainder so the lines always add up to the parent.

The fee on a conversion is a real `Transaction` rather than a field that every report would need to learn about. Balances, budgets, reports and exports pick it up with no special case, and the user can recategorize it.

The wire format keeps the existing camel-case enum convention, so currencies travel as `eur`, `usd`. The frontend upper-cases the code for `Intl.NumberFormat` and `Intl.DisplayNames`. `useMoney().format(value, currency?)` defaults to the reporting currency from `GET /api/currencies`, fetched once without suspense and falling back to `eur`, so existing call sites that only ever show reporting-currency totals needed no change. Formatters are cached per language and currency at module scope. `CurrencySelect` lists the account's held currencies first, then the rest alphabetically.

Integration tests replace the provider with `FixedRateProvider` (1 EUR = 1.10 USD = 0.80 GBP on every day) so no test touches the network.

## Installation settings

`IInstanceSettingsStore` is a singleton holding an immutable `InstanceSettingsSnapshot`. It loads the row lazily on first use, falls back to configuration defaults without caching if the database is unreachable (which also covers OpenAPI export), and is replaced by `SettingsService` after a successful save. `SystemClock`, `ExchangeRateService`, `AccountMapper`, `CurrencyService` and the background jobs read the snapshot, so a change takes effect on the next request with no restart. The store assumes one API process; a second instance would keep its own snapshot until restarted.

`FeatureGateMiddleware` runs after authorization and maps route prefixes to features. A disabled feature answers 404 problem details with code `feature_disabled`. The one exception is `GET /api/households`, which answers an empty list, because account and category forms read it to offer sharing and should degrade to "nothing to share with" instead of failing. Assets and debts belong to the net worth feature; conversions belong to multi-currency.

Currency restrictions are enforced where money is written: `IExchangeRateService.UnusableReason` rejects a currency that is not enabled, or any foreign currency when multi-currency is off. Updating a transaction or account that already uses a now-disabled currency is allowed as long as the currency does not change. CSV import is not restricted, because the bank statement is the source of truth.

On the client, `useSettings` reads `GET /api/settings` without suspense and falls back to everything enabled; `requireFeature` in a route's `beforeLoad` redirects to the dashboard using the same cached query. `GET /api/settings/public` is anonymous and carries only the installation name and default language, for the sign-in page, the brand lockup and the document title. `CurrencySelect` offers only usable currencies plus the record's current one, and its compact form renders nothing when a single currency is usable, which is how multi-currency "off" hides the pickers without each form knowing about it.

## Investments

The feature lives under `Endpoints/Investments` and is gated as `Feature.Investments` on the `/api/investments` prefix. `InvestmentService` serves the portfolio, entries and securities; `HoldingsValuation` is the small piece `AccountService` depends on, so account totals include holdings without the account code knowing about lots. Gains are computed in the security's currency. Portfolio totals convert market value and cost at the newest rate, and convert realised gains, dividends, tax and fees at each entry's own date through the stored `ReportingAmount`; a sale's reporting gain is its gain scaled by that sale's reporting-to-cash ratio. Within one day buys and splits replay before sells, which is exact for long-only first-in-first-out and needs no execution time. Each lot carries its cost in the reporting currency at the buy-date rate, so a sale's reporting gain is proceeds at the sale-date rate minus cost at the buy-date rate. Short positions are not modelled: a manual entry or deletion that would leave a sale uncovered is rejected, and an imported oversell marks the portfolio incomplete.

`FlexParser` reads Interactive Brokers Flex Query XML with DTD processing off. Each section has its own list of summary rows to drop (orders, closed lots, symbol and asset summaries and wash sales for trades; summaries for cash; lots for open positions), so a query configured with several levels of detail does not double count. Direction comes from the sign of the quantity, so a cancellation reverses the original trade, and the cash effect is proceeds plus commission plus taxes with the broker's own signs. Dates accept `yyyyMMdd` and `yyyy-MM-dd` with or without a time part; ambiguous slash formats are refused. A report covering more than one broker account is refused. `BrokerImportService` runs the whole import in one database transaction, fetches the exchange-rate range once up front, takes a per-account advisory lock so an upload cannot race the daily sync, refuses currencies that are not enabled, resolves securities by contract id, then ISIN within the currency, then symbol within the currency when the ISINs do not conflict, and books a commission charged in a different currency from the trade as a separate fee entry. It is all or nothing: a missing exchange rate fails the import with the date and currency named.

Bonds are skipped until a price factor is modelled, because they are quoted in percent of par. Only the account's owner can connect it to a broker. `FlexClient` parses with DTD processing off, caps the response at 50 MB, has its HTTP logging removed because the token travels in the query string, and calls `SendRequest` and then polls `GetStatement` every five seconds, up to six times, while Interactive Brokers answers 1019 (report in progress). The base address is `App:InteractiveBrokersFlexUrl`. `BrokerSyncJob` runs daily, skips when the feature is off, skips locked-out owners and archived accounts, isolates each connection's failure, and imports each enabled connection under its owner's identity with a per-user `AppDbContext`, the same way the net worth snapshot job does. The token only ever travels from the browser to the API once and from the API to Interactive Brokers; responses carry no token field.

Investment cash flows stay out of `Transaction`, so dividends do not appear as income in reports or budgets. That is deliberate for now and listed under open questions.
