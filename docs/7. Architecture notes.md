# Architecture and deployment

The browser requests `/api` on the same origin. Vite proxies that path during development; Caddy proxies it to the API in Compose. Endpoints validate and delegate to feature services. Services use AppDbContext directly. Domain types have no framework dependencies, enforced by architecture tests. Generated client code is isolated under frontend/src/api/generated.

EF query filters enforce visibility, including the optional narrowing to one active household. Administrative/background operations that bypass filters constrain their queries explicitly. Financial writes use decimal values, and repeat-sensitive operations use transaction-scoped PostgreSQL advisory locks. The net-worth scheduler creates a separate context per user so ordinary ownership filters still apply.

Startup applies pending EF migrations directly. Only in the Development environment it then runs `DevDataSeeder.SeedAsync`, which creates a passwordless `dev@localhost` user and its starter categories when the database has no user at all; first-run setup takes that user over. Every other environment starts with an empty user table: `IsSetupNeededAsync` is true while no user has a password, `ProvisionAdminAsync` creates the administrator and gives it the starter categories itself through `StarterCategories.SeedAsync` (`Infrastructure/Data/StarterCategories.cs`, also used when an administrator creates a user and by the demo data command; the dev seeder only calls its `AddAsync`), so production and the end-to-end stack never hold a placeholder account. Schema changes are versioned. Database dump, backup scheduler and offsite copies were removed by request on 2026-09-05 and stay removed; the API image does not install PostgreSQL client tools. The backups an administrator takes from Settings are written by the application itself, see Backup and restore below.

## Table filtering and sorting
Every table header carries its own controls: clicking a column name sorts by it and toggles direction on a second click; a filter icon beside the name opens a popover with that column's filter. The sort arrow shows the current field and direction, and the filter icon is highlighted while that column is filtered. `ColumnHeader` composes the two; `ColumnFilter` is the popover shell and `TextColumnFilter` wraps it for the text case. Popovers use the shadcn `Popover` on Base UI, shared with `DatePicker`.

All filtering and sorting happens on the server. `GET /api/transactions`, `/api/accounts` and `/api/users` each take their filters plus `sort` and `direction`; all are optional, and the service applies the default order when they are absent. Transactions sort in SQL, including correlated subqueries for category and account name. Accounts and users are unpaged, so their services filter in SQL and then sort the mapped responses — current balance and active status are computed rather than stored, so they cannot be ordered in the query itself.

Dates filter as one range, not two fields. `DateRangePicker` shows the selected span on a single control and takes the two ends from one calendar: the first click sets the start, the second sets the end, and a click before the current start becomes the new start instead. It backs the transactions date column and the reports range, both of which still write `dateFrom`/`dateTo` separately to the URL and the API. It shares its month grid with `DatePicker` through `Calendar` and `lib/calendar.ts`; the single-date picker renders as a range whose ends are the same day.

Filter and sort state lives in the route's search params for all three tables, so a view is shareable by URL and survives reload. Transaction filters also reset paging and feed the CSV/PDF export links. Text filters keep a local draft and debounce for 300 ms, because each committed change is a navigation: `useDebouncedDraft(value, onCommit, wait)` in `src/hooks` holds the draft, follows the committed value when it changes elsewhere and commits through `useDebouncer` from TanStack Pacer (`@tanstack/react-pacer`); `TextColumnFilter` and the phone filters dialog both use it. Pacer is the project's standard for debouncing and throttling; do not hand-roll timers. `useSearchTable(search, patchSearch)` turns a route's search object and a patch function into `setFilter`, `setSort`, `toggleSort` and `sortProps(key)` (the four sort props of a `ColumnHeader` or `SortableTableHead`); the route keeps its own typed `useSearch` and `useNavigate`, so the hook needs no route generics. The transactions table and its phone filters dialog share `useTransactionFilters` (`features/transactions/use-transaction-filters.ts`): the search table with paging reset to 1, the type, category and account options, the tag list with `selectedTagIds` and `setTagIds`, the date range, `activeCount`, `clearFilters` (keeps the sort) and `clearAll`. The tag filter is one comma-separated `tagIds` search param rather than a repeated key, because the generated client joins an array param with commas anyway and the export links are plain URLs built by `buildExportUrl`.

An empty result distinguishes the two causes: `filters.noMatches` when filters are applied, the table's own empty copy otherwise. `EmptyText` (`components/ui/empty-text`) is that paragraph for lists and `TableEmptyRow` the same for a table body; both take `filtered`. `ScrollRegion` in `components/ui/table` is the labelled, focusable horizontal scroll wrapper every wide table sits in.

## Frontend loading and failure states
Queries use TanStack Query's suspense hooks, so components read `data` directly and never branch on status. Loading and failure are handled by position in the tree instead: `QueryBoundary` pairs a `Suspense` fallback with an error boundary wired to `QueryErrorResetBoundary`, so its retry re-runs the failed queries rather than only re-rendering. A failed query has exactly one surface, decided by whether there is anything on screen. The query client's `throwOnError` is `throwWithoutData` (`src/lib/query-client.ts`): a query that fails with no data throws to the boundary, which shows the error state and its retry, and the `QueryCache` stays quiet. A query that fails while it already holds data (a focus or invalidation refetch) keeps its rows on screen, does not throw, and the `QueryCache` `onError` raises one toast instead. Before this split a first load that failed showed both the boundary and a toast. `meta: { silent: true }` still suppresses the toast, and the handful of optional lookups (settings, currencies, the reference exchange rate, quotes) combine it with `throwOnError: false` so they fail without any surface and fall back to defaults. Imperative reads in `beforeLoad` gates and at startup catch their own failures and no longer toast. Mutation errors always toast unless silent, because a form shows its own `FormError`.

Boundaries sit at two levels. One wraps `<Outlet />` in the root layout and covers whole-page queries, falling back to `RoutePending`. Finer ones wrap the sections that load independently — the dashboard sections, the net-worth sections, transfers, imports — so one slow request does not blank unrelated content. The sidebar and notification bell render outside the outlet and carry their own.

Two queries stay on the non-suspense hooks because they are conditional, and `useSuspenseQuery` accepts neither `enabled` nor `placeholderData`: the root layout's profile lookup, disabled on the login and setup routes, and the import transfer picker.

`useSuspenseQuery` accepts no `placeholderData`, so keeping previous rows on screen through a filter or sort change is done with `useDeferredValue` instead, in `useDeferredParams`.

Relying on the router's `startTransition` alone does not work here, and the reason is worth recording. TanStack Router publishes search params through `useSyncExternalStore`, and React deliberately renders external-store updates synchronously to avoid tearing — the transition does not defer them. The new params therefore reached the query on a synchronous render, the query suspended with no cached data, and the boundary dropped to its skeleton: every filter change looked like a full page reload.

`useDeferredParams` breaks that chain. The synchronous render still uses the previous params, so the query stays resolved and nothing unmounts; React then re-renders with the new params in a transition, and a transition *is* allowed to suspend without hiding revealed content. The flag it returns is exact staleness — old data on screen, new data in flight — and drives the stale rule (`StaleRegion` and `staleVariants`, see Visual system).

It defers `JSON.stringify(params)` rather than the params object. `useDeferredValue` compares by identity, so deferring an object that is rebuilt each render never settles and spins. Deferring a string derived from the values cannot, regardless of what the router or the compiler does with object identity.

Background refetches (the window-focus refetch is on) have no indicator at all. They replace data the user is already reading, so signalling them only produces flicker on every refocus.

Mutations still report progress on the control that started them, since they are not queries. `Button` takes a `pending` prop that disables the button, sets `aria-busy` and renders a spinner; icon-only buttons swap their icon for the spinner. That spinner is the only one in the application. Row-level actions scope pending state to the affected row by comparing `mutation.variables` with the row id. Where the affected control is not a button (a role dropdown, a notification about to disappear) the control or row carries the stale rule instead. Optimistic transaction rows keep the rule until the server confirms them.

## Frontend file layout
Every component lives in its own folder named after it, holding the component, its `*.stories.tsx`, and any helper used only by that component. This applies to `src/components`, `src/components/ui` and each `src/features/<feature>`. A folder with one public module has no `index.ts`; import the file: `@/components/ui/button/button`, `@/features/goals/goals-page/goals-page`. An `index.ts` exists only where it does real work: a folder that exposes several modules (`components/form`, `components/modal`), or a chart folder whose `index.ts` exports the lazily loaded wrapper. Files inside one folder import each other with `./name`.

A component that only one non-page sibling uses moves into that sibling's folder: `split-lines-editor` sits in `transaction-form/`, `member-row` and `add-member-form` in `household-card/`, the column hooks and `table-features` in `transactions-table/`, `date-range-presets` in `report-filters/`. Pages never absorb their children, so a feature stays a flat list of page, section, table and form folders. Stories that show several components together live in `src/storybook/showcase`.

The shadcn CLI still writes flat files such as `src/components/ui/tooltip.tsx`. After `shadcn add`, move the file into `ui/tooltip/` and add its story.

## UI components
`src/components/ui` holds shadcn/ui components generated with the `base-nova` style, which builds on Base UI (`@base-ui/react`) instead of Radix. Add or refresh one with `shadcn add <name> --overwrite`; the CLI shells out to npm, which cannot install into a nub project, so install any new dependency with `nub add` first. Generated files import `cn` from `@/lib/utils`. Local changes to generated files are deliberate: `Button` has a `pending` prop, `Dialog` close labels are translated, and `Table` has no scroll container because every table sits in its own labelled, focusable scroll region. `sonner.tsx` is hand-written because the shadcn version depends on `next-themes` and the app has its own theme store.

Three wrappers keep call sites short: `Modal` (titled dialog with a scrolling body; `onOpenChange` for a boolean state setter, `onClose` for everything else), `SelectField` (Base UI select driven by an `options` array and a plain `onChange(value)`), and `ConfirmDeleteDialog` (alert dialog in front of every delete). `EditModal` takes `item`, `title` and a render function; it keeps the last item through `useRetained` so the closing animation still has content, and keys the body by the item's id. `useRetained(value, keep?)` is the render-time "remember the last value" state without an effect. `useConfirmedDelete(mutation, items, labelOf, undoKind?)` owns the delete target and returns `request(id)`, `pendingId`, `busy` and the `dialogProps` to spread on `ConfirmDeleteDialog`; it takes the mutation object, not the hook. With a `TrashKind` it also passes an `onSuccess` into the mutation that raises the undo toast from `useUndoToast`, and puts the "you can undo this" sentence into `dialogProps.description`; without one both stay as they were, so the dialog still says a delete is final on the screens where it is. `usePagedList()` gives `page`, `setPage`, the deferred `shownPage` and `stale`, and `usePageClamp(paging, total, pageSize)` returns the page count and pulls the page back when the list shrinks; they are two calls because the total comes from the query that needs `shownPage`. `RecordRow` (title, subtitle, amount, edit and delete) renders transfer and conversion rows, `SectionHeader` is a section title with an action slot, `TextLink` is the inline router link, and `Hint` sits beside `FieldError`. `src/lib/options.ts` has `namedOptions(items, blankLabel?)`, `nameById(items)` and `withMissingOption(options, id, label)` for selects over named records. The unused parts of the generated dialog, alert dialog, select, popover, table and button files were removed; add one back with the CLI when it is needed. `DatePicker` and `DateRangePicker` share `CalendarPopover` (`components/ui/calendar`: the trigger, open state and visible month) and combine `Popover` with the shadcn `Calendar` (react-day-picker, date-fns locale by language, weeks start on Monday) and keep ISO `yyyy-MM-dd` strings as their value. The generated `Calendar` contains the only `useEffect` in the frontend; it moves focus for day-picker keyboard navigation and is left as generated.

Every field control (`Input`, `SelectTrigger`, the date picker triggers) shares one look: 36px tall, `border-input`, `bg-muted/40` that turns to `bg-background` on focus, 17px text below the `md` breakpoint so iOS does not zoom and 15px above it. Default buttons are 36px, `sm` 32px, `lg` 40px. The destructive button is solid rather than tinted so it keeps contrast in dark mode. `SelectField` wraps the Base UI root in its own element because Base UI renders a hidden form input beside the trigger, which would otherwise pick up the parent stack spacing.

## Visual system
`PRODUCT.md` records who the product is for and `DESIGN.md` records the visual system, "The Household Ledger"; both sit at the repository root and are the reference for any new screen. The short version: the page is paper and content sits directly on it. A section is a tonal surface with a title (`Section` with a `SectionTitle`, or `Panel` for a block without a title of its own), rows are separated by hairlines (`Rows`), and a net total carries a double rule (`border-b-3 border-double border-rule`). `Card` is kept for objects that really are separate: the sign-in and setup forms and story frames. Page content is never boxed and surfaces never nest.

These surfaces are React components in `src/components/ui`, built from Tailwind utilities with `cn`; `global.css` holds tokens, base rules and view transitions and no semantic classes. `Card`, `Panel`, `Section` and `FormGrid` take `as` for the few call sites that need another element (`Section as="form"`, `Panel as={Rows}`, `Panel as={SplitColumns}`, `FormGrid as="form"`); the accepted values are listed in each component's props, which keeps event handlers typed. `Panel` and `Section` mark themselves with `data-surface` and flatten (no fill, radius or padding) inside another surface or inside `role="dialog"` through an arbitrary variant, `[:is([data-surface],[role=dialog])_&]:p-0`. That selector is more specific than a plain utility, so a padding or background passed through `className` does not apply to a flattened surface; nothing needs it today. `FormGrid` sets its columns with `grid-cols-[repeat(auto-fit,minmax(min(100%,13rem),1fr))]`, so the number of columns follows the width of the form's container, not the viewport, and gives its children `min-width: 0` through `[:where(&>*)]:min-w-0`, which has no specificity and loses to any utility on the child. `SplitColumns` is the five-to-seven two-column split used by the summary stats and the reports page. The page title and the lead figure are used in one and two places, so their utilities are written inline (`PageHeader`, `SummaryStats`, `DashboardStats`).

Stale content keeps full contrast. While `useDeferredParams` reports old data on screen, or a row waits for its mutation, the element sets `aria-busy`, shows a progress cursor and carries a two-pixel ink rule (`bg-rule`) along its top edge, drawn as an `::after` so it needs no markup and pulsing only under `motion-safe`. `StaleRegion` is the `div` form (`stale` prop, `aria-busy`, `data-stale`); `staleVariants({ stale })` from the same folder gives the classes to a `Table`, a `TableRow`, a list item or a control. Before 2026-09-20 the state dimmed its content to 70% opacity, which cannot hold 4.5:1 for muted text and needed seven `color-contrast` exemptions in Storybook.

Type is self-hosted: Source Serif 4 for page titles, the wordmark and lead figures, Source Sans 3 for everything else. The variable woff2 files (Latin and Latin Extended, which covers Lithuanian) are vendored in `src/assets/fonts` with their OFL license and declared in `src/fonts.css`. They are vendored rather than imported from a package because nub keeps packages in a store outside the project, which the Vite dev server refuses to serve as raw assets. The fonts are bundled by Vite and served from the same origin, so the Content-Security-Policy is unchanged and no third-party request is made. Tailwind's `text-xs`, `text-sm` and `text-base` are raised by one pixel in `global.css` because Source Sans runs smaller than Segoe UI. Serif figures need `lining-nums` next to `tabular-nums`; the lead figures and the page title already apply it.

Color is semantic. `text-income` and `text-expense` are the money text colors and hold AA contrast in both themes; `secondary` and `destructive` remain the fill colors for meters, chart bars and destructive buttons. Signed amounts carry "+" or "−" so direction never depends on color. Lists, meters and charts do not use a palette to tell rows apart. `Tag` replaces every hand-written pill and `Meter` every progress bar; neither is rounded.

Per-browser preferences live in one TanStack DB local-storage collection, `preferencesCollection` in `src/stores/preferences.ts`, built with `localStorageCollectionOptions`, the explicit `storageKey` `jx-preferences` and a zod schema. The collection holds a single row with the id `browser`: `theme` (absent means follow the system), `palette`, `font`, `textSize`, `sidebarCollapsed` and `locale` (absent means use the installation default). Every field of the schema has a `.catch` default, so a value written by an older or newer build degrades field by field instead of discarding the row. The library stores the collection as one JSON object, `{ "s:browser": { "versionKey": "…", "data": { … } } }`, where `s:` marks a string key and `versionKey` changes on every write; that format cannot hold the six raw strings used before (`jx-theme`, `jx-palette`, `jx-font`, `jx-text-size`, `jx-sidebar-collapsed`, `jx.locale`), so `migrateLegacyKeys` runs once at module scope: when the row is missing and any old key exists it inserts the row from them and removes the old keys.

`theme-store.ts`, `sidebar-store.ts` and `app-store.ts` are thin functions over that row and keep their old exports. Reads go through `usePreferences`, a `useSyncExternalStore` over `collection.subscribeChanges`, rather than `useLiveQuery`, because one row needs no query engine and the live-query compiler would land in the entry chunk; `readPreferences` parses the row through the schema and keeps the parsed object's identity until the stored JSON changes, which `useSyncExternalStore` requires. Writes are `collection.insert` for the first write and `collection.update` afterwards, so nothing is stored until the user chooses something. `theme-store.ts` subscribes once at module scope and applies the `dark` class and the `data-*` attributes from the row, which means a change made in another tab arrives through the collection's `storage` event and restyles this tab too; `app-store.ts` does the same for the chosen language and keeps a small TanStack Store only for the installation default language, which is session state and is never stored.

`src/stores/transaction-views.ts` adds two more collections built the same way, `savedFiltersCollection` (`jx-saved-filters`) and `transactionTemplatesCollection` (`jx-transaction-templates`). They differ from the preferences row in one respect: they are lists, so each row carries its own id and name and the getKey is the row's id rather than a constant. Everything else is the same shape — an explicit storage key, the shared `browserStorage()` object, a zod schema whose inner fields all carry `.catch` defaults so a row written by another build degrades field by field, a `getSyncMetadata` that returns only the storage key, and a `useSyncExternalStore` read that keeps the parsed array's identity until the stored JSON changes. `readSavedFilters` and `readTransactionTemplates` sort by name with `toSorted`, so the menus show a stable list and the snapshot identity is still tied to the stored content. `clearTransactionViews` exists for the story runner, which deletes every row between stories exactly as it deletes the preferences row.

Storage that is blocked must not break the app. `browserStorage()` in `src/lib/browser-storage.ts` probes `localStorage` with a write inside try/catch and returns the real object when it works, so the collection's cross-tab check `event.storageArea === storage` still holds, and an in-memory object with the same three methods when reading the property or writing throws (Chrome with site data blocked throws on the property itself). The collection's own default would touch `window.localStorage` unguarded at import time, and its `getSyncMetadata` does so on every mutation, so `preferences.ts` passes `storage` explicitly and replaces `getSyncMetadata` with one that returns only the storage key. With the in-memory storage, choices last for the session. `public/theme-init.js` runs before the bundle and cannot import the library, so it reads `jx-preferences` itself inside try/catch, takes `["s:browser"].data`, falls back to the old keys for the one load before the migration has run, and falls back to the system colour scheme when storage is blocked or the JSON is unreadable; `theme-init.dom.test.ts` runs the real file against a row written by the collection so the two cannot drift apart.

Color palettes are a per-browser choice, separate from light/dark. `stores/theme-store.ts` keeps the palette in the preferences row and sets `data-palette` on `<html>`; `public/theme-init.js` applies it before first paint. The default palette, `ledger`, sets no attribute. Each palette (`plum`, `sepia`, `graphite`) overrides only the neutral and primary tokens in `global.css`, for light and dark; the values are the ledger tokens with the OKLCH hue rotated and lightness kept, so every contrast ratio matches the default. Income, expense, secondary and destructive colors never change with the palette. `PalettePicker` (`components/palette-picker`) is a native radio group shown on Settings and Profile; its swatches carry their own `data-palette`, which is why the dark selectors also match `.dark [data-palette]` descendants.

Typeface and text size follow the same per-browser pattern: `font` sets `data-font` and `textSize` sets `data-text-size` on `<html>`, both applied by `theme-init.js`, and the defaults (`ledger`, `default`) set no attribute. Tailwind `font-sans` and `font-serif` resolve to `--font-body` and `--font-display`, which each `[data-font]` block redefines: `sans` and `serif` use one Source family for both roles, `system` uses the device fonts, and `inter`, `hyperlegible` (Atkinson Hyperlegible Next), `plex` (IBM Plex Sans with Plex Serif 600 for display) and `editorial` (Inter with Newsreader for display) use extra self-hosted families. Their `woff2` files, latin and latin-ext subsets taken from the Fontsource packages, sit in `src/assets/fonts` beside one `OFL-*.txt` license per family and are declared in `fonts.css`; a browser downloads a family only when it is used, so the extra files cost nothing until someone opens the picker or chooses that option. Text size changes the root `font-size` (93.75% or 112.5%); every size and control height is in `rem`, so the whole interface scales. `FontPicker` (`components/font-picker`) sits under `PalettePicker` on Settings and Profile, and each typeface option carries its own `data-font` so it previews itself.

The desktop shell has no top bar. Notifications, language, theme and the collapse control live in the sidebar foot, and `NotificationBell` takes `placement="above"` there so its panel opens upward. Below the `md` breakpoint a compact header and a scrolling navigation strip take over. Navigation items are grouped by job with a gap between groups instead of labels. The language control shows the current language code and names the language it switches to; flags are not used because a flag stands for a country, not a language.

Tables have no surrounding box. The `Table` primitive supplies the muted header text, the ink header rule and `px-3` cells, and each table's scroll region is pulled out with `-mx-3` so cell text aligns with the page edge while row hover still has room.

## Brand assets
The mark is a single vector path, the ledger bird, kept in `frontend/scripts/brand/bird.svg`. `scripts/brand/build.mjs` reads that path, measures its bounding box in headless Chromium and writes `src/components/brand/mark-paths.ts`, which the `BrandMark` component and every static asset share. `favicon.svg` carries a `prefers-color-scheme` rule so the bird stays legible on dark browser chrome; the PNG and ICO files are screenshots of the same SVG on a navy tile, taken with the Playwright already installed for tests, and the ICO container is assembled in the script, so the generator needs no extra dependency. From `frontend/` run `node scripts/brand/build.mjs`; Storybook maps `public/favicon.svg` through `staticDirs` in `.storybook/main.ts`, so there is no second copy. If the mark changes, regenerate all of them together so the favicon, the manifest icons and the in-app logo cannot drift. Storybook uses the same favicon and a branded manager theme (`.storybook/manager.ts`, `.storybook/manager-head.html`). The manifest is covered by the existing Content-Security-Policy because `default-src 'self'` applies to `manifest-src`.

## Accessibility conventions
Row actions name their row: `aria-label` and `title` read "Edit: Maistas", not "Edit", so a screen reader list of buttons is usable. `ConfirmDeleteDialog` takes `itemLabel` and shows what is about to be deleted above the warning; `useConfirmedDelete` looks the label up from the list the call site already has. `FieldError` takes an `id`, and each control points at it with `aria-describedby` while the field has an error. A `SelectField` without a visible `Label` must be given `aria-label`.

Money direction never depends on color. `SummaryStats` items take `sign` (`"+"`, `"−"` or `"auto"`), and tables prefix signed amounts the same way. Charts are wrapped in an element with `role="img"` and a label, format their axis with `useAxisMoney` (compact euro amounts in the active locale) and do not animate, because Recharts animation ignores `prefers-reduced-motion`.

Controls are 36px for the desktop bookkeeping session and grow to 44px on touch devices through `pointer-coarse:` variants on `Button` and the column filter trigger. Under reduced motion view transitions keep a 100 ms cross-fade and drop all movement, so state changes stay visible without sliding.

Recharts is about 330 KB minified (97 KB gzipped) and only six components draw with it, so none of them is imported statically by a page. `lazyChart` in `src/components/chart/lazy-chart.tsx` wraps a dynamic import in `React.lazy` and its own `Suspense` with a skeleton of the chart's height, and the `index.ts` of each chart folder (`IncomeExpenseChart`, `SpendingPaceChart`, `NetWorthHistoryChart`, `NetWorthCompositionChart`, `BudgetUsageChart`, `BillsForecastChart`) exports the wrapped component. A page's text, tables and totals therefore paint from the route chunk alone and the chart chunk arrives beside them, without the layout moving when it does. `axisProps` (tick style, no axis or tick lines) and `chartCursor` live in `chart-theme.ts` so that importing them does not pull Recharts in. Both net worth charts are `TimeSeriesLineChart` (`components/chart/time-series-line-chart.tsx`), which is imported by path from the lazily loaded chart files and is not re-exported from the folder's `index.ts`, because that would put Recharts in every chunk that imports the chart helpers. Stories and tests import the chart file itself and stay synchronous.

The CSV export is a plain link, but the PDF export is fetched: `ExportMenu` runs a mutation over `fetchFile` from `src/api/client.ts` (same cookies, session renewal and `ApiError` mapping as `customFetch`, but the body is read as a blob and the name comes from `Content-Disposition`) and hands the blob to `saveFile`. A link cannot show why the server refused, and the PDF endpoint answers 400 `export.tooManyRows` above 5000 rows; as a mutation that failure reaches the usual error toast. A link carries no request header either, so both URLs are built by `useExportUrl` (`src/hooks/use-export-url.ts`), which adds the active household to the query string the way `customFetch` adds it to the header; the hook reads the preference, so a link follows the switcher without a refetch.

A holding's price is changed through `PUT /api/investments/securities/{id}/price` (`useSetSecurityPrice`), which a holder of the security may call; the full security form uses `PUT /api/investments/securities/{id}`, which is administrator-only, so `SecuritiesDialog` shows the edit button only when `me.role` is `Admin`. Both forms and the create form show server failures in their own `FormError` (`security.notHeld`, `conflict.duplicate` for an existing symbol and currency) instead of a toast.

`QueryBoundary` takes `errorFallback` for places where the default sentence does not fit; the notification bell uses it to stay an icon (`NotificationBellUnavailable`) instead of breaking the sidebar foot. `Pagination` renders nothing when there is a single page. Dialog overlays are a flat scrim without blur, in line with the paper surfaces.

Category rows on the dashboard and in reports link to the transactions list filtered by that category and date range, so a total can always be traced to its rows.

## Transactions and import workflow
The transactions page reads three things from the same filter set: the paged list, `GET /api/transactions/summary` for the totals line, and the export links. The summary runs through `useDeferredParams` like the list and has its own `QueryBoundary`, so it carries the stale rule together with the rows and a slow summary never blocks the table. Every mutation that changes the list also invalidates the summary.

Row selection is rendered by the table itself, not by a column definition, because `FlexRender` remounts cell contents on each render and a remounted checkbox loses keyboard focus. Selection state is stored together with the current filter, sort and page key, which clears it on any of those changes without an effect. Bulk recategorize calls `POST /api/transactions/bulk-category`; the toolbar offers only categories whose type matches every selected row and disables itself on a mixed selection, which mirrors what the server accepts. Split rows cannot be selected. The same toolbar sets tags through `POST /api/transactions/bulk-tags`, which replaces the whole set on every selected row; that half has no type rule, because a tag has no flow type.

"Save and add another" keeps the dialog open, resets the form but keeps type, account and date, and returns focus to Amount through a ref. The add dialog is opened by the `new` search param so the `n` shortcut and the button share one path; the param is stripped before the deferred params are computed so opening the dialog does not mark the rows stale. Below `md` the page renders `TransactionsList` instead of the table and moves filters and sort into `TransactionsFiltersDialog`; both layouts share one data source, one pagination and the same handlers, and the switch is CSS only.

Import has no route. `ImportDataSection` (`features/imports/import-data-section`) renders on Settings and Profile when the `import` feature is on and opens `ImportDialog`, which holds the chosen provider in local state (a provider list first, then `ImportSection` in a wide `Modal`). Adding a provider means adding an entry to the `providers` list in `import-dialog.tsx` and a branch for its upload and review. Settings itself is split by a `section` search param (`general`, `features`, `currencies`, `regional`, `defaults`, `import`, `backups`, `appearance`) rendered by `SettingsNav`; the settings form stays mounted and hides inactive sections with `hidden`, so unsaved edits survive switching sections. Review helpers live in `preview-rows.ts` and are pure (selection summary, select-all, bulk apply, recall), which is what `preview-rows.test.ts` beside it covers. ## Keyboard shortcuts
`lib/shortcuts.ts` owns the key map and is the single source for both the handler and the help popover, so the two cannot drift. Key matching is done by TanStack Hotkeys (`@tanstack/react-hotkeys`), the project's standard for keyboard shortcuts: single keys are registered with `getHotkeyManager()` and the `g` sequences with `getSequenceManager()`. `app.tsx` calls `registerShortcuts` once at module scope, the same way it registers the session-expired listener, because the project does not use effects; that is why the managers are used directly instead of the `useHotkey` hooks. The library matches modifiers exactly and skips inputs, selects and editable elements. Registrations turn off the library's `preventDefault` and `stopPropagation` so the handler can first apply the app's own guards and only then prevent the default. The handler ignores repeated keydowns, events already handled, events from elements with a combobox or textbox role, events while a dialog is open, and everything on the sign-in and setup routes.

`n` opens the add-transaction dialog by navigating to `/transactions?new=true`; the route owns the `new` search param, so the dialog state is a URL like every other view state. `/` clicks the element marked `data-shortcut="search"` when the page has one and otherwise goes to the transactions list. `g` followed by a letter within 1.2 seconds navigates (`d` dashboard, `t` transactions, `i` import, `a` accounts, `c` categories, `b` budgets, `o` goals, `l` bills, `w` net worth, `r` reports, `h` households). `?` toggles the help popover in the sidebar foot; its open state lives in a small TanStack Store so the key handler and the popover share it without an effect. `toHotkeySteps` maps each entry of the key map to library hotkeys (`?` becomes `{ key: "?", shift: true }` because the typed hotkey strings exclude shifted punctuation); `shortcuts.dom.test.ts` covers that mapping, the ignore rules, the sequence timeout and the registered handlers against a real DOM.

## Forms
Forms use TanStack Form 2 (`@tanstack/react-form@alpha`). Each form passes one zod schema as `validators: [{ run: schema, triggers: ["change"] }]`; submit runs it again. Render props read `field.value`, `field.errors[0]?.message` and `field.meta`, not `field.state`. Lists use `form.ArrayField` with `pushValue` and `removeValue`. In alpha.2 an `ArrayField` re-renders only when the array length changes, not when its errors change, so an error attached to the array path itself (the split total mismatch on `lines`) is rendered through a nested `form.Field name="lines"`. Remove that wrapper once the library subscribes array fields to their meta. The package-update workflow re-pins the `alpha` tag after `nub update --latest`, because `latest` still points at 1.x.

### Shared field components and server errors
`src/components/form` builds on TanStack Form composition: `useAppForm` exposes field components (`TextField`, `MoneyInputField`, `MoneyAmountField`, `SelectFieldControl`, `DateField`, `CheckboxField`, `CurrencyField`) and the form components `SubmitButton`, `FormShell` and `FormActions`. `FormShell` is the `<form noValidate>` whose submit handler stops the event and calls `form.handleSubmit()`; `as={FormGrid}` (or `as={Section}`) renders that layout component as the form, and `onBeforeSubmit` runs first. `FormActions` is the Cancel and submit footer; `span` makes it cover the whole grid. `useServerForm({ defaultValues, schema, submit, aliases })` is `useAppForm` with the schema validated on change and `submit` wrapped in `submitToServer`; forms that need `formApi` inside the submit keep `useAppForm`. Groups of fields that repeat across forms are TanStack Form field groups made with `defineAppFieldGroup` and bound by name: `MoneyPairField` (an amount with its currency), `SharingFields` in `src/components/sharing-fields` (scope and household, with `sharingShape`, `refineSharing` and `sharedHouseholdId` in `validation.ts`), and the settings sections (`FeaturesFields`, `CurrenciesFields`, `RegionalFields`). `silent(options)` in `src/lib/mutations.ts` builds the options of a mutation whose error the form shows inline instead of the toast, and `upsert(createMutation, updateMutation)` merges a create and an update mutation into `create`, `update`, `pending` and `error`. A field component takes `id`, `label`, optional `hint` and derives the error id, `aria-invalid`, `aria-describedby` and the `FieldError` itself, so a form declares one element per field. Blocks with their own layout (split lines, the conversion rate line, currency lists) stay hand-written inside the same form. Schemas are composed from the builders in `src/lib/validation.ts` (`requiredText`, `optionalText`, `requiredValue`, `positiveMoney`, `password`, ...), which pair each rule with its translated message; length limits come from the generated zod constants.

A form submits through `submitToServer` with `mutateAsync` (a parent that owns the mutation returns the promise from its `onSubmit` prop). When the API answers with field entries, `serverFieldErrors` places each one on the field whose name equals the entry's JSON path (`amount`, `lines[1].amount`), where it renders through the same `FieldError` and aria wiring as a client error and clears on the next edit; `FormError` lists only the entries that match no field. `hasServerErrorCode(error, code)` answers whether a failure carries a code, at the top level or on an entry; forms use it where one code needs its own reaction: the password dialogs empty only the current-password box on `password.incorrect`, the bill confirmation replaces the generic `conflict.stale` text, and the conversion form replaces `transaction.splitNotAllowed`, whose shared text is about bulk recategorizing, with a sentence about the fee expense.

Editing reuses the create form instead of copying it. `TransferForm` and `ConversionForm` take the record (`transfer`, `conversion`) and an `error`; with a record they start from its values, label the button Save and render the owner's mutation error in a `FormError`. The create dialogs do the same: their mutations are silent, and the error is cleared when the dialog opens (transfers) or closes (conversions). `TransferEditDialog` and `ConversionEditDialog` sit in the section's folder, own a silent update mutation and render through `EditModal`, which keeps the last record so the closing animation still has content. The transfer locks follow `fromAccountImported` and `toAccountImported`: an imported side disables its account and amount and the date, and the sent amount is also disabled while the receiving side is imported and both currencies are equal, because then the two amounts are one number; choosing a sending account in another currency releases it. The request always carries `currency` and `receivedCurrency` as the form holds them. An account the user can no longer see is added to the select as "Account not available" so the value still shows. A conversion's fee fields state the fee as it should be afterwards: an empty amount sends `feeAmount`, `feeCurrency` and `feeCategoryId` as null, which deletes the fee transaction. The fee category select needs the categories, so `ConversionsSection` reads them and the accounts route warms them when multi-currency is on. `RecurringBillForm` follows the same rule: without a `bill` it creates one, with a `bill` it starts from its values, prefixes its field ids with the bill id, adds the `isActive` checkbox and sends every field of `UpdateRecurringBillRequest`; both modes validate the reminder days against the generated minimum and maximum. `RecurringBillConfirmForm` reads `bill.nextDueDate` from its props when it submits, not from form state, so after a `conflict.stale` answer (the mutation cache refreshes the bills on every settle) the second attempt uses the refreshed date.

`ConfirmDeleteDialog` takes optional `title`, `description` and `confirmLabel`, so an irreversible action that is not a delete (deactivating a user) uses the same dialog with its own words.

## Frontend tests
Vitest has three projects. `unit` (node) and `dom` (jsdom) are what `nub run test` runs. `stories` (jsdom) runs every Storybook story, including its `play` function and an axe scan, and is what `nub run test:stories` and `just test-stories` run; a story is therefore a test, and a selector that no longer matches fails CI instead of rotting. It is a project of its own because it takes about three minutes against about two and a half for the other two, so `nub run test` stays the quicker loop; `just check` runs both and CI runs all three under coverage with `test:coverage`. No browser is involved. Storybook itself is for looking at the interface; until 2026-09-20 the stories also ran in headless Chromium, which the decision log records as superseded.

The story runner lives in `src/test/stories`. `story-runner.ts` finds every `src/**/*.stories.tsx` with `import.meta.glob`, sorts the paths and deals them round-robin to six shard files (`shard-1.test.ts` to `shard-6.test.ts`), because Vitest runs test files in parallel and a single file would use a single core. Each shard imports its story files once, which matters: importing the preview pulls in the whole route tree, and paying that per story file instead of per shard would multiply the run time. `story-session.ts` composes each file with `composeStories` after `setProjectAnnotations` has been given the real `.storybook/preview.tsx`, so decorators, providers, i18n, theme, router and the five-second `findBy*` timeout are the ones Storybook uses. Every story becomes one test named after its file and its story, for example `components/ui/button/button.stories.tsx > Default`, and the test awaits `Story.run()` (loaders, `beforeEach`, mount, `play`) and then the axe scan.

The only thing the runner swaps is the mock transport. `.storybook/mock-worker.ts` holds the service worker start-up (`startMockWorker`, up to three attempts, because `worker.start()` occasionally never resolved in a fresh iframe) and exports it as `mockWorkerLoader`; the runner replaces that one loader with the same `mswLoader` from `msw-storybook-addon`, pointed at a `setupServer()` from `msw/node`. Handlers therefore resolve exactly as in Storybook: the merged `parameters.msw`, as an array or as an object of arrays, with a story's own list replacing the preview default. An unhandled request prints a warning and is not an error, which is what the worker does as well. Relative URLs such as `/api/accounts` work because MSW resolves them against the jsdom location.

Between stories the runner calls the finished story's `load()`, which is how Storybook's portable stories run the pending clean-ups (unmount, hook clean-up, `beforeEach` returns) without mounting anything new; it then resets the MSW handlers and deletes the preferences row from the TanStack DB collection, while `disposeStoryState` clears the saved filters and transaction templates the same way, and `src/test/setup.ts` clears `localStorage`, the theme attributes and the language as it does for DOM tests. The preview has a `beforeEach` whose clean-up (`disposeStoryState` in `src/storybook/decorators.tsx`) clears every query client a story created and dismisses toasts, in Storybook as well as in the runner. Measured on 2026-09-20 over a shard of 222 stories with garbage collection forced before each sample, the heap went from 127 MB to 192 MB, in steps that coincide with lazily loaded modules such as Recharts; without forced collection a worker's resident memory ended between 0.5 and 1 GB.

jsdom lacks a few things the stories need, and `src/test/polyfills.ts`, loaded by `src/test/setup.ts`, supplies only these. `Blob`, `File`, `FormData` and `Request` are replaced by Node's own classes: jsdom's `FormData` cannot be sent by Node's `fetch`, and the conversion Vitest 5.0.1 ships for it reads a private field that jsdom 30 renamed, so every upload failed with `Cannot read properties of undefined (reading '_buffer')`. Remove the replacement when Vitest and jsdom agree again. `scrollTo` is an empty function because the router calls it on every navigation and jsdom only prints "Not implemented". `matchMedia` was already stubbed. Nothing else is stubbed: Base UI popups, dialogs and the lazy charts pass without `ResizeObserver` or `IntersectionObserver`, and `chooseOption` and `openedDialog` in `src/storybook/interactions.ts` needed no change, since they wait on the DOM (the listbox leaving, the dialog being visible) and not on a transition event.

jsdom applies no stylesheet and computes no layout, so an assertion that needs real CSS or geometry cannot run there. Such a story carries `tags: ["browser-only"]`; the runner registers it as skipped, Vitest reports the count in its summary, and its `play` function still runs in Storybook's Interactions panel. Today the list has one entry: `ClosedPositionsOpen` in `features/investments/positions-section`, which checks `offsetParent` to prove that a row inside an opened disclosure is laid out. Do not loosen an assertion to get it through jsdom; tag the story instead, and keep the list short.

Accessibility is part of the run. After the `play` function the runner scans `document.body` with `axe-core`, portalled popups included, and any violation fails the test with the rule, the help text and the offending markup. `region` is off as in Storybook's own accessibility addon, because a component in isolation has no landmarks. Five rules are off because they need paint or layout that jsdom does not have: `color-contrast` and `color-contrast-enhanced` (computed colours), `link-in-text-block` (colour and underline comparison), `target-size` (element geometry) and `scrollable-region-focusable` (overflow measurement). Without CSS the mobile and desktop variants of a layout are both in the tree, which made the two navigation landmarks of the root layout collide; the scan therefore leaves out elements with a `sm:hidden`, `md:hidden`, `lg:hidden` or `xl:hidden` class, matching the 1280 pixel desktop width the stories were written for. A rule is switched off for a single story with `parameters.a11y.config.rules`, which both the runner and Storybook honour, and no story does so today; there are no exemptions for vendored primitives. Colour contrast is a manual check: `.storybook/preview.tsx` keeps `a11y: { test: "error" }`, so the Accessibility panel of `nub run storybook` shows violations, contrast included, as errors, and a change to colours or a new surface is reviewed there in both themes. A play function that picks from a select uses `chooseOption`, which waits for the listbox to leave the DOM; axe otherwise inspects the popup while it closes and reports Base UI's focus guards and the half-closed listbox.

To run the stories of one file, set `STORY_FILE` to any part of its path; shards with no matching file skip without importing anything. From `frontend` in PowerShell: `$env:STORY_FILE = "button.stories"; node_modules\.bin\vitest.cmd run --project stories; Remove-Item Env:STORY_FILE`. Add `-t "Default"` to narrow it to one story by name. `nub run test:stories -- <path>` does not work for this, because nub does not pass the filter on; `node_modules\.bin\vitest.cmd run --project stories src/test/stories/shard-1.test.ts` runs one shard. Even a single story takes about a minute, nearly all of it transforming the application that the preview imports.

`just e2e` starts a throwaway Compose project (`docker-compose.e2e.yml`: project `jx-e2e`, port 8089, own volumes, no database or API ports published), runs the Playwright smoke tests in `frontend/e2e` against it (first-run setup, closed setup, refused login, account form, ledger and balance, sign out) and removes it; it never touches the dev database. The Playwright config has three projects that run in order: `smoke` (`smoke.spec.ts`, which performs the first-run setup), `setup` (`auth.setup.ts`, one administrator sign-in saved to `e2e/.auth/admin.json`, ignored by git) and `chromium` (every other spec, started with that stored state). Each of those specs creates what it needs through the API under unique names and does not depend on another spec: statement import with a matched transfer, cross-currency transfer create and edit, recurring bill create and confirm, a feature switched off and on, the member lifecycle with a password reset, two-factor enrolment with a code from `otpauth` and a recovery code, backup and restore, the language toggle and the phone navigation. Three things in `e2e/support.ts` are not obvious. The refresh token rotates, so a stored state goes stale as soon as one test refreshes; the automatic `keepAdminState` fixture therefore checks `/api/auth/me` before each test (refreshing, or signing in again when a restore ended every session) and writes the cookies back afterwards, without local storage, so a language chosen in one test does not leak into the next. `browser.newContext()` inherits the project's stored state, so `newVisitor` passes an empty one for a second person. Sign-in is throttled to ten calls per five minutes per client, which the suite exceeds, and FastEndpoints identifies the client by `X-Forwarded-For`; `frontend/Caddyfile` has `trusted_proxies static {$TRUSTED_PROXIES:127.0.0.1/32}`, `docker-compose.e2e.yml` sets it to `private_ranges` for the throwaway stack only, and every test sends its own address derived from its title. Everywhere else the default trusts only loopback, so a client still cannot choose its own throttle bucket. A known backend defect is written as a test marked `test.fail` with the reason, so the suite stays green and turns red when the defect is fixed and the mark has to go. `just e2e-install` downloads the Chromium build they need.

Translation keys are typed: `src/i18next.d.ts` registers `locales/en/common.json` as the resource type, so `t("…")` only accepts existing keys and a key held in a variable is typed `TranslationKey`. `locales.test.ts` fails when English and Lithuanian differ in keys or in the placeholders of a text.

Vitest runs the frontend tests; `nub run --cwd frontend test` runs them once, `test:watch` watches and `test:coverage` writes a V8 coverage report. Tests sit beside the file they cover. `vitest.config.ts` is separate from `vite.config.ts` so a test run never regenerates the route tree, and it keeps the React Compiler preset so components are tested as they ship.

Of the unit and DOM projects, `*.test.ts` runs in plain Node and is for pure logic (validation, calendar, cash effect, import preview rows, report presets). `*.test.tsx` and `*.dom.test.ts` run in jsdom with `src/test/setup.ts`, which loads the jest-dom matchers, stubs `matchMedia`, and after each test unmounts, clears `localStorage`, resets the theme attributes and returns i18n to English. Anything touching `window`, `document`, `localStorage` or a React hook belongs in the jsdom project; the split exists because creating a jsdom environment per file is the slowest part of a run.

The preferences collection reads storage when its module loads, so store tests seed storage with `seedPreferences` from `src/test/preferences.ts` (which writes the collection's stored format) and take a fresh copy of the store for each test from a loader made by `freshModuleLoader` in `src/test/fresh-module.ts`, which calls `vi.resetModules()` and imports the module again; `storedPreferences` reads the row back and `blockStorage` makes the `localStorage` property throw, which is how the blocked-storage path is tested. `src/test/query.tsx` gives hooks and components a fresh `QueryClient` seeded with settings and currencies and a `fetch` that never resolves, so a test states the loaded data it needs and nothing reaches the network. Text from `Intl` goes through `plain()` before comparison because locales use non-breaking spaces. Time zone tests set `TZ` through `vi.stubEnv` and build their dates inside the test. Exit animations do not run in jsdom, so behaviour that only exists while a dialog closes stays a Storybook concern.

A test's own time is limited to 5 seconds, and whatever a test body imports for the first time is counted in it. A full run keeps one worker per CPU thread but one busy (eleven on a 12-thread laptop), and because files are isolated every file gets a fresh worker, each loading jsdom and its packages from disk while the single main process transforms every source file through Babel and the React Compiler, and Vitest starts the slowest files first, so the first seconds are the busiest. A module loaded inside a test in that window waited behind all of it: the first test of `transaction-views.dom.test.ts` took up to 24 seconds (the store pulls in the generated model barrel of about 200 files), the other store tests 2 to 3 seconds, and the command palette test up to 6 seconds while React loaded the two lazy net worth charts. Both run alone in well under a second, which is why they only failed in the full run. So module loading happens before the tests: `freshModuleLoader` imports the module once at the top of the file, where the time counts towards collection and not a test, and later copies reuse the transformed code; the palette test imports the two chart modules at the top as well. Keep new tests that way: import heavy or lazy modules at the top of the file, not inside a test.

`src/test/app-router.tsx` mounts the real route tree for `route-prefetch.test.tsx` and `command-palette.test.tsx`: the whole shell with a page, several suspense queries in a row and, for the palette, the palette on top. That work is real and takes 0.5 to 2.3 seconds per test in a full run, against a Testing Library default of 1 second for `findBy` and `waitFor`, so these two files wait up to 5 seconds (`appWait`) and allow 20 seconds per test (`APP_TEST_TIMEOUT`); nothing else raises a timeout. The query client there has an infinite `staleTime` because both files count requests. With the default of 0, a suspense query treats data older than one second as stale when its component mounts, so on a slow run the transactions page asked for `/api/transactions` again after the loader had fetched it and the "asked once" assertion failed; the tests check that loader and page build the same keys, which an infinite `staleTime` still catches, and not how quickly the machine renders.

Paged lists show the new page number as soon as the button is pressed and keep the previous rows until the next page arrives, so a test or story that pages waits for a row of the new page before it counts rows; the `Paged` story of `HouseholdActivity` counted after the page number alone and failed whenever the response was slow.

`vitest.config.ts` sets coverage thresholds per folder for the three areas that are tested directly, a little under what `test:coverage` measured on 2026-09-19 (statements, branches, functions, lines): `src/hooks/**` 83/79/63/88, `src/lib/**` 85/83/90/91, `src/stores/**` 95/92/95/96. There is deliberately no global threshold: pages, forms and tables are covered by stories, which the V8 report of the unit and DOM projects does not see, so the overall figure (about 20%) says nothing. Raise a folder's numbers when its coverage rises.

Covered: `src/lib`, `src/api/client.ts` (money normalization, session refresh, problem details), stores, the settings and formatter hooks, the pure feature helpers, and the shared components with behaviour of their own (pagination, error state, query boundary, confirm delete, money field, meter, the theme, language and palette controls, sidebar visibility). Pages, forms and tables are exercised through Storybook stories and their play functions instead.

## API contract and generated client
The backend is the single source of the contract. `OpenApiExtensions` builds the document; `OperationNames.Shorten` strips the `Endpoint` class suffix from every operation id, so an endpoint class `GetAccountsEndpoint` becomes operation `GetAccounts`. `ArrayWrappers.Inline` replaces every array wrapper schema with an inline array, so TypeScript sees `AccountResponse[]` rather than a named `IReadOnlyListOfAccountResponse`, and `SchemaVariants.Collapse` merges per-operation copies of one request type. Collapse leaves array variants alone: FastEndpoints gives every annotated collection property its own `IReadOnlyListOf…__op…` copy carrying that property's description, example and `minItems`, and merging those into the plain wrapper dropped the constraints and, once a second property of the same element type existed, mixed up the descriptions. Because `ArrayWrappers.Inline` runs next and inlines each copy where it is referenced, every collection property keeps its own annotations and no `__op` name survives (`OpenApiArrayPropertyTests`). A backend test fails if a schema name contains `__op` or a collection prefix. On the Orval side `operationName` in `orval.config.ts` drops the `Get` prefix of GET operations, giving `useAccountsSuspense`, `getAccountsQueryKey` and `getAccountsMockHandler` instead of `useGetAccounts…` and `getGetAccounts…`; mutations keep their verb (`useCreateAccount`).

Only what the app uses is generated: suspense hooks for every query, plain `useQuery` hooks only for the operations listed in `plainQueryOperations`, MSW handlers without faker response factories (stories always pass an override), and zod schemas for request bodies and responses only. The zod project reads the spec through the `forValidation` input transformer in `orval.config.ts`, which only affects `src/api/schemas`: it gives every `format: decimal` schema a pattern (digits, optional dot and up to eight decimals), so the generated schema rejects `12,50` or text, and it adds a synthetic `GET /__contract/problem-details` operation because Orval emits zod only for success responses; that yields `ProblemDetailsResponse`, which the fixture contract test uses to check every problem fixture, including that each `code` is a published `ErrorCode`. The synthetic path never reaches the client or the MSW handlers. Generated folders are marked `linguist-generated` in `.gitattributes` so reviews collapse them.

`frontend/orval.config.ts` runs two Orval projects over `frontend/openapi.json`:

| Output | Content | Committed |
| --- | --- | --- |
| `src/api/generated/<tag>/<tag>.ts` | fetch functions, query keys, query/suspense/mutation hooks, one file per OpenAPI tag | yes |

App code imports hooks from the `@/api/generated` barrel and types from `@/api/generated/model`. The barrel deliberately has no `.msw` exports; stories and tests import a handler from its own file (`@/api/generated/accounts/accounts.msw`) so faker and msw never reach the production bundle. Generated code is formatted by the Orval `afterAllFilesWrite` hook, which runs `oxfmt` over the output folder rather than over the list of written files that Orval would append to a plain command: with one more tag that list, under a checkout path like a OneDrive folder, passed the Windows command-line limit and the hook failed. It is excluded from lint, not from formatting.

Regenerate with `just gen` (`scripts/gen.mjs`, which CI and the package update workflow call too). It runs the API with `--export-openapi-docs true`, which writes `backend/JxFinance.Api/wwwroot/openapi/v1.json` and exits before migrations, so neither a database nor a running server is needed, and copies the result to `frontend/openapi.json`. The export does not depend on the HTTP routes below and produces the same file in any environment. The document transformer empties `servers`, which otherwise appeared or not depending on whether Kestrel had bound its port when the document was built.

The HTTP routes `/openapi/v1.json`, `/scalar/v1` and the redirect from `/` exist only in the Development environment (`ApiPipelineExtensions.ServesApiDocs`), so a deployed installation does not publish its API description to anyone who can reach it. `App:ApiDocs=true` switches them on elsewhere; the integration tests use it because they run in the `Testing` environment and compare the served document with the committed contract. The rule itself is covered by `ApiDocsGateTests` rather than by starting a second host: FastEndpoints keeps process-wide state, and a second application in the test process broke authentication for every test that ran after it. That file is the one committed copy of the contract: Orval reads it, and the backend test `OpenApi_document_matches_the_approved_contract` compares it semantically (ignoring `servers` and formatting) with what the running API serves, so there is no separate snapshot to refresh. CI runs the identical export, then fails when `git status` shows any change (including new untracked files) to `frontend/openapi.json`, `src/api/generated` or `src/api/schemas`. The export and the EF recipes build in Release so they work while `just dev` holds the Debug output.

`src/api/client.ts` is the Orval mutator. Every failed request throws an `ApiError` (a real `Error` subclass carrying `status`, `title`, `detail` and per-field `errors`). The file exports `ErrorType`, which Orval picks up, and `query-client.ts` registers `defaultError: ApiError`, so `error` on every query and mutation is typed as `ApiError` without casts; use `isApiError` when the value comes from somewhere untyped.

### Route loaders and optimistic updates
Every route has a `loader` that warms the page's primary queries through `warm` in `src/lib/route-prefetch.ts`, a non-awaited `prefetchQuery` with the generated `get…SuspenseQueryOptions`. Loaders never await and never throw, so navigation is not blocked and `QueryBoundary` still owns error display; with `defaultPreload: "intent"` the data is usually cached before the click. The query client reaches loaders and `beforeLoad` gates through router context. Loader and component must build identical query keys, so params derived from search state or settings live in small `*-queries.ts` files used by both; `route-prefetch.test.tsx` mounts the real route tree and asserts each endpoint is requested once.

`src/lib/optimistic.ts` provides `optimisticUpdate`, `optimisticRemoval` and `optimisticPagedRemoval`, which return the `onMutate` and `onError` pair for a generated mutation hook: cancel in-flight reads, rewrite the cached list, roll back on failure. They take the `QueryClient` from the mutation callback context (`context.client`), so callers pass only query keys and do not call `useQueryClient`. They are used for creating a transaction, deleting rows from lists and marking notifications read. Refreshing afterwards is not their job.

### Cache invalidation
Components do not call `invalidateQueries` after a mutation. `src/api/invalidation.ts` holds the only map from mutation to the query roots it makes stale, and the `MutationCache` built by `createMutationCache` applies it in `onSettled` for every mutation, wherever it was triggered. A root is the URL in a generated query key; invalidating `/api/accounts` also covers `/api/accounts/{id}` and any parameterised variant. Storybook uses the same cache, so stories behave like the app. `invalidation.test.ts` enumerates every generated `get*MutationKey` and fails until a new mutation is either given a rule or listed in `mutationsWithoutInvalidation`. Optimistic updates (`onMutate`, rollback) stay in the component that owns them.

The map follows what the server writes, not what the screen shows. `ledger` is the set of roots that any income or expense row feeds: transactions, accounts, dashboard summary, category breakdown, monthly trend, report summary, budgets and net worth. A conversion can book a fee expense, and a broker import or sync books conversion fees, so both refresh `ledger` on top of their own lists; broker operations also refresh `holdings`. Confirming a recurring entry refreshes `ledger`, the entries, the notifications and the transfer list, because the shape decides whether it wrote a transaction or a transfer. Removing a household member or deleting a household changes which shared accounts, categories and tags the user can see, so those refresh households, categories, tags, transfers, conversions, recurring bills and `ledger`. An exchange-rate sync refreshes accounts, net worth, the dashboard summary and the portfolio, because those are valued at the newest rate. Resetting a user's password refreshes the users list, because the same call can switch off that user's two-factor flag; reactivating one does so because the status changes. The eight deletes that write a trash entry are split out of the rules they shared with their create and update so that only they also refresh the trash list, and `restoreDeleted` is one of the two mutations mapped to `"everything"`, beside changing the installation settings: a restore can bring back any of eight kinds and there is no honest smaller set. `invalidation.test.ts` has a table of these derived refreshes; add a row when a mutation gains a side effect.

### Error codes
Every failure carries a stable code from the closed set in `Common/Errors/ErrorCodes.cs`: each FluentValidation rule sets one (the shared `CommonRules` and `DecimalRules` extensions set it for you, and `ValidatorErrorCodeTests` fails on a rule without a published code), JSON binding failures map to `decimal.malformed` or `request.malformed`, and service failures return a `DomainError(code, message)` whose code also decides the HTTP status. The OpenAPI `ErrorCode` enum is built from the constants by reflection, so Orval emits an `ErrorCode` union; `errors[].code` is never null and a top-level `code` covers problems without entries. The English `reason` stays as a fallback only.

A service method that can fail returns `Result<T>`, or the non-generic `Result` when success carries no value (confirming a password, consuming a two-factor code, deleting a backup). Both convert implicitly from the value and from `DomainError`, so a service writes `return account;` or `return new DomainError(ErrorCodes.ResourceNotFound, "Account not found.");`, and passes another result's failure on with `return other.Error;`. `Result<T>.Success(value)` is still needed where the value is typed as an interface, because C# does not apply user-defined conversions from interface types. Endpoints call `EnsureSuccess()` or `ValueOrThrow()`, which turn a failure into the problem response.

`Common/EntityLookup.cs` holds the lookup that answers 404. `FindOrNotFoundAsync(predicate, message, ct)` on any `IQueryable<T>` returns the tracked entity or a `resource.notFound` failure with the entity's own message, and a caller that needs the entity reads it with `result.TryGetValue(out var entity)` and otherwise returns `result.Error`. `UpdateOrNotFoundAsync` and `DeleteOrNotFoundAsync` on `AppDbContext` add apply-and-save and remove-and-save for services whose update and delete do nothing else (goals, assets, debts, deleting a budget or a recurring bill); they go through `db.Set<T>()`, so the owner query filters apply exactly as on the `DbSet` property. It is used where it shortens the code: a lookup followed by its own checks reads the same either way and was left as it is. `HouseholdService.FindOwnedAsync` builds on it for the five operations that need the household and the caller's ownership of it.

`IReferenceGuard` (`Common/References`) answers the two questions several services asked with their own queries: `AccountExistsAsync` returns `reference.notFound` "Account does not exist." or null, and `CategoryOfTypeAsync` checks a category's flow type. The second has two forms because the callers publish different failures for a missing category: given a message it returns `reference.notFound` for a missing category and `category.wrongType` with that message for the wrong type (transactions, budgets); given a whole `DomainError` it returns that one error for both cases (recurring bills, the conversion fee category). Codes and messages are those each call site had before.

The four hosted jobs derive from `Infrastructure/BackgroundJobs/PeriodicJob.cs`, which owns the `PeriodicTimer` loop, the service scope, the optional feature gate (`RequiredFeature`) and the error log "{Job} failed."; a job declares `Name`, `Interval` and `RunAsync(services, ct)`. `RunOnceAsync` stays public for tests and runs one gated pass immediately, which is also the first thing the loop does, so there is no start-up delay. `AppUser.IsActive` is the expression for "has a password and is not deactivated" that the broker sync and the net worth snapshot filter users with.

Transaction-scoped PostgreSQL advisory locks are taken through `Database.LockAsync` in `Common/AdvisoryLock.cs`. The overload taking a `Guid` derives the key from the first eight bytes of the id (per account, per user, per recurring bill); the overload taking `AppLock` is for installation-wide locks, and the numeric values of that enum are the lock keys, so they must never change or be reused.

On the frontend `serverErrorText` in `src/lib/form-server-errors.ts` is the single place that turns an entry into text: it looks up `serverErrors.<code>` in the locale files and falls back to `reason`. `server-error-codes.test.ts` fails when a published code lacks an English or Lithuanian translation, or when a translation exists for a code the API dropped, so adding a code on the backend is: constant, `just gen`, two translations.

Money, prices and quantities are `decimal` in every backend DTO and a JSON string on the wire (`"42.50"`), so nothing passes through floating point. The property carries `[property: Money]` (two decimals, written `0.00`) or `[property: Quantity]` (up to eight, written `0.########`); both attributes derive from `JsonConverterAttribute` and live in `Common/Json` next to their converters. The converters read only a JSON string in invariant culture with a dot separator, so `"12,50"`, grouping, `NaN` and bare numbers fail during binding; FastEndpoints reports that as a 400 problem whose `errors` entry is named after the JSON path (`amount`, `lines[1].amount`), which keeps per-field form errors working. Sign, scale and range rules are the shared FluentValidation extensions in `Common/Validation/DecimalRules.cs` (`IsPositiveMoney`, `IsNonNegativeQuantity`, ...). Request fields where zero is a valid value are `[JsonRequired]`, because a missing non-nullable decimal would otherwise bind as 0. `decimal? InterestRate` on debts is a plain JSON number and carries no attribute.

The same attributes drive the contract: a schema transformer in `OpenApiExtensions` describes such a property as `type: string, format: decimal`. `orval.config.ts` walks every request body in the spec and writes the names of those properties to the generated `src/api/generated/decimal-fields.ts`; the mutator in `client.ts` normalizes exactly those fields (trim, decimal comma to point) before sending, so a user typing `12,50` sends `12.50`. There is no hand-kept list on the frontend: a new money field needs the attribute, then `just gen`.

### Validation limits
Form schemas stay hand-written because they validate form state (strings, localized messages), not request bodies, but the numeric limits and patterns come from the generated zod constants rather than being retyped, so a limit changed in a backend validator reaches the form on the next `just gen`.

## Motion
Motion is limited to four things, all built on view transitions: changing page, table rows changing in place, a list row being added, removed or moved, and a section replacing its skeleton. Durations are 120 to 240 ms with an exponential ease-out, and nothing animates on its own.

The page change is driven by the router, not by React. TanStack Router publishes location through `useSyncExternalStore`, and React renders external-store updates synchronously even inside `startTransition`, so a React `ViewTransition` around `<Outlet />` never activates on navigation; an earlier version of this page relied on that and silently stopped animating. Instead the router is created with `defaultViewTransition` set to `pageViewTransition` from `lib/page-transition.ts`, which asks the router to wrap the commit in `document.startViewTransition` with the type `page`, and only when the pathname changed. Sorting, filtering and paging are navigations too, but they only change search params, so they return `false` and the page does not fade on every keystroke. The element around `<Outlet />` has the class `page-transition`, and `global.css` gives it `view-transition-name: page` only while `:root:active-view-transition-type(page)` matches, so it is not captured during any other transition. `::view-transition-old(page)` and `::view-transition-new(page)` give it a short fade and slide. The Storybook router in `src/storybook/decorators.tsx` uses the same option so page stories behave like the app.

Everything else uses React's `ViewTransition`, which needs the update to be a React transition. Query results arrive through an external store as well, so lists pass their data through `useDeferredValue` before rendering: the deferred render is a transition, and that is what lets a row animate. Defer the query's `data` itself and apply `?? []` afterwards; deferring a fresh array literal never settles. `RowTransition` (`components/row-transition`) wraps a list row and carries the classes `row-in`, `row-out` and `row-move`: a new row fades and drops in, a removed row fades out, and the rows below slide to their new position. `QueryBoundary` wraps its fallback and its content in boundaries with `reveal-out` and `reveal-in`, so a section cross-fades from its skeleton instead of snapping. Both content boundaries carry `update="none"` so they are captured only when they appear or disappear, never when something inside them changes. The boundary around `<Outlet />` passes `reveal={false}` because the page transition already covers it.

Each table then carries its own `ViewTransition` around its scroll container, so sorting and filtering cross-fade the rows alone; the reports results block has the same treatment. The names are per-owner (`transactions-rows`, `accounts-rows`, `users-rows`, `report-results`) so two can never claim one name.

Two rules keep those scoped transitions from spilling over the rest of the page.

`:root` is given `view-transition-name: none`. Without it the browser captures everything unnamed into a default `root` group and cross-fades it, so any one scoped transition repainted the entire page — picking a date in a column filter looked like a full reload. Opting the root out means only explicitly named elements animate and the rest of the DOM updates in place. Do not "fix" this by putting `animation: none` on `::view-transition-old(root)`: the old snapshot then sits at full opacity above the new content for the group's duration, freezing the page instead of skipping it.

The scoped boundaries carry `enter="none" exit="none"` so they are named only while their content changes in place. Without this, a table's boundary would also be captured whenever its whole section appears, animating twice.

Dialogs, popovers and select menus are Base UI components rendered through a portal, so `ViewTransition` does not capture them. They animate with the `data-open` and `data-closed` classes that shadcn ships, driven by `tw-animate-css`; Base UI keeps the element mounted until the exit animation ends, so no manual close delay is needed. `#root` sets `isolation: isolate` so portalled layers always stack above page content.

Tooltips use the Base UI `Tooltip` wrapper in `components/ui/tooltip` instead of the native `title` attribute. `Button` shows its `aria-label` as the tooltip when its size is `icon` or `icon-sm`, so an icon-only action passes `tooltip` only when the hint should differ from the label (and `tooltipSide` to move it); other elements (sort and filter header buttons, collapsed sidebar links, checkboxes, the icon picker, drill-down category links) are wrapped in `<Tooltip content={...}>`. An empty `content` renders the child untouched. Disabled controls do not receive pointer events, so their tooltip goes on a wrapping `span`. A single `TooltipProvider` in `app.tsx` shares the 400 ms open delay, so moving between adjacent actions shows the next tooltip instantly. Native `title` remains only on truncated text, where it reveals the full value.

Reduced motion is handled in two places: the `*` rule covers dialogs, popovers and menus, and a separate rule covers the view-transition pseudo-elements, which `*` does not match.

## Authentication
Sign-in creates a `UserSessions` row with a 1-day or 30-day absolute expiry and issues two HttpOnly, SameSite=Strict cookies: `jx_access`, a 10-minute JWT built with FastEndpoints.Security (`JwtBearer.CreateToken`), and `jx_refresh`, an opaque token scoped to `/api/auth/refresh` whose SHA-256 hash is all the database keeps. The bearer handler reads the JWT from the cookie, so no token is ever reachable from JavaScript. `POST /api/auth/refresh` rotates the refresh token and issues a new access token without extending the session's expiry; the frontend fetch client calls it once on a 401 and retries the request.

Rotation tolerates two tabs. The session row keeps the hash of the previous refresh token and the time of the rotation. The rotation itself is one conditional `UPDATE … WHERE TokenHash = <the hash that was read>`, so of several simultaneous refreshes exactly one rotates and answers with both cookies. A request that loses that race, or that presents the previous token within 30 seconds of the rotation, answers 204 with a fresh access cookie only and leaves the refresh cookie alone: the browser keeps the refresh cookie the winning response set, whichever response arrives first, and the losing tab can retry its request at once instead of waiting for the other tab's cookies. Nothing is cleared on that path. The previous token presented after those 30 seconds is treated as a stolen copy: the session row is deleted and the cookies are cleared, so the legitimate browser has to sign in again. A token that matches neither hash answers 401 and clears the cookies without touching the session, because anyone can send a well-formed cookie for a known session id. `SignInAsync` and `RenewAsync` forget the previous hash, so a token from before a password change has no grace.

Deactivation and the failed-attempt lockout share Identity's lockout columns but mean different things. Deactivating a user sets `LockoutEnd` to `AppUser.DeactivatedUntil` (`DateTimeOffset.MaxValue`) and `AppUser.IsDeactivated` tests exactly that; it is what `isActive`, the bearer handler, the refresh endpoint and the background jobs look at. The temporary lockout is Identity's own (`Lockout.MaxFailedAccessAttempts` 5, `DefaultLockoutTimeSpan` 15 minutes, set in `DependencyInjection`) and is consulted only where a secret is verified, all of which goes through `AuthService.AttemptAsync`: the sign-in password, the authenticator or recovery code, the password that confirms 2FA setup and disable, the current password of a password change and the password that confirms a restore. A failure calls `AccessFailedAsync`; a locked account answers 429 `credentials.lockedOut` without checking the secret. The counter resets only when a sign-in completes, so the password step of a 2FA sign-in does not reset it and an attacker who knows the password cannot try codes without limit. A temporary lockout deliberately does not end the sessions the user already has: otherwise anyone who knows an email address could sign its owner out every 15 minutes. A deactivated user always gets `credentials.invalid`. The per-client throttle on the endpoints stays in place. `--recover-admin` clears both the lockout end and the counter.

`POST /api/users/{id}/reactivate` is the inverse of deactivation: it clears `LockoutEnd` and the failed-attempt counter and changes the security stamp. Deactivation had already changed the stamp, so no session from before it can come back; the second change only keeps the rule that every change of account state moves the stamp. For a user who is not deactivated it does nothing and answers 204, which makes it safe to repeat and means it cannot be used to lift a temporary lockout. It has no self rule because a deactivated administrator cannot be signed in to call it.

An installation always keeps one active administrator. Because nobody may demote or deactivate themselves, a single request can never remove the last one; two administrators removing each other at the same moment could. `UserService.ChangeRoleAsync` and `DeactivateAsync` therefore run in a transaction that first takes the advisory lock `AppLock.AdministratorChange` (`738192437`), and under it count the administrators who are not deactivated. If the target is the only one, the change answers 403 `user.lastAdministrator`. The second of two crossing requests waits for the lock, sees the first one's result and is refused. Reactivation and password reset only ever add an active administrator, so they do not take the lock. The tests remove the other administrators' role rows for the duration of a test, because the shared fixture administrator would otherwise always be the one that remains.

`POST /api/users/{id}/reset-password` is the administrator's way to let a member back in; since 2026-09-20 a member who has a working mailbox can also do it themselves through `POST /api/auth/forgot-password`, and both ways stay. The administrator sends the new password and their own current password. The confirmation goes through `ConfirmPasswordAsync`, so it counts toward the administrator's lockout, answers 400 `password.incorrect` for the same reason restore does, and is checked before the target is looked up, so a wrong password learns nothing about user ids. The password is set through Identity's reset token inside one database transaction, which applies the configured password validators (`password.tooWeak`) and changes the stamp, so every session of the target ends; the failed-attempt counter and a temporary lockout are cleared, a deactivation is left in place. `resetTwoFactor` also disables the authenticator, replaces its key and invalidates the recovery codes, the same three steps as `--recover-admin`. The target may be another administrator, never the caller (`user.selfChange`, 403): changing your own password belongs to the profile, where the session is renewed instead of revoked. The endpoint is throttled to 10 calls per five minutes per client. There is no forced change at next sign-in; see the decision log.

Each request still validates the security stamp and that the user is not deactivated (`JwtCookieAuthentication`), then checks that the `UserSessions` row named by the token's `sid` claim exists for that user and has not expired, so deleting a row (sign out, a revocation from the profile's list of signed-in browsers, a restore) ends that browser on its next request instead of when its 10-minute access token runs out. The check is one more lookup by primary key next to the user lookup that was already there. A token whose user id claim is missing or not a GUID fails authentication with 401 rather than reaching the ownership filters as an empty user. Role changes/deactivation therefore invalidate access and refresh tokens at once. Own-password and 2FA changes re-issue the initiating session's tokens with the new stamp (`ISessionService.RenewAsync`). FastEndpoints' `RefreshTokenService` is not used: it carries tokens in the request and response body and slides the refresh expiry, which contradicts both the cookie transport and the absolute session lifetime. First-run setup is serialized. 2FA setup/disable requires the current password, and setup refuses to expose a key for an already-enabled authenticator.

The Compose API persists Data Protection keys and the JWT signing key (`jwt-signing.key`, generated on first start unless `App:Jwt:SigningKey` is configured) in `auth_keys`. A key file that exists but is blank, as a crash during the first write can leave it, is replaced by a new key; a key file that cannot be read or written stops the start instead of falling back to a key that would change on every restart. Both are plain files there and only the `api` service mounts the volume; protect it as sensitive deployment data, see "Secrets at rest" in `docs/8. Non-functional requirements.md`. The production overlay enables secure cookies. API/database development ports bind only to loopback; the frontend bind address is configurable.

## Containers
`docker compose up -d --build` runs PostgreSQL, API and frontend. The API healthcheck checks PostgreSQL connectivity and is defined only in `docker-compose.yml`, not in the Dockerfile, because every overlay includes that file and `depends_on` needs its timing; the port the API listens on (`ASPNETCORE_URLS`) is set only in the Dockerfile; the frontend healthcheck asks Caddy's admin endpoint inside the container (`http://127.0.0.1:2019/config/`), which answers the same way with the plain and the production Caddyfile, where a request to the site itself would need the certificate and the hostname. Services restart unless stopped. Every service logs through the `json-file` driver with five files of 10 MB (`x-logging` in `docker-compose.yml`), so container logs cannot fill the disk. The production overlay uses Caddy internal TLS, persistent Caddy state, and SITE_ADDRESS; install/trust its root certificate on authorized client devices and map the hostname to the private server address. Do not bypass browser certificate interstitials.

The production overlay (`docker-compose.production.yml`) replaces port lists rather than adding to them. Compose merges `ports` from several files, so a plain `ports:` entry in the overlay left `8081:80` published next to 443; the overlay now uses `!override` for the frontend and `!reset` for the database and the API. With the overlay only `${BIND_ADDRESS}:${HTTPS_PORT:-443}` is published; PostgreSQL and the API are reachable only inside the Compose network. `Caddyfile.production` is copied into the frontend image next to the plain Caddyfile and the overlay selects it with the container command, so the overlay needs no bind mount and works where the Docker daemon cannot see the checkout (a CI job that talks to the host's Docker socket). After changing either Caddyfile, rebuild the image (`--build`).

The overlay also sets `AllowedHosts` to `${SITE_ADDRESS};localhost`. `appsettings.json` keeps `*`, which suits development; in production ASP.NET Core's host filtering then answers 400 to any other `Host` header. `localhost` stays in the list because the API healthcheck calls `http://localhost:8080/health` from inside the container. `SITE_ADDRESS` must therefore be a bare hostname, without scheme or port.

Base images are pinned as `name:patch-tag@sha256:digest` in `docker-compose.yml` and both Dockerfiles: a floating tag such as `postgres:16` gives a different image on each build host and makes a rebuild unreviewable. `just update-images` (`scripts/update-images.mjs`) asks the registries for the newest patch tag inside the same line (PostgreSQL 16, Caddy 2 alpine, Node 24 alpine, .NET 10.0, Aspire dashboard 13) and rewrites tag and digest; `just update-images --check` only reports and exits 1 when something is behind. It needs no Docker. A new PostgreSQL major is deliberately outside its range because the data directory needs a dump and restore.

`.dockerignore` keeps the build context to what the two images compile. It excludes, among the usual build output, `backend/JxFinance.Api/backups`, `backend/JxFinance.Api/attachments`, `*.json.gz`, `*.info.json`, `.local`, `*.user`, test results, coverage, Storybook output and the agent tool directories. The API Dockerfile copies the whole `backend/` directory, so without those lines a backup taken in development, which holds password hashes and two-factor secrets, would enter the build layers and the Web SDK would publish the `.info.json` files into the final image.

`just verify-production` (`scripts/verify-production.mjs`, also the CI job `production-overlay`) starts the overlay as a throwaway project `jx-verify` on `https://127.0.0.1:8443` with its own volumes and checks: only 443 is published, `auth_keys`, `backups` and `attachments` are mounted only into `api`, the API runs as a non-root user, HSTS and the other headers are present, both sign-in cookies are `Secure` and `HttpOnly`, the access token still authenticates after the API container is recreated (which proves the signing key persists on `auth_keys`), and a foreign `Host` header gets 400. It removes the stack and its volumes afterwards; `--keep` leaves it running. It does not prove certificate trust on client devices.

The API container runs as the non-root `app` user and the image pre-creates `/keys`, `/backups` and `/attachments` owned by it. Files attached to transactions live on the `attachments` volume at `App:AttachmentDirectory` (`/attachments`), each under its attachment id; see [Attachments](<features/31. Attachments.md>). An `auth_keys` volume created by an older root image keeps root ownership; fix it once with `docker compose run --rm --no-deps --user root --entrypoint chown api -R app:app /keys`, otherwise key persistence fails and sessions reset on restart.

Caddy sends `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin` and a `Permissions-Policy` that switches off camera, microphone, geolocation, motion sensors, payment and USB on every response, and removes its `Server` header. The static site gets the full Content-Security-Policy; `/api/*` responses get `default-src 'none'; frame-ancestors 'none'` and `nosniff`, set with `defer` so they replace anything the upstream might send: an API response is data and must never be rendered as a document that can load anything. The production file adds `Strict-Transport-Security: max-age=31536000` without `includeSubDomains` and without `preload`. `SITE_ADDRESS` is chosen by the operator and may sit under a name whose other subdomains serve plain HTTP on the same private network; the application sets host-only cookies, so covering subdomains would protect nothing of its own while it could break those neighbours for a year. Scripts are limited to same-origin files, which is why the theme bootstrap lives in `public/theme-init.js` rather than inline in `index.html`. Inline styles stay allowed because the chart and toast libraries set style attributes.

Run a single API instance for this release. Configure the private interface deliberately when enabling remote access. Environment-specific secrets remain in the ignored .env.

## Recovery command
`docker compose run --rm --no-deps -it api --recover-admin admin@example.com`

This requires an existing administrator and interactive password entry. It resets the password, clears lockout and 2FA, invalidates recovery codes, and revokes sessions. It does not create users or change application records. The database must already be migrated. The host command was tested against a disposable administrator; the container invocation still requires validation on a working Docker host.

## Background work
Bills are checked immediately at startup and every 15 minutes. Notifications deduplicate per bill/local day under a database lock. Unconfirmed bills retain their due date and can remind again the next day. Budgets are checked immediately at startup and hourly by `BudgetAlertJob`, which asks `BudgetUsageCalculator` — the calculator the budgets endpoints use, never a second spending path — for each budget's current window and raises one notification at 80% and one at 100% of the effective limit. It iterates active users in id order with a per-user `AppDbContext`, because that calculator reads through the ownership query filter, and each user sits in its own try block. Deduplication is per budget, window and threshold: the read of what was already raised and the insert happen in one transaction holding `AppLock.BudgetAlerts`, so restarts and concurrent passes cannot double up, and spending that dips back below a threshold inside one window does not re-arm it. Net worth refreshes immediately and hourly for active users; each user is handled in its own try block, so one user whose snapshot fails is logged with the user id and the rest still get theirs, the same way `BrokerSyncJob` isolates connections. The per-user work sits behind `INetWorthSnapshotter` (`NetWorthSnapshotter`, a singleton that opens a scope and a per-user `AppDbContext` for each call), which the job receives through its constructor and calls for users in id order. That interface is the seam the isolation test uses: it wraps the real snapshotter in one that throws for the user with the lowest id, so every other user is processed after the failure, and the test fails when the try block is removed. Exchange rates sync at startup and every six hours. Missed historical observations are not fabricated. No job talks to a mail server except `EmailOutboxJob`, which is the sixth job: every minute it claims up to twenty due rows of `EmailMessages` in one short transaction holding `AppLock.EmailOutbox`, counting the attempt and setting the next attempt time before any socket is opened, then sends each one in its own try block with a twenty-second cap, retries a failure at 4, 16, 64 and 240 minutes, gives up after five attempts and deletes sent and given-up rows after a week. It returns immediately when the mail server is switched off or incomplete. The reminder job writes an email row beside the notification inside the same transaction and under the same lock, so the two can never disagree and no request or scan ever waits for SMTP; see [Email](<features/26. Email.md>). `GET /api/networth` and the hourly job share `GetCurrentAsync`. The snapshot columns are numeric(18,2), and assets or debts that are each within range can add up beyond it; writing that snapshot used to fail the request with a 500. The totals are now compared with the column range first and the snapshot is skipped when any of them does not fit, so the response still carries the true totals as decimal strings and the history gets no point for that day, the same outcome as a missing exchange rate.

The reminder job deduplicates per local day, so it needs the instant at which today began in the installation's time zone. That is `IClock.StartOfDay`, the only place that turns a local date into an instant. `TimeZoneInfo.ConvertTimeToUtc` throws for a local time that does not exist, and in zones that start daylight saving at midnight (America/Santiago, America/Havana, Asia/Beirut) midnight itself is skipped once a year, which stopped the scan for that whole day. `StartOfDay` tries the offsets in force twelve hours before and after local midnight and returns the earliest resulting instant that falls on the requested date: the transition instant when midnight is skipped, the first of the two midnights when it repeats.

## Recurring entry schedule
An entry stores `AnchorDay`, the day of month the user picked. Monthly, quarterly and yearly advances clamp the anchor to the length of the target month, so an entry on the 31st lands on 28 February and returns to 31 March. The anchor is reset only when an update changes `NextDueDate`. Weekly entries ignore it.

`RecurringBillService` is the one service that calls another tag's service: confirming a `Transfer`-shaped entry builds a `CreateTransferRequest` and hands it to `ITransferService.CreateAsync` rather than adding a `Transfer` row itself. That path owns the cross-currency rules — resolving each account's currency, demanding `receivedAmount` when the two differ, refusing a mismatched pair in one currency, refusing a disabled currency — and a second writer would have to repeat them and would drift. Both services resolve the same request-scoped `AppDbContext`, so the nested `SaveChangesAsync` joins the transaction the confirmation opened and commits with the schedule advance and the read reminders, under the same per-entry advisory lock.

## Shared category deletion
Any household member can rename a shared category, but only its owner can delete it. Deletion clears the category from every member's transactions, split lines and bills and soft-deletes its budgets, bypassing visibility filters so no dangling references remain. A shared tag follows the same rule: a member renames, the owner deletes, and deleting removes the `TransactionTags` rows outright and soft-deletes the tag inside one database transaction, leaving the transactions themselves untouched.

## Removing a household member
Removing a member resets that member's own shared accounts, categories and tags in the household to personal, in the same transaction that deletes the membership, exactly as deleting the household does for everyone's records (`HouseholdService.MakePersonalAsync`). Without it the remaining members would keep reading, and editing, records of someone who can no longer see the household. The removed member keeps the records; what other members entered on such an account stays on it and disappears from their view, which is the same outcome as the owner re-scoping the account. `AddMember` and `UpdateMemberRole` validate the email and the role, and `role` is `[JsonRequired]` because a missing enum would otherwise bind as its first value, `owner`.

## Transaction aggregates and receipts
Split lines are part of the transaction aggregate and the one exception to soft delete: editing a split hard-deletes the previous lines and inserts the new set, because a line has no identity a user could refer to. Deleting the transaction leaves them where they are, so that restoring it from the trash brings its categories back; they are unreachable in the meantime, because every reader of `TransactionLines` starts from a transaction the query filters already answered. `ICategoryAttributionService` is the single projection charts and budgets read: a split transaction contributes its lines, an unsplit one its own category and amount, so the two can never disagree. Each attributed amount carries its transaction's date, which is what lets `BudgetUsageCalculator` ask once for the whole span a rollover walks back over and bucket the rows into windows in memory; callers that only total by category, the dashboard breakdown and the reports, ignore it. Files attached to a transaction are not part of the aggregate's rows either: they live on disk under their own ids, are hidden and restored with the transaction by the attachment query filter, and are the only thing a background job hard-deletes after the trash window, see [Attachments](<features/31. Attachments.md>). A `TransferImport` row is an immutable receipt of a bank entry; it is kept when its transfer is deleted so the same statement line is not imported a second time by accident. `ImportService.ConfirmAsync` takes a transaction-scoped advisory lock derived from the account id, which serializes imports into one account across concurrent requests and processes. Matching a bank entry to an existing transfer writes a receipt for that account, and a transfer can hold only one receipt per account: two identical bank entries, in one file or in two imports, cannot both be matched to the same transfer. The second is refused with `import.transferAlreadyMatched` and, like every other confirm error, nothing of that request is written. The entry on the other account of the transfer is a different receipt and still matches.

The CSV export prefixes a text cell (description, account, category) with a single quote when it starts with `=`, `+`, `-`, `@`, a tab or a carriage return, so a spreadsheet shows it as text instead of evaluating it as a formula. Dates, types, currencies and amounts are produced by the application and are never prefixed; an amount must stay a number.

The CSV export streams: `TransactionService.StreamExportAsync` returns the filtered, sorted query as an async sequence without tracking, account, category and tag names are loaded first because the connection is busy while rows stream, together with the tag map of the filtered set, which is the one per-row value the streamed row cannot carry, and the endpoint writes each row to the response as it arrives. Memory does not grow with the ledger and the response has no `Content-Length`. A failure after the first byte can only cut the file short, since the status line is already sent. The PDF cannot stream, because MigraDoc lays out the whole document in memory, so `ExportForPdfAsync` reads one row more than `App:PdfExportMaxRows` (default 5000) and answers 400 `export.tooManyRows` when that extra row exists. Neither export loads split lines; a split is one row with its total, as before.

Text search on transactions, accounts, users and securities goes through `LikePattern.Contains`, which escapes backslash, percent and underscore, and the queries pass the backslash as the escape character of `ILIKE`. The two-argument `EF.Functions.ILike` would not do: Npgsql translates it with an empty `ESCAPE` clause, which switches escaping off, so a typed `%` or `_` acted as a wildcard. All four searches ignore case.

`CategoryAttributionService` sums unsplit rows per category in SQL and returns one attribution per category; only split transactions are read row by row, because a line's share of the reporting amount is rounded per line with the last line taking the remainder. Every consumer groups by category anyway, and the totals equal the row-by-row sums to the cent because both add the same stored two-decimal values.

## Transaction summary and bulk recategorization
`GET /api/transactions/summary` and the list, CSV and PDF endpoints all build their query through the one `Filtered` method in `TransactionService`, which takes `ITransactionFilter`; both request types implement it, so a filter cannot mean different things in the totals and in the rows. A split transaction that matches a category filter through one of its lines counts with its whole amount, exactly as the list shows it, not with the matching line's share.

`POST /api/transactions/bulk-tags` replaces the whole tag set of every listed transaction and is all-or-nothing in the same way as the category operation, but it accepts split rows, because a tag belongs to the payment and not to a line, and it has no type rule.

`POST /api/transactions/bulk-category` is all-or-nothing: it loads every listed id through the visibility filter, fails with `not_found` if any is missing, and writes all changes in a single `SaveChanges`. Transactions have no edit rule beyond visibility, matching `PUT /api/transactions/{id}`, so `forbidden` never applies, and like that endpoint it takes no advisory lock because repeating it is harmless. Split transactions are rejected rather than having their lines rewritten, since a split's categories live on its lines. The category check is the same `ValidateCategoryAsync` used by create and update, run once per transaction type present in the batch.

## Multi-currency

Rates come from `IExchangeRateProvider`. The shipped implementation, `FrankfurterRateProvider`, reads ECB reference rates from `App:ExchangeRates:BaseUrl` (default `https://api.frankfurter.dev/v1/`); `App:ExchangeRates:Enabled` only seeds the automatic-sync setting on a new installation; after that the administrator's switch decides, and Sync now always fetches. `ExchangeRateSyncJob` runs at startup and every six hours and fetches from the day after the newest stored rate, or the last 30 days on an empty table.

`ExchangeRateService.GetForDateAsync` answers with the newest stored rates on or before the date, because the ECB publishes nothing on weekends and holidays. If nothing is stored within five days of the date it fetches the ten days ending there on demand, which is how back-dated transactions get historic rates without a full history download. `ExchangeRateFetchLog` stops a failing range from being retried more than once per fifteen minutes. Future dates use today's rates. If the newest rate is still more than five days older than the date, writes in a foreign currency fail with a validation error instead of freezing a stale value. Read-side totals leave a currency without a rate out, and the net worth snapshot is skipped for that day so an understated total is never stored. Fetched rates are inserted with `ON CONFLICT DO NOTHING` outside the change tracker, so concurrent fetches cannot collide and a fetch never flushes the caller's pending changes. A change of the reporting currency revalues history inside the transaction of the settings update. `SettingsService.RevalueAsync` first takes `LOCK TABLE "Transactions", "InvestmentTransactions" IN SHARE ROW EXCLUSIVE MODE`, so no row appears or disappears while it works, fetches the needed rate range once, then walks the rows in a foreign currency ordered by id in batches of `App:RevalueBatchSize` (default 500), saving and detaching each batch, and finally sets the rows already in the new currency with one `UPDATE` per table. Memory stays at one batch, and a missing rate still rolls the whole change back. `ExchangeRateFetchLog` lives in memory and is pruned by `ExchangeRateSyncJob` on every run: an entry older than the fifteen-minute retry window decides nothing any more, so nothing older is kept. Money rounds half away from zero everywhere through `Money.Round`. A split transaction's reporting value is shared across its lines in proportion, with the last line taking the remainder so the lines always add up to the parent.

`PUT /api/transfers/{id}` shares `ResolveAmountsAsync` with create, so the cross-currency rules cannot differ between the two. It first requires both current accounts to be visible (403 `access.forbidden`, as delete does), then resolves the requested accounts through the visibility filter (400 `reference.notFound`). A currency the transfer already uses is accepted even when it has been switched off since; only a currency that the update introduces is checked against the enabled list. `TransferImport` receipts limit the edit: with any receipt the date is fixed, and for each receipt its account must stay on the same side and the amount on that side must stay the same, otherwise 400 `value.locked`. The point of the receipt is that the transfer keeps describing the bank entry it was matched to; a transfer that drifted from its receipt would make the duplicate check lie. `TransferResponse.fromAccountImported` and `toAccountImported` tell the client which side is fixed. They are two booleans rather than a list of account ids. That was chosen while a second `IReadOnlyList<Guid>` property still collided with `transactionIds` of the bulk recategorize request in the contract; `SchemaVariants.Collapse` no longer merges array variants, so the reason is historical.

`PUT /api/conversions/{id}` keeps the account and replaces everything else. The fee fields state the fee as it should be afterwards: with `feeAmount` the linked transaction is created or updated in place (amount, currency, category, date, `ReportingAmount` at the rate for the new date, and the generated description when the user has not renamed it), without it the transaction is removed and `FeeTransactionId` cleared. A fee transaction the user deleted under Transactions is simply booked again. All of it is one `SaveChanges`, so conversion and fee change together or not at all. A fee the user has split into lines is left alone: a request that would change its amount, currency or date, or remove it, answers `transaction.splitNotAllowed`, because the lines would no longer add up and rewriting them is the job of the transaction form. A conversion with `ImportRef` answers `resource.readOnly`, the code investment entries use for broker data. Deleting a conversion soft-deletes its fee transaction and keeps the lines of a split fee, exactly as deleting a transaction does, and records the fee's id on the trash entry so that restoring the conversion brings the fee back; the delete also rewrites `FeeTransactionId` to the value it already had, because removing the fee in the same change tracker clears the link on its way out.

The fee on a conversion is a real `Transaction` rather than a field that every report would need to learn about. Balances, budgets, reports and exports pick it up with no special case, and the user can recategorize it.

The wire format keeps the existing camel-case enum convention, so currencies travel as `eur`, `usd`. The frontend upper-cases the code for `Intl.NumberFormat` and `Intl.DisplayNames`. `useMoney().format(value, currency?)` defaults to the reporting currency from `GET /api/currencies`, fetched once without suspense and falling back to `eur`, so existing call sites that only ever show reporting-currency totals needed no change. Formatters are cached per language and currency at module scope. `CurrencySelect` lists the account's held currencies first, then the rest alphabetically.

Integration tests replace the provider with `FixedRateProvider` (1 EUR = 1.10 USD = 0.80 GBP on every day) so no test touches the network.

## Installation settings

`IInstanceSettingsStore` is a singleton holding an immutable `InstanceSettingsSnapshot`. It loads the row lazily on first use, falls back to configuration defaults without caching if the database is unreachable (which also covers OpenAPI export), and is replaced by `SettingsService` after a successful save. `SystemClock`, `ExchangeRateService`, `AccountMapper`, `CurrencyService` and the background jobs read the snapshot, so a change takes effect on the next request with no restart. The store assumes one API process; a second instance would keep its own snapshot until restarted.

`FeatureGateMiddleware` runs after authorization and maps route prefixes to features. A disabled feature answers 404 problem details with code `feature_disabled`. The one exception is `GET /api/households`, which answers an empty list, because account and category forms read it to offer sharing and should degrade to "nothing to share with" instead of failing. Assets and debts belong to the net worth feature; conversions belong to multi-currency.

`ActiveHouseholdMiddleware` runs straight after it and is the only thing that trusts the `X-Active-Household` header. It does nothing unless the caller is authenticated, the Households feature is on, the value parses as an id and one membership row matches it and the caller; only then does it put the id in `HttpContext.Items`, where `HttpCurrentUser.ActiveHouseholdId` finds it. `ICurrentUser` declares that property with a default implementation returning null, so the background jobs, the snapshotter and every other non-request implementation are unscoped without knowing the feature exists. The membership check itself runs before anything is stored, so it is answered by the unscoped context and cannot be narrowed by the value it is checking. `AppDbContext` reads the property inside the shareable query filter, which makes the scope a property of the data access rather than of an endpoint.

Currency restrictions are enforced where money is written: `IExchangeRateService.UnusableReason` rejects a currency that is not enabled, or any foreign currency when multi-currency is off. Updating a transaction or account that already uses a now-disabled currency is allowed as long as the currency does not change. CSV import is not restricted, because the bank statement is the source of truth.

On the client, `useSettings` reads `GET /api/settings` without suspense and falls back to everything enabled; `requireFeature` in a route's `beforeLoad` redirects to the dashboard using the same cached query. `GET /api/settings/public` is anonymous and carries only the installation name and default language, for the sign-in page, the brand lockup and the document title. `CurrencySelect` offers only usable currencies plus the record's current one, and its compact form renders nothing when a single currency is usable, which is how multi-currency "off" hides the pickers without each form knowing about it.

## Investments

The feature lives under `Endpoints/Investments` and is gated as `Feature.Investments` on the `/api/investments` prefix. `InvestmentService` serves the portfolio, entries and securities; `HoldingsValuation` is the small piece `AccountService` depends on, so account totals include holdings without the account code knowing about lots. Gains are computed in the security's currency. Portfolio totals convert market value and cost at the newest rate, and convert realised gains, dividends, tax and fees at each entry's own date through the stored `ReportingAmount`; a sale's reporting gain is its gain scaled by that sale's reporting-to-cash ratio. Within one day splits replay first, then buys, then sells, which is exact for long-only first-in-first-out and needs no execution time: a split is dated on the day it takes effect, and that day's trades are already in new shares. Each lot carries its cost in the reporting currency at the buy-date rate, so a sale's reporting gain is proceeds at the sale-date rate minus cost at the buy-date rate. Short positions are not modelled: a manual entry or deletion that would leave a sale uncovered is rejected, and an imported oversell marks the portfolio incomplete.

Fees in the portfolio totals and in the income-by-year table are standalone `Fee` entries only. The commission of a buy is part of its cost basis and the commission of a sale is taken off its proceeds, so both already lower the realised gain; counting them as fees too would subtract the same money twice. A broker commission charged in another currency than the trade is booked as its own `Fee` entry and is therefore listed, because it is in no cost basis.

Securities have no owner, so who may write them is decided per operation. `POST /api/investments/securities` is open to every signed-in user because recording a first trade needs it; it only ever inserts, ignores any id in the request, and answers 409 `conflict.duplicate` for an existing symbol and currency, also when two requests race on the unique index. `PUT /api/investments/securities/{id}` requires the Admin role. `PUT /api/investments/securities/{id}/price` takes `lastPrice` and an optional `lastPriceDate` (today when absent) and is allowed for an administrator, or for a caller who has an open position in that security: `InvestmentService` replays the entries the caller can see, per account, and looks for a quantity above zero. Everyone else gets 403 `security.notHeld`. A user who sold everything loses the right again, and a household member gains it through a shared account.

`HoldingsValuation` is called for every account list, the dashboard total, net worth and the hourly snapshot. It reads only buys, sells and splits, as a projection of the columns the replay needs, without tracking, in one query for all requested accounts; accounts without such entries cost nothing beyond that query. The service is scoped and remembers what it valued, so one request never replays an account twice. There is deliberately no cache across requests: the value depends on entries, splits, security prices, broker imports, restore, the reporting currency and the newest exchange rate, and a missed invalidation would show a wrong balance. The value of one position (quantity times last price, converted to the reporting currency, complete only with a price, a rate and no oversold lots) is computed by `Position.Value` in the domain, and both this service and the portfolio in `InvestmentService` call it, so the balance on an account and the market value on the investments page cannot drift apart.

`FlexParser` reads Interactive Brokers Flex Query XML with DTD processing off. Each section has its own list of summary rows to drop (orders, closed lots, symbol and asset summaries and wash sales for trades; summaries for cash; lots for open positions), so a query configured with several levels of detail does not double count. Direction comes from the sign of the quantity, so a cancellation reverses the original trade, and the cash effect is proceeds plus commission plus taxes with the broker's own signs. Dates accept `yyyyMMdd` and `yyyy-MM-dd` with or without a time part; ambiguous slash formats are refused. A report covering more than one broker account is refused. `BrokerImportService` runs the whole import in one database transaction, fetches the exchange-rate range once up front, takes a per-account advisory lock so an upload cannot race the daily sync, refuses currencies that are not enabled, resolves securities by contract id, then ISIN within the currency, then symbol within the currency when the ISINs do not conflict, and books a commission charged in a different currency from the trade as a separate fee entry. It is all or nothing: a missing exchange rate fails the import with the date and currency named. The advisory lock is per account, so two imports into different accounts can both decide to create the same new security; the second one then fails on the unique symbol and currency index. `ImportAsync` catches exactly that violation, discards the change tracker and runs the import again from the parsed statement, at most three times, and the second run finds the security the first one committed. Upload and sync both go through `ImportAsync`, so both are covered.

The Corporate Actions section is read as well. Interactive Brokers documents the row's fields (`type`, `actionID`, `transactionID`, `reportDate`, `dateTime`, `quantity`, `description`, `actionDescription` and the instrument fields) and the two-letter type codes, among them `FS` forward split, `RS` reverse split, `TC` merger, `SO` spin-off, `SD` stock dividend and `IC` issue change. There is no ratio field. The ratio is read from the text the broker puts in the description, `SPLIT <new> FOR <old>`, and stored as new divided by old, rounded to eight decimals, exactly what the manual split entry stores. That wording is taken from Interactive Brokers statements and is not part of the published field reference, so a split whose description does not contain it is not guessed at: it is counted as skipped under its type, and the position check below then names the security. The entry is dated on `reportDate`, the day the statement reflects the action, falling back to `dateTime`.

Rows are grouped by `actionID`, falling back to `transactionID`, and one group becomes one `Split` entry with `ExternalId` `ibkr:ca:<id>`, so a repeated import and a split deleted here are both recognised as already known. A reverse split usually arrives as two rows, the old contract leaving and a new contract with a new ISIN and contract id arriving. The group is booked on the security the application already has, that security takes over the contract id and ISIN of the arriving row, and for the rest of the import both sets of identifiers resolve to it, so trades from before and after the split stay on one security. Corporate actions are processed before trades for that reason. One import run is a `StatementImport` object (`Endpoints/Investments/Services/StatementImport.cs`) created by `BrokerImportService` for each attempt: it holds the known references, the securities and the counters as fields, opens the transaction and takes the account lock, then runs corporate actions, trades, cash entries and price updates in that order, saves once, compares positions and commits. A retry after a security collision starts from a new object, so no state leaks between attempts. A report from before the action, imported afterwards, carries only the old identifiers and no action row to translate them. Securities are unique per symbol and currency, so such an instrument resolves to the existing row with that symbol and currency as the last step after contract id and ISIN, and the row keeps its newer identifiers because missing identifiers are only ever filled in, never overwritten. A unique violation on `Securities` that still remains is another import creating the same security at the same time; the import is retried from the start up to three times and then answers 409 `conflict.busy` with nothing imported instead of a 500. Without `actionID` the two rows cannot be told to belong together and would be booked twice, which is why the query instructions ask for that field. Every other type is counted in `skipped` and per type in `skippedCorporateActions`; none of them changes a holding.

After saving, and still inside the transaction, the import replays the account's buys, sells and splits up to the report date of the Open Positions section and compares each quantity with the `position` the broker reports, including securities the broker no longer lists. Differences above 0.0001 shares, the slack a rounded ratio such as one third needs, are returned as `positionMismatches` with both quantities; the field is null when the report has no open positions to compare with. It is a warning, not a failure: history that starts before the first imported period is a legitimate reason for a difference. The daily sync gets the same result but does not store it; only the upload and Sync now show it.

Bonds are skipped until a price factor is modelled, because they are quoted in percent of par. Only the account's owner can connect it to a broker. `FlexClient` parses with DTD processing off, caps the response at 50 MB, has its HTTP logging removed because the token travels in the query string, and calls `SendRequest` and then polls `GetStatement` every five seconds, up to six times, while Interactive Brokers answers 1019 (report in progress). The base address is `App:InteractiveBrokersFlexUrl`. `BrokerSyncJob` runs daily, skips when the feature is off, skips locked-out owners and archived accounts, isolates each connection's failure, and imports each enabled connection under its owner's identity with a per-user `AppDbContext`, the same way the net worth snapshot job does. The token only ever travels from the browser to the API once and from the API to Interactive Brokers; responses carry no token field.

Investment cash flows stay out of `Transaction`. Reports and the dashboard read them separately through `IInvestmentCashFlowService` (`Common/InvestmentCashFlows`), which answers one signed total per day and side for a date range: `Dividend` and `Interest` as income, `WithholdingTax` and `Fee` as expense, from the frozen `ReportingAmount`, and nothing at all while the `Investments` feature is off. Buys, sells and splits are never income or expense, the commission inside a trade stays inside its cost or proceeds, and realised gain is shown only in the portfolio. The rows are `IAccountScoped`, so the global query filter already limits them to accounts the caller can see. `ReportService` and `DashboardService` add the totals to their income, expense and trend figures, and `CategoryBreakdownBuilder` (`Endpoints/Dashboard/Shared`) appends them to a breakdown as one item with `CategoryId` null and `SyntheticGroup` set (`investmentIncome` or `investmentTaxesAndFees`), which a client localizes and does not link. Budgets read `ICategoryAttributionService` only and therefore never see them; the transaction CSV and PDF export is unchanged.

The yearly tax summary is `TaxSummaryService` (`Endpoints/Investments/Services`) behind `ITaxSummaryService`, serving `GET /api/investments/tax-summary` and its CSV. It reads the accounts the caller can see for their names, keeps the ids the request named that are among them, loads every investment entry on those accounts in one query — every year, because a first-in-first-out cost basis needs the whole history of a holding — and replays each account with the same `Portfolio.Positions` the portfolio and the value chart use. `Position` now carries the acquisition date of each lot and, for each sale, the lots it consumed with their quantity and cost, so there is no second implementation of the rule to drift from the first. A split rewrites a lot's quantity and unit cost and leaves its acquisition date alone, which is what makes a lot bought before a split still report the date it was bought. Withholding tax and fees are reported as positive amounts paid, with exactly the sign flip `PortfolioResponse.Years` already applies, so the two pages cannot disagree. The summary reads no price at all: prices decide unrealised value, and nothing on this page is unrealised. `IsComplete` is false when a replayed position is oversold. A year the caller asks for that holds nothing answers zeroed totals and empty lists.

Both CSV exports share `Common/CsvCell`: `CsvCell.Text` guards a cell that begins with `= + - @`, a tab or a carriage return with a leading quote and then escapes it, `CsvCell.Value` only escapes, and `CsvCell.Row` joins prepared cells with commas. The split matters — running the formula guard over a numeric cell would put a quote in front of every negative amount — and it is why the transaction export applies `Text` to descriptions, account, category and tag names and `Value` to the date, type, amount and currency.

## Backup and restore

Everything under `/api/backups` is administrator-only and lives in `Endpoints/Backups`: list, take (`POST /api/backups`), upload a downloaded file, change the note, download, restore and delete. Nothing is scheduled and nothing is copied offsite; a backup that lives only next to the database is lost with it, so the page tells the administrator to download copies.

Storage is a directory, `App:BackupDirectory` (`/backups` on the `backups` volume in Compose, `.local/backups` in development, ignored by git). The development value comes from `scripts/dev-env.ps1`, which `scripts/dev.ps1` and `scripts/with-dev-database.ps1` apply to their process and which fills the `.local/api-debug.env` that `just setup` writes for the VS Code debugger; an API started any other way still falls back to `backups` under its content root, `backend/JxFinance.Api/backups`, which git and `.dockerignore` both exclude. `.local` is outside the Docker build context and outside git, but it is still inside the checkout: when the checkout lives in a cloud-synced folder, development backups are uploaded with it, so keep real data out of the development database or point `App__BackupDirectory` elsewhere. `BackupStore` keeps two files per backup, named after its id: the data, `<id>.zip` for an archive or `<id>.json.gz` for a backup from before attachments, told apart by their first bytes, and `<id>.info.json` with the date, note, migration, table, row and attachment counts and whether it was uploaded. The size is read from the file. The list is deliberately not a database table: a restore replaces every table, so a table of backups would be replaced by the one inside the backup and no longer match the files. A backup is written to `<id>.tmp` and renamed when complete, so a crash leaves no half-written entry; a data file without its info file is not listed. When writing the info file fails after the rename, `AddAsync` deletes the data file again before rethrowing. What a crash can still leave behind, a `.tmp` file or a data file without info, is removed by `RemoveOrphans`, which runs on every listing and only touches files last written more than an hour ago, so a backup that another request is still writing is never swept.

The file is a zip archive (`BackupArchive`). Its `backup.json` entry is the JSON document: `format`, `version`, `createdAt`, `migration` (the last applied EF migration) and one entry per table with its column names and rows. Every other entry is `attachments/<id>`, the file of one attachment row, stored uncompressed; a backup from before attachments is that JSON gzip-compressed on its own, and is still read. How the files are checked and written back is in [Attachments](<features/31. Attachments.md>). `BackupService` works on tables, not entities. The table list, column store types and foreign key names come from the EF relational model, every value is read as `column::text` and written back with `CAST($n AS <store type>)`. PostgreSQL's text form round-trips every type exactly, so strongly-typed ids, `Money` complex properties, soft-deleted rows, query filters and the `NextDueDate` concurrency token need no special handling, and a new entity is covered without touching the service. Taking a backup runs in one `REPEATABLE READ` transaction, so the file is a single snapshot.

What the file holds: every table of the model, including users with password hashes and two-factor secrets, households, settings and exchange rates. Treat it, and the backup directory, as a secret. `UserSessions` is left out. Broker tokens are in the file but stay encrypted with the key directory (`App:DataProtectionDirectory`) of the installation that wrote them; on another installation the connection answers `broker.tokenRequired` until the token is entered again.

Reading a backup never holds the document in memory. `BackupReader` walks the JSON with `Utf8JsonReader` over a 64 KB buffer that grows only for a single value larger than that (16 MB at most) and hands an `IBackupVisitor` the header, each table's name and columns, and one row at a time. It is strict because the format is our own: `format`, `version`, `createdAt` and `migration` must come before `tables`, a table must give `name` and `columns` before `rows`, a cell is a string or null, and any other property or shape is `backup.invalidFile`. Upload uses a visitor that only counts (`BackupInspector`); restore uses one that inserts (`BackupRestorer`, which owns the restore transaction). Both sit beside `BackupReader` in `Endpoints/Backups/Services`, and `BackupDatabase` in the same folder holds the PostgreSQL plumbing they share with `BackupService`: the table shapes read from the EF model, identifier quoting, deferring and restoring foreign keys, and resetting sequences. The decompressed stream is wrapped in `LimitedReadStream`, which fails with `backup.tooLarge` once more than `App:BackupMaxDecompressedBytes` (default 1 GiB) has been read, at upload and at restore, so a small gzip file cannot expand without bound.

Upload only stores a file: it checks `format` and `version`, checks that every other entry of an archive is an attachment of at most 10 MB, compresses plain JSON, and lists the backup under the date it was taken. A backup whose `migration` differs from the running application is listed with `restorable: false`; it can be downloaded but a restore answers `backup.schemaMismatch`. To restore an older backup, run the application version that wrote it, upload, restore, then upgrade; startup migrates the data forward. Moving to a fresh installation needs the first-run setup first, because only a signed-in administrator can upload and restore; that administrator is replaced by the users of the backup.

Restore asks for the administrator's current password in the request body (`{ "password": "…" }`) and verifies it before anything else. A wrong password answers 400 `password.incorrect`, not 401, because the frontend client answers a 401 with a refresh and a retry, which would count every typing mistake twice; it counts toward the failed-attempt lockout described under Authentication, and a locked account answers 429 `credentials.lockedOut`. Restore is throttled to 5 calls per five minutes per client, taking and uploading a backup to 10 each.

Restore replaces everything in one transaction: the foreign keys are switched to `DEFERRABLE INITIALLY DEFERRED` so table order, self-references and cycles do not matter, every table of the model is truncated, rows are inserted in batches of 500, `SET CONSTRAINTS ALL IMMEDIATE` checks the foreign keys, the constraints go back to `NOT DEFERRABLE` and identity sequences are moved past the restored ids. `TRUNCATE` holds an exclusive lock until commit, so other requests wait rather than see a half-restored database. The transaction opens once the header of the file has been read and accepted, so the table names, columns and row lengths are checked while rows stream in; any mismatch rolls the truncation back like every other failure. A value or a reference the database rejects (SQLSTATE class 22 or 23) rolls everything back and answers `backup.invalidFile`. The transaction sets `lock_timeout` to `App:BackupLockTimeoutSeconds` (default 15), so a restore that cannot get its locks gives up instead of hanging; that timeout (55P03), a deadlock (40P01) and a serialization failure (40001) roll back and answer 409 `conflict.busy`, which means nothing changed and the same request can be sent again. Afterwards the cached instance settings are reloaded. The stored backups are untouched, so a wrong restore can be undone by restoring another one; taking a backup first is the administrator's call, the application does not do it silently.

On the client the confirmation is `RestoreBackupDialog`: an alert dialog whose body is a `useAppForm` form with the typed confirmation word and the administrator's current password, submitted through `submitToServer`, so a `required` error on `password` lands on the input and every other failure shows in the dialog's `FormError` while the dialog stays open. After `password.incorrect` the password field is cleared; `credentials.lockedOut` (429) and `conflict.busy` (409) show their `serverErrors` text and leave the form ready to retry. A rate-limited 429 carries no body at all: `customFetch` turns any failed response into an `ApiError` even when the body is empty or not the JSON its content type promised, and `errorMessage` in `src/lib/query-client.ts` gives a 429 without a code the text `errors.tooManyRequests`, which covers login, two-factor, the profile password and the backup endpoints alike.

Sessions: all session rows are gone after a restore and the caller's cookies are cleared, so the client clears its cache and goes to the sign-in page. Other signed-in users are refused on their next request, because every request checks its session row, and their refresh fails too.

Limits: an upload is at most 2 GB of file (`UploadBackupEndpoint.MaxFileBytes`, with the multipart form limit raised to match; every other endpoint keeps Kestrel's 30 MB default), the `backup.json` of any backup at most `App:BackupMaxDecompressedBytes` once decompressed, and each attached file at most 10 MB; memory use during upload and restore is one read buffer plus one batch of 500 rows. There is no retention rule; backups stay until an administrator deletes them.
