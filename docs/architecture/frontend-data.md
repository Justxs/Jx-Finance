# Frontend data, loading and tables

## Table filtering and sorting
Every table header carries its own controls: clicking a column name sorts by it and toggles direction on a second click; a filter icon beside the name opens a popover with that column's filter. The sort arrow shows the current field and direction, and the filter icon is highlighted while that column is filtered. `ColumnHeader` composes the two; `ColumnFilter` is the popover shell, `TextColumnFilter` wraps it for the text case and `SelectColumnFilter` (`components/select-column-filter`, outside `components/ui` because it draws a `SelectField`) for a select whose empty value means no filter. `ColumnFilter` takes the applied `value`, the `empty` value and `onApply`, and renders its content through `children(draft, setDraft)`: the popover copies the applied value into a draft when it opens, and nothing reaches the table until the footer is used. Apply (or Enter, since the popover is a form) commits the draft and closes; Clear commits the empty value and closes; closing any other way drops the draft. Popovers use the shadcn `Popover` on Base UI, shared with `DatePicker`.

All filtering and sorting happens on the server. `GET /api/transactions`, `/api/accounts` and `/api/users` each take their filters plus `sort` and `direction`; all are optional, and the service applies the default order when they are absent. Transactions sort in SQL, including correlated subqueries for category and account name. Accounts and users are unpaged, so their services filter in SQL and then sort the mapped responses — current balance and active status are computed rather than stored, so they cannot be ordered in the query itself.

Dates filter as one range, not two fields. `DateRangePicker` shows the selected span on a single control and takes the two ends from one calendar: the first click sets the start, the second sets the end, and a click before the current start becomes the new start instead. It backs the transactions date column and the reports range, both of which still write `dateFrom`/`dateTo` separately to the URL and the API. It shares its month grid with `DatePicker` through `Calendar` and `lib/calendar.ts`; the single-date picker renders as a range whose ends are the same day.

Filter and sort state lives in the route's search params for all three tables, so a view is shareable by URL and survives reload. Transaction filters also reset paging and feed the CSV/PDF export links. Each committed change is a navigation, so column filters commit only on Apply. The phone filters dialog applies as it goes and debounces its text field for 300 ms: `useDebouncedDraft(value, onCommit, wait)` in `src/hooks` holds the draft, follows the committed value when it changes elsewhere and commits through `useDebouncer` from TanStack Pacer (`@tanstack/react-pacer`). Pacer is the project's standard for debouncing and throttling; do not hand-roll timers. `useSearchTable(search, patchSearch)` turns a route's search object and a patch function into `setSort` and `sortProps(key)` (the four sort props of a `ColumnHeader` or `SortableTableHead`, whose `onSort` flips the direction of the active column); the route keeps its own typed `useSearch` and `useNavigate`, so the hook needs no route generics. The transactions table and its phone filters dialog share `useTransactionFilters` (`features/transactions/use-transaction-filters.ts`): the search table with paging reset to 1, the type, category and account options, the tag list with `selectedTagIds` and `setTagIds`, the date range, `activeCount`, `clearFilters` (keeps the sort) and `clearAll`. The page calls it once and passes the result down as `filters`, and the filter keys themselves are one zod schema, `transactionFilterSchema`, that the route's search schema extends and a saved filter reuses. The tag filter is one comma-separated `tagIds` search param rather than a repeated key, because the generated client joins an array param with commas anyway and the export links are plain URLs built by the generated `getExportTransactionsUrl` and `getExportTransactionsPdfUrl`.

An empty result distinguishes the two causes: `filters.noMatches` when filters are applied, the table's own empty copy otherwise. `EmptyText` (`components/ui/empty-text`) is that paragraph for lists and `TableEmptyRow` the same for a table body; both take `filtered`. `ScrollRegion` in `components/ui/table` is the labelled, focusable horizontal scroll wrapper every wide table sits in; `Table` adds it when given a `label`.

## Frontend loading and failure states
Queries use TanStack Query's suspense hooks, so components read `data` directly and never branch on status. Loading and failure are handled by position in the tree instead: `QueryBoundary` pairs a `Suspense` fallback with an error boundary wired to `QueryErrorResetBoundary`, so its retry re-runs the failed queries rather than only re-rendering. A failed query has exactly one surface, decided by whether there is anything on screen. The query client's `throwOnError` is `throwWithoutData` (`src/lib/query-client.ts`): a query that fails with no data throws to the boundary, which shows the error state and its retry, and the `QueryCache` stays quiet. A query that fails while it already holds data (a focus or invalidation refetch) keeps its rows on screen, does not throw, and the `QueryCache` `onError` raises one toast instead. Before this split a first load that failed showed both the boundary and a toast. `meta: { silent: true }` still suppresses the toast, and the handful of optional lookups (settings, currencies, the reference exchange rate, quotes, the command palette's lists) spread `silentQuery` from `src/lib/query-client.ts`, which adds `throwOnError: false` and `retry: false`, so they fail once, without any surface, and fall back to defaults.

Imperative reads in `beforeLoad` gates and at startup catch their own failures and no longer toast. The root gate reads the setup status and the profile through the query client with `staleTime: "static"` (`checkSetupNeeded` and `checkIsAuthenticated` in `src/lib/auth-gate.ts`), so each is asked once per session; finishing first-run setup writes `needsSetup: false` into that cache through `setSetupNeeded`, and a failed status request answers "no setup" and is asked again on the next navigation.

Mutation errors always toast unless silent, because a form shows its own `FormError`. A success toast is declared the same way: the `MutationCache` raises `toast.success(meta.success)` when a mutation carrying that message succeeds, so a mutation whose only reaction is the toast passes `{ mutation: notify(message) }` (`notify` in `src/lib/mutations.ts` returns the meta, so it spreads next to other callbacks the way `silentMutation` does), or `{ mutation: { meta: { silent: true, success } } }` when its error is shown inline.

Boundaries sit at two levels. One wraps `<Outlet />` in the root layout and covers whole-page queries, falling back to `RoutePending`. Each signed-in route sets a `pendingComponent` that mirrors its page (built on `PagePending`, in a `*-pending.tsx` module beside the page), and `RoutePending` looks up the matched leaf route and renders that component, falling back to a generic shell. The router shows the same component while the route's code chunk loads, so the router's pending state and the Suspense fallback look identical. The TanStack Router plugin does not code-split `pendingComponent`, so a pending module sits in the main bundle: it imports only skeleton primitives and layout components, never its page or a chart. Storybook's route list in `src/storybook/decorators.tsx` registers the same pending components, so a page's Loading story shows its real skeleton. Finer ones wrap the sections that load independently — the dashboard sections, the net-worth sections, transfers, imports — so one slow request does not blank unrelated content. The sidebar and notification bell render outside the outlet and carry their own.

Two queries stay on the non-suspense hooks because they are conditional, and `useSuspenseQuery` accepts neither `enabled` nor `placeholderData`: the root layout's profile lookup, disabled on the login and setup routes, and the import transfer picker.

`useSuspenseQuery` accepts no `placeholderData`, so keeping previous rows on screen through a filter or sort change is done with `useDeferredValue` instead, in `useDeferredParams`.

Relying on the router's `startTransition` alone does not work here, and the reason is worth recording. TanStack Router publishes search params through `useSyncExternalStore`, and React deliberately renders external-store updates synchronously to avoid tearing — the transition does not defer them. The new params therefore reached the query on a synchronous render, the query suspended with no cached data, and the boundary dropped to its skeleton: every filter change looked like a full page reload.

`useDeferredParams` breaks that chain. The synchronous render still uses the previous params, so the query stays resolved and nothing unmounts; React then re-renders with the new params in a transition, and a transition *is* allowed to suspend without hiding revealed content. The flag it returns is exact staleness — old data on screen, new data in flight — and drives the stale state (`StaleRegion` and the `stale` utility, see Visual system).

It defers `JSON.stringify(params)` rather than the params object. `useDeferredValue` compares by identity, so deferring an object that is rebuilt each render never settles and spins. Deferring a string derived from the values cannot, regardless of what the router or the compiler does with object identity.

Background refetches (the window-focus refetch is on) have no indicator at all. They replace data the user is already reading, so signalling them only produces flicker on every refocus.

A form whose defaults come from query data is not remounted when that data changes, so it carries no `key` built from the data. TanStack Form compares `defaultValues` deeply on every render and applies changed ones to the fields the user has not touched, keeping whatever is being typed. A form that stays on screen after saving, such as the installation settings, the mail server settings and the notification choices, owns its mutation and calls `formApi.reset(value)` once the save succeeds; that clears `isDirty` and the touched flags, so the refetched values land on every field. A refetch that answers the same data changes nothing, which is why the window-focus refetch cannot throw away unsaved edits. The dashboard customiser keeps a plain `useState` draft instead, and copies the answered layout into it after Save or Reset.

A mutation stays pending until the queries it changed have refetched. `createMutationCache` awaits `invalidateAfterMutation` in its `onSuccess`, which TanStack Query runs before the mutation's own `onSuccess`, and `invalidateQueries` resolves once every invalidated query that is on screen has answered (it refetches only active queries; the rest are only marked stale, and a failed refetch resolves too, with its toast). So `mutateAsync`, `isPending`, the submit button's spinner, the `onSuccess: onClose` of a form dialog and the success toast all wait for the fresh rows, and a list without an optimistic update no longer shows the old rows for a moment after its dialog has closed. The wait is one round trip for the lists on screen, mostly a single page of the ledger or one unpaged list; a delete in a paged list keeps its row's spinner until the page has refetched instead of the row lingering without one. After a failure the refresh still runs, in `onSettled`, after the mutation's own `onError` has rolled back any optimistic change, and it is awaited there too, so the form's error appears with the refreshed data, which is what `RecurringBillConfirmForm` relies on after `conflict.stale`. Callbacks passed to `mutate(variables, { onSuccess })` run after all of this, as before.

Mutations still report progress on the control that started them, since they are not queries. `Button` takes a `pending` prop that disables the button, sets `aria-busy` and renders a spinner over its content. The content stays in place with transparent text and hidden icons, so the button keeps its width and its accessible name, and nothing beside it moves. Apart from the splash, that spinner is the only one in the application. Row-level actions scope pending state to the affected row by comparing `mutation.variables` with the row id. Where the affected control is not a button (a role dropdown, a notification about to disappear) the control or row carries the stale state instead. Optimistic transaction rows stay dimmed until the server confirms them.
