# Investments

The feature lives under `Endpoints/Investments` and is gated as `Feature.Investments` on the `/api/investments` prefix. `InvestmentService` serves the portfolio, entries and securities; `HoldingsValuation` is the small piece `AccountService` depends on, so account totals include holdings without the account code knowing about lots. Gains are computed in the security's currency. Portfolio totals convert market value at the newest rate, take cost at each buy's own date, and convert realised gains, dividends, tax and fees at each entry's own date through the stored `ReportingAmount`; a sale's reporting gain is its gain scaled by that sale's reporting-to-cash ratio. Within one day splits replay first, then buys, then sells, which is exact for long-only first-in-first-out and needs no execution time: a split is dated on the day it takes effect, and that day's trades are already in new shares. Each lot carries its cost in the reporting currency at the buy-date rate, so a sale's reporting gain is proceeds at the sale-date rate minus cost at the buy-date rate. Short positions are not modelled: a manual entry or deletion that would leave a sale uncovered is rejected, and an imported oversell marks the portfolio incomplete.

Fees in the portfolio totals and in the income-by-year table are standalone `Fee` entries only. The commission of a buy is part of its cost basis and the commission of a sale is taken off its proceeds, so both already lower the realised gain; counting them as fees too would subtract the same money twice. A broker commission charged in another currency than the trade is booked as its own `Fee` entry and is therefore listed, because it is in no cost basis.

Securities have no owner, so who may write them is decided per operation. `POST /api/investments/securities` is open to every signed-in user because recording a first trade needs it; it only ever inserts, ignores any id in the request, and answers 409 `conflict.duplicate` for an existing symbol and currency, also when two requests race on the unique index. `PUT /api/investments/securities/{id}` requires the Admin role. `PUT /api/investments/securities/{id}/price` takes `lastPrice` and an optional `lastPriceDate` (today when absent) and is allowed for an administrator, or for a caller who has an open position in that security: `InvestmentService` replays the entries the caller can see, per account, and looks for a quantity above zero. Everyone else gets 403 `security.notHeld`. A user who sold everything loses the right again, and a household member gains it through a shared account.

`HoldingsValuation` is called for every account list, the dashboard total, net worth and the hourly snapshot. It reads only buys, sells, splits and corporate actions (`Portfolio.PositionTypes`), as a projection of the columns the replay needs, without tracking, in one query for all requested accounts; accounts without such entries cost nothing beyond that query. The service is scoped and remembers what it valued per account and date, so one request never replays an account twice. Given a date, as for the dashboard balance at a past month's end, it replays only entries dated on or before it and values each position at the newest `SecurityPrices` row on or before it and that day's exchange rate; `Security.LastPrice` is always the newest of those rows, so the two paths agree on today. There is deliberately no cache across requests: the value depends on entries, splits, security prices, broker imports, restore, the reporting currency and the newest exchange rate, and a missed invalidation would show a wrong balance. The value of one position (quantity times last price, converted to the reporting currency, complete only with a price, a rate and no oversold lots) is computed by `Position.Value` in the domain, and both this service and the portfolio in `InvestmentService` call it, so the balance on an account and the market value on the investments page cannot drift apart.

`FlexParser` reads Interactive Brokers Flex Query XML with DTD processing off. Each section has its own list of summary rows to drop (orders, closed lots, symbol and asset summaries and wash sales for trades; summaries for cash; lots for open positions), so a query configured with several levels of detail does not double count. Direction comes from the sign of the quantity, so a cancellation reverses the original trade, and the cash effect is proceeds plus commission plus taxes with the broker's own signs. Dates accept `yyyyMMdd` and `yyyy-MM-dd` with or without a time part; ambiguous slash formats are refused. A report covering more than one broker account is refused. `BrokerImportService` runs the whole import in one database transaction, fetches the exchange-rate range once up front, takes a per-account advisory lock so an upload cannot race the daily sync, refuses currencies that are not enabled, resolves securities by contract id, then ISIN within the currency, then symbol within the currency when the ISINs do not conflict, and books a commission charged in a different currency from the trade as a separate fee entry. It is all or nothing: a missing exchange rate fails the import with the date and currency named. The advisory lock is per account, so two imports into different accounts can both decide to create the same new security; the second one then fails on the unique symbol and currency index. `ImportAsync` catches exactly that violation, discards the change tracker and runs the import again from the parsed statement, at most three times, and the second run finds the security the first one committed. Upload and sync both go through `ImportAsync`, so both are covered.

The Corporate Actions section is read as well. Interactive Brokers documents the row's fields (`type`, `actionID`, `transactionID`, `reportDate`, `dateTime`, `quantity`, `description`, `actionDescription` and the instrument fields) and the two-letter type codes, among them `FS` forward split, `RS` reverse split, `TC` merger, `SO` spin-off, `SD` stock dividend and `IC` issue change. There is no ratio field. The ratio is read from the text the broker puts in the description, `SPLIT <new> FOR <old>`, and stored as new divided by old, rounded to eight decimals, exactly what the manual split entry stores. That wording is taken from Interactive Brokers statements and is not part of the published field reference, so a split whose description does not contain it is not guessed at: it is counted as skipped under its type, and the position check below then names the security. The entry is dated on `reportDate`, the day the statement reflects the action, falling back to `dateTime`.

Rows are grouped by `actionID`, falling back to `transactionID`, and one group becomes one `Split` entry with `ExternalId` `ibkr:ca:<id>`, so a repeated import and a split deleted here are both recognised as already known. A reverse split usually arrives as two rows, the old contract leaving and a new contract with a new ISIN and contract id arriving. The group is booked on the security the application already has, that security takes over the contract id and ISIN of the arriving row, and for the rest of the import both sets of identifiers resolve to it, so trades from before and after the split stay on one security. Corporate actions are processed before trades for that reason.
One import run is a `StatementImport` object (`Endpoints/Investments/Services/StatementImport.cs`) created by `BrokerImportService` for each attempt: it holds the known references, the securities and the counters as fields, opens the transaction and takes the account lock, then runs corporate actions, trades, cash entries and price updates in that order, saves once, compares positions and commits. A retry after a security collision starts from a new object, so no state leaks between attempts. A report from before the action, imported afterwards, carries only the old identifiers and no action row to translate them. Securities are unique per symbol and currency, so such an instrument resolves to the existing row with that symbol and currency as the last step after contract id and ISIN, and the row keeps its newer identifiers because missing identifiers are only ever filled in, never overwritten.
A unique violation on `Securities` that still remains is another import creating the same security at the same time; the import is retried from the start up to three times and then answers 409 `conflict.busy` with nothing imported instead of a 500. Without `actionID` the two rows cannot be told to belong together and would be booked twice, which is why the query instructions ask for that field. Every other type is counted in `skipped` and per type in `skippedCorporateActions`; none of them changes a holding. Since 2026-10-02 `ImportCorporateActions` hands each group to a booking method by type, `BookSplit`, `BookSymbolChange` and `BookMergerAsync`, and a method that cannot book its group answers false, which counts it as skipped. The merger books an entry with cash, so it needs the exchange rate of the day and runs asynchronously; a missing rate fails the import like any other entry. The parser now reads `proceeds` and `value` of a corporate action row for it. `BookSymbolChange` resolves the leaving row to the existing security and the arriving row separately; only when both are the same security does it fall back to the split's identity takeover (`TakeOver`), otherwise it writes a `SymbolChange` entry between the two.

A corporate action that moves a holding is one `InvestmentTransaction` with a second security in `RelatedSecurityId`. `Portfolio.Apply` takes the lots from the first security's `Position` with `Position.Take`, the first-in-first-out walk a sale uses, which also marks the entry oversold when the lots run out, and gives them to the second with `Position.Receive`, which inserts each lot before the first lot acquired later, so the receiving position stays in acquisition order and first in, first out stays true across securities. Because lots now cross securities, `Position.Realize` records a disposal from lots already taken, which is what `Sell` now does after `Take`; a merger takes its lots once and splits each one with `Portfolio.CarriedShare`, the cost share over 100 (100% when unset, 0% without a received security): the carried part of each lot's cost goes to the acquirer through `Receive` at the ratio `RelatedQuantity / Quantity`, and the rest of its quantity and cost is realised against the cash, the remainder taken by subtraction so the two parts add up to the lot exactly. `IHoldingLedger.NewlyOversoldAsync` replays every position entry of the account, not of one security, and answers the first oversold entry of each security that was not oversold before the change; `SecurityPriceService` decides whether a caller holds a security from the whole history of every account with an entry naming it, and `HeldSecurities` dates a security's first trade from entries naming it in either column.

After saving, and still inside the transaction, the import replays the account's buys, sells and splits up to the report date of the Open Positions section and compares each quantity with the `position` the broker reports, including securities the broker no longer lists. Differences above 0.0001 shares, the slack a rounded ratio such as one third needs, are returned as `positionMismatches` with both quantities; the field is null when the report has no open positions to compare with. It is a warning, not a failure: history that starts before the first imported period is a legitimate reason for a difference. The daily sync gets the same result but does not store it; only the upload and Sync now show it.

Bonds are skipped until a price factor is modelled, because they are quoted in percent of par. Only the account's owner can connect it to a broker. `FlexClient` parses with DTD processing off, caps the response at 50 MB, has its HTTP logging removed because the token travels in the query string, and calls `SendRequest` and then polls `GetStatement` every five seconds, up to six times, while Interactive Brokers answers 1019 (report in progress). The base address is `App:InteractiveBrokersFlexUrl`. `BrokerSyncJob` runs daily, skips when the feature is off, skips locked-out owners and archived accounts, isolates each connection's failure, and imports each enabled connection under its owner's identity with a per-user `AppDbContext`, the same way the net worth snapshot job does. The token only ever travels from the browser to the API once and from the API to Interactive Brokers; responses carry no token field.

Investment cash flows stay out of `Transaction`. Reports and the dashboard read them separately through `IInvestmentCashFlowService` (`Common/InvestmentCashFlows`), which answers one signed total per day and side for a date range: `Dividend` and `Interest` as income, `WithholdingTax` and `Fee` as expense, from the frozen `ReportingAmount`, and nothing at all while the `Investments` feature is off. Buys, sells and splits are never income or expense, the commission inside a trade stays inside its cost or proceeds, and realised gain is shown only in the portfolio. The rows are `IAccountScoped`, so the global query filter already limits them to accounts the caller can see. `ReportService` and `DashboardService` add the totals to their income, expense and trend figures, and `CategoryBreakdownBuilder` (`Endpoints/Dashboard/Shared`) appends them to a breakdown as one item with `CategoryId` null and `SyntheticGroup` set (`investmentIncome` or `investmentTaxesAndFees`), which a client localizes and does not link. Budgets read `ICategoryAttributionService` only and therefore never see them; the transaction CSV and PDF export is unchanged.

The yearly tax summary is `TaxSummaryService` (`Endpoints/Investments/Services`) behind `ITaxSummaryService`, serving `GET /api/investments/tax-summary` and its CSV. It reads the accounts the caller can see for their names, keeps the ids the request named that are among them, loads every investment entry on those accounts in one query — every year, because a first-in-first-out cost basis needs the whole history of a holding — and replays each account with the same `Portfolio.Positions` the portfolio and the value chart use. `Position` now carries the acquisition date of each lot and, for each sale, the lots it consumed with their quantity and cost, so there is no second implementation of the rule to drift from the first. A split rewrites a lot's quantity, keeps its total cost and leaves its acquisition date alone, which is what makes a lot bought before a split still report the date it was bought. Withholding tax and fees are reported as positive amounts paid, with exactly the sign flip `PortfolioResponse.Years` already applies, so the two pages cannot disagree. The summary reads no price at all: prices decide unrealised value, and nothing on this page is unrealised. `IsComplete` is false when a replayed position is oversold. A year the caller asks for that holds nothing answers zeroed totals and empty lists.

Both CSV exports share `Common/CsvCell`: `CsvCell.Text` guards a cell that begins with `= + - @`, a tab or a carriage return with a leading quote and then escapes it, `CsvCell.Value` only escapes, and `CsvCell.Row` joins prepared cells with commas. The split matters — running the formula guard over a numeric cell would put a quote in front of every negative amount — and it is why the transaction export applies `Text` to descriptions, account, category and tag names and `Value` to the date, type, amount and currency.

## Market prices

Every write to the price history goes through `SecurityPriceBook.Record`, which now takes a `PriceSourceKind` and applies one rule: a `Feed` price never replaces a `Manual`, `Broker` or `File` point of the same date and then leaves `LastPrice` alone, and every other write replaces the point and its source. The writers pass their source: `SecurityPriceService.SetPriceAsync` and the security save `Manual`, `StatementImport.UpdatePricesAsync` `Broker`, `SecurityPriceService.ImportPricesAsync` `File` and `PriceSyncService` `Feed`. The broker trade CSV writes no prices. `LastPrice` stays the newest point whatever its source, so the value chart, `HoldingsValuation` and the member export's journal read prices exactly as before. The column's default is `Manual`, which is what the migration `AddMarketPrices` gave every existing point.

The providers live in `Infrastructure/MarketPrices` behind `IMarketPriceProvider`: `Source`, `CallsFor(security)`, `CloseAsync(security, from, to, apiKey)` answering dated closes with the currency they are quoted in, and `FindAsync(isin, apiKey)` answering candidate listings. `EodhdPriceProvider` and `KrakenPriceProvider` are typed `HttpClient`s registered in `ApiServiceExtensions` with a 20-second timeout, a 5 MB response cap, the `JxFinance/1.0` user agent and their HTTP logging removed, because the EODHD key travels in the query string as `api_token`; they are then registered as `IMarketPriceProvider`, and `PriceSyncService` picks one by `Source` from `IEnumerable<IMarketPriceProvider>`. `TelemetryExtensions.RedactedEodhdUrl` replaces the key's value with `***` in the recorded URL of a trace, as `RedactedDiscordUrl` does for webhooks.
EODHD's end-of-day answer (`api/eod/{symbol}?from=&to=&fmt=json`) has no currency field, so the provider asks `api/search/{code}?exchange={exchange}` once per mapping and writes the listing's currency to `Security.PriceQuoteCurrency`, which `PriceSyncService` saves with the fetch result, a failed one included. `CallsFor` answers 1 once the currency is stored and 2 before. Find keeps the currency of every listing it answers in the singleton `EodhdQuoteCurrencies`, and the first fetch of a remembered symbol takes the currency from there and stores it instead of searching, so `CallsFor` answers 1 for it as well; that memory is lost on a restart, the stored column is not. Only three-letter currencies are taken from either search, the width of the column. Kraken's `0/public/OHLC?pair=&interval=1440&since=` answers the result under its own name for the pair, such as `XXBTZEUR` for `XBTEUR`, so the provider reads the first array in `result` and takes the quote currency from the last three letters of the requested pair; the candle of the current day is not yet final and is cut off by the `to` date, yesterday. A server error, a timeout or an unreadable body is `marketPrices.unavailable`; any other refusal is `marketPrices.rejected` with the provider's words, cut to 150 characters.

`HeldSecurities.FirstTradesAsync` in `Common/Holdings` answers the securities with a non-zero position on any account, with the date of their first trade or of the corporate action that moved them in, reading buys, sells, splits and corporate actions with `IgnoreQueryFilters(QueryFilters.OwnerOnly)` as `BrokerSyncJob` does, because the job runs as no one and Fetch now must see every member's holdings. `PriceSyncService.SyncAsync` runs in one transaction under `AppLock.PriceSync`, loads the settings row tracked, and saves after each security so the counter and the prices move together; Find takes the same lock to count its call. The rules it applies are pure functions in `PriceSyncRules` (`Target`, `IsDue`, `From`, `CallsLeft`, `Spend`, `InSecurityCurrency`), which the unit tests cover. `PriceSyncJob` is a `PeriodicJob` every six hours with `RequiredFeature = Investments` that returns before touching the database while `InstanceSettingsSnapshot.PriceSyncEnabled` is off. In the tests `ApiFixture` removes both providers and registers a `FixedPriceProvider` per source, so no test or build calls a provider; the parsing tests read recorded answers from `Support/SampleMarketPrices.cs`.
