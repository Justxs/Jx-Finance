# Developer tooling and package updates

## Developer tooling
`just` lists every recipe. `just setup` prepares a checkout (generated `.env`, packages, tools, hooks, `.local/api-debug.env` for the VS Code debugger) and ends with `just doctor`, which checks tool versions, that Docker runs, and the known broken global `node` shim that makes git hooks exit with 127. `scripts/dev.ps1` keeps `dotnet watch` in the same terminal as Vite, so a compile error or a crash is visible, and starts Vite only after `/health` answers; it fails with a message when the API exits during startup. `scripts/dev-env.ps1` is the one place that reads `.env` and builds the development connection string and `App__BackupDirectory`; `dev.ps1`, `with-dev-database.ps1` and `setup.ps1` dot-source it.

Data: `just seed <email>` runs the API with `--seed-demo`, which fills an existing user that has no accounts with six months of deterministic data in the installation's reporting currency (`DemoDataCommand`); it refuses a user that already has accounts.
Besides salary, bills, groceries and a monthly transfer to savings, the ledger holds card payees (a café, Bolt, Spotify) categorized in the first three months and left uncategorized in the last three, two of them with a payee display name, so rule and learned suggestions have something to offer; places with Vilnius coordinates on the grocery, fuel and pharmacy rows; a yearly car insurance spread over 12 months; a "Riga weekend" group across the main account and the wallet; and a "Home" household the member owns, with the flat shared in it.
Five recurring entries (rent, electricity, salary, the standing order matched by its `monthly saving` key, and the yearly car insurance) fall on fixed days, and everything the command adds is backdated to the start of the first month, so the bills calendar shows paid occurrences matched by their rows from then on.
The command changes no feature switch, so Locations and Learned categories stay off until an administrator turns them on. `DatabaseToolingTests` checks the paid first month and each of these. `--evaluate-categorizer <email>` only reads; it has no recipe, and [Learned categories](../features/learned-categories.md#evaluating-on-a-ledger) shows how to run it against the dev database with a read-only connection. `just db-reset` asks for confirmation, removes the dev database volume and starts an empty PostgreSQL. `just migrate-add|remove|list|script` wrap the pinned `dotnet-ef` local tool, and `DatabaseToolingTests` fails when the model has changes without a migration.
`just migrate-add <Name>` is `scripts/migrate-add.mjs`: it builds `backend/JxFinance.Api` in Release with `--no-incremental` and then calls `dotnet ef migrations add --no-build`, because an incremental build in this OneDrive folder once went stale and produced an empty migration. It then strips the BOM and turns CRLF into LF in the new files and the model snapshot, which EF writes that way and the formatters skip. When the new migration's `Up` and `Down` are both empty it deletes the new files, puts the snapshot back and fails.

Build rules live in `backend/Directory.Build.props` (warnings are errors, `latest-recommended` analyzers, code style enforced in the build) and `backend/Directory.Packages.props` (every NuGet version in one place); `.editorconfig` holds the C# style rules and the few analyzer rules that are switched off, with a wider exemption for the test project and none for migrations, which are treated as generated code. `global.json` pins the SDK feature band. The API Dockerfile copies these files before `dotnet restore`, otherwise the image build would use different rules than the local build.

Backend tests: `just test` runs the whole backend suite and needs Docker, `just test-unit` only the `Unit` and `Architecture` namespaces (`--filter-namespace`, no Docker, about 20 seconds), `just test-class <Name>` one class by its short name (`--filter-class "*.<Name>"`) and `just test-method <Name>` one method (`--filter-method "*.<Name>"`). `just test-fe <path>` runs the frontend unit and DOM tests of one file or folder, the path relative to `frontend`. [Tests and Storybook](testing.md#backend-tests) explains the collections the integration tests run in.

Checks: `just check-changed` (`scripts/check-changed.mjs`) reads the files changed against HEAD, staged, unstaged and untracked, and runs only what they need: Oxlint and `oxfmt --check` on the changed frontend files plus `tsc -b` when anything under `frontend` changed, the backend format check and `just test-unit` when anything under `backend` changed, and `just check-docs` when a Markdown file changed; it runs every step, reports the failed ones at the end, and never runs the frontend test suite. `just check-fast` needs no Docker (`just check-docs`, backend format, frontend types, lint, format, unit and DOM tests, and `just test-unit`, which builds the backend in Release); `just check` adds backend tests, contract drift and the app and Storybook builds.
lefthook formats and lints staged frontend files, fixes whitespace in staged C# files (`dotnet format whitespace`, a few seconds; the full style rules run in the pre-push backend build and in CI) and validates the commit subject as a conventional commit (`scripts/check-commit-message.mjs`). The two format jobs have `stage_fixed: true`, which re-stages the files they fixed; lefthook 2 hides the unstaged hunks of a partially staged file before the jobs run and puts them back afterwards, so only the staged hunks are committed, and when a fix touches a line an unstaged hunk also changed the commit stops with a conflict message and keeps both versions. Before a push lefthook type-checks the frontend (`tsc -b`, about 7 seconds; not incremental, see [Testing](testing.md)) and builds the backend in Release, which takes a few seconds when it is up to date; it runs no tests, see the [development decisions](../decisions/development.md). CI (`.gitea/workflows/ci.yaml`) first detects which areas changed and skips the backend or frontend job when its area is untouched; it uploads test results, coverage and, on failure, the Playwright report. Files that affect both areas (`.gitea/`, `scripts/`, `justfile`, `lefthook.yml`, `.editorconfig`, `.dockerignore`, `.env.example`, `global.json`, the compose files) run every job;
`backend/Directory.*.props` already counts as backend. The backend job fails when `dotnet list package --vulnerable --include-transitive` reports a package, the frontend job fails when `nub audit --prod --audit-level moderate` does, and advisories in development-only frontend packages are printed without failing the job. Both live in `scripts/audit.mjs`: `just audit` runs it whole, the backend job runs it with `--backend` and the frontend job with `--frontend`. In the same way `scripts/format-backend.mjs` holds the `dotnet format` call with its migrations exclude for `just format-check-backend`, `just fix` and the backend job, and `scripts/gen.mjs --check` is both `just gen-check` and the `client-drift` job. `scripts/gen.mjs` runs the API with `--no-launch-profile`, `ASPNETCORE_ENVIRONMENT=Development` and `ASPNETCORE_URLS=http://127.0.0.1:0`, so the export binds a free port and works while `just dev` holds port 8091; the scripts share the process helper in `scripts/run.mjs`.
The drift check hashes `frontend/openapi.json`, `docs/api.md` and every file under `frontend/src/api/generated` and `frontend/src/api/schemas` before it regenerates and again after, and fails only when regenerating added, removed or changed a file, which it lists (in CI it also prints the `git diff`). Generated changes that are correct but still staged or uncommitted therefore pass; until 2026-10-03 the check read `git status` on those paths and failed on them.
Job setup is kept in two local composite actions, `.gitea/actions/setup-dotnet` (SDK from `global.json`, NuGet cache keyed by `Directory.Packages.props`) and `.gitea/actions/setup-frontend` (pinned nub and Node, package cache keyed by `nub.lock`, `nub ci`); a job must check out the repository before it can use them. The `production-overlay` job checks that every base image is pinned by digest, validates both Caddyfiles with the pinned Caddy image and runs `scripts/verify-production.mjs`, see Containers. Third-party actions are pinned by commit SHA.

`just check-docs` (`scripts/check-docs.mjs`, also run by the pre-commit hook on the staged Markdown) fails on a broken link or heading anchor, a docs file name with spaces or capitals, or a line over 2000 characters. It also holds `DESIGN.md` to the code (`scripts/design-drift.mjs`), and reports each failure as `DESIGN.md:<line>`:
- Every code span in the body that names code must exist. A PascalCase name (`SummaryStats`) must be declared as a function, constant, class, interface, type or enum in `frontend/src`; a camelCase name (`sidebarRowClass`, or `useMoney` in a call) and a dotted name (`TabsPrimitive.Indicator`) must appear in its code. Stories, tests and `src/storybook` do not count.
- A path (`components/brand`, `lib/navigation.ts`, `favicon.svg`) must resolve under `frontend/src`, `frontend/public`, `frontend` or the repository root, with or without a `.ts` or `.tsx` ending.
- A CSS variable (`--sidebar`) must appear in `frontend/src/global.css` or the frontend code; Base UI variables such as `--active-tab-left` appear only in class strings.
- Each `colors` entry of the frontmatter must equal, ignoring case, the light Ledger value in the `:root` block of `global.css` of the variable that the Colors section pairs with it, written as a name span followed by a variable span (`` `paper`, `--background` ``). A color the Colors section does not pair with a variable fails too.

Other code spans (Tailwind classes, attributes such as `role="img"`, plain words, symbols) are not checked, so the check has no allowlist. It reads the frontend source once and adds about a second.

The same run holds `AGENTS.md` and the pages under `docs/` to the code (`scripts/code-references.mjs`), except `decisions/` and `plans/` and any section headed Done or Log, whose entries are history; fenced blocks are skipped. Each failure reads `<file>:<line>: no name <Name> in the code; renamed? update or drop the reference`.
- A path span (`Common/ResultResponses.cs`, `Endpoints/Goals/Services`, `@/lib/money`) must be the tail of a file or folder that `git ls-files` lists, tracked or untracked, with `.cs`, `.ts` or `.tsx` optional and `@/` read as `frontend/src/`. A span counts as a path when it contains a `/` and either its first segment is a folder at the root, in `backend`, `JxFinance.Api`, `Endpoints`, `JxFinance.Tests`, `frontend` or `frontend/src`, or it ends in a source or config extension; a bare file name counts only with a `.cs`, `.ts`, `.tsx`, `.mjs` or `.ps1` ending. Routes (`/api/goals`), placeholders (`<feature>`, `{id}`, `*`), spans with spaces, package imports whose first segment is a frontend dependency, and gitignored paths are skipped.
- A name span that is an identifier, a dotted chain or a call (`EntityLookup.NotFound(message)`) has each PascalCase segment with at least two capitals (`GoalService`, not `Goals`) looked up as a whole word among the identifiers of every source and config file outside `docs/`, `frontend/openapi.json` included, so an operation id counts. Names with `__` (environment variables, hashed schema names) are skipped, and so are the library names the docs explain, listed in `libraryNames` in the script; add one there when a page names a framework type the code does not use.
- camelCase names are not checked. On 2026-10-04 they would have caught 2 stale names against about 20 React, TanStack, DOM and config-key names that exist only in packages, which no rule short of a long allowlist tells apart.

On 2026-10-04 it looked at about 760 paths and 4,400 names; it found 7 stale references and 6 deliberate mentions of things that do not exist, which were rephrased, and it adds about 1.5 seconds. The run also rebuilds the Routes section of [API surface](../api.md#routes) in memory from `frontend/openapi.json` (`scripts/api-docs.mjs`) and fails when the committed section differs. `just gen` and `just gen-client` write that section, and `just gen-check` counts `docs/api.md` among the generated files.

Claude Code reads the committed `.claude/settings.json`: it allows the everyday checks without a prompt (the `just` checks and test recipes, `nub run test`, lint, format and `tsc`, `dotnet build` and `dotnet test`, read-only `git`), and a `PreToolUse` hook, `.claude/hooks/guard.mjs`, refuses `nub` through the Bash tool and `Set-Content`, `Add-Content` or `Out-File` as a command, telling the agent what to use instead. Everything else in `.claude` stays local and ignored: `settings.local.json` with personal allow entries and the Impeccable design hooks, the skills and the agent worktrees.

`just new-endpoint <Tag> <Name> <verb> "<route>"` (`scripts/new-endpoint.mjs`) writes the slice with its route as an `ApiRoutes` constant plus the rest when a constant is a prefix of it, and a create that answers through `CreatedOrProblemAsync(result, created => created.Id, ct)`. It also writes `<Name>Tests` in `JxFinance.Tests/Integration/<Tag>`, in the collection the folder's other tests use (`--collection=<Name>` for a tag without tests), asserting the status the placeholder answers. `--service` (`--service=<IName>` when the tag has several interfaces) declares `<Name>Async` on the interface, adds a placeholder implementation to the class registered for it and makes the endpoint call it. The summary keeps the placeholder text that `ScaffoldPlaceholderTests` refuses until it is written. `just new-component <feature> <name>` writes the component, the stories `Default` (with a `play` that finds its heading), `Empty`, `Loading` and `ServerError` on `emptyHandlers`, `loadingHandlers` and `errorHandlers`, and a DOM test on `mockApi` and `renderInApp`. Both were checked on 2026-10-04 by scaffolding into a throwaway tag and feature: the backend built in Release and passed `dotnet format`, and the component passed `tsc`, Oxlint, oxfmt, its DOM test and its four stories. [Adding a feature](../adding-a-feature.md) walks through the whole path.

## The squashed migration history
On 2026-10-03 the migration history was squashed into one migration, `20261003165252_InitialCreate` (see [Data model](../data-model.md#model-configuration-and-migrations)). A development database migrated before that holds the old rows in `__EFMigrationsHistory`, so this version would try to create every table again and fail at startup. Its schema already matches `InitialCreate` except for two kinds of leftovers: the database defaults that old migrations left on the non-null columns they added to existing rows, which the model does not declare and the application never relies on, and the partial index on pending payee keys that the script below drops, which served only the removed startup fill of payee keys.

Rewrite it once, before this version first starts on it. The newest row of `__EFMigrationsHistory` must be `20261003152510_AddRowVersions` or `20261003131532_DebtInterestRatePrecision` (the first changes no schema); a database further behind is easier to drop with `just db-reset`. Run this with `docker compose exec -T db psql -U <POSTGRES_USER> -d <POSTGRES_DB>`, the two values from `.env`:

The rows keep their data; only the defaults, the index and the history change. Backups taken before the squash stay unrestorable even after this, because each names its own old migration.

## Package updates
`.gitea/workflows/update-packages.yaml` runs every Monday at 05:00 UTC and on manual dispatch. It upgrades every NuGet package with `dotnet-outdated` and every frontend package with `nub update --latest`, majors included, moves the pinned Docker base images to their newest patch tag and digest (`scripts/update-images.mjs`), regenerates the API client with `scripts/gen.mjs` so the drift check stays green, then force-pushes `chore/package-updates` and opens a pull request through the Gitea API. An already-open pull request is refreshed in place. The job needs a `PACKAGE_UPDATE_TOKEN` repository secret holding a personal access token with repository write scope; the built-in Actions token is not used because pull requests it opens do not trigger CI. Nothing is pushed to `master`; majors and the forced `@tanstack/react-form@alpha` reach it only through that pull request and its CI run. The pinned nub version (in `.gitea/actions/setup-frontend/action.yml`) and the action versions are not covered: actions are pinned by commit SHA with the release in a trailing comment, and moving one means resolving the new SHA with `git ls-remote https://github.com/<owner>/<action> refs/tags/<tag>`.
