# Developer tooling and package updates

## Developer tooling
`just` lists every recipe. `just setup` prepares a checkout (generated `.env`, packages, tools, hooks, `.local/api-debug.env` for the VS Code debugger) and ends with `just doctor`, which checks tool versions, that Docker runs, and the known broken global `node` shim that makes git hooks exit with 127. `scripts/dev.ps1` keeps `dotnet watch` in the same terminal as Vite, so a compile error or a crash is visible, and starts Vite only after `/health` answers; it fails with a message when the API exits during startup. `scripts/dev-env.ps1` is the one place that reads `.env` and builds the development connection string and `App__BackupDirectory`; `dev.ps1`, `with-dev-database.ps1` and `setup.ps1` dot-source it.

Data: `just seed <email>` runs the API with `--seed-demo`, which fills an existing user that has no accounts with six months of deterministic EUR data (`DemoDataCommand`); it refuses a user that already has accounts. `just db-reset` asks for confirmation, removes the dev database volume and starts an empty PostgreSQL. `just migrate-add|remove|list|script` wrap the pinned `dotnet-ef` local tool, and `DatabaseToolingTests` fails when the model has changes without a migration.

Build rules live in `backend/Directory.Build.props` (warnings are errors, `latest-recommended` analyzers, code style enforced in the build) and `backend/Directory.Packages.props` (every NuGet version in one place); `.editorconfig` holds the C# style rules and the few analyzer rules that are switched off, with a wider exemption for the test project and none for migrations, which are treated as generated code. `global.json` pins the SDK feature band. The API Dockerfile copies these files before `dotnet restore`, otherwise the image build would use different rules than the local build.

Checks: `just check-fast` needs no Docker (backend format and build, frontend types, lint, format, unit and DOM tests); `just check` adds backend tests, contract drift and the app and Storybook builds. lefthook formats and lints staged frontend files, fixes whitespace in staged C# files (`dotnet format whitespace`, a few seconds; the full style rules run in the pre-push backend build and in CI) and validates the commit subject as a conventional commit (`scripts/check-commit-message.mjs`); before a push it type-checks, runs `vitest related` for the pushed files and builds the backend. CI (`.gitea/workflows/ci.yaml`) first detects which areas changed and skips the backend or frontend job when its area is untouched; it uploads test results, coverage and, on failure, the Playwright report. Files that affect both areas (`.gitea/`, `scripts/`, `justfile`, `lefthook.yml`, `.editorconfig`, `.dockerignore`, `.env.example`, `global.json`, the compose files) run every job;
`backend/Directory.*.props` already counts as backend. The backend job fails when `dotnet list package --vulnerable --include-transitive` reports a package, the frontend job fails when `nub audit --prod --audit-level moderate` does, and advisories in development-only frontend packages are printed without failing the job. All three live in `scripts/audit.mjs`: `just audit` runs it whole, the backend job runs it with `--backend` and the frontend job with `--frontend`. In the same way `scripts/format-backend.mjs` holds the `dotnet format` call with its migrations exclude for `just format-check-backend`, `just fix` and the backend job, and `scripts/gen.mjs --check` is both `just gen-check` and the `client-drift` job; the scripts share the process helper in `scripts/run.mjs`.
Job setup is kept in two local composite actions, `.gitea/actions/setup-dotnet` (SDK from `global.json`, NuGet cache keyed by `Directory.Packages.props`) and `.gitea/actions/setup-frontend` (pinned nub and Node, package cache keyed by `nub.lock`, `nub ci`); a job must check out the repository before it can use them. The `production-overlay` job checks that every base image is pinned by digest, validates both Caddyfiles with the pinned Caddy image and runs `scripts/verify-production.mjs`, see Containers. Third-party actions are pinned by commit SHA.

`just new-endpoint` and `just new-component` scaffold a backend slice and a frontend component with story and test; [Adding a feature](../adding-a-feature.md) walks through the whole path.

## Package updates
`.gitea/workflows/update-packages.yaml` runs every Monday at 05:00 UTC and on manual dispatch. It upgrades every NuGet package with `dotnet-outdated` and every frontend package with `nub update --latest`, majors included, moves the pinned Docker base images to their newest patch tag and digest (`scripts/update-images.mjs`), regenerates the API client with `scripts/gen.mjs` so the drift check stays green, then force-pushes `chore/package-updates` and opens a pull request through the Gitea API. An already-open pull request is refreshed in place. The job needs a `PACKAGE_UPDATE_TOKEN` repository secret holding a personal access token with repository write scope; the built-in Actions token is not used because pull requests it opens do not trigger CI. Nothing is pushed to `master`; majors and the forced `@tanstack/react-form@alpha` reach it only through that pull request and its CI run. The pinned nub version (in `.gitea/actions/setup-frontend/action.yml`) and the action versions are not covered: actions are pinned by commit SHA with the release in a trailing comment, and moving one means resolving the new SHA with `git ls-remote https://github.com/<owner>/<action> refs/tags/<tag>`.
