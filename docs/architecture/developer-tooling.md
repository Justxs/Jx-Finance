# Developer tooling and package updates

## Developer tooling
`just` lists every recipe. `just setup` prepares a checkout (generated `.env`, packages, tools, hooks, `.local/api-debug.env` for the VS Code debugger) and ends with `just doctor`, which checks tool versions, that Docker runs, and the known broken global `node` shim that makes git hooks exit with 127. `scripts/dev.ps1` keeps `dotnet watch` in the same terminal as Vite, so a compile error or a crash is visible, and starts Vite only after `/health` answers; it fails with a message when the API exits during startup. `scripts/dev-env.ps1` is the one place that reads `.env` and builds the development connection string and `App__BackupDirectory`; `dev.ps1`, `with-dev-database.ps1` and `setup.ps1` dot-source it.

Data: `just seed <email>` runs the API with `--seed-demo`, which fills an existing user that has no accounts with six months of deterministic data in the installation's reporting currency (`DemoDataCommand`); it refuses a user that already has accounts.
Besides salary, bills, groceries and a monthly transfer to savings, the ledger holds card payees (a café, Bolt, Spotify) categorized in the first three months and left uncategorized in the last three, two of them with a payee display name, so rule and learned suggestions have something to offer; places with Vilnius coordinates on the grocery, fuel and pharmacy rows; a yearly car insurance spread over 12 months; a "Riga weekend" group across the main account and the wallet; and a "Home" household the member owns, with the flat shared in it.
Five recurring entries (rent, electricity, salary, the standing order matched by its `monthly saving` key, and the yearly car insurance) fall on fixed days, and everything the command adds is backdated to the start of the first month, so the bills calendar shows paid occurrences matched by their rows from then on.
The command changes no feature switch, so Locations and Learned categories stay off until an administrator turns them on. `DatabaseToolingTests` checks the paid first month and each of these. `--evaluate-categorizer <email>` only reads; it has no recipe, and [Learned categories](../features/learned-categories.md#evaluating-on-a-ledger) shows how to run it against the dev database with a read-only connection. `just db-reset` asks for confirmation, removes the dev database volume and starts an empty PostgreSQL. `just migrate-add|remove|list|script` wrap the pinned `dotnet-ef` local tool, and `DatabaseToolingTests` fails when the model has changes without a migration.

Build rules live in `backend/Directory.Build.props` (warnings are errors, `latest-recommended` analyzers, code style enforced in the build) and `backend/Directory.Packages.props` (every NuGet version in one place); `.editorconfig` holds the C# style rules and the few analyzer rules that are switched off, with a wider exemption for the test project and none for migrations, which are treated as generated code. `global.json` pins the SDK feature band. The API Dockerfile copies these files before `dotnet restore`, otherwise the image build would use different rules than the local build.

Backend tests: `just test` runs the whole backend suite and needs Docker, `just test-unit` only the `Unit` and `Architecture` namespaces (`--filter-namespace`, no Docker, about 20 seconds), and `just test-class <Name>` one class by its short name (`--filter-class "*.<Name>"`). [Tests and Storybook](testing.md#backend-tests) explains the collections the integration tests run in.

Checks: `just check-fast` needs no Docker (`just check-docs`, backend format and build, frontend types, lint, format, unit and DOM tests); `just check` adds backend tests, contract drift and the app and Storybook builds. lefthook formats and lints staged frontend files, fixes whitespace in staged C# files (`dotnet format whitespace`, a few seconds; the full style rules run in the pre-push backend build and in CI) and validates the commit subject as a conventional commit (`scripts/check-commit-message.mjs`); before a push it type-checks, runs `vitest related` for the pushed files and builds the backend. CI (`.gitea/workflows/ci.yaml`) first detects which areas changed and skips the backend or frontend job when its area is untouched; it uploads test results, coverage and, on failure, the Playwright report. Files that affect both areas (`.gitea/`, `scripts/`, `justfile`, `lefthook.yml`, `.editorconfig`, `.dockerignore`, `.env.example`, `global.json`, the compose files) run every job;
`backend/Directory.*.props` already counts as backend. The backend job fails when `dotnet list package --vulnerable --include-transitive` reports a package, the frontend job fails when `nub audit --prod --audit-level moderate` does, and advisories in development-only frontend packages are printed without failing the job. Both live in `scripts/audit.mjs`: `just audit` runs it whole, the backend job runs it with `--backend` and the frontend job with `--frontend`. In the same way `scripts/format-backend.mjs` holds the `dotnet format` call with its migrations exclude for `just format-check-backend`, `just fix` and the backend job, and `scripts/gen.mjs --check` is both `just gen-check` and the `client-drift` job; the scripts share the process helper in `scripts/run.mjs`.
The drift check hashes every file under `frontend/openapi.json`, `frontend/src/api/generated` and `frontend/src/api/schemas` before it regenerates and again after, and fails only when regenerating added, removed or changed a file, which it lists (in CI it also prints the `git diff`). Generated changes that are correct but still staged or uncommitted therefore pass; until 2026-10-03 the check read `git status` on those paths and failed on them.
Job setup is kept in two local composite actions, `.gitea/actions/setup-dotnet` (SDK from `global.json`, NuGet cache keyed by `Directory.Packages.props`) and `.gitea/actions/setup-frontend` (pinned nub and Node, package cache keyed by `nub.lock`, `nub ci`); a job must check out the repository before it can use them. The `production-overlay` job checks that every base image is pinned by digest, validates both Caddyfiles with the pinned Caddy image and runs `scripts/verify-production.mjs`, see Containers. Third-party actions are pinned by commit SHA.

`just check-docs` (`scripts/check-docs.mjs`, also run by the pre-commit hook on the staged Markdown) fails on a broken link or heading anchor, a docs file name with spaces or capitals, or a line over 2000 characters. It also holds `DESIGN.md` to the code (`scripts/design-drift.mjs`), and reports each failure as `DESIGN.md:<line>`:
- Every code span in the body that names code must exist. A PascalCase name (`SummaryStats`) must be declared as a function, constant, class, interface, type or enum in `frontend/src`; a camelCase name (`sidebarRowClass`, or `useMoney` in a call) and a dotted name (`TabsPrimitive.Indicator`) must appear in its code. Stories, tests and `src/storybook` do not count.
- A path (`components/brand`, `lib/navigation.ts`, `favicon.svg`) must resolve under `frontend/src`, `frontend/public`, `frontend` or the repository root, with or without a `.ts` or `.tsx` ending.
- A CSS variable (`--sidebar`) must appear in `frontend/src/global.css` or the frontend code; Base UI variables such as `--active-tab-left` appear only in class strings.
- Each `colors` entry of the frontmatter must equal, ignoring case, the light Ledger value in the `:root` block of `global.css` of the variable that the Colors section pairs with it, written as a name span followed by a variable span (`` `paper`, `--background` ``). A color the Colors section does not pair with a variable fails too.

Other code spans (Tailwind classes, attributes such as `role="img"`, plain words, symbols) are not checked, so the check has no allowlist. It reads the frontend source once and adds about a second.

`just new-endpoint` and `just new-component` scaffold a backend slice and a frontend component with story and test; [Adding a feature](../adding-a-feature.md) walks through the whole path.

## The squashed migration history
On 2026-10-03 the migration history was squashed into one migration, `20261003165252_InitialCreate` (see [Data model](../data-model.md#model-configuration-and-migrations)). A development database migrated before that holds the old rows in `__EFMigrationsHistory`, so this version would try to create every table again and fail at startup. Its schema already matches `InitialCreate` except for two kinds of leftovers: the database defaults that old migrations left on the non-null columns they added to existing rows, which the model does not declare and the application never relies on, and the partial index `IX_Transactions_PayeeKeyPending`, which served only the removed startup fill of payee keys.

Rewrite it once, before this version first starts on it. The newest row of `__EFMigrationsHistory` must be `20261003152510_AddRowVersions` or `20261003131532_DebtInterestRatePrecision` (the first changes no schema); a database further behind is easier to drop with `just db-reset`. Run this with `docker compose exec -T db psql -U <POSTGRES_USER> -d <POSTGRES_DB>`, the two values from `.env`:

```sql

The rows keep their data; only the defaults, the index and the history change. Backups taken before the squash stay unrestorable even after this, because each names its own old migration.

## Package updates
`.gitea/workflows/update-packages.yaml` runs every Monday at 05:00 UTC and on manual dispatch. It upgrades every NuGet package with `dotnet-outdated` and every frontend package with `nub update --latest`, majors included, moves the pinned Docker base images to their newest patch tag and digest (`scripts/update-images.mjs`), regenerates the API client with `scripts/gen.mjs` so the drift check stays green, then force-pushes `chore/package-updates` and opens a pull request through the Gitea API. An already-open pull request is refreshed in place. The job needs a `PACKAGE_UPDATE_TOKEN` repository secret holding a personal access token with repository write scope; the built-in Actions token is not used because pull requests it opens do not trigger CI. Nothing is pushed to `master`; majors and the forced `@tanstack/react-form@alpha` reach it only through that pull request and its CI run. The pinned nub version (in `.gitea/actions/setup-frontend/action.yml`) and the action versions are not covered: actions are pinned by commit SHA with the release in a trailing comment, and moving one means resolving the new SHA with `git ls-remote https://github.com/<owner>/<action> refs/tags/<tag>`.
