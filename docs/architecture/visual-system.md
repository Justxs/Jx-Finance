# Visual system and motion

## Visual system
`PRODUCT.md` records who the product is for and `DESIGN.md` records the visual system, "The Household Ledger"; both sit at the repository root and are the reference for any new screen. The short version: the page is paper and content sits directly on it. A section is a tonal surface with a title (`Section` with a `SectionTitle`, or `Section as="div"` for a block without a title of its own), rows are separated by hairlines (`Rows`), and a net total carries a double rule (`border-b-3 border-double border-rule`). `Card` is kept for objects that really are separate: the sign-in and setup forms and story frames. Page content is never boxed and surfaces never nest.

### Components, stale content and focus

These surfaces are React components in `src/components/ui`, built from Tailwind utilities with `cn`; `global.css` holds tokens, base rules, view transitions and a few utilities (`stale`, `focus-ring`, the swatch backgrounds, `transition-width`, `transition-reveal` and `collapse-rows`) and no semantic classes. `Card`, `Section` and `FormGrid` take `as` for the few call sites that need another element (`Section as="form"`, `Section as="div"`, `Section as={Rows}`, `Section as={SplitColumns}`, `FormGrid as="form"`); the accepted values are listed in each component's props, which keeps event handlers typed. `Section` marks itself with `data-surface` and flattens (no fill, radius or padding) inside another surface or inside `role="dialog"` through an arbitrary variant, `[:is([data-surface],[role=dialog])_&]:p-0`. That selector is more specific than a plain utility, so a padding or background passed through `className` does not apply to a flattened surface; nothing needs it today. `FormGrid` sets its columns with `grid-cols-[repeat(auto-fit,minmax(min(100%,13rem),1fr))]`, so the number of columns follows the width of the form's container, not the viewport, and gives its children `min-width: 0` through `[:where(&>*)]:min-w-0`, which has no specificity and loses to any utility on the child. `SplitColumns` is the five-to-seven two-column split used by the summary stats and the reports page. The page title and the lead figure are used in one and two places, so their utilities are written inline (`PageHeader`, `SummaryStats`, `DashboardStats`).

Stale content dims. While `useDeferredParams` reports old data on screen, or a row waits for its mutation, the element sets `aria-busy`, shows a progress cursor and fades to 75% opacity after a 150 ms delay, so an answer that comes back quickly never flickers. At 75% ink text still measures at least 6.6:1 and muted text at least 3.1:1 on a section panel in every palette and both themes; the earlier 55% dropped muted text to 2.2:1 in light. The `stale` utility in `global.css` holds those classes and goes on a `Table`, a `TableRow`, a list item or a control; `StaleRegion` is the `div` form (`stale` prop, `aria-busy`, `data-stale`). From 2026-09-20 to 2026-09-26 the state kept full contrast and drew a pulsing ink rule along the top edge instead; see the [interface decisions](../decisions/interface.md) for why it went back to dimming.

Keyboard focus has one treatment, defined once in `global.css`. The base `:focus-visible` rule draws a 2px `ring` outline offset by 3px for anything that sets nothing else. Controls and links replace it with the `focus-ring` utility: on `:focus-visible` it removes the outline and draws a 3px box-shadow ring of `--ring` at 60%. `focus-ring-inset` draws the same ring inside the element, for tabs, segmented-control items and notification entries, whose neighbours or scroll container would cover an outer ring. A destructive button tints the ring with `focus-visible:ring-destructive/30`, an invalid field with `aria-invalid:ring-destructive/20`, and a field also sets `focus-visible:border-ring`; these variant classes sort after the bare utility, so they win. Three places keep the ring classes written out because the trigger is not the element's own focus: `FileInput` (`has-focus-visible:`), the focused calendar day (`group-data-[focused=true]/day:`) and the command palette's search row (`has-[input:focus-visible]:border-ring`).

### Type and color

Type is self-hosted: Source Serif 4 for page titles, the wordmark and lead figures, Source Sans 3 for everything else. The variable woff2 files (Latin and Latin Extended, which covers Lithuanian) are vendored in `src/assets/fonts` with their OFL license and declared in `src/fonts.css`. The four files of the default pair (both subsets of Source Sans 3 and Source Serif 4) are preloaded: a small plugin in `vite.config.ts` injects `<link rel="preload" as="font">` with their hashed build names, because `font-display: swap` and the `unicode-range` split otherwise fetch the Latin Extended file only when the first Lithuanian letter is drawn, and the text visibly swaps. Other typefaces load on first use. They are vendored rather than imported from a package because nub keeps packages in a store outside the project, which the Vite dev server refuses to serve as raw assets. The fonts are bundled by Vite and served from the same origin, so the Content-Security-Policy is unchanged and no third-party request is made. Tailwind's `text-xs`, `text-sm` and `text-base` are raised by one pixel in `global.css` because Source Sans runs smaller than Segoe UI. Serif figures need `lining-nums` next to `tabular-nums`; the lead figures and the page title already apply it.

Color is semantic. `text-income` and `text-expense` are the money text colors and hold AA contrast in both themes; `secondary` and `destructive` remain the fill colors for meters, chart bars and destructive buttons. Signed amounts carry "+" or "−" so direction never depends on color. `SignedAmount` (`components/signed-amount`) is the one way to show a net or a change: it formats with `formatSigned` and takes its tone from `gainTone(value, sign)` in `lib/tone.ts`, falling back to ink so a zero inside muted text still reads as a figure; `SummaryStats` derives the same tone for an item with `sign: "auto"` unless the item passes its own `tone`. Transaction rows, the ledger totals line and investment charges keep an expense "−" in ink and do not use it. Lists, meters and charts do not use a palette to tell rows apart. `Tag` replaces every hand-written pill and `Meter` every progress bar; neither is rounded.

### Per-browser preferences

Per-browser preferences live in one TanStack DB local-storage collection, `preferencesCollection` in `src/stores/preferences.ts`, built with `localStorageCollectionOptions`, the explicit `storageKey` `jx-preferences` and a zod schema. The collection holds a single row with the id `browser`: `theme` (absent means follow the system), `palette`, `font`, `textSize`, `sidebarCollapsed` and `locale` (absent means use the installation default). Every field of the schema has a `.catch` default, so a value written by an older or newer build degrades field by field instead of discarding the row. The library stores the collection as one JSON object, `{ "s:browser": { "versionKey": "…", "data": { … } } }`, where `s:` marks a string key and `versionKey` changes on every write.

`theme-store.ts`, `sidebar-store.ts` and `app-store.ts` are thin functions over that row and keep their old exports. Reads go through `usePreferences`, a `useSyncExternalStore` over `collection.subscribeChanges`, rather than `useLiveQuery`, because one row needs no query engine and the live-query compiler would land in the entry chunk; `readPreferences` parses the row through the schema and keeps the parsed object's identity until the stored JSON changes, which `useSyncExternalStore` requires. Writes are `collection.insert` for the first write and `collection.update` afterwards, so nothing is stored until the user chooses something. `theme-store.ts` subscribes once at module scope and applies the `dark` class and the `data-*` attributes from the row, which means a change made in another tab arrives through the collection's `storage` event and restyles this tab too; since 2026-10-03 it also listens to `change` on `matchMedia("(prefers-color-scheme: dark)")` and reapplies, and `useTheme` reads the system scheme through `useSyncExternalStore` like `useWideLedger`, so with no theme chosen the page and the theme toggle follow the operating system switching between light and dark without a reload; `app-store.ts` does the same for the chosen language and keeps a small TanStack Store only for the installation default language, which is session state and is never stored.

`src/features/transactions/transaction-views.ts` adds two more collections built the same way, `savedFilters` (`jx-saved-filters`) and `transactionTemplates` (`jx-transaction-templates`), each with `read`, `useRows`, `save`, `rename`, `remove` and `clear`. It sits in the feature because a saved filter's schema is the ledger's own `transactionFilterSchema`, and code under `stores` may not import a feature. They differ from the preferences row in one respect: they are lists, so each row carries its own id and name and the getKey is the row's id rather than a constant. Everything else is the same shape — an explicit storage key, the shared `browserStorage()` object, a zod schema whose inner fields all carry `.catch` defaults so a row written by another build degrades field by field, a `getSyncMetadata` that returns only the storage key, and a `useLiveQuery` read in `useRows` that keeps the parsed array's identity until the stored rows change. `read` and `useRows` sort by name with `toSorted`, so the menus show a stable list and the snapshot identity is still tied to the stored content. `clearTransactionViews` exists for the story runner, which deletes every row between stories exactly as it deletes the preferences row.

Storage that is blocked must not break the app. `browserStorage()` in `src/lib/browser-storage.ts` probes `localStorage` with a write inside try/catch and returns the real object when it works, so the collection's cross-tab check `event.storageArea === storage` still holds, and an in-memory object with the same three methods when reading the property or writing throws (Chrome with site data blocked throws on the property itself). The collection's own default would touch `window.localStorage` unguarded at import time, and its `getSyncMetadata` does so on every mutation, so `preferences.ts` passes `storage` explicitly and replaces `getSyncMetadata` with one that returns only the storage key. With the in-memory storage, choices last for the session. `public/theme-init.js` runs before the bundle and cannot import the library, so it reads `jx-preferences` itself inside try/catch, takes `["s:browser"].data`, and falls back to the system colour scheme when storage is blocked or the JSON is unreadable; `theme-init.dom.test.ts` runs the real file against a row written by the collection so the two cannot drift apart.

Color palettes are a per-browser choice, separate from light/dark. `stores/theme-store.ts` keeps the palette in the preferences row and sets `data-palette` on `<html>`; `public/theme-init.js` applies it before first paint. The default palette, `ledger`, sets no attribute. Each palette (`plum`, `sepia`, `graphite`) overrides only the neutral and primary tokens in `global.css`, for light and dark; the values are the ledger tokens with the OKLCH hue rotated and lightness kept, so every contrast ratio matches the default. Income, expense, secondary and destructive colors never change with the palette. `AppearancePicker` (`components/appearance-picker`) renders it as a native radio group in the Appearance section of Settings (`/profile?section=appearance`), between the theme and language groups; its swatches carry their own `data-palette`, which is why the dark selectors also match `.dark [data-palette]` descendants.
`src/theme-contrast.test.ts` reads these tokens from `global.css` and fails when any palette in either theme drops a text pair below 4.5:1 or the focus ring, input stroke or chart colors below 3:1; see [testing](testing.md#frontend-tests).

Typeface and text size follow the same per-browser pattern: `font` sets `data-font` and `textSize` sets `data-text-size` on `<html>`, both applied by `theme-init.js`, and the defaults (`ledger`, `default`) set no attribute. Tailwind `font-sans` and `font-serif` resolve to `--font-body` and `--font-display`, which each `[data-font]` block redefines: `sans` and `serif` use one Source family for both roles, `system` uses the device fonts, and `inter`, `hyperlegible` (Atkinson Hyperlegible Next), `plex` (IBM Plex Sans with Plex Serif 600 for display) and `editorial` (Inter with Newsreader for display) use extra self-hosted families. Their `woff2` files, latin and latin-ext subsets taken from the Fontsource packages, sit in `src/assets/fonts` beside one `OFL-*.txt` license per family and are declared in `fonts.css`; a browser downloads a family only when it is used, so the extra files cost nothing until someone opens the picker or chooses that option. Text size changes the root `font-size` (93.75% or 112.5%); every size and control height is in `rem`, so the whole interface scales. The same `AppearancePicker` shows the typeface and text size groups in a second section under the palettes, all three built from one `ChoiceGroup` of radio cards, and each typeface option carries its own `data-font` so it previews itself.

### Shell, tables and hidden amounts

The desktop shell has no top bar. The collapse control is a small round handle straddling the sidebar's right border, level with the brand, with a chevron that points the way the sidebar will move. The sidebar foot holds the Ko-fi row and a Notifications row, with the user tile under them; `NotificationBell` takes `sidebar="expanded"` or `sidebar="collapsed"` there to render as a full-width row (or the bell alone in the rail) and open its panel upward or to the right. The mobile header keeps the icon button. The user tile opens `AccountMenu`, whose rows name each setting with its current value (Language, English; Theme, Light) so the menu reads as settings rather than bare actions, and an up-down chevron marks the tile as something that opens. Language and theme are also radio cards at the top of Appearance, so the menu is a shortcut and not their only home. Below the `md` breakpoint a compact header and a scrolling navigation strip take over. Navigation items are grouped by job with a gap between groups instead of labels, related pages share one hub entry with tabs under the page title, and Settings sits at the bottom of the list; [Interface](../features/interface.md#navigation) describes how the entries are built. Languages are named in their own language; flags are not used because a flag stands for a country, not a language. The signed-out screens keep the small language and theme toggles in their corner.

Tables have no surrounding box. The `Table` primitive supplies the muted header text, the hairline header rule and `px-3` cells. Two props carry the rest of the table rules, so a call site cannot forget them. `label` wraps the table in a `ScrollRegion` (`role="region"`, `tabIndex={0}`, the label as its name), which lets a keyboard user scroll a table wider than its panel, and pulls it out with `-mx-3` so cell text aligns with the page edge while row hover still has room; `TableSkeleton` carries the same `-mx-3`, so a placeholder lines up with the table it stands in for. `columns` takes one width class per column, `undefined` for the one that takes the remaining space, and renders them as a `colgroup` on a `table-fixed` table, so long names truncate instead of pushing the row actions out of view. Every table in a page or dialog passes `label`; the notification channel grid in the profile does not, because it is a fixed grid of checkboxes inside a form that always fits and a scroll region would only add a tab stop. Responsive visibility (`hidden md:block`) and outer spacing go on a wrapping element, since `className` styles the `table` itself. `ScrollRegion` stays exported for the few vertically scrolling lists (price history, exchange-rate entries) and the small mismatch table of a broker import result, which sits inside a warning block that is not pulled out.

A status line or a short summary that is not a list sits between two rules instead of in a box: `RuledLine` (`components/ui/ruled-line`) draws `border-y` with `py-2.5` and `text-sm`, takes `as` (`p`, `dl`) like `Section`, and a `tone` of `hairline` (Settings status lines) or `ink` (a figure inside a form or a result). A single rule above or below a block (`FormSection`, a header bar with a rule under it) stays written out, since it is a different shape.

Hidden amounts are drawn with one glyph, five bullets (`•••••`, `AMOUNT_MASK` in `src/lib/mask-amount.ts`), whatever the size of the number. `maskParts` takes the parts of `Intl.NumberFormat.formatToParts` and replaces the run from the first to the last `integer`, `group`, `decimal`, `fraction` or `compact` part, literals inside it included, with a single mask, so a thousands group, a decimal comma or a compact suffix such as `tūkst.` never leaves a second mask or a stray letter behind. The currency sign, the minus or plus sign and the literals outside the run stay where the locale puts them, so `−€•••••` in English and `−••••• €` in Lithuanian still read as money and as a direction. The formatter hooks in `src/hooks/use-formatters.ts` apply it while `amountsHidden` is on; `useMaskedNumber` does the same for a plain number that is money, such as the ledger's amount range chip. Masked cells keep their table and their `tabular-nums`, and a column may become narrower than the real figures would make it; nothing reserves the width of the hidden number, so the layout is the one a short amount would have. `maskDigits` is the blunt version for free text the application did not format, and only the notification bell uses it, for the server's fallback message.

## Brand assets
The mark is a single vector path, the ledger bird, kept in `frontend/scripts/brand/bird.svg`. `scripts/brand/build.mjs` reads that path, measures its bounding box in headless Chromium and writes `src/components/brand/mark-paths.ts`, which the `BrandMark` component and every static asset share. `favicon.svg` carries a `prefers-color-scheme` rule so the bird stays legible on dark browser chrome; the PNG and ICO files are screenshots of the same SVG on a navy tile, taken with the Playwright already installed for tests, and the ICO container is assembled in the script, so the generator needs no extra dependency. From `frontend/` run `node scripts/brand/build.mjs`; Storybook maps `public/favicon.svg` through `staticDirs` in `.storybook/main.ts`, so there is no second copy. If the mark changes, regenerate all of them together so the favicon, the manifest icons and the in-app logo cannot drift. Storybook uses the same favicon and a branded manager theme (`.storybook/manager.ts`, `.storybook/manager-head.html`). The manifest is covered by the existing Content-Security-Policy because `default-src 'self'` applies to `manifest-src`.

## Motion
Motion is limited to four things, all built on view transitions: changing page, table rows changing in place, a list row being added, removed or moved, and a section replacing its skeleton. Durations are 90 to 280 ms with an exponential ease-out, and nothing animates on its own.

The common durations are theme tokens in `global.css`, declared in the `--transition-duration-*` namespace that Tailwind's `duration-*` utility reads, so each one is both a class and a CSS variable: `duration-quick` (100ms) opens and closes dialogs, popovers, menus and tooltips; `duration-base` (200ms) carries hover and state changes, the sidebar width, the stale fade and the hub strip fading in; `duration-view` (220ms) is a page or a section entering in a view transition and the sidebar link's cross-fade; `duration-slow` (300ms) moves the tab underline and fills a meter. The view-transition rules use the variables (`var(--transition-duration-view)`), and reduced motion falls back to `--transition-duration-quick`. Exits and one-off timings stay literal next to their rule: 90 to 160ms fades out, the 240ms row drop and slide, and the 280ms hub tab slide. A transition with no `duration-*` class keeps Tailwind's 150ms default. `cn` registers the four names with `tailwind-merge` as durations, so a `duration-*` passed in `className` replaces one.
`buttonVariants` runs its classes through `cn`, so a link styled as a button resolves conflicts such as the base `border-transparent` against the outline variant's `border-border` exactly as `Button` does.

The page change is driven by the router, not by React. TanStack Router publishes location through `useSyncExternalStore`, and React renders external-store updates synchronously even inside `startTransition`, so a React `ViewTransition` around `<Outlet />` never activates on navigation; an earlier version of this page relied on that and silently stopped animating. Instead the router is created with `defaultViewTransition` set to `pageViewTransition` from `lib/page-transition.ts`, which asks the router to wrap the commit in `document.startViewTransition` with the type `page`, and only when the pathname changed. Sorting, filtering and paging are navigations too, but they only change search params, so they return `false` and the page does not fade on every keystroke. The element around `<Outlet />` has the class `page-transition`, and `global.css` gives it `view-transition-name: page` only while `:root:active-view-transition-type(page)` matches, so it is not captured during any other transition. `::view-transition-old(page)` and `::view-transition-new(page)` give it a short fade and slide. The Storybook router in `src/storybook/decorators.tsx` uses the same option so page stories behave like the app.

A page change also scrolls the window to the top as soon as navigation to a new path starts: `app.tsx` subscribes `scrollToTopOnPageChange` to the router's `onBeforeNavigate` event. The router's own scroll reset runs only on `onRendered`, after the next route has loaded and the view transition has run, so the new page's skeleton used to appear at the previous page's scroll position.

Inside a hub the `h1` and `HubTabs` are lifted out of that cross-fade. While a `page` transition runs, `.hub-title` and `.hub-tabs` take the names `hub-title-<hub>` and `hub-tabs-<hub>` from custom properties that `PageHeader` and `HubTabs` set, with the class `hub-part`. Between two tabs of the same hub both snapshots exist: the title carries no animation and stays still, and the strip (class `hub-strip` as well) cross-fades its labels in 200ms while the page below fades. The active tab's 2px underline is a separate element, `.hub-tab-indicator`, named `hub-tab-indicator-<hub>` with the class `hub-slide`; its old and new snapshots are identical and not animated, so only its group moves, sliding from the old tab to the new one in 280ms on the expo ease. Leaving the hub leaves one snapshot of each, which `:only-child` fades like the page. Pseudo-classes other than `:only-child` are not allowed after a view-transition pseudo-element, so the rules are written as a base rule plus an `:only-child` override rather than with `:not()`.
Sidebar and phone-strip links cannot rely on CSS transitions: the router runs the class change inside `startViewTransition`, whose update callback waits for the next route to load while rendering is suppressed, so a 200ms transition has finished before anything is painted. Each link therefore carries `--nav-link` (`nav-side-<index>`, `nav-strip-<index>`; the two lists never render at the same width, so the names stay unique) and the class `nav-link`, which names it during a `page` transition; its old and new snapshots cross-fade over 220ms once the new page is captured. Section-nav links change within one page and keep a plain CSS transition of their colour and fill (`transition-colors duration-base`, expo ease). Components name the properties they transition instead of using `transition-all`, which `jx/no-transition-all` rejects: `TabsList` uses `transition-[left,width]` on its indicator, the sidebar `transition-width`, the month-close details panel `collapse-rows` on a wrapper inside Base UI's `Collapsible.Panel`, which moves `grid-template-rows` between `0fr` and `1fr` while the panel carries its starting or ending style, so no height is animated; the panel itself only fades its opacity over the same duration, which gives Base UI a transition to wait for before it unmounts the content (the grid cannot sit on the panel, because Base UI measures the panel's own height to end its starting style and a `0fr` grid measures zero), and the dashboard's "current month" button `transition-reveal`, which also transitions `visibility` so the button fades out before it leaves the tab order. `RoutePending` renders the same hub header, so a tab whose data is still loading does not swap the title for a skeleton.

Everything else uses React's `ViewTransition`, which needs the update to be a React transition. Query results arrive through an external store as well, so lists pass their data through `useDeferredValue` before rendering: the deferred render is a transition, and that is what lets a row animate. Defer the query's `data` itself and apply `?? []` afterwards; deferring a fresh array literal never settles. `RowTransition` (`components/row-transition`) wraps a list row and carries the classes `row-in`, `row-out` and `row-move`: a new row fades and drops in, a removed row fades out, and the rows below slide to their new position. `QueryBoundary` wraps its fallback and its content in boundaries with `reveal-out` and `reveal-in`, so a section cross-fades from its skeleton instead of snapping. Both content boundaries carry `update="none"` so they are captured only when they appear or disappear, never when something inside them changes. The boundary around `<Outlet />` passes `reveal={false}` because the page transition already covers it.

Each table then carries its own `ViewTransition` around its scroll container, so sorting and filtering cross-fade the rows alone; the reports results block has the same treatment. The names are per-owner (`transactions-rows`, `accounts-rows`, `users-rows`, `report-results`, `month-results`) so two can never claim one name.

The month page body holds animated rows (its uncategorized and bills-due lines), so an update boundary around it would cross-fade the whole body whenever one line left and the body shrank. Its `month-results` boundary is keyed by the shown month instead and sets `default="none" share="auto"`: stepping to another month unmounts one keyed boundary and mounts the next under the same name, which React animates as a shared pair, while a line resolving inside it never names the body.

Two rules keep those scoped transitions from spilling over the rest of the page.

`:root` is given `view-transition-name: none`. Without it the browser captures everything unnamed into a default `root` group and cross-fades it, so any one scoped transition repainted the entire page — picking a date in a column filter looked like a full reload. Opting the root out means only explicitly named elements animate and the rest of the DOM updates in place. Do not "fix" this by putting `animation: none` on `::view-transition-old(root)`: the old snapshot then sits at full opacity above the new content for the group's duration, freezing the page instead of skipping it.

The scoped boundaries carry `enter="none" exit="none"` so they are named only while their content changes in place. Without this, a table's boundary would also be captured whenever its whole section appears, animating twice.

Dialogs, popovers and select menus are Base UI components rendered through a portal, so `ViewTransition` does not capture them. They animate with the `data-open` and `data-closed` classes that shadcn ships, driven by `tw-animate-css`; Base UI keeps the element mounted until the exit animation ends, so no manual close delay is needed. `#root` sets `isolation: isolate` so portalled layers always stack above page content.

Tooltips use the Base UI `Tooltip` wrapper in `components/ui/tooltip` instead of the native `title` attribute. `Button` shows its `aria-label` as the tooltip when its size is `icon` or `icon-sm`, so an icon-only action passes `tooltip` only when the hint should differ from the label (and `tooltipSide` to move it), and `tooltip={false}` where a hint would get in the way, as on the calendar day buttons; other elements (sort and filter header buttons, collapsed sidebar links, checkboxes, the icon picker, drill-down category links) are wrapped in `<Tooltip content={...}>`. An empty `content` renders the child untouched. Disabled controls do not receive pointer events, so their tooltip goes on a wrapping `span`. A single `TooltipProvider` in `app.tsx` shares the 400 ms open delay, so moving between adjacent actions shows the next tooltip instantly. Native `title` remains only on non-interactive text, mostly truncated names where it reveals the full value; `jx/no-native-title` rejects it on a link, a button, a form control or anything with `onClick` or an interactive `role`, so a truncated bill name that opens its form is wrapped in `Tooltip` instead.

Reduced motion is handled in two places: the `*` rule covers dialogs, popovers and menus, and a separate rule covers the view-transition pseudo-elements, which `*` does not match.
