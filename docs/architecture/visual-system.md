# Visual system and motion

## Visual system
`PRODUCT.md` records who the product is for and `DESIGN.md` records the visual system, "The Household Ledger"; both sit at the repository root and are the reference for any new screen. The short version: the page is paper and content sits directly on it. A section is a tonal surface with a title (`Section` with a `SectionTitle`, or `Section as="div"` for a block without a title of its own), rows are separated by hairlines (`Rows`), and a net total carries a double rule (`border-b-3 border-double border-rule`). `Card` is kept for objects that really are separate: the sign-in and setup forms and story frames. Page content is never boxed and surfaces never nest.

These surfaces are React components in `src/components/ui`, built from Tailwind utilities with `cn`; `global.css` holds tokens, base rules and view transitions and no semantic classes. `Card`, `Section` and `FormGrid` take `as` for the few call sites that need another element (`Section as="form"`, `Section as="div"`, `Section as={Rows}`, `Section as={SplitColumns}`, `FormGrid as="form"`); the accepted values are listed in each component's props, which keeps event handlers typed. `Section` marks itself with `data-surface` and flattens (no fill, radius or padding) inside another surface or inside `role="dialog"` through an arbitrary variant, `[:is([data-surface],[role=dialog])_&]:p-0`. That selector is more specific than a plain utility, so a padding or background passed through `className` does not apply to a flattened surface; nothing needs it today. `FormGrid` sets its columns with `grid-cols-[repeat(auto-fit,minmax(min(100%,13rem),1fr))]`, so the number of columns follows the width of the form's container, not the viewport, and gives its children `min-width: 0` through `[:where(&>*)]:min-w-0`, which has no specificity and loses to any utility on the child. `SplitColumns` is the five-to-seven two-column split used by the summary stats and the reports page. The page title and the lead figure are used in one and two places, so their utilities are written inline (`PageHeader`, `SummaryStats`, `DashboardStats`).

Stale content dims. While `useDeferredParams` reports old data on screen, or a row waits for its mutation, the element sets `aria-busy`, shows a progress cursor and fades to 55% opacity after a 150 ms delay, so an answer that comes back quickly never flickers. The `stale` utility in `global.css` holds those classes and goes on a `Table`, a `TableRow`, a list item or a control; `StaleRegion` is the `div` form (`stale` prop, `aria-busy`, `data-stale`). From 2026-09-20 to 2026-09-26 the state kept full contrast and drew a pulsing ink rule along the top edge instead; see the [interface decisions](../decisions/interface.md) for why it went back to dimming.

Type is self-hosted: Source Serif 4 for page titles, the wordmark and lead figures, Source Sans 3 for everything else. The variable woff2 files (Latin and Latin Extended, which covers Lithuanian) are vendored in `src/assets/fonts` with their OFL license and declared in `src/fonts.css`. They are vendored rather than imported from a package because nub keeps packages in a store outside the project, which the Vite dev server refuses to serve as raw assets. The fonts are bundled by Vite and served from the same origin, so the Content-Security-Policy is unchanged and no third-party request is made. Tailwind's `text-xs`, `text-sm` and `text-base` are raised by one pixel in `global.css` because Source Sans runs smaller than Segoe UI. Serif figures need `lining-nums` next to `tabular-nums`; the lead figures and the page title already apply it.

Color is semantic. `text-income` and `text-expense` are the money text colors and hold AA contrast in both themes; `secondary` and `destructive` remain the fill colors for meters, chart bars and destructive buttons. Signed amounts carry "+" or "−" so direction never depends on color. Lists, meters and charts do not use a palette to tell rows apart. `Tag` replaces every hand-written pill and `Meter` every progress bar; neither is rounded.

Per-browser preferences live in one TanStack DB local-storage collection, `preferencesCollection` in `src/stores/preferences.ts`, built with `localStorageCollectionOptions`, the explicit `storageKey` `jx-preferences` and a zod schema. The collection holds a single row with the id `browser`: `theme` (absent means follow the system), `palette`, `font`, `textSize`, `sidebarCollapsed` and `locale` (absent means use the installation default). Every field of the schema has a `.catch` default, so a value written by an older or newer build degrades field by field instead of discarding the row. The library stores the collection as one JSON object, `{ "s:browser": { "versionKey": "…", "data": { … } } }`, where `s:` marks a string key and `versionKey` changes on every write.

`theme-store.ts`, `sidebar-store.ts` and `app-store.ts` are thin functions over that row and keep their old exports. Reads go through `usePreferences`, a `useSyncExternalStore` over `collection.subscribeChanges`, rather than `useLiveQuery`, because one row needs no query engine and the live-query compiler would land in the entry chunk; `readPreferences` parses the row through the schema and keeps the parsed object's identity until the stored JSON changes, which `useSyncExternalStore` requires. Writes are `collection.insert` for the first write and `collection.update` afterwards, so nothing is stored until the user chooses something. `theme-store.ts` subscribes once at module scope and applies the `dark` class and the `data-*` attributes from the row, which means a change made in another tab arrives through the collection's `storage` event and restyles this tab too; `app-store.ts` does the same for the chosen language and keeps a small TanStack Store only for the installation default language, which is session state and is never stored.

`src/stores/transaction-views.ts` adds two more collections built the same way, `savedFiltersCollection` (`jx-saved-filters`) and `transactionTemplatesCollection` (`jx-transaction-templates`). They differ from the preferences row in one respect: they are lists, so each row carries its own id and name and the getKey is the row's id rather than a constant. Everything else is the same shape — an explicit storage key, the shared `browserStorage()` object, a zod schema whose inner fields all carry `.catch` defaults so a row written by another build degrades field by field, a `getSyncMetadata` that returns only the storage key, and a `useSyncExternalStore` read that keeps the parsed array's identity until the stored JSON changes. `readSavedFilters` and `readTransactionTemplates` sort by name with `toSorted`, so the menus show a stable list and the snapshot identity is still tied to the stored content. `clearTransactionViews` exists for the story runner, which deletes every row between stories exactly as it deletes the preferences row.

Storage that is blocked must not break the app. `browserStorage()` in `src/lib/browser-storage.ts` probes `localStorage` with a write inside try/catch and returns the real object when it works, so the collection's cross-tab check `event.storageArea === storage` still holds, and an in-memory object with the same three methods when reading the property or writing throws (Chrome with site data blocked throws on the property itself). The collection's own default would touch `window.localStorage` unguarded at import time, and its `getSyncMetadata` does so on every mutation, so `preferences.ts` passes `storage` explicitly and replaces `getSyncMetadata` with one that returns only the storage key. With the in-memory storage, choices last for the session. `public/theme-init.js` runs before the bundle and cannot import the library, so it reads `jx-preferences` itself inside try/catch, takes `["s:browser"].data`, and falls back to the system colour scheme when storage is blocked or the JSON is unreadable; `theme-init.dom.test.ts` runs the real file against a row written by the collection so the two cannot drift apart.

Color palettes are a per-browser choice, separate from light/dark. `stores/theme-store.ts` keeps the palette in the preferences row and sets `data-palette` on `<html>`; `public/theme-init.js` applies it before first paint. The default palette, `ledger`, sets no attribute. Each palette (`plum`, `sepia`, `graphite`) overrides only the neutral and primary tokens in `global.css`, for light and dark; the values are the ledger tokens with the OKLCH hue rotated and lightness kept, so every contrast ratio matches the default. Income, expense, secondary and destructive colors never change with the palette. `AppearancePicker` (`components/appearance-picker`) renders it as a native radio group on Settings and Profile; its swatches carry their own `data-palette`, which is why the dark selectors also match `.dark [data-palette]` descendants.

Typeface and text size follow the same per-browser pattern: `font` sets `data-font` and `textSize` sets `data-text-size` on `<html>`, both applied by `theme-init.js`, and the defaults (`ledger`, `default`) set no attribute. Tailwind `font-sans` and `font-serif` resolve to `--font-body` and `--font-display`, which each `[data-font]` block redefines: `sans` and `serif` use one Source family for both roles, `system` uses the device fonts, and `inter`, `hyperlegible` (Atkinson Hyperlegible Next), `plex` (IBM Plex Sans with Plex Serif 600 for display) and `editorial` (Inter with Newsreader for display) use extra self-hosted families. Their `woff2` files, latin and latin-ext subsets taken from the Fontsource packages, sit in `src/assets/fonts` beside one `OFL-*.txt` license per family and are declared in `fonts.css`; a browser downloads a family only when it is used, so the extra files cost nothing until someone opens the picker or chooses that option. Text size changes the root `font-size` (93.75% or 112.5%); every size and control height is in `rem`, so the whole interface scales. The same `AppearancePicker` shows the typeface and text size groups in a second section under the palettes, all three built from one `ChoiceGroup` of radio cards, and each typeface option carries its own `data-font` so it previews itself.

The desktop shell has no top bar. Notifications, language, theme and the collapse control live in the sidebar foot, and `NotificationBell` takes `placement="above"` there so its panel opens upward. Below the `md` breakpoint a compact header and a scrolling navigation strip take over. Navigation items are grouped by job with a gap between groups instead of labels. The language control shows the current language code and names the language it switches to; flags are not used because a flag stands for a country, not a language.

Tables have no surrounding box. The `Table` primitive supplies the muted header text, the ink header rule and `px-3` cells, and each table's scroll region is pulled out with `-mx-3` so cell text aligns with the page edge while row hover still has room.

## Brand assets
The mark is a single vector path, the ledger bird, kept in `frontend/scripts/brand/bird.svg`. `scripts/brand/build.mjs` reads that path, measures its bounding box in headless Chromium and writes `src/components/brand/mark-paths.ts`, which the `BrandMark` component and every static asset share. `favicon.svg` carries a `prefers-color-scheme` rule so the bird stays legible on dark browser chrome; the PNG and ICO files are screenshots of the same SVG on a navy tile, taken with the Playwright already installed for tests, and the ICO container is assembled in the script, so the generator needs no extra dependency. From `frontend/` run `node scripts/brand/build.mjs`; Storybook maps `public/favicon.svg` through `staticDirs` in `.storybook/main.ts`, so there is no second copy. If the mark changes, regenerate all of them together so the favicon, the manifest icons and the in-app logo cannot drift. Storybook uses the same favicon and a branded manager theme (`.storybook/manager.ts`, `.storybook/manager-head.html`). The manifest is covered by the existing Content-Security-Policy because `default-src 'self'` applies to `manifest-src`.

## Motion
Motion is limited to four things, all built on view transitions: changing page, table rows changing in place, a list row being added, removed or moved, and a section replacing its skeleton. Durations are 120 to 240 ms with an exponential ease-out, and nothing animates on its own.

The page change is driven by the router, not by React. TanStack Router publishes location through `useSyncExternalStore`, and React renders external-store updates synchronously even inside `startTransition`, so a React `ViewTransition` around `<Outlet />` never activates on navigation; an earlier version of this page relied on that and silently stopped animating. Instead the router is created with `defaultViewTransition` set to `pageViewTransition` from `lib/page-transition.ts`, which asks the router to wrap the commit in `document.startViewTransition` with the type `page`, and only when the pathname changed. Sorting, filtering and paging are navigations too, but they only change search params, so they return `false` and the page does not fade on every keystroke. The element around `<Outlet />` has the class `page-transition`, and `global.css` gives it `view-transition-name: page` only while `:root:active-view-transition-type(page)` matches, so it is not captured during any other transition. `::view-transition-old(page)` and `::view-transition-new(page)` give it a short fade and slide. The Storybook router in `src/storybook/decorators.tsx` uses the same option so page stories behave like the app.

Everything else uses React's `ViewTransition`, which needs the update to be a React transition. Query results arrive through an external store as well, so lists pass their data through `useDeferredValue` before rendering: the deferred render is a transition, and that is what lets a row animate. Defer the query's `data` itself and apply `?? []` afterwards; deferring a fresh array literal never settles. `RowTransition` (`components/row-transition`) wraps a list row and carries the classes `row-in`, `row-out` and `row-move`: a new row fades and drops in, a removed row fades out, and the rows below slide to their new position. `QueryBoundary` wraps its fallback and its content in boundaries with `reveal-out` and `reveal-in`, so a section cross-fades from its skeleton instead of snapping. Both content boundaries carry `update="none"` so they are captured only when they appear or disappear, never when something inside them changes. The boundary around `<Outlet />` passes `reveal={false}` because the page transition already covers it.

Each table then carries its own `ViewTransition` around its scroll container, so sorting and filtering cross-fade the rows alone; the reports results block has the same treatment. The names are per-owner (`transactions-rows`, `accounts-rows`, `users-rows`, `report-results`) so two can never claim one name.

Two rules keep those scoped transitions from spilling over the rest of the page.

`:root` is given `view-transition-name: none`. Without it the browser captures everything unnamed into a default `root` group and cross-fades it, so any one scoped transition repainted the entire page — picking a date in a column filter looked like a full reload. Opting the root out means only explicitly named elements animate and the rest of the DOM updates in place. Do not "fix" this by putting `animation: none` on `::view-transition-old(root)`: the old snapshot then sits at full opacity above the new content for the group's duration, freezing the page instead of skipping it.

The scoped boundaries carry `enter="none" exit="none"` so they are named only while their content changes in place. Without this, a table's boundary would also be captured whenever its whole section appears, animating twice.

Dialogs, popovers and select menus are Base UI components rendered through a portal, so `ViewTransition` does not capture them. They animate with the `data-open` and `data-closed` classes that shadcn ships, driven by `tw-animate-css`; Base UI keeps the element mounted until the exit animation ends, so no manual close delay is needed. `#root` sets `isolation: isolate` so portalled layers always stack above page content.

Tooltips use the Base UI `Tooltip` wrapper in `components/ui/tooltip` instead of the native `title` attribute. `Button` shows its `aria-label` as the tooltip when its size is `icon` or `icon-sm`, so an icon-only action passes `tooltip` only when the hint should differ from the label (and `tooltipSide` to move it); other elements (sort and filter header buttons, collapsed sidebar links, checkboxes, the icon picker, drill-down category links) are wrapped in `<Tooltip content={...}>`. An empty `content` renders the child untouched. Disabled controls do not receive pointer events, so their tooltip goes on a wrapping `span`. A single `TooltipProvider` in `app.tsx` shares the 400 ms open delay, so moving between adjacent actions shows the next tooltip instantly. Native `title` remains only on truncated text, where it reveals the full value.

Reduced motion is handled in two places: the `*` rule covers dialogs, popovers and menus, and a separate rule covers the view-transition pseudo-elements, which `*` does not match.
