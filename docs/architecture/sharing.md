# Sharing and households

## Shared category deletion
Any household member can rename a shared category, but only its owner can delete it. Deletion clears the category from every member's transactions, split lines and bills and soft-deletes its budgets, bypassing visibility filters so no dangling references remain. A shared tag follows the same rule: a member renames, the owner deletes, and deleting removes the `TransactionTags` rows outright and soft-deletes the tag inside one database transaction, leaving the transactions themselves untouched.

## Shareable records
Accounts, categories, tags, budgets, goals, recurring entries, assets and debts implement `IShareable` and share one set of rules in `Common/Sharing`. Their create and update requests implement `IShareableInput`; the validator rule `RequiresHouseholdWhenShared(noun)` answers `household.required` when a shared record has no household, and the mappers copy scope and household with `ApplySharing`, which drops the household of a personal record; `SharingState.From(input)` computes the same state from the request without touching an entity. Services check before they apply: a create passes the request to `ISharingGuard.CheckAsync(input)`, an update passes the loaded record and the request to `CheckAsync(existing, input)`, and the guard compares the record's current sharing with the requested one. It refuses a household the caller is not a member of, or one that has been deleted and so is only kept for the trash (`household.notMember`) and a change of scope or household by anyone but the owner (`access.forbidden`). A shared record that points at other records also passes them to `ISharingGuard.CheckReferencesAsync(input, SharedReferences)`, which answers `household.referenceNotShared` unless every account, category, tag and debt it names is shared with the same household. `ShareableSet.All` lists every shareable entity set once; deleting a household, removing a member and restoring a household from the trash iterate it, so a new shareable entity is one line there plus its `DeletionChangeKind`, and `ShareableSetTests` fails when an `IShareable` type is missing from it.

## Records that follow their parent
`DebtPayment` has a branch of its own in `AppDbContext.OwnerFilter`, like the attachment filter: a link is visible when `Debts.Any(d => d.Id == p.DebtId)`, so it follows the debt's owner, sharing and active household rather than who linked it, and a link of a deleted debt disappears with the debt. The one query that must see such links, the clean-up of links of deleted debts when a transaction is linked again, drops the owner filter with `IgnoreQueryFilters(QueryFilters.OwnerOnly)`, which drops it for the debts in its subquery as well and keeps the soft delete, so it removes only links whose debt is deleted, whoever made them. `AssetValuation` needs nothing: it is not an `EntityBase`, has no filter and is only reached through its asset. The audit collector reports both on their parent: the Shareable pass also takes the asset or debt of every `AssetValuation` or `DebtPayment` row added, changed or removed in the save, loading it when the save did not, and adds a `valuations` or `payments` change that lists the rows before and after.

## Household-scoped records
Split expenses and settle-up payments belong to a household rather than to an account, so they cannot use the shareable filter (which also lets the owner see a personal row) or the account filter (a split may sit on a personal account the others must not see). They implement `IHouseholdScoped` (`Domain/Households`), and `AppDbContext.OwnerFilter` gives them a branch of their own, checked before the ownable one: a row is visible when `Households.Any(h => h.Id == row.HouseholdId)`, which through the household's own filter means a current, not removed membership of the caller in a household that is not deleted, and, while a household is active, only when it is that household. The filter is named `Owner` like the others, so `IgnoreQueryFilters(QueryFilters.OwnerOnly)` drops it and keeps the soft delete; the settle-up service uses that only to ask whether a split is taken already, and reads the deleted flag of a split's transaction the same way so that nothing else of a personal transaction reaches another member. Who may change a row is the service's rule, not the filter's: the payer for a split, either party for a payment. Endpoints that take a household id in the route also answer 404 while another household is active, as the activity log does. See [Household settle-up](../features/household-settle-up.md).

## Removing a household member
Removing a member resets that member's own shared records in the household (every set of `ShareableSet.All`) to personal, in the same transaction that deletes the membership, exactly as deleting the household does for everyone's records (`HouseholdService.MakePersonalAsync`, which walks `ShareableSet.All`). Without it the remaining members would keep reading, and editing, records of someone who can no longer see the household. The removed member keeps the records; what other members entered on such an account stays on it and disappears from their view, which is the same outcome as the owner re-scoping the account. Split expenses and payments are not touched: they stay in the household, the removed member stops seeing them through the household-scoped filter, and the remaining members keep that member's open balance. `AddMember` and `UpdateMemberRole` validate the email and the role, and `role` is `[JsonRequired]` because a missing enum would otherwise bind as its first value, `owner`.
