# Background work and notifications

## Background work
Bills are checked immediately at startup and every 15 minutes. Notifications deduplicate per bill/local day under a database lock. Unconfirmed bills retain their due date and can remind again the next day. Budgets are checked immediately at startup and hourly by `BudgetAlertJob`, which asks `BudgetUsageCalculator` — the calculator the budgets endpoints use, never a second spending path — for each budget's current window and raises one notification at 80% and one at 100% of the effective limit. It iterates active users in id order with a per-user `AppDbContext`, because that calculator reads through the ownership query filter, and each user sits in its own try block. Deduplication is per budget, window and threshold: the read of what was already raised and the insert happen in one transaction holding `AppLock.BudgetAlerts`, so restarts and concurrent passes cannot double up, and spending that dips back below a threshold inside one window does not re-arm it.
Net worth refreshes immediately and hourly for active users; each user is handled in its own try block, so one user whose snapshot fails is logged with the user id and the rest still get theirs, the same way `BrokerSyncJob` isolates connections. The per-user work sits behind `INetWorthSnapshotter` (`NetWorthSnapshotter`, a singleton that opens a scope and a per-user `AppDbContext` for each call), which the job receives through its constructor and calls for users in id order. That interface is the seam the isolation test uses: it wraps the real snapshotter in one that throws for the user with the lowest id, so every other user is processed after the failure, and the test fails when the try block is removed. Exchange rates sync at startup and every six hours. Missed historical observations are not fabricated. No job talks to a mail server except `EmailOutboxJob`, and none talks to Discord except `DiscordOutboxJob`, described under Notification fan-out and Discord below.
`EmailOutboxJob`: every minute it claims up to twenty due rows of `EmailMessages` in one short transaction holding `AppLock.EmailOutbox`, counting the attempt and setting the next attempt time before any socket is opened, then sends each one in its own try block with a twenty-second cap, retries a failure at 4, 16, 64 and 240 minutes, gives up after five attempts and deletes sent and given-up rows after a week. It returns immediately when the mail server is switched off or incomplete. Every producer hands its notifications to `INotificationPublisher`, which enqueues the email for the kinds the owner ticked and writes it with the notification inside the job's transaction and under the same lock, so the two can never disagree and no request or scan ever waits for SMTP; see [Email](../features/email.md). `GET /api/networth` and the hourly job share `GetCurrentAsync`. The snapshot columns are numeric(18,2), and assets or debts that are each within range can add up beyond it; writing that snapshot used to fail the request with a 500.
The totals are now compared with the column range first and the snapshot is skipped when any of them does not fit, so the response still carries the true totals as decimal strings and the history gets no point for that day, the same outcome as a missing exchange rate.

`UnusualAmountJob` runs immediately and every 15 minutes while `UnusualAmounts` is on. In one transaction holding `AppLock.UnusualAmounts` it pages the expenses whose `UnusualCheckedAt` is null, 500 at a time and at most 40 pages a pass, evaluates each account owner's rows through `UnusualAmountService` on a per-owner `AppDbContext` (one bounded history query per batch, grouped in memory), and writes the verdicts with `ExecuteUpdate`, so a check never moves `UpdatedAt`, never reaches the audit collector and never asks for a check of its own. The backfill is silent: a pass where nothing was ever checked notifies nobody, and later passes notify only rows written after the earliest check that are newly flagged, not dismissed and dated within 45 days, one summary when an owner has more than three, and, while `RecurringBills` is on, bank charges that cost more than the recurring entry they match. Notifications go through `INotificationPublisher` inside the job's transaction like the other producers. The rule's constants live in the pure `UnusualAmountRule` and `PriceRiseRule`; see [Unusual amounts](../features/unusual-amounts.md).

`MonthCloseReminderJob` runs immediately and hourly while `MonthClose` is on, but does nothing unless today, in the installation time zone, is day 1 to 5 of a month (`LastReminderDay`). On those days it opens a transaction, takes `AppLock.MonthCloseReminders` and, in one query, picks the active users who have closed at least one month under any scope, have not closed the previous month under any scope, and have no `MonthReadyToClose` notification for that month yet, deleted ones included. The month is the notification's `Message` (`yyyy-MM`) and its payload's `Month`, so the deduplication is per user and month rather than per day, and a user who reads or clears the reminder is not reminded again. It preloads those users and publishes one notification each through `INotificationPublisher`, so the reminder reaches Discord like the other kinds. Having closed a month once is the opt-in: nobody who never used the page is reminded. See [Month-end close](../features/month-end-close.md).

Month-end drift depends on `UpdatedAt`: a close counts a row as changed when its `UpdatedAt` is later than the close. The change tracker stamps it on every tracked edit, soft delete and restore, and every set-based write that rewrites transactions stamps it too: the category delete's clearing of `CategoryId`, a categorization rule run, the trash's category restore, and a reporting-currency change, which stamps only the rows whose `ReportingAmount` it actually rewrites. Writes that change neither the figures nor the month of a row deliberately leave it alone: the unusual-amount verdict and its dismissal, tags (`BulkTagAsync` and a tag delete only touch `TransactionTags`) and attachments.

The reminder job deduplicates per local day, so it needs the instant at which today began in the installation's time zone. That is `IClock.StartOfDay`, the only place that turns a local date into an instant. `TimeZoneInfo.ConvertTimeToUtc` throws for a local time that does not exist, and in zones that start daylight saving at midnight (America/Santiago, America/Havana, Asia/Beirut) midnight itself is skipped once a year, which stopped the scan for that whole day. `StartOfDay` tries the offsets in force twelve hours before and after local midnight and returns the earliest resulting instant that falls on the requested date: the transition instant when midnight is skipped, the first of the two midnights when it repeats.

## Running a service as a member
Most jobs that need one user's view build it by hand: `AppDbContext.For(services, userId)` gives a context whose query filters are that user's, and `BudgetAlertJob`, `UnusualAmountJob` and `NetWorthSnapshotter` compose the few services they need around it with `ActivatorUtilities`. That stops working for a service with a deep graph: `MonthCloseService` takes ten dependencies, each with its own, and composing them in a job would copy the DI graph and drift from it the first time a constructor changed. `MonthlyDigestJob` therefore resolves the real service in a scope that belongs to the member.

`JobUser` (`Infrastructure/Auth`) is a scoped holder with one property, `FixedUser? User`. `ICurrentUser` is registered as a scoped factory, `JobUser.User ?? HttpCurrentUser`, with `HttpCurrentUser` registered as itself. In a request nothing sets `JobUser.User`, so every request resolves `HttpCurrentUser` exactly as before and request authentication is unchanged. `PeriodicJob.RunAsUserAsync(userId, work)` opens a new scope, sets `JobUser.User = new FixedUser(userId)` before anything else is resolved from it, runs `work` with that scope's provider and logs and swallows a failure with the job name and the user id, like `ForEachActiveUserAsync`. Everything resolved in that scope, the `AppDbContext`, the services and the `INotificationPublisher`, sees the member's ownership filters. `FixedUser` has no active household, so the scope is always "Everything". The existing jobs keep their hand-built contexts; an integration test runs a probe job that resolves `ICurrentUser` inside and outside the member's scope.

## Notification fan-out and Discord
Every notification is written through `INotificationPublisher` (`Common/Notifications`). A producer preloads the owners it is about to notify with `PreloadAsync(userIds)`, which reads their enabled Discord webhooks and today's queued Discord dedupe keys, and their emailed kinds and today's queued email keys, then calls `Publish(notification)` for each. The preload skips deactivated owners and, for email, unconfirmed addresses, so nothing they are notified about leaves the application. The publisher adds the `Notification`, a `DiscordMessages` row when `DiscordEnabled` is on and the owner's webhook takes that kind, and an `EmailMessages` row through `IEmailOutbox` when the owner ticked that kind for email and the mail server is on, all to the caller's `AppDbContext`, so the producer's transaction and advisory lock cover every channel. Publishing for an owner who was not preloaded throws `InvalidOperationException`. `NotificationPublisher.For(services, db)` binds a publisher and its email outbox to a per-user context, which is what `BudgetAlertJob` uses. No producer enqueues mail itself.
`NotificationPublisherTests` is an architecture test in the style of the others: it scans the `JxFinance.Api` sources and fails when anything outside `Common/Notifications/NotificationPublisher.cs` calls `Notifications.Add` or `AddRange`, so a new producer cannot bypass the other channels. `DiscordOutboxJob` drains the Discord rows every 30 seconds the way `EmailOutboxJob` drains mail: a claim of up to 50 due rows, at most five per user, under `AppLock.DiscordOutbox` in a transaction that counts the attempt and commits before any socket opens, then one post at a time per user in `CreatedAt` order. A 429 gives the attempt back and waits Discord's `retry_after`, a 401, 403 or 404 gives up the user's pending rows and marks the webhook `DisabledByDiscordAt`, and everything else backs off `min(4^attempts, 240)` minutes for five attempts; rows older than a week are deleted whether they were sent or not.
The publisher was chosen over a change-tracker hook like the audit collector because an explicit call is visible at the call site and testable on its own; see the [Discord notification decisions](../decisions/discord-notifications.md).

The Discord webhook URL is typed by a user and posted to by the server, so it is treated as a request-forgery risk as well as a secret. `DiscordWebhookUrl.TryParse` is an allowlist, not a blocklist: `https` on the default port, a DNS host that is exactly `discord.com`, `discordapp.com`, `ptb.discord.com` or `canary.discord.com` (so no IP literal and no look-alike suffix), no user info, none of `?`, `#`, `\`, `@` or a space anywhere, the path exactly `/api/webhooks/{1–20 digits}/{1–100 of [A-Za-z0-9_-]}`, and at most 500 characters. It answers a `DiscordTarget(Id, Token)`, and `DiscordWebhookClient` builds `api/webhooks/{id}/{token}` from those two parts against its fixed base address, `https://discord.com/`; the typed string is validated and stored, never requested. The client's timeout is 10 seconds and it reads at most 64 KB of a response. The URL is protected with Data Protection purpose `JxFinance.Discord.Webhook` and no response carries it.

Every post sends `allowed_mentions: { "parse": [] }`, so `@everyone`, `@here`, a role or a user id inside a category, bill or payee name renders as text and pings nobody, and `DiscordText.Escape` backslash-escapes Discord's markdown characters and flattens line breaks and tabs, so a name cannot restyle or break the message. Link previews are suppressed by putting the page link in angle brackets.

The token must not reach a log or a trace. The typed client is registered with `.RemoveAllLoggers()`, like `FlexClient`, so `HttpClientFactory` writes no request line. The OpenTelemetry HTTP client instrumentation would still record the full URL on its span, so `TelemetryExtensions` enriches every outgoing request whose host ends in `discord.com`: `url.full` becomes `https://{host}/api/webhooks/***` and `url.path` and `url.query` are dropped. `RedactedDiscordUrl` is unit tested, and the records that carry the URL or the token print `***` as described under Authentication.

## Recurring entry schedule
An entry stores `AnchorDay`, the day of month the user picked. Monthly, quarterly and yearly advances clamp the anchor to the length of the target month, so an entry on the 31st lands on 28 February and returns to 31 March. The anchor is reset only when an update changes `NextDueDate`. Weekly entries ignore it.

`RecurringBillService` is the one service that calls another tag's service: confirming a `Transfer`-shaped entry builds a `CreateTransferRequest` and hands it to `ITransferService.CreateAsync` rather than adding a `Transfer` row itself. That path owns the cross-currency rules — resolving each account's currency, demanding `receivedAmount` when the two differ, refusing a mismatched pair in one currency, refusing a disabled currency — and a second writer would have to repeat them and would drift. Both services resolve the same request-scoped `AppDbContext`, so the nested `SaveChangesAsync` joins the transaction the confirmation opened and commits with the schedule advance and the read reminders, under the same per-entry advisory lock.
