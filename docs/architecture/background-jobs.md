# Background work and notifications

## Background work
Bills are checked immediately at startup and every 15 minutes. Notifications deduplicate per bill/local day under a database lock. Unconfirmed bills retain their due date and can remind again the next day. Budgets are checked immediately at startup and hourly by `BudgetAlertJob`, which asks `BudgetUsageCalculator` — the calculator the budgets endpoints use, never a second spending path — for each budget's current window and raises one notification at 80% and one at 100% of the effective limit. It iterates active users in id order with a per-user `AppDbContext`, because that calculator reads through the ownership query filter, and each user sits in its own try block. Deduplication is per budget, window and threshold: the read of what was already raised and the insert happen in one transaction holding `AppLock.BudgetAlerts`, so restarts and concurrent passes cannot double up, and spending that dips back below a threshold inside one window does not re-arm it.
Net worth refreshes immediately and hourly for active users; each user is handled in its own try block, so one user whose snapshot fails is logged with the user id and the rest still get theirs, the same way `BrokerSyncJob` isolates connections. The per-user work sits behind `INetWorthSnapshotter` (`NetWorthSnapshotter`, a singleton that opens a scope and a per-user `AppDbContext` for each call), which the job receives through its constructor and calls for users in id order. That interface is the seam the isolation test uses: it wraps the real snapshotter in one that throws for the user with the lowest id, so every other user is processed after the failure, and the test fails when the try block is removed. Exchange rates sync at startup and every six hours. Missed historical observations are not fabricated.
No job talks to a mail server except `EmailOutboxJob`, which is the sixth job: every minute it claims up to twenty due rows of `EmailMessages` in one short transaction holding `AppLock.EmailOutbox`, counting the attempt and setting the next attempt time before any socket is opened, then sends each one in its own try block with a twenty-second cap, retries a failure at 4, 16, 64 and 240 minutes, gives up after five attempts and deletes sent and given-up rows after a week. It returns immediately when the mail server is switched off or incomplete. The reminder job writes an email row beside the notification inside the same transaction and under the same lock, so the two can never disagree and no request or scan ever waits for SMTP; see [Email](../features/email.md). `GET /api/networth` and the hourly job share `GetCurrentAsync`.
The snapshot columns are numeric(18,2), and assets or debts that are each within range can add up beyond it; writing that snapshot used to fail the request with a 500. The totals are now compared with the column range first and the snapshot is skipped when any of them does not fit, so the response still carries the true totals as decimal strings and the history gets no point for that day, the same outcome as a missing exchange rate.

The reminder job deduplicates per local day, so it needs the instant at which today began in the installation's time zone. That is `IClock.StartOfDay`, the only place that turns a local date into an instant. `TimeZoneInfo.ConvertTimeToUtc` throws for a local time that does not exist, and in zones that start daylight saving at midnight (America/Santiago, America/Havana, Asia/Beirut) midnight itself is skipped once a year, which stopped the scan for that whole day. `StartOfDay` tries the offsets in force twelve hours before and after local midnight and returns the earliest resulting instant that falls on the requested date: the transition instant when midnight is skipped, the first of the two midnights when it repeats.

## Recurring entry schedule
An entry stores `AnchorDay`, the day of month the user picked. Monthly, quarterly and yearly advances clamp the anchor to the length of the target month, so an entry on the 31st lands on 28 February and returns to 31 March. The anchor is reset only when an update changes `NextDueDate`. Weekly entries ignore it.

`RecurringBillService` is the one service that calls another tag's service: confirming a `Transfer`-shaped entry builds a `CreateTransferRequest` and hands it to `ITransferService.CreateAsync` rather than adding a `Transfer` row itself. That path owns the cross-currency rules — resolving each account's currency, demanding `receivedAmount` when the two differ, refusing a mismatched pair in one currency, refusing a disabled currency — and a second writer would have to repeat them and would drift. Both services resolve the same request-scoped `AppDbContext`, so the nested `SaveChangesAsync` joins the transaction the confirmation opened and commits with the schedule advance and the read reminders, under the same per-entry advisory lock.
