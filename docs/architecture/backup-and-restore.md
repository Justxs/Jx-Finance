# Backup and restore

Everything under `/api/backups` is administrator-only and lives in `Endpoints/Backups`: list, take (`POST /api/backups`), upload a downloaded file, change the note, download, restore and delete. Nothing is scheduled and nothing is copied offsite; a backup that lives only next to the database is lost with it, so the page tells the administrator to download copies.

Storage is a directory, `App:BackupDirectory` (`/backups` on the `backups` volume in Compose, `.local/backups` in development, ignored by git). The development value comes from `scripts/dev-env.ps1`, which `scripts/dev.ps1` and `scripts/with-dev-database.ps1` apply to their process and which fills the `.local/api-debug.env` that `just setup` writes for the VS Code debugger; an API started any other way still falls back to `backups` under its content root, `backend/JxFinance.Api/backups`, which git and `.dockerignore` both exclude. `.local` is outside the Docker build context and outside git, but it is still inside the checkout: when the checkout lives in a cloud-synced folder, development backups are uploaded with it, so keep real data out of the development database or point `App__BackupDirectory` elsewhere.
`BackupStore` keeps two files per backup, named after its id: the data, `<id>.zip` for an archive or `<id>.json.gz` for a backup from before attachments, told apart by their first bytes, and `<id>.info.json` with the date, note, migration, table, row and attachment counts and whether it was uploaded. The size is read from the file. The list is deliberately not a database table: a restore replaces every table, so a table of backups would be replaced by the one inside the backup and no longer match the files. A backup is written to `<id>.tmp` and renamed when complete, so a crash leaves no half-written entry; a data file without its info file is not listed. When writing the info file fails after the rename, `AddAsync` deletes the data file again before rethrowing.
What a crash can still leave behind, a `.tmp` file or a data file without info, is removed by `RemoveOrphans`, which runs on every listing and only touches files last written more than an hour ago, so a backup that another request is still writing is never swept.

The file is a zip archive (`BackupArchive`). Its `backup.json` entry is the JSON document: `format`, `version`, `createdAt`, `migration` (the last applied EF migration) and one entry per table with its column names and rows. Every other entry is `attachments/<id>`, the file of one attachment row, stored uncompressed; a backup from before attachments is that JSON gzip-compressed on its own, and is still read. How the files are checked and written back is in [Attachments](../features/attachments.md). `BackupService` works on tables, not entities. The table list, column store types and foreign key names come from the EF relational model, every value is read as `column::text` and written back with `CAST($n AS <store type>)`. PostgreSQL's text form round-trips every type exactly, so strongly-typed ids, `Money` complex properties, soft-deleted rows, query filters and the `NextDueDate` concurrency token need no special handling, and a new entity is covered without touching the service. Taking a backup runs in one `REPEATABLE READ` transaction, so the file is a single snapshot.

What the file holds: every table of the model, including users with password hashes and two-factor secrets, households, settings and exchange rates. Treat it, and the backup directory, as a secret. The transient tables `UserSessions`, `EmailMessages` and `DiscordMessages` are left out. Broker tokens, the SMTP password, Discord webhook URLs and the Anthropic API key of receipt reading are in the file but stay encrypted with the key directory (`App:DataProtectionDirectory`) of the installation that wrote them; on another installation they answer `broker.tokenRequired`, `email.passwordUnreadable`, `discord.webhookUnreadable` and `receipt.keyUnreadable` until they are entered again. The receipt tables `ReceiptReadings`, `ReceiptItemCategories` and `ReceiptReadingUsages` are ordinary exported tables and need no restore step: a reading follows the restored attachment rows by the file hash.

Reading a backup never holds the document in memory. `BackupReader` walks the JSON with `Utf8JsonReader` over a 64 KB buffer that grows only for a single value larger than that (16 MB at most) and hands an `IBackupVisitor` the header, each table's name and columns, and one row at a time. It is strict because the format is our own: `format`, `version`, `createdAt` and `migration` must come before `tables`, a table must give `name` and `columns` before `rows`, a cell is a string or null, and any other property or shape is `backup.invalidFile`. Upload uses a visitor that only counts (`BackupInspector`); restore uses one that inserts (`BackupRestorer`, which owns the restore transaction). Both sit beside `BackupReader` in `Endpoints/Backups/Services`, and `BackupDatabase` in the same folder holds the PostgreSQL plumbing they share with `BackupService`: the table shapes read from the EF model, identifier quoting, deferring and restoring foreign keys, and resetting sequences. The decompressed stream is wrapped in `LimitedReadStream`, which fails with `backup.tooLarge` once more than `App:BackupMaxDecompressedBytes` (default 1 GiB) has been read, at upload and at restore, so a small gzip file cannot expand without bound.

Upload only stores a file: it checks `format` and `version`, checks that every other entry of an archive is an attachment of at most 10 MB, compresses plain JSON, and lists the backup under the date it was taken. A backup whose `migration` differs from the running application is listed with `restorable: false`; it can be downloaded but a restore answers `backup.schemaMismatch`. To restore an older backup, run the application version that wrote it, upload, restore, then upgrade; startup migrates the data forward. Moving to a fresh installation needs the first-run setup first, because only a signed-in administrator can upload and restore; that administrator is replaced by the users of the backup.

Restore asks for the administrator's current password in the request body (`{ "password": "…" }`) and verifies it before anything else. A wrong password answers 400 `password.incorrect`, not 401, because the frontend client answers a 401 with a refresh and a retry, which would count every typing mistake twice; it counts toward the failed-attempt lockout described under Authentication, and a locked account answers 429 `credentials.lockedOut`. Restore is throttled to 5 calls per five minutes per client, taking and uploading a backup to 10 each.

Restore replaces everything in one transaction: the foreign keys are switched to `DEFERRABLE INITIALLY DEFERRED` so table order, self-references and cycles do not matter, every table of the model is truncated, rows are inserted in batches of 500, `SET CONSTRAINTS ALL IMMEDIATE` checks the foreign keys, the constraints go back to `NOT DEFERRABLE` and identity sequences are moved past the restored ids. `TRUNCATE` holds an exclusive lock until commit, so other requests wait rather than see a half-restored database. The transaction opens once the header of the file has been read and accepted, so the table names, columns and row lengths are checked while rows stream in; any mismatch rolls the truncation back like every other failure. A value or a reference the database rejects (SQLSTATE class 22 or 23) rolls everything back and answers `backup.invalidFile`. The transaction sets `lock_timeout` to `App:BackupLockTimeoutSeconds` (default 15), so a restore that cannot get its locks gives up instead of hanging; that timeout (55P03), a deadlock (40P01) and a serialization failure (40001) roll back and answer 409 `conflict.busy`, which means nothing changed and the same request can be sent again. Afterwards the cached instance settings are reloaded. The stored backups are untouched, so a wrong restore can be undone by restoring another one; taking a backup first is the administrator's call, the application does not do it silently.

On the client the confirmation is `RestoreBackupDialog`: an alert dialog whose body is a `useAppForm` form with the typed confirmation word and the administrator's current password, submitted through `submitToServer`, so a `required` error on `password` lands on the input and every other failure shows in the dialog's `FormError` while the dialog stays open. After `password.incorrect` the password field is cleared; `credentials.lockedOut` (429) and `conflict.busy` (409) show their `serverErrors` text and leave the form ready to retry. A rate-limited 429 carries no body at all: `customFetch` turns any failed response into an `ApiError` even when the body is empty or not the JSON its content type promised, and `errorMessage` in `src/lib/query-client.ts` gives a 429 without a code the text `errors.tooManyRequests`, which covers login, two-factor, the profile password and the backup endpoints alike.

Sessions: all session rows are gone after a restore and the caller's cookies are cleared, so the client clears its cache and goes to the sign-in page. Other signed-in users are refused on their next request, because every request checks its session row, and their refresh fails too.

Limits: an upload is at most 2 GB of file (`UploadBackupEndpoint.MaxFileBytes`, with the multipart form limit raised to match; every other endpoint keeps Kestrel's 30 MB default), the `backup.json` of any backup at most `App:BackupMaxDecompressedBytes` once decompressed, and each attached file at most 10 MB; memory use during upload and restore is one read buffer plus one batch of 500 rows. There is no retention rule; backups stay until an administrator deletes them.
