# Backup and restore

Everything under `/api/backups` is administrator-only and lives in `Endpoints/Backups`: list, take (`POST /api/backups`), upload a downloaded file, change the note, download, restore and delete. Nothing is scheduled and nothing is copied offsite; a backup that lives only next to the database is lost with it, so the page tells the administrator to download copies.

Storage is a directory, `App:BackupDirectory` (`/backups` on the `backups` volume in Compose, `.local/backups` in development, ignored by git). The development value comes from `scripts/dev-env.ps1`, which `scripts/dev.ps1` and `scripts/with-dev-database.ps1` apply to their process and which fills the `.local/api-debug.env` that `just setup` writes for the VS Code debugger; an API started any other way still falls back to `backups` under its content root, `backend/JxFinance.Api/backups`, which git and `.dockerignore` both exclude. `.local` is outside the Docker build context and outside git, but it is still inside the checkout: when the checkout lives in a cloud-synced folder, development backups are uploaded with it, so keep real data out of the development database or point `App__BackupDirectory` elsewhere.
`BackupStore` keeps two files per backup, named after its id: the data, `<id>.zip` for an archive or `<id>.json.gz` for a backup from before attachments, told apart by their first bytes, and `<id>.info.json` with the date, note, migration, table, row and attachment counts and whether it was uploaded. The size is read from the file. The list is deliberately not a database table: a restore replaces every table, so a table of backups would be replaced by the one inside the backup and no longer match the files. A backup is written to `<id>.tmp` and renamed when complete, so a crash leaves no half-written entry; a data file without its info file is not listed. When writing the info file fails after the rename, `AddAsync` deletes the data file again before rethrowing.
What a crash can still leave behind, a `.tmp` file or a data file without info, is removed by `RemoveOrphans`, which runs on every listing and only touches files last written more than an hour ago, so a backup that another request is still writing is never swept.

The file is a zip archive (`BackupArchive`). Its `backup.json` entry is the JSON document: `format`, `version`, `createdAt`, `migration` (the last applied EF migration) and one entry per table with its column names and rows. Every other entry is `attachments/<id>`, the file of one attachment row, stored uncompressed; a backup from before attachments is that JSON gzip-compressed on its own, and is still read. How the files are checked and written back is in [Attachments](../features/attachments.md). `BackupService` works on tables, not entities. The table list, column store types and foreign key names come from the EF relational model, every value is read as `column::text` and written back with `CAST($n AS <store type>)`. PostgreSQL's text form round-trips every type exactly, so strongly-typed ids, `Money` complex properties, soft-deleted rows, query filters and the `NextDueDate` concurrency token need no special handling, and a new entity is covered without touching the service. Taking a backup runs in one `REPEATABLE READ` transaction, so the file is a single snapshot.

What the file holds: every table of the model, including users with password hashes and two-factor secrets, households, settings and exchange rates. Treat it, and the backup directory, as a secret.
The transient tables `UserSessions`, `PersonalApiTokens` (since 2026-10-01), `ApiIdempotencyKeys`, `EmailMessages`, `DiscordMessages` and `ImportInboxFiles` (since 2026-10-01, the statements waiting in the [import inbox](../features/bank-statement-import.md#import-inbox), copies of files its folder keeps) are left out. `BackupRestorer` truncates them like every table and skips the rows of any of them that a file still holds, so a backup taken while tokens travelled restores without bringing a revoked token back. Broker tokens, the SMTP password, the EODHD API key of the market prices (`InstanceSettings.EodhdProtectedKey`, since 2026-09-30) and the installation's Discord webhook URL (`InstanceSettings.DiscordProtectedUrl`, since 2026-10-03) are in the file but stay encrypted with the key directory (`App:DataProtectionDirectory`) of the installation that wrote them; on another installation they answer `broker.tokenRequired`, `email.passwordUnreadable`, `marketPrices.keyUnreadable` and `discord.webhookUnreadable` until they are entered again. The day's EODHD call counter and each security's last fetch result travel with their rows. The receipt tables `ReceiptReadings` and `ReceiptItemCategories` are ordinary exported tables and need no restore step: a reading follows the restored attachment rows by the file hash. The settle-up tables `SharedExpenses`, `SharedExpenseShares` and `Settlements` are ordinary exported tables with no restore step, since their foreign keys are deferred like every other. `AspNetUserPasskeys`, the passkeys since 2026-09-29, is an ordinary exported table too; its credential data is a `jsonb` column. A restored passkey signs in again only under the same relying party id, so a backup moved to an installation with another `SITE_ADDRESS` brings back passkeys that no authenticator will offer (see [Passkeys](../features/passkeys.md#relying-party-and-https)).

Reading a backup never holds the document in memory. `BackupReader` walks the JSON with `Utf8JsonReader` over a 64 KB buffer that grows only for a single value larger than that (16 MB at most) and hands an `IBackupVisitor` the header, each table's name and columns, and one row at a time. It is strict because the format is our own: `format`, `version`, `createdAt` and `migration` must come before `tables`, a table must give `name` and `columns` before `rows`, a cell is a string or null, and any other property or shape is `backup.invalidFile`. Upload uses a visitor that only counts (`BackupInspector`); restore uses one that inserts (`BackupRestorer`, which owns the restore transaction). Both sit beside `BackupReader` in `Endpoints/Backups/Services`, and `BackupDatabase` in the same folder holds the PostgreSQL plumbing they share with `BackupService`: the table shapes read from the EF model, the table writer the member export shares, identifier quoting, deferring and restoring foreign keys, and resetting sequences. The decompressed stream is wrapped in `LimitedReadStream`, which fails with `backup.tooLarge` once more than `App:BackupMaxDecompressedBytes` (default 1 GiB) has been read, at upload and at restore, so a small gzip file cannot expand without bound.

Upload only stores a file: it checks `format` and `version`, checks that every other entry of an archive is an attachment of at most 10 MB, compresses plain JSON, and lists the backup under the date it was taken. A backup whose `migration` differs from the running application is listed with `restorable: false`; it can be downloaded but a restore answers `backup.schemaMismatch`. To restore an older backup, run the application version that wrote it, upload, restore, then upgrade; startup migrates the data forward. Moving to a fresh installation needs the first-run setup first, because only a signed-in administrator can upload and restore; that administrator is replaced by the users of the backup.

Restore asks for the administrator's current password in the request body (`{ "password": "…" }`) and verifies it before anything else. A wrong password answers 400 `password.incorrect`, not 401, because the frontend client answers a 401 with a refresh and a retry, which would count every typing mistake twice; it counts toward the failed-attempt lockout described under Authentication, and a locked account answers 429 `credentials.lockedOut`. Restore is throttled to 5 calls per five minutes per client, taking and uploading a backup to 10 each.

Restore replaces everything in one transaction: the foreign keys are switched to `DEFERRABLE INITIALLY DEFERRED` so table order, self-references and cycles do not matter, every table of the model is truncated, rows are inserted in batches of 500, `SET CONSTRAINTS ALL IMMEDIATE` checks the foreign keys, the constraints go back to `NOT DEFERRABLE` and identity sequences are moved past the restored ids. `TRUNCATE` holds an exclusive lock until commit, so other requests wait rather than see a half-restored database. The transaction opens once the header of the file has been read and accepted, so the table names, columns and row lengths are checked while rows stream in; any mismatch rolls the truncation back like every other failure. A value or a reference the database rejects (SQLSTATE class 22 or 23) rolls everything back and answers `backup.invalidFile`. The transaction sets `lock_timeout` to `App:BackupLockTimeoutSeconds` (default 15), so a restore that cannot get its locks gives up instead of hanging; that timeout (55P03), a deadlock (40P01) and a serialization failure (40001) roll back and answer 409 `conflict.busy`, which means nothing changed and the same request can be sent again. Afterwards the cached instance settings are reloaded. The stored backups are untouched, so a wrong restore can be undone by restoring another one; taking a backup first is the administrator's call, the application does not do it silently.

On the client the confirmation is `RestoreBackupDialog`: an alert dialog whose body is a `useAppForm` form with the typed confirmation word and the administrator's current password, submitted through `submitToServer`, so a `required` error on `password` lands on the input and every other failure shows in the dialog's `FormError` while the dialog stays open. After `password.incorrect` the password field is cleared; `credentials.lockedOut` (429) and `conflict.busy` (409) show their `serverErrors` text and leave the form ready to retry. A rate-limited 429 carries no body at all: `customFetch` turns any failed response into an `ApiError` even when the body is empty or not the JSON its content type promised, and `errorMessage` in `src/lib/query-client.ts` gives a 429 without a code the text `errors.tooManyRequests`, which covers login, two-factor, the profile password and the backup endpoints alike.

Sessions: all session rows are gone after a restore and the caller's cookies are cleared, so the client clears its cache and goes to the sign-in page. Other signed-in users are refused on their next request, because every request checks its session row, and their refresh fails too. Every personal API token ends the same way: its row is gone, so its next request answers 401 `token.invalid` and its member creates a new one.

Limits: an upload is at most 2 GB of file (`UploadBackupEndpoint.MaxFileBytes`, with the multipart form limit raised to match; every other endpoint keeps Kestrel's 30 MB default), the `backup.json` of any backup at most `App:BackupMaxDecompressedBytes` once decompressed, and each attached file at most 10 MB; memory use during upload and restore is one read buffer plus one batch of 500 rows. There is no retention rule; backups stay until an administrator deletes them.

## The member export

The [data export per user](../features/data-export-per-user.md) reuses the table format and the row writer. `BackupDatabase.WriteTableAsync` writes one table object (`name`, `columns`, `rows` of `column::text`) and takes an optional condition with its parameters and a table shape whose columns may be a subset; the backup calls it with neither, so its output is what it was, and `UserExportService` calls it with the condition and allowed columns of `UserExportTables` and the member's id as `$1`. The export writes `format` `jx-finance-user-export` and adds two header properties before `tables`, `userId` and `missingAttachments`; `BackupReader` accepts both and skips them, since a visitor has no use for them, and every other unknown property is still `backup.invalidFile`. An upload of an export as a backup is refused by `EnsureSupported`, because its `format` is not `jx-finance-backup`. After the CSVs and before the commit, the export writes `ledger.beancount`: `UserJournalSource` reads its rows in the same transaction, and `BeancountWriter` builds the whole text in memory, since lot replay, debt tracking and name collisions need every row, and hands it to the entry in one asynchronous write. See [the double-entry journal](../features/data-export-per-user.md#double-entry-journal).

The import is a third visitor, `MemberImport` in `Users/Services`. It opens the transaction when the header arrives, defers every foreign key as the restore does, and inserts the rows of the tables it imports with the same `CAST($n AS type)` batches, rewriting on the way every column whose foreign key points at `AspNetUsers` to the member, every column pointing at `Households` to null and `Scope` to personal; the columns come from the EF relational model, so a new owner column needs no change here. Securities are inserted with `ON CONFLICT DO NOTHING`, and investment entries and allocation targets by security that pointed at a skipped one are moved to the existing security with the same symbol and currency. Before the constraints are checked, it walks the single-column foreign keys of the imported tables and clears a nullable reference to a missing row or deletes the row of a required one, until a pass changes nothing; a budget's category or tag counts as required because of its check constraint. `UserImportService` reads `data.json` from the zip through `LimitedReadStream`, stages the attached files with `AttachmentStaging` after checking their SHA-256, and publishes them only after the commit.

Unlike a restore, the import accepts a file from an older version. `MemberImport.BeginAsync` takes any `migration` in `Database.GetMigrations()`, which EF orders and which ends at the running one, so every listed migration is an ancestor of the current schema; an id it does not list is `import.newerVersion` when it sorts after the current one and `import.unknownVersion` otherwise. Nothing else depends on the version. The insert names only the columns the file holds, so a column added since takes its database default, which is the value its migration gave the rows that already existed, and a table added since is simply not in the file. A column the file holds that the table no longer has still fails the import, so a rename or drop needs an explicit mapping in `MemberImport`; no migration has needed one yet. After the repair passes, `RepairAsync` runs the startup backfills (`PayeeKeyBackfill`, `DebtBalanceBackfill`, `SpreadFromBackfill` in `Infrastructure/Data`) on the import's connection and transaction. They select only rows still missing their value, and startup has already filled every other row, so they reach just the imported ones.

The export is written to the response rather than to a file, and Kestrel forbids synchronous writes to a response. .NET 10's `ZipArchive.CreateAsync` and `ZipArchiveEntry.OpenAsync` write entry data asynchronously, but closing an entry (the last deflate block and the data descriptor) and closing the archive (the central directory) still write synchronously. `Common/DeferredWriteStream` sits between the archive and the response body: a synchronous write goes into a memory buffer, the next asynchronous write or `FlushAsync` sends the buffer first, and the service flushes it once the archive is closed. The buffer only ever holds those small trailers, the central directory at the end being the largest at about a hundred bytes per entry.
