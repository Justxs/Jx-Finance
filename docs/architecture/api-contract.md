# API contract and generated client

The backend is the single source of the contract. `OpenApiExtensions` builds the document; `OperationNames.Shorten` strips the `Endpoint` class suffix from every operation id, so an endpoint class `GetAccountsEndpoint` becomes operation `GetAccounts`. `ArrayWrappers.Inline` replaces every array wrapper schema with an inline array, so TypeScript sees `AccountResponse[]` rather than a named `IReadOnlyListOfAccountResponse`, and `SchemaVariants.Collapse` merges per-operation copies of one request type. Collapse leaves array variants alone: FastEndpoints gives every annotated collection property its own `IReadOnlyListOf…__op…` copy carrying that property's description, example and `minItems`, and merging those into the plain wrapper dropped the constraints and, once a second property of the same element type existed, mixed up the descriptions. Because `ArrayWrappers.Inline` runs next and inlines each copy where it is referenced, every collection property keeps its own annotations and no `__op` name survives (`OpenApiArrayPropertyTests`). A backend test fails if a schema name contains `__op` or a collection prefix. On the Orval side `operationName` in `orval.config.ts` drops the `Get` prefix of GET operations, giving `useAccountsSuspense`, `getAccountsQueryKey` and `getAccountsMockHandler` instead of `useGetAccounts…` and `getGetAccounts…`; mutations keep their verb (`useCreateAccount`).

Only what the app uses is generated: suspense hooks for every query, plain `useQuery` hooks only for the operations listed in `plainQueryOperations`, MSW handlers without faker response factories (stories always pass an override), and zod schemas for request bodies and responses only. The zod project reads the spec through the `forValidation` input transformer in `orval.config.ts`, which only affects `src/api/schemas`: it gives every `format: decimal` schema a pattern (digits, optional dot and up to eight decimals), so the generated schema rejects `12,50` or text, and it adds a synthetic `GET /__contract/problem-details` operation because Orval emits zod only for success responses; that yields `ProblemDetailsResponse`, which the fixture contract test uses to check every problem fixture, including that each `code` is a published `ErrorCode`. The synthetic path never reaches the client or the MSW handlers. Generated folders are marked `linguist-generated` in `.gitattributes` so reviews collapse them.

`frontend/orval.config.ts` runs two Orval projects over `frontend/openapi.json`:

| Output | Content | Committed |
| --- | --- | --- |
| `src/api/generated/<tag>/<tag>.ts` | fetch functions, query keys, query/suspense/mutation hooks, one file per OpenAPI tag | yes |
| `src/api/generated/<tag>/<tag>.msw.ts` | typed MSW handler factories (`getAccountsMockHandler`) with path, method and success status from the spec | yes |
| `src/api/generated/model` | request and response types | yes |
| `src/api/schemas/<tag>/<tag>.zod.ts` | zod schemas and constraint constants (`createAccountBodyNameMax`) | yes |

App code imports hooks from the `@/api/generated` barrel and types from `@/api/generated/model`. The barrel deliberately has no `.msw` exports; stories and tests import a handler from its own file (`@/api/generated/accounts/accounts.msw`) so faker and msw never reach the production bundle. Generated code is formatted by the Orval `afterAllFilesWrite` hook, which runs `oxfmt` over the output folder rather than over the list of written files that Orval would append to a plain command: with one more tag that list, under a checkout path like a OneDrive folder, passed the Windows command-line limit and the hook failed. It is excluded from lint, not from formatting.

Regenerate with `just gen` (`scripts/gen.mjs`, which CI and the package update workflow call too). It runs the API with `--export-openapi-docs true`, which writes `backend/JxFinance.Api/wwwroot/openapi/v1.json` and exits before migrations, so neither a database nor a running server is needed, and copies the result to `frontend/openapi.json`. The export does not depend on the HTTP routes below and produces the same file in any environment. The document transformer empties `servers`, which otherwise appeared or not depending on whether Kestrel had bound its port when the document was built.

The HTTP routes `/openapi/v1.json`, `/scalar/v1` and the redirect from `/` exist only in the Development environment (`ApiPipelineExtensions.ServesApiDocs`), so a deployed installation does not publish its API description to anyone who can reach it. `App:ApiDocs=true` switches them on elsewhere; the integration tests use it because they run in the `Testing` environment and compare the served document with the committed contract. The rule itself is covered by `ApiDocsGateTests` rather than by starting a second host: FastEndpoints keeps process-wide state, and a second application in the test process broke authentication for every test that ran after it. That file is the one committed copy of the contract: Orval reads it, and the backend test `OpenApi_document_matches_the_approved_contract` compares it semantically (ignoring `servers` and formatting) with what the running API serves, so there is no separate snapshot to refresh. CI runs the identical export, then fails when `git status` shows any change (including new untracked files) to `frontend/openapi.json`, `src/api/generated` or `src/api/schemas`. The export and the EF recipes build in Release so they work while `just dev` holds the Debug output.

`src/api/client.ts` is the Orval mutator. Every failed request throws an `ApiError` (a real `Error` subclass carrying `status`, `title`, `detail` and per-field `errors`). The file exports `ErrorType`, which Orval picks up, and `query-client.ts` registers `defaultError: ApiError`, so `error` on every query and mutation is typed as `ApiError` without casts; use `isApiError` when the value comes from somewhere untyped.

## Route loaders and optimistic updates
Every route has a `loader` that warms the page's primary queries through `warm` in `src/lib/route-prefetch.ts`, a non-awaited `prefetchQuery` with the generated `get…SuspenseQueryOptions`. Loaders never await and never throw, so navigation is not blocked and `QueryBoundary` still owns error display; with `defaultPreload: "intent"` the data is usually cached before the click. The query client reaches loaders and `beforeLoad` gates through router context. Loader and component must build identical query keys, so params derived from search state or settings live in small `*-queries.ts` files used by both; `route-prefetch.test.tsx` mounts the real route tree and asserts each endpoint is requested once.

`src/lib/optimistic.ts` provides `optimisticUpdate`, `optimisticRemoval` and `optimisticPagedRemoval`, which return the `onMutate` and `onError` pair for a generated mutation hook: cancel in-flight reads, rewrite the cached list, roll back on failure. They take the `QueryClient` from the mutation callback context (`context.client`), so callers pass only query keys and do not call `useQueryClient`. They are used for creating a transaction, deleting rows from lists and marking notifications read. Refreshing afterwards is not their job.

## Cache invalidation
Components do not call `invalidateQueries` after a mutation. `src/api/invalidation.ts` holds the only map from mutation to the query roots it makes stale, and the `MutationCache` built by `createMutationCache` applies it in `onSettled` for every mutation, wherever it was triggered. A root is the URL in a generated query key; invalidating `/api/accounts` also covers `/api/accounts/{id}` and any parameterised variant. Storybook uses the same cache, so stories behave like the app. `invalidation.test.ts` enumerates every generated `get*MutationKey` and fails until a new mutation is either given a rule or listed in `mutationsWithoutInvalidation`. Optimistic updates (`onMutate`, rollback) stay in the component that owns them.

The map follows what the server writes, not what the screen shows. `ledger` is the set of roots that any income or expense row feeds: transactions, accounts, dashboard summary, category breakdown, monthly trend, report summary, budgets and net worth. A conversion can book a fee expense, and a broker import or sync books conversion fees, so both refresh `ledger` on top of their own lists; broker operations also refresh `holdings`. Confirming a recurring entry refreshes `ledger`, the entries, the notifications and the transfer list, because the shape decides whether it wrote a transaction or a transfer. Removing a household member or deleting a household changes which shared accounts, categories and tags the user can see, so those refresh households, categories, tags, transfers, conversions, recurring bills and `ledger`. An exchange-rate sync refreshes accounts, net worth, the dashboard summary and the portfolio, because those are valued at the newest rate. Resetting a user's password refreshes the users list, because the same call can switch off that user's two-factor flag; reactivating one does so because the status changes. The eight deletes that write a trash entry are split out of the rules they shared with their create and update so that only they also refresh the trash list, and `restoreDeleted` is one of the two mutations mapped to `"everything"`, beside changing the installation settings: a restore can bring back any of eight kinds and there is no honest smaller set. `invalidation.test.ts` has a table of these derived refreshes; add a row when a mutation gains a side effect.

## Error codes
Every failure carries a stable code from the closed set in `Common/Errors/ErrorCodes.cs`: each FluentValidation rule sets one (the shared `CommonRules` and `DecimalRules` extensions set it for you, and `ValidatorErrorCodeTests` fails on a rule without a published code), JSON binding failures map to `decimal.malformed` or `request.malformed`, and service failures return a `DomainError(code, message)` whose code also decides the HTTP status. The OpenAPI `ErrorCode` enum is built from the constants by reflection, so Orval emits an `ErrorCode` union; `errors[].code` is never null; there is no top-level `code`, because every problem that has a code carries it in an `errors` entry, including the ones written by middleware. The English `reason` stays as a fallback only.

A service method that can fail returns `Result<T>`, or the non-generic `Result` when success carries no value (confirming a password, consuming a two-factor code, deleting a backup). Both convert implicitly from the value and from `DomainError`, so a service writes `return account;` or `return new DomainError(ErrorCodes.AccessForbidden, "Only the owner can archive an account.");`, and passes another result's failure on with `return other.Error;`. `Result<T>.Success(value)` is still needed where the value is typed as an interface, because C# does not apply user-defined conversions from interface types. Endpoints pass the result to `Send.OkOrProblemAsync`, `Send.CreatedOrProblemAsync` or `Send.NoContentOrProblemAsync` (`Common/ResultResponses.cs`), which write the problem response for a failure without throwing; see [Errors](../api.md#errors).

`Common/EntityLookup.cs` holds the lookup that answers 404. `FindOrNotFoundAsync(predicate, message, ct)` on any `IQueryable<T>` returns the tracked entity or a `resource.notFound` failure with the entity's own message, and a caller that needs the entity reads it with `result.TryGetValue(out var entity)` and otherwise returns `result.Error`. `UpdateOrNotFoundAsync` and `DeleteOrNotFoundAsync` on `AppDbContext` add apply-and-save and remove-and-save for services whose update and delete do nothing else (goals, assets, debts, deleting a budget or a recurring bill); they go through `db.Set<T>()`, so the owner query filters apply exactly as on the `DbSet` property. Every lookup that answers 404 goes through `FindOrNotFoundAsync`, including one on a query that adds `AsNoTracking()`, `IgnoreQueryFilters()` or an ordering first. A 404 that is not a single-row lookup (an `AnyAsync` check, a missing file, a bulk load that finds fewer rows, an exchange rate that is not published) builds its error with `EntityLookup.NotFound(message)`. `NotFoundTests` fails when a file other than `EntityLookup.cs` and `ErrorCodes.cs` mentions `ResourceNotFound`. `HouseholdService.FindOwnedAsync` builds on it for the five operations that need the household and the caller's ownership of it.

`AppDbContext` takes `ICurrentUser` and `IClock`. Every save runs `ApplyEntityRules` over the change tracker first: it stamps `CreatedAt` and `UpdatedAt` from `IClock.UtcNow`, fills an empty `UserId` from the current user and turns a delete into a soft delete. Reading the clock rather than `DateTimeOffset.UtcNow` is what makes a row's `UpdatedAt` the same instant as the `DeletedAt` its trash entry records, which is what lets `RetentionJob` compare the two against one cutoff, and it lets a test freeze time. The hand-built contexts — the net worth snapshotter, the broker sync, the budget alert scan, the design-time factory and the integration test helpers — all pass the same clock the container holds; the design-time factory has no container and uses `Infrastructure/Time/UtcClock.cs`.

The synchronous `SaveChanges` throws `NotSupportedException`. It used to block on the async audit path with `GetAwaiter().GetResult()`, which is a deadlock waiting for a caller; nothing in the product, in Identity or in the migration and seeding paths calls it, so refusing it is cheaper than keeping a second save path correct.

A query whose rows are only read and mapped to a response adds `AsNoTracking()`, so nothing lands in the change tracker that a later `SaveChanges` would have to walk: the transaction page, the conversion page (whose fee is a projection of the four columns a response needs rather than the whole fee transaction), the recurring entries, a transaction's attachments, the categorization rules behind `GetAll`, `Suggest` and a run, the accounts behind `GetReportingTotalAsync` and `GetReportingBalancesAsync`, and the user list. A query whose rows are then changed keeps its tracking; the rule is what happens to the rows, not what the endpoint is called.

`IReferenceGuard` (`Common/References`) answers the two questions several services asked with their own queries: `AccountExistsAsync` returns `reference.notFound` "Account does not exist." or null, and `CategoryOfTypeAsync` checks a category's flow type. The second has two forms because the callers publish different failures for a missing category: given a message it returns `reference.notFound` for a missing category and `category.wrongType` with that message for the wrong type (transactions, budgets); given a whole `DomainError` it returns that one error for both cases (recurring bills, the conversion fee category). Codes and messages are those each call site had before.

The eight hosted jobs derive from `Infrastructure/BackgroundJobs/PeriodicJob.cs`, which owns the `PeriodicTimer` loop, the service scope, the optional feature gate (`RequiredFeature`) and the error log "{Job} failed."; a job declares `Name`, `Interval` and `RunAsync(services, ct)`. `RetentionJob` is the one that deletes rows because they are old — audit events, dead sessions, records past the trash window and the trash entries that described them — and its steps are static methods in `Retention.cs` so each can be read and tested on its own; see [Background jobs](../features/background-jobs.md). `RunOnceAsync` stays public for tests and runs one gated pass immediately, which is also the first thing the loop does, so there is no start-up delay. `AppUser.IsActive` is the expression for "has a password and is not deactivated" that the broker sync and the net worth snapshot filter users with.

Transaction-scoped PostgreSQL advisory locks are taken through `Database.LockAsync` in `Common/AdvisoryLock.cs`. The overload taking a `Guid` derives the key from the first eight bytes of the id (per account, per user, per recurring bill); the overload taking `AppLock` is for installation-wide locks, and the numeric values of that enum are the lock keys, so they must never change or be reused.

On the frontend `serverErrorText` in `src/lib/form-server-errors.ts` is the single place that turns an entry into text: it looks up `serverErrors.<code>` in the locale files and falls back to `reason`. `server-error-codes.test.ts` fails when a published code lacks an English or Lithuanian translation, or when a translation exists for a code the API dropped, so adding a code on the backend is: constant, `just gen`, two translations.

Money, prices and quantities are `decimal` in every backend DTO and a JSON string on the wire (`"42.50"`), so nothing passes through floating point. The property carries `[property: Money]` (two decimals, written `0.00`) or `[property: Quantity]` (up to eight, written `0.########`); both attributes derive from `JsonConverterAttribute` and live in `Common/Json` next to their converters. The converters read only a JSON string in invariant culture with a dot separator, so `"12,50"`, grouping, `NaN` and bare numbers fail during binding; FastEndpoints reports that as a 400 problem whose `errors` entry is named after the JSON path (`amount`, `lines[1].amount`), which keeps per-field form errors working. Sign, scale and range rules are the shared FluentValidation extensions in `Common/Validation/DecimalRules.cs` (`IsPositiveMoney`, `IsNonNegativeQuantity`, ...). Request fields where zero is a valid value are `[JsonRequired]`, because a missing non-nullable decimal would otherwise bind as 0. `decimal? InterestRate` on debts is a plain JSON number and carries no attribute.

The same attributes drive the contract: a schema transformer in `OpenApiExtensions` describes such a property as `type: string, format: decimal`. `orval.config.ts` walks every request body in the spec and writes the names of those properties to the generated `src/api/generated/decimal-fields.ts`; the mutator in `client.ts` normalizes exactly those fields (trim, decimal comma to point) before sending, so a user typing `12,50` sends `12.50`. There is no hand-kept list on the frontend: a new money field needs the attribute, then `just gen`.

## Validation limits
Form schemas stay hand-written because they validate form state (strings, localized messages), not request bodies, but the numeric limits and patterns come from the generated zod constants rather than being retyped, so a limit changed in a backend validator reaches the form on the next `just gen`.
