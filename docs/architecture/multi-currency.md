# Multi-currency

Rates come from `IExchangeRateProvider`. The shipped implementation, `FrankfurterRateProvider`, reads ECB reference rates from `App:ExchangeRates:BaseUrl` (default `https://api.frankfurter.dev/v1/`); `App:ExchangeRates:Enabled` only seeds the automatic-sync setting on a new installation; after that the administrator's switch decides, and Sync now always fetches. `ExchangeRateSyncJob` runs at startup and every six hours and fetches from the day after the newest stored rate, or the last 30 days on an empty table.

`ExchangeRateService.GetForDateAsync` answers with the newest stored rates on or before the date, because the ECB publishes nothing on weekends and holidays. If nothing is stored within five days of the date it fetches the ten days ending there on demand, which is how back-dated transactions get historic rates without a full history download. `ExchangeRateFetchLog` stops a failing range from being retried more than once per fifteen minutes. Future dates use today's rates. If the newest rate is still more than five days older than the date, writes in a foreign currency fail with a validation error instead of freezing a stale value. Read-side totals leave a currency without a rate out, and the net worth snapshot is skipped for that day so an understated total is never stored. Fetched rates are inserted with `ON CONFLICT DO NOTHING` outside the change tracker, so concurrent fetches cannot collide and a fetch never flushes the caller's pending changes.
Rates entered by hand live in `ManualExchangeRates` (Date, Currency, Rate), apart from the synced `ExchangeRates`. `RateHistory` merges the two: it walks the dates in order, keeps each currency's newest rate, lets a hand rate overwrite the synced rate of the same date, and builds each date's `RateTable` from the currencies whose rate is at most five days older than that date. That carry-forward is what keeps a hand rate entered on a Sunday from hiding Friday's rates of the other currencies, and the five-day cut is what keeps a hand rate entered today after three weeks without sync from making those three-week-old rates look fresh. With synced rates alone every date holds every currency, so tables are what they were before. `RateTable.AsOf` is the newest date of either kind and drives freshness, while `SyncedAsOf` is the newest synced date and decides the on-demand fetch, so a hand rate never stops `GetForDateAsync` from fetching the ECB rates around a back-dated day. `GetForDateAsync` without a preload now goes through `GetHistoryAsync` for a single day: it reads the newest date of each table on or before the day and loads both tables from five days before the newer of the two. The sync, `EnsureRangeAsync` and the newest-date lookup of the sync job read `ExchangeRates` only, so a hand rate never counts as fetched coverage.
`ExchangeRateEntryService` (`Endpoints/Settings`) writes a hand rate. It opens a transaction, takes the same table lock as the reporting-currency change (which also queues two rate saves behind each other), inserts, replaces or removes the row, and revalues through `IReportingRevaluation` the rows whose value depends on it: transactions and investment entries, deleted ones included, dated from the rate's date up to the day before the next stored rate of that currency of either kind and never after today, in that currency, or every row not in the reporting currency when the hand rate is for the reporting currency itself. It preloads the window first and `PreloadAsync` clears the per-date cache, so the lookups see the change. A row that can no longer be valued rolls everything back with `exchangeRate.unavailable`.
A change of the reporting currency revalues history inside the transaction of the settings update. `SettingsService.RevalueAsync` first takes `LOCK TABLE "Transactions", "InvestmentTransactions" IN SHARE ROW EXCLUSIVE MODE` through `IReportingRevaluation.LockAsync`, so no row appears or disappears while it works, fetches the needed rate range once, then hands the rows in a foreign currency to `IReportingRevaluation.RevalueAsync` (`Common/ExchangeRates`), which walks them ordered by id in batches of `App:RevalueBatchSize` (default 500), saving and detaching each batch, and finally sets the rows already in the new currency with one `UPDATE` per table. Each batch asks for the rows whose id is above the last id of the batch before it, rather than skipping a growing offset, so the work is linear in the number of rows instead of quadratic; `TransactionId` and `InvestmentTransactionId` carry the comparison operators that make that filter translatable, and they order the way PostgreSQL orders `uuid`, byte by byte, rather than the way `Guid.CompareTo` does. Soft-deleted rows are revalued on both tables. Last, `IReportingRevaluation.ConvertPlansAsync` loads every budget and goal, deleted ones included, through the change tracker, and multiplies `LimitAmount`, `TargetAmount` and `CurrentAmount` by the rate from the old to the new currency in the table `GetForDateAsync` answers for today; those columns hold a bare amount that is always read in the reporting currency, so there is nothing else to change. It skips the rate lookup when there are no budgets or goals, so an installation without them can still switch while rates are stale. Because the save goes through `ApplyEntityRules`, a deleted budget or goal gets a new `UpdatedAt` and stays in the trash up to 30 days longer than its entry, which only ever keeps a row longer.
An investment entry used to be skipped while it was in the trash, so restoring it brought back a reporting amount priced in a currency the installation had left behind; a transaction was always revalued deleted or not, and the two now agree. Memory stays at one batch, and a missing rate still rolls the whole change back. `ExchangeRateFetchLog` lives in memory and is pruned by `ExchangeRateSyncJob` on every run: an entry older than the fifteen-minute retry window decides nothing any more, so nothing older is kept. Money rounds half away from zero everywhere through `Money.Round`. A split transaction's reporting value is shared across its lines in proportion, with the last line taking the remainder so the lines always add up to the parent.

`PUT /api/transfers/{id}` shares `ITransferAmountResolver` (`Common/Transfers`) with create and with the import of a new transfer row, so the cross-currency rules cannot differ between them. Every transaction the server builds itself — the transaction form, an imported row, a conversion fee, a confirmed recurring entry — takes its currency and `ReportingAmount` from `ITransactionValuation` (`Common/ExchangeRates`): the currency is the requested one or the account's, a currency outside the given in-use set must be enabled, and the reporting value is taken at the rate for the date. It first requires both current accounts to be visible (403 `access.forbidden`, as delete does), then resolves the requested accounts through the visibility filter (400 `reference.notFound`). A currency the transfer already uses is accepted even when it has been switched off since; only a currency that the update introduces is checked against the enabled list. `TransferImport` receipts limit the edit: with any receipt the date is fixed, and for each receipt its account must stay on the same side and the amount on that side must stay the same, otherwise 400 `value.locked`. The point of the receipt is that the transfer keeps describing the bank entry it was matched to; a transfer that drifted from its receipt would make the duplicate check lie. `TransferResponse.fromAccountImported` and `toAccountImported` tell the client which side is fixed. They are two booleans rather than a list of account ids. That was chosen while a second `IReadOnlyList<Guid>` property still collided with `transactionIds` of the bulk recategorize request in the contract; `SchemaVariants.Collapse` no longer merges array variants, so the reason is historical.

`PUT /api/conversions/{id}` keeps the account and replaces everything else. The fee fields state the fee as it should be afterwards: with `feeAmount` the linked transaction is created or updated in place (amount, currency, category, date, `ReportingAmount` at the rate for the new date, and the generated description when the user has not renamed it), without it the transaction is removed and `FeeTransactionId` cleared. A fee transaction the user deleted under Transactions is simply booked again. All of it is one `SaveChanges`, so conversion and fee change together or not at all. A fee the user has split into lines is left alone: a request that would change its amount, currency or date, or remove it, answers `transaction.splitNotAllowed`, because the lines would no longer add up and rewriting them is the job of the transaction form. A conversion with `ImportRef` answers `resource.readOnly`, the code investment entries use for broker data. Deleting a conversion soft-deletes its fee transaction and keeps the lines of a split fee, exactly as deleting a transaction does, and records the fee's id on the trash entry so that restoring the conversion brings the fee back; the delete also rewrites `FeeTransactionId` to the value it already had, because removing the fee in the same change tracker clears the link on its way out.

The fee on a conversion is a real `Transaction` rather than a field that every report would need to learn about. Balances, budgets, reports and exports pick it up with no special case, and the user can recategorize it.

The wire format keeps the existing camel-case enum convention, so currencies travel as `eur`, `usd`. The frontend upper-cases the code for `Intl.NumberFormat` and `Intl.DisplayNames`. `useMoney().format(value, currency?)` defaults to the reporting currency from `GET /api/currencies`, fetched once without suspense and falling back to `eur`, so existing call sites that only ever show reporting-currency totals needed no change. Formatters are cached per language and currency at module scope. `CurrencySelect` lists the account's held currencies first, then the rest alphabetically.

Integration tests replace the provider with `FixedRateProvider` (1 EUR = 1.10 USD = 0.80 GBP on every day) so no test touches the network.
