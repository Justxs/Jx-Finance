# Frontend components and forms

## Frontend file layout
Every component lives in its own folder named after it, holding the component, its `*.stories.tsx`, and any helper used only by that component. This applies to `src/components`, `src/components/ui` and each `src/features/<feature>`. A folder with one public module has no `index.ts`; import the file: `@/components/ui/button/button`, `@/features/goals/goals-page/goals-page`. An `index.ts` exists only where it does real work: a folder that exposes several modules (`components/form`, `components/modal`), or a chart folder whose `index.ts` exports the lazily loaded wrapper. Files inside one folder import each other with `./name`.

A component that only one non-page sibling uses moves into that sibling's folder: `split-lines-editor` sits in `transaction-form/`, `member-row` and `add-member-form` in `household-card/`, the column hooks and `table-features` in `transactions-table/`, `date-range-presets` in `report-filters/`. Pages never absorb their children, so a feature stays a flat list of page, section, table and form folders. Stories that show several components together live in `src/storybook/showcase`.

The shadcn CLI still writes flat files such as `src/components/ui/tooltip.tsx`. After `shadcn add`, move the file into `ui/tooltip/` and add its story.

## UI components
`src/components/ui` holds shadcn/ui components generated with the `base-nova` style, which builds on Base UI (`@base-ui/react`) instead of Radix. Add or refresh one with `shadcn add <name> --overwrite`; the CLI shells out to npm, which cannot install into a nub project, so install any new dependency with `nub add` first. Generated files import `cn` from `@/lib/utils`. Local changes to generated files are deliberate: `Button` has a `pending` prop, `Dialog` close labels are translated, and `Table` has no scroll container because every table sits in its own labelled, focusable scroll region. `sonner.tsx` is hand-written because the shadcn version depends on `next-themes` and the app has its own theme store.

Three wrappers keep call sites short: `Modal` (titled dialog with a scrolling body; `onOpenChange` for a boolean state setter, `onClose` for everything else), `SelectField` (Base UI select driven by an `options` array and a plain `onChange(value)`), and `ConfirmDeleteDialog` (alert dialog in front of every delete). `EditModal` takes `item`, `title` and a render function `(item, close)`, the same `close` that `CreateDialog` hands its children; it keeps the last item through `useRetained` so the closing animation still has content, and keys the body by the item's id. `useRetained(value, keep?)` is the render-time "remember the last value" state without an effect.
`useConfirmedDelete(mutation, items, labelOf, undoKind?)` owns the delete target and returns `request(id)`, `pendingId`, `busy`, `deleteProps(id)` (the `onDelete`, `deletePending` and `deleteDisabled` of the `DeleteProps` type that every row passes on to `RowActions`) and the `dialogProps` to spread on `ConfirmDeleteDialog`; it takes the mutation object, not the hook. With a `TrashKind` it also passes an `onSuccess` into the mutation that raises the undo toast, and puts the "you can undo this" sentence into `dialogProps.description`; without one both stay as they were, so the dialog still says a delete is final on the screens where it is. `usePagedList()` gives `page`, `setPage`, the deferred `shownPage` and `stale`, and `usePageClamp(paging, total, pageSize)` returns the page count and pulls the page back when the list shrinks; they are two calls because the total comes from the query that needs `shownPage`.
`RecordRow` (title, subtitle, amount, edit and delete) renders transfer and conversion rows, `SectionHeader` is a section title with an action slot, `TextLink` is the inline router link, and `Hint` sits beside `FieldError`. `src/lib/options.ts` has `namedOptions(items, blankLabel?)`, `nameById(items)` and `withMissingOption(options, id, label)` for selects over named records. The unused parts of the generated dialog, alert dialog, select, popover, table and button files were removed; add one back with the CLI when it is needed. `DatePicker` and `DateRangePicker` share `CalendarPopover` (`components/ui/calendar`: the trigger, open state and visible month) and combine `Popover` with the shadcn `Calendar` (react-day-picker, date-fns locale by language, weeks start on Monday) and keep ISO `yyyy-MM-dd` strings as their value. The generated `Calendar` contains the only `useEffect` in the frontend; it moves focus for day-picker keyboard navigation and is left as generated.

Every field control (`Input`, `SelectTrigger`, the date picker triggers) shares one look: 36px tall, `border-input`, `bg-muted/40` that turns to `bg-background` on focus, 17px text below the `md` breakpoint so iOS does not zoom and 15px above it. Default buttons are 36px, `sm` 32px, `lg` 40px. The destructive button is solid rather than tinted so it keeps contrast in dark mode. `SelectField` wraps the Base UI root in its own element because Base UI renders a hidden form input beside the trigger, which would otherwise pick up the parent stack spacing.

## Forms
Forms use TanStack Form 2 (`@tanstack/react-form@alpha`). Each form passes one zod schema as `validators: [{ run: schema, triggers: ["change"] }]`; submit runs it again. Render props read `field.value`, `field.errors[0]?.message` and `field.meta`, not `field.state`. Lists use `form.ArrayField` with `pushValue` and `removeValue`. In alpha.2 an `ArrayField` re-renders only when the array length changes, not when its errors change, so an error attached to the array path itself (the split total mismatch on `lines`) is rendered through a nested `form.Field name="lines"`. Remove that wrapper once the library subscribes array fields to their meta. The package-update workflow re-pins the `alpha` tag after `nub update --latest`, because `latest` still points at 1.x.

### Shared field components and server errors
`src/components/form` builds on TanStack Form composition: `useAppForm` exposes field components (`TextField`, `MoneyInputField`, `MoneyAmountField`, `SelectFieldControl`, `DateField`, `CheckboxField`, `CurrencyField`) and the form components `SubmitButton`, `FormShell` and `FormActions`. `FormShell` is the `<form noValidate>` whose submit handler stops the event and calls `form.handleSubmit()`; `as={FormGrid}` (or `as={Section}`) renders that layout component as the form, and `onBeforeSubmit` runs first. `FormActions` is the Cancel and submit footer; `span` makes it cover the whole grid. `useServerForm({ defaultValues, schema, submit, aliases })` is `useAppForm` with the schema validated on change and `submit(value, formApi)` wrapped in `submitToServer`; `clearingWrongPassword(formApi, field, send)` in `form-server-errors.ts` empties a password field when the server answers `password.incorrect`.
Groups of fields that repeat across forms are TanStack Form field groups made with `defineAppFieldGroup` and bound by name: `MoneyPairField` (an amount with its currency), `SharingFields` in `src/components/sharing-fields` (scope and household, with `sharingShape`, `refineSharing` and `sharedHouseholdId` in `validation.ts`), and the settings sections (`FeaturesFields`, `CurrenciesFields`, `RegionalFields`). `silent(options)` in `src/lib/mutations.ts` builds the options of a mutation whose error the form shows inline instead of the toast, and `upsert(createMutation, updateMutation)` merges a create and an update mutation into `create`, `update`, `pending` and `error`. A form that saves itself this way takes one `onClose` and calls it both after a successful save and from its Cancel button, so every call site passes the dialog's `close` once.
A field component takes `id`, `label`, optional `hint` and derives the error id, `aria-invalid`, `aria-describedby` and the `FieldError` itself, so a form declares one element per field. A control outside the form hooks (a file input, a filter, a draft input) sits in `FieldShell` and spreads `shellAria({ id, hint, error })`; `useFileField(id, maxBytes, problemKeys)` in `src/hooks` holds a file input's ref, validation error and reset key. Blocks with their own layout (split lines, the conversion rate line, currency lists) stay hand-written inside the same form. Schemas are composed from the builders in `src/lib/validation.ts` (`requiredText`, `optionalText`, `requiredValue`, `positiveMoney`, `password`, ...), which pair each rule with its translated message; length limits come from the generated zod constants.

A form submits through `submitToServer` with `mutateAsync` (a parent that owns the mutation returns the promise from its `onSubmit` prop). When the API answers with field entries, `serverFieldErrors` places each one on the field whose name equals the entry's JSON path (`amount`, `lines[1].amount`), where it renders through the same `FieldError` and aria wiring as a client error and clears on the next edit; `FormError` lists only the entries that match no field. `hasServerErrorCode(error, code)` answers whether a failure carries a code, at the top level or on an entry; forms use it where one code needs its own reaction: the password dialogs empty only the current-password box on `password.incorrect`, the bill confirmation replaces the generic `conflict.stale` text, and the conversion form replaces `transaction.splitNotAllowed`, whose shared text is about bulk recategorizing, with a sentence about the fee expense.

Editing reuses the create form instead of copying it. `AccountForm`, `TransferForm` and `ConversionForm` take the record (`initial`, `transfer`, `conversion`) and `onClose`; with a record they start from its values, label the button Save and send the update, without one they create, and both silent mutations live in the form through `upsert`, so their error shows in a `FormError` and starts empty each time the dialog mounts the form. The sections render them straight in `Modal` and `EditModal`, which keeps the last record so the closing animation still has content. A conversion update leaves `accountId` out of the request because the account cannot change.
The transfer locks follow `fromAccountImported` and `toAccountImported`: an imported side disables its account and amount and the date, and the sent amount is also disabled while the receiving side is imported and both currencies are equal, because then the two amounts are one number; choosing a sending account in another currency releases it. The request always carries `currency` and `receivedCurrency` as the form holds them. An account the user can no longer see is added to the select as "Account not available" so the value still shows. A conversion's fee fields state the fee as it should be afterwards: an empty amount sends `feeAmount`, `feeCurrency` and `feeCategoryId` as null, which deletes the fee transaction. The fee category select needs the categories, so `ConversionsSection` reads them and the accounts route warms them when multi-currency is on.
`RecurringBillForm` follows the same rule: without a `bill` it creates one, with a `bill` it starts from its values, prefixes its field ids with the bill id, adds the `isActive` checkbox and sends every field of `UpdateRecurringBillRequest`; both modes validate the reminder days against the generated minimum and maximum. `RecurringBillConfirmForm` reads `bill.nextDueDate` from its props when it submits, not from form state, so after a `conflict.stale` answer (the mutation cache refreshes the bills on every settle) the second attempt uses the refreshed date.

`ConfirmDeleteDialog` takes optional `title`, `description` and `confirmLabel`, so an irreversible action that is not a delete (deactivating a user) uses the same dialog with its own words.
