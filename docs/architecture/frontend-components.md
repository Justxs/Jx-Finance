# Frontend components and forms

## Frontend file layout
Every component lives in its own folder named after it, holding the component, its `*.stories.tsx`, and any helper used only by that component. This applies to `src/components`, `src/components/ui` and each `src/features/<feature>`. A folder with one public module has no `index.ts`; import the file: `@/components/ui/button/button`, `@/features/goals/goals-page/goals-page`. An `index.ts` exists only where it does real work: the shared `components/form` and `components/modal` folders, or a chart folder whose `index.ts` exports the lazily loaded wrapper. A feature folder that holds several modules has no barrel either; import each file. Files inside one folder import each other with `./name`; a file in another folder, also of the same feature, is imported by its `@/` path, never with `../`.

Shared code does not depend on features. `src/components`, `src/lib`, `src/hooks` and `src/stores` cannot import `@/features/...`, which the `jx-code/layer-imports` rule in `frontend/lint/code-rules.mjs` enforces. A piece that two features use moves out of the feature: a component to `src/components` (`TagPicker`, `TagChips`, `SettingsLayout`), a pure helper to `src/lib` (the month keys in `calendar.ts`, `userName` in `user-name.ts`, `browserLabel` in `user-agent.ts`, the settings query options and `FeatureKey` in `settings.ts`).

Features do not depend on each other either. A file in `src/features/<a>/` may not import from `src/features/<b>/`, through the `@/features/` alias, a relative path or a dynamic `import()`; the rule is `jx-code/no-cross-feature-import` from the local Oxlint plugin `frontend/lint/code-rules.mjs`, and it derives the importing feature from the file path, so a new feature is covered without configuration. A file directly under `src/features` (`amounts-hidden.test.tsx`) belongs to no feature and is not checked.
The rule's `allow` option in `.oxlintrc.json` lists, per importing feature, the few modules of another feature it may embed: a page-level dialog or section that belongs to its own feature and that moving would split from the code it uses. The list is `accounts` → `imports/import-dialog/import-dialog`; `transactions` → `imports/import-dialog/import-dialog`; `month-close` → `imports/import-dialog/import-dialog` and `accounts/reconcile-dialog/reconcile-dialog`; `dashboard` → `month-close/month-close-line/month-close-line` and `month-close/month-close-prompt/month-close-prompt`; `profile` → `dashboard/dashboard-customiser/dashboard-customiser` and `imports/import-data-section/import-data-section`; `tags` → `places/places-section/places-section`; and `command-palette` → `net-worth/net-worth-composition-chart/net-worth-composition-chart`, which only the app test `command-palette.test.tsx` loads ahead so the lazy chart is ready. Anything else that two features use moves out.
The pieces moved out of features on 2026-10-03: to `src/components`, `BudgetRows` (`budget-rows`, the dashboard budget card and the month close), `BudgetRemaining` (`budget-remaining`), `CashFlowForecast` with its series and lazy chart (`cash-flow-forecast`) and `ForecastWhatIf` (`forecast-what-if`), `NetWorthHistoryChart` with `NetWorthSeriesChart` (`net-worth-history-chart`), `ClosedMonthHint`, `TransactionAmount`, `UnusualAmountBadge` with `useUnusualSentence`, `CategorySuggestion` with `confidencePercent`, `CategoryCell` with `useInlineCategory`, `SpreadFields` with `spread-choice.ts`, `RecurringBillConfirmForm`, `DebtPaymentForm` and `PayeeNameForm`, each in a folder of its name with its story; to `src/lib`, `budgets.ts` (`budgetOverview`, `budgetPeriodLabel`, `periodOrder`), `category-recall.ts` (`recallParams`, `recallCategoryId`), `held-currencies.ts`, `month-close.ts` (`isClosedStatus`), `net-worth-pace.ts`, `suggested-rule.ts` (`ruleFromSuggestion`), `transaction-draft.ts` (the `TransactionDraft` type and the router `HistoryState` it travels in), `transaction-filter.ts` (`transactionFilterSchema`, `TransactionFilter`) and `transaction-row.ts`. The contact split and household split forms, `share-allocation.ts` and `useSuggestedRuleToast` moved into `src/features/transactions`, their only user.

A component that only one non-page sibling uses moves into that sibling's folder: `split-lines-editor` sits in `transaction-form/`, `member-row` and `add-member-form` in `household-card/`, the column hooks and `table-features` in `transactions-table/`, `date-range-presets` in `report-filters/`. Pages never absorb their children, so a feature stays a flat list of page, section, table and form folders. Stories that show several components together live in `src/storybook/showcase`.

The shadcn CLI still writes flat files such as `src/components/ui/tooltip.tsx`. After `shadcn add`, move the file into `ui/tooltip/` and add its story.

## UI components
`src/components/ui` holds shadcn/ui components generated with the `base-nova` style, which builds on Base UI (`@base-ui/react`) instead of Radix. Add or refresh one with `shadcn add <name> --overwrite`; the CLI shells out to npm, which cannot install into a nub project, so install any new dependency with `nub add` first. Generated files import `cn` from `@/lib/utils`. Local changes to generated files are deliberate: `Button` has a `pending` prop, `Dialog` close labels are translated, and `Table` has no scroll container because every table sits in its own labelled, focusable scroll region. `sonner.tsx` is hand-written because the shadcn version depends on `next-themes` and the app has its own theme store.
A file in `components/ui` imports only other `components/ui` files, `@/lib` and packages: the `jx-code/layer-imports` rule in `frontend/lint/code-rules.mjs` refuses `@/api`, `@/features`, `@/hooks`, `@/stores` and any other `@/components` folder there, so a primitive takes what it shows as props and its story needs no query client. A piece that reads settings or composes a non-ui component lives one level up: `DatePicker` and `DateRangePicker` in `src/components`, and `SelectColumnFilter`, which draws a `SelectField`, in `components/select-column-filter`.

Three wrappers keep call sites short: `Modal` (titled dialog with a scrolling body; `onOpenChange` for a boolean state setter, `onClose` for everything else), `SelectField` (Base UI select driven by an `options` array and a plain `onChange(value)`), and `ConfirmDeleteDialog` (alert dialog in front of every delete). `EditModal` takes `item`, `title` and a render function `(item, close)`, the same `close` that `CreateDialog` hands its children; it keeps the last item through `useRetained` so the closing animation still has content, and keys the body by the item's id. `useRetained(value, keep?)` is the render-time "remember the last value" state without an effect.
`useConfirmedDelete(mutation, items, labelOf, undoKind?)` owns the delete target and returns `request(id)`, `pendingId`, `busy`, `deleteProps(id)` (the `onDelete`, `deletePending` and `deleteDisabled` of the `DeleteProps` type that every row passes on to `RowActions`) and the `dialogProps` to spread on `ConfirmDeleteDialog`; it takes the mutation object, not the hook. With a `TrashKind` it also passes an `onSuccess` into the mutation that raises the undo toast, and puts the "you can undo this" sentence into `dialogProps.description`; without one both stay as they were, so the dialog still says a delete is final on the screens where it is. `usePagedList()` gives `page`, `setPage`, the deferred `shownPage` and `stale`, and `usePageClamp(paging, total, pageSize)` returns the page count and pulls the page back when the list shrinks; they are two calls because the total comes from the query that needs `shownPage`.
`RowActions` takes `label`, optional `onEdit`, the `DeleteProps` and an `actions` array of extra `RowAction`s (`icon`, `label`, `onSelect`, `disabled`, `pending`), in the order extra actions, edit, remove. Two or fewer render as icon buttons labelled like "Edit: Groceries"; three or more collapse into one `Menu` trigger labelled "Actions: Groceries" whose items carry the plain action names, and the trigger shows the spinner while any action is pending. Its `children` are content placed before the actions, not actions. A dialog opened from a menu item cannot live in the item, because the item unmounts when the menu closes, and it should not live in every row either: a page-level hook holds the target row and one dialog, and answers the row's action, as `useDebtPaymentLinks()` and `useSharedExpenseSplits()` do with `{ actionFor(transaction), dialog }`, which the page renders once beside its rows. `Menu`, `MenuTrigger`, `MenuContent` and `MenuItem` in `src/components/ui/menu` wrap the Base UI menu.
`RecordRow` (title, subtitle, amount, edit and delete) renders transfer and conversion rows, `SectionHeader` is a section title with an action slot, `TextLink` is the inline router link, and `Hint` sits beside `FieldError`. `TransactionsLink` (`components/transactions-link`) is a name that opens `/transactions` filtered to it, with the "Show … transactions" tooltip; budget rows, budget suggestions and every `BreakdownList` row use it. `CreateDialog` is the button that opens a `Modal` and hands its children `close`: it shows a `Plus` unless given another `icon`, and `secondary` makes it the small outline button. `PanelRows` is a page's list of `ProgressRow`s in one `Section`, and `PanelRowsSkeleton` is the same panel on a pending page. `ProgressRow`, `RecordRow` and `NamedRow` keep their layout classes in module constants that the row and its skeleton share, so the two cannot drift apart.
`src/lib/options.ts` has the `SelectOption` type, `namedOptions(items, blankLabel?)`, `nameById(items)` and `withMissingOption(options, id, label)` for selects over named records. `SelectOption<T, L>` takes the label type as its second parameter; the named-record helpers return string labels, so their labels can also be read as text. The unused parts of the generated dialog, alert dialog, select, popover, table and button files were removed; add one back with the CLI when it is needed. `DatePicker` and `DateRangePicker` (`components/date-picker`, `components/date-range-picker`) share `CalendarPopover` (`components/ui/calendar`: the trigger, open state and visible month) and combine `Popover` with the shadcn `Calendar` (react-day-picker) and keep ISO `yyyy-MM-dd` strings as their value. The two pickers read the settings and pass them down: the date-fns locale by language, `weekStartsOn` from the first day of the week, and `today` in the installation's time zone, which `CalendarPopover` also takes as the month to open on when nothing is chosen. `Calendar` and `CalendarPopover` read nothing themselves. The generated `Calendar` moves focus for day-picker keyboard navigation in a ref callback on the day button, so the frontend has no `useEffect`.

Every field control (`Input`, `SelectTrigger`, the date picker triggers) shares one look: 36px tall, `border-input`, `bg-muted/40` that turns to `bg-background` on focus, 17px text below the `md` breakpoint so iOS does not zoom and 15px above it. Default buttons are 36px, `sm` 32px, `lg` 40px. The destructive button is solid rather than tinted so it keeps contrast in dark mode. `SelectField` wraps the Base UI root in its own element because Base UI renders a hidden form input beside the trigger, which would otherwise pick up the parent stack spacing. `CalendarPopover` wraps its popover in a `div` for a similar reason: while the popover is open, Base UI inserts hidden focus-guard spans beside the trigger, so inside a `space-y-*` field wrapper the trigger stopped being the last child, gained a bottom margin and pushed the page down by 6px.

`EmptyText` takes an `action` shown beside the text and an `onClearFilters` that renders a "Clear filters" button in place of the action while `filtered` is set; `TableEmptyRow` passes both through. `Pagination` takes an optional `range` (`{ total, pageSize }`) and then reads "51–100 of 438" instead of "Page 2 of 9"; from five pages on it adds a page number field that jumps on Enter, clamped to the last page. `usePagedItems` returns that `range` and `PagedRows` forwards it. A `SelectOption` may name a `group`, and `SelectField` draws consecutive options with the same group under a labelled `SelectGroup`; `CurrencySelect` uses it when given `preferredLabel`, which `MoneyAmountField` sets to "Account currencies" and `CurrencyField` to "Reporting currency". `SelectTrigger`, `SelectField` and `ComboboxField` take `variant="ghost"` and `size="sm"` for a borderless control inside a table cell. `SelectField` and `ComboboxField` share one props type, `ChoiceFieldProps`, and the combobox draws its trigger and items with the `selectTriggerClass` and `selectItemClass` that `components/ui/select` exports, so the two controls look alike in every state.

`BreakdownList` and `ShareBars` take their meter scale and percent shares from `shareOf(amounts, format)` in `src/lib/share.ts`: the scale is the largest absolute amount, and a share is a positive amount over the sum of the positive amounts, blank for zero or negative rows. `BreakdownList` passes negative rows in as zero, so a category with more refunds than spending does not shrink the other bars. Its rows carry the raw `comparisonAmount`; once any row has one, every row gets the "was" line, and a row without one counts as zero.

`PageHeader` takes the page's own `title` and optional `description`. On a page of a tabbed hub it renders `HubHeader` instead, with the hub's name and `HubTabs`, and neither prop shows; the page still passes both because whether it sits in a hub depends on which features are on. `PageHeaderSkeleton` renders the same `HubHeader` there, so it never needs a title of its own.

Inside `Modal`, the actions of a form stay at the bottom of the scrolling body while the fields scroll: `FormActions` and `TransactionFormActions` carry `modalFooterClass`, whose utilities apply only under the body's `data-slot="modal-body"` and make the row sticky with a top border and the popover background. The sticky row is bounded by its form, so content after the form, such as a transaction's attachments, scrolls past it as before.

## Forms
Forms use TanStack Form 2 (`@tanstack/react-form@alpha`). Each form passes one zod schema as `validators: [{ run: schema, triggers: ["change"] }]`; submit runs it again. Render props read `field.value`, `field.errors[0]?.message` and `field.meta`, not `field.state`. Lists use `form.ArrayField` with `pushValue` and `removeValue`. In alpha.2 an `ArrayField` re-renders only when the array length changes, not when its errors change, so an error attached to the array path itself (the split total mismatch on `lines`) is rendered through a nested `form.Field name="lines"`. Remove that wrapper once the library subscribes array fields to their meta. The package-update workflow re-pins the `alpha` tag after `nub update --latest`, because `latest` still points at 1.x.

### Shared field components and server errors
Two controls sit beside `SelectField` with the same `value`, `onChange(value)` and `options` props. `ComboboxField` is a Base UI combobox whose trigger looks like a select and whose popup opens with a search box; it is used for every category picker. `SegmentedControl` in `components/ui` is a Base UI radio group drawn as joined buttons, for two or three short options. `SelectFieldControl` takes `kind: "select" | "search" | "segments"` to render one of the three inside the same field shell. A segmented control is labelled by `aria-label`, because a `<label for>` cannot name a radio group.

`src/components/form` builds on TanStack Form composition: `useAppForm` exposes field components (`TextField`, `MoneyInputField`, `MoneyAmountField`, `SelectFieldControl`, `DateField`, `CheckboxField`, `CurrencyField`) and the form components `SubmitButton`, `FormShell` and `FormActions`. `FormShell` is the `<form noValidate>` whose submit handler stops the event and calls `form.handleSubmit()`. A form whose values its parent owns, such as `ImportUploadForm` (the account and file of a statement import), still takes `useAppForm({ defaultValues: {}, onSubmit })` for the shell, and `ForecastWhatIf` keeps its amount and date in a `useAppForm` with `optionalPositiveMoney`, its Try button enabled only for a positive amount from today on; `as={FormGrid}` (or `as={Section}`) renders that layout component as the form, and `onBeforeSubmit` runs first. `FormActions` is the Cancel and submit footer; `span` makes it cover the whole grid. `useServerForm({ defaultValues, schema, submit, aliases })` is `useAppForm` with the schema validated on change and `submit(value, formApi)` wrapped in `submitToServer`, which puts each server error on the field its `name` names; `aliases` renames either the whole path (`depreciation.lifeMonths` to `lifeYears` in the asset form) or its first segment (`currentValue` to `amount`); `clearingWrongPassword(formApi, field, send)` in `form-server-errors.ts` empties a password field when the server answers `password.incorrect`.
Groups of fields that repeat across forms are TanStack Form field groups made with `defineAppFieldGroup` and bound by name: `MoneyPairField` (an amount with its currency), `SharingFields` in `src/components/sharing-fields` (scope and household, with `sharingShape`, `refineSharing` and `sharingPayload` in `validation.ts`), and the settings sections (`FeaturesFields`, `CurrenciesFields`, `RegionalFields`). `silentMutation` in `src/lib/mutations.ts` is the meta of a mutation whose error the form shows inline instead of the toast; a call site spreads it next to its own callbacks, `{ mutation: { ...silentMutation, onSuccess } }`, so the generated hook still infers the callback's types, and `upsert(createMutation, updateMutation)` merges a create and an update mutation into `create`, `update`, `pending` and `error`. A form that saves itself this way takes one `onClose` and calls it both after a successful save and from its Cancel button, so every call site passes the dialog's `close` once.
`SharingFields` reads the households itself and renders nothing when the user has none, so a form places it without a guard; `grid` wraps its fields in their own `FormGrid` for a form whose shell is not one. `sharingPayload(value)` gives the request's `scope` and `householdId`, the id only when the scope is shared. `SharedScopeTag` takes a `householdId` and finds the household's name in the households query, which every route that lists shared records warms; `NamedRow` passes its `householdId` through.
`FormSection` in `components/form/form-section` is a titled `fieldset` with a rule above it, for a long form split into parts (the CSV mapping and rule forms).
A field component takes `id`, `label`, optional `hint` and derives the error id, `aria-invalid`, `aria-describedby` and the `FieldError` itself, so a form declares one element per field. A control outside the form hooks (a file input, a filter, a draft input) sits in `FieldShell` and spreads `shellAria({ id, hint, error })` from `src/lib/field-aria.ts`; `useFileField(id, maxBytes, problemKeys)` in `src/hooks` holds a file input's ref, validation error and reset key. `FileInput` in `components/ui/file-input` is a dashed drop zone by default: the real input covers the zone so a dropped file lands in it, `dropPlaceholder` replaces the text while a file is dragged over, and the chosen file's name shows until the caller clears the input. `variant="button"` draws it as a small outline button with an `icon`, as the receipt reader does. Both variants show the hidden input's focus ring and dim while it is disabled. Blocks with their own layout (split lines, the conversion rate line, currency lists) stay hand-written inside the same form. Schemas are composed from the builders in `src/lib/validation.ts` (`requiredText`, `optionalText`, `requiredValue`, `positiveMoney`, `password`, ...), which pair each rule with its translated message; length limits come from the generated zod constants.

A form submits through `submitToServer` with `mutateAsync` (a parent that owns the mutation returns the promise from its `onSubmit` prop). When the API answers with field entries, `serverFieldErrors` places each one on the field whose name equals the entry's JSON path (`amount`, `lines[1].amount`), where it renders through the same `FieldError` and aria wiring as a client error and clears on the next edit; `FormError` lists only the entries that match no field. `hasServerErrorCode(error, code)` answers whether a failure carries a code, at the top level or on an entry; forms use it where one code needs its own reaction: the password dialogs empty only the current-password box on `password.incorrect`, the bill confirmation replaces the generic `conflict.stale` text, and the conversion form replaces `transaction.splitNotAllowed`, whose shared text is about bulk recategorizing, with a sentence about the fee expense.

Editing reuses the create form instead of copying it. `AccountForm`, `TransferForm` and `ConversionForm` take the record (`initial`, `transfer`, `conversion`) and `onClose`; with a record they start from its values, label the button Save and send the update, without one they create, and both silent mutations live in the form through `upsert`, so their error shows in a `FormError` and starts empty each time the dialog mounts the form. The sections render them straight in `Modal` and `EditModal`, which keeps the last record so the closing animation still has content. A conversion update leaves `accountId` out of the request because the account cannot change.
The transfer locks follow `fromAccountImported` and `toAccountImported`: an imported side disables its account and amount and the date, and the sent amount is also disabled while the receiving side is imported and both currencies are equal, because then the two amounts are one number; choosing a sending account in another currency releases it. The request always carries `currency` and `receivedCurrency` as the form holds them. An account the user can no longer see is added to the select as "Account not available" so the value still shows. A conversion's fee fields state the fee as it should be afterwards: an empty amount sends `feeAmount`, `feeCurrency` and `feeCategoryId` as null, which deletes the fee transaction. The fee category select needs the categories, so `ConversionsSection` reads them and the accounts route warms them when multi-currency is on.
`BudgetForm`, `GoalForm` and `RecurringBillForm` follow the same rule with the record in `initial`, and their edit dialogs are titled "Edit budget", "Edit goal" and "Edit recurring entry" with the record's name as the description. Without `initial` the recurring entry form creates one, with it it starts from its values, prefixes its field ids with the bill id, adds the `isActive` checkbox and sends every field of `UpdateRecurringBillRequest`; both modes validate the reminder days against the generated minimum and maximum. `RecurringBillConfirmForm` reads `bill.nextDueDate` from its props when it submits, not from form state, so after a `conflict.stale` answer (the mutation cache refreshes the bills on every settle) the second attempt uses the refreshed date.

`ConfirmDeleteDialog` takes optional `title`, `description` and `confirmLabel`, so an irreversible action that is not a delete (deactivating a user) uses the same dialog with its own words.
