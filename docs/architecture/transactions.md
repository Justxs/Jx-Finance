# Transactions, imports and receipts

## Transactions and import workflow
The transactions page reads three things from the same filter set: the paged ledger (`GET /api/transactions/ledger`, see [Ledger items and groups](#ledger-items-and-groups)), `GET /api/transactions/summary` for the totals line, and the export links. The summary runs through `useDeferredParams` like the list and has its own `QueryBoundary`, so it dims together with the rows and a slow summary never blocks the table. Every mutation that changes the list also invalidates the summary.

Row selection is rendered by the table itself, not by a column definition, because `FlexRender` remounts cell contents on each render and a remounted checkbox loses keyboard focus. Selection state is stored together with the current filter, sort and page key, which clears it on any of those changes without an effect. Bulk recategorize calls `POST /api/transactions/bulk-category`; the toolbar offers only categories whose type matches every selected row and disables itself on a mixed selection, which mirrors what the server accepts. Split rows cannot be selected, nor can the members of an expanded group, which show an indent arrow in the checkbox column; the toolbar's Group opens the group dialog for two or more rows you entered. The same toolbar sets tags through `POST /api/transactions/bulk-tags`, which replaces the whole set on every selected row; that half has no type rule, because a tag has no flow type.

"Save and add another" keeps the dialog open, resets the form but keeps type, account and date, and returns focus to Amount through a ref. The add dialog is opened by the `new` search param so the `n` shortcut and the button share one path; the param is stripped before the deferred params are computed so opening the dialog does not mark the rows stale. Below `md` the page renders `TransactionsList` instead of the table and moves filters and sort into `TransactionsFiltersDialog`; both layouts share one data source, one pagination and the same handlers, and the switch is CSS only.

Import has no route. `ImportDataSection` (`features/imports/import-data-section`) renders in the Import and export section of Settings › Personal (`/profile?section=import`), above the [data export](../features/data-export-per-user.md), when the `import` feature is on and opens `ImportDialog`, which holds the chosen provider in local state (a provider list first, then `ImportSection` in a wide `Modal`). A fixed provider is a statement format: adding one means a parser returning `ParsedStatement` in `Endpoints/Imports/Parsing`, a `StatementFormat` value and an arm of the switch in `ImportPreviewService.PreviewAsync`, an entry in the `fixed` list in `import-providers.tsx` and one in `importFormats` in `import-upload-form.tsx`; preview, review and confirm are shared. Saved CSV mappings are providers too, read from `GET /api/import/csv-mappings` and all of format `genericCsv`: `ImportSection` keeps the chosen mapping in state, sends its id with preview and confirm, and for "Other bank (CSV)" without one calls inspect instead of preview and shows `CsvMappingForm`, keyed on the inspected encoding, delimiter and header line so a re-read starts the form over. The file stays in the file input throughout, which is how saving a mapping previews the same file without choosing it again. Settings itself is split by a `section` search param (`general`, `features`, `currencies`, `regional`, `defaults`, `import`, `backups`, `appearance`) rendered by `SettingsNav`; the settings form stays mounted and hides inactive sections with `hidden`, so unsaved edits survive switching sections. Review helpers live in `preview-rows.ts` and are pure (selection summary, select-all, bulk apply, recall), which is what `preview-rows.test.ts` beside it covers. Category recall is one query for the latest 200 transactions, the API's page-size clamp, matched on exact description and type; it is recall, not the out-of-scope rules feature, and older history is not consulted.

## Transaction aggregates and receipts
Split lines are part of the transaction aggregate and the one exception to soft delete: editing a split hard-deletes the previous lines and inserts the new set, because a line has no identity a user could refer to. Deleting the transaction leaves them where they are, so that restoring it from the trash brings its categories back; they are unreachable in the meantime, because every reader of `TransactionLines` starts from a transaction the query filters already answered. `ICategoryAttributionService` is the single projection charts and budgets read: a split transaction contributes its lines, an unsplit one its own category and amount, so the two can never disagree. Each attributed amount carries its transaction's date, which is what lets `BudgetUsageCalculator` ask once for the whole span a rollover walks back over and bucket the rows into windows in memory; callers that only total by category, the dashboard breakdown and the reports, ignore it.
Files attached to a transaction are not part of the aggregate's rows either: they live on disk under their own ids, images upright and without their EXIF, XMP or IPTC metadata, are hidden and restored with the transaction by the attachment query filter, and are the only thing a background job hard-deletes after the trash window, see [Attachments](../features/attachments.md). A `TransferImport` row is an immutable receipt of a bank entry; it is kept when its transfer is deleted so the same statement line is not imported a second time by accident. `ImportConfirmService.ConfirmAsync` takes a transaction-scoped advisory lock derived from the account id, which serializes imports into one account across concurrent requests and processes. Matching a bank entry to an existing transfer writes a receipt for that account, and a transfer can hold only one receipt per account: two identical bank entries, in one file or in two imports, cannot both be matched to the same transfer.
The second is refused with `import.transferAlreadyMatched` and, like every other confirm error, nothing of that request is written. The entry on the other account of the transfer is a different receipt and still matches. Linking a bank entry to a hand-entered transaction needs no receipt: the bank's reference is written into that transaction's `ImportRef` and its `Source` becomes imported, so the ordinary reference check deduplicates it from then on and the transaction can be linked only once.

The CSV export prefixes a text cell (description, account, category) with a single quote when it starts with `=`, `+`, `-`, `@`, a tab or a carriage return, so a spreadsheet shows it as text instead of evaluating it as a formula. Dates, types, currencies and amounts are produced by the application and are never prefixed; an amount must stay a number.

The CSV export streams: `TransactionService.StreamExportAsync` returns the filtered, sorted query as an async sequence without tracking, account, category and tag names are loaded first because the connection is busy while rows stream, together with the tag map of the filtered set, which is the one per-row value the streamed row cannot carry, and the endpoint writes each row to the response as it arrives. Memory does not grow with the ledger and the response has no `Content-Length`. A failure after the first byte can only cut the file short, since the status line is already sent. The PDF cannot stream, because MigraDoc lays out the whole document in memory, so `ExportForPdfAsync` reads one row more than `App:PdfExportMaxRows` (default 5000) and answers 400 `export.tooManyRows` when that extra row exists. Neither export loads split lines; a split is one row with its total, as before.

Text search on transactions, accounts, users and securities goes through `LikePattern.Contains`, which escapes backslash, percent and underscore, and the queries pass the backslash as the escape character of `ILIKE`. The two-argument `EF.Functions.ILike` would not do: Npgsql translates it with an empty `ESCAPE` clause, which switches escaping off, so a typed `%` or `_` acted as a wildcard. All four searches ignore case.

`CategoryAttributionService` sums unsplit rows per category in SQL and returns one attribution per category; only split transactions are read row by row, because a line's share of the reporting amount is rounded per line with the last line taking the remainder. Beside that split proration, a spread row is cut in time rather than across categories: `SpreadSlices` turns it into dated monthly slices, which the service appends as attributions of the row's category. Every consumer groups by category anyway, and the totals equal the row-by-row sums to the cent because both add the same stored two-decimal values.

## Spread rows
A transaction spread over months (`SpreadMonths` 2 to 36) is still one row; its monthly slices are computed on every read and never stored. `Common/Spreads/SpreadSlices.Of(date, amount, months)` puts a slice on the same day of each month from the payment's month on, with `DateOnly.AddMonths` clamping to the month's last day, and divides the amount with `ShareAllocator`'s equal largest-remainder split, so the slices add up to the cent and the leftover cents go to the first months. `SpreadSlices.Until` is the date of the last slice, and `AppDbContext.ApplyEntityRules` stores it in `SpreadUntil` whenever a transaction is added or its `Date` or `SpreadMonths` changes, next to the `PayeeKey` rule, so "does this row reach into the window" is a plain comparison on an indexed column. Nothing writes either column with `ExecuteUpdate`, and a reporting-currency change only rewrites `ReportingAmount`, from which the slices follow.

`SpreadRows.SlicesAsync` is the one loader. It takes the caller's visible query before any date filter, so ownership, the active household, a household predicate and soft delete apply, reads the spread rows with `Date <= end && SpreadUntil >= start` over the period and the comparison window with their tag ids (through the `Transaction.Tags` navigation, the only navigation on a transaction), and returns `SpreadSlice`s for the slices inside either window. Every aggregate that counts spending by period adds `SpreadMonths == null` to its SQL and appends the slices:

| Path | Slices |
| --- | --- |
| `DatedFlows.DailyFlowsAsync` (report totals and trend, dashboard summary and trend, the month-close year view) | Yes |
| `CategoryAttributionService`, both overloads (report and dashboard breakdowns, category budgets personal and shared, budget limits from history, the month close and the monthly digest through `ReportService`) | Yes |
| `BudgetUsageCalculator.TagSpendAsync` | Yes, per tag the row carries |
| `ReportService`'s tag, payee and place breakdowns | Yes; a payee's or place's `Count` counts a spread row once per period its slices touch, and its label or spelling can come from a spread row dated before the period |
| `TransactionService`'s summary, the refunded amount of the refund marks and the PDF totals | No: the ledger's totals are sums of the rows it lists |
| `AccountMovements`, reconciliation, the cash-flow forecast, `UnusualAmountService`, subscription detection and price rises, debt payments, settle-up, the receipt items report, the member export's double-entry journal | No: they are about the money that moved and when |

The month-end close keeps its drift honest with the same columns. `SnapshotAsync` adds the ids of spread rows whose slices land in the month to `RowIds` but not to `TransactionCount`, which is compared with the month's own row count. `Changes` also picks up spread rows edited after the close whose range covers the month, and each changed row carries the last date it counts on (`SpreadUntil`, or its own date), so a spread row that still reaches the month is Edited or Created and never Moved out.

The ledger reaches back the same way: with `spreadOverlap=true` and both dates, `TransactionService.Filtered` keeps the rows dated in the range or spread rows with `Date <= dateTo && SpreadUntil >= dateFrom`; without both dates the flag is ignored. See [Transactions](../features/transactions.md#spreading-over-months).

## Refunds and the sign of an expense
A refund is an expense with a negative amount, and nothing marks it but the sign. That is the whole mechanism, and it works in two directions. Every total sums `ReportingAmount` (or `Amount` for a balance) over `Type == Expense` and so nets a refund without knowing about it: the ledger summary, `CategoryAttributionService` and everything that reads it (reports, the dashboard, budgets, budget limits from history, month close and through it the monthly digest), the report's trend, tag, payee and place breakdowns, the forecast's usual spending, the PDF totals, and `AccountMovements`, whose `-Amount` of a negative expense raises the balance in both the summing query and the listing that reconciliation reads. The places that look for charges must not see it, and each adds `Amount > 0` (or `ReportingAmount > 0`) to its own expense filter: `UnusualAmountService` for the history, with a non-positive candidate getting no verdict so `UnusualAmountJob` marks it checked, `SubscriptionDetectionService`, `PriceRiseMatcher.LoadChargesAsync` (price rises), `RecurringHistory.LoadAsync` (the forecast's and the bills calendar's matching rows and variable estimates), the job's own price comparison, `NetWorthService`'s debt payment candidates and link check, and `SuggestedRuleService`'s evidence. `AppDbContext.ApplyEntityRules` clears an unusual verdict when an edit makes the row a refund. A new query over expenses has to choose one of the two, and the table in [Transactions](../features/transactions.md#refunds) lists the choice each existing one made.

Two helpers keep the writers consistent. `Common/Refunds/RefundOriginal` checks `refundOfTransactionId` for the transaction form's save (one id, not the row itself) and for the import's confirm (every id of the file in one query): the purchase must be visible through the query filter, an expense and not negative. `ManualEntryMatcher` compares signed money in, income as it is and an expense negated, so a hand-entered refund fits the bank's incoming line of the same size. The ledger's `refundOf` and `refundedAmount` are read after the page with two queries over its ids, the way `debtPayment` is, and are not stored.

## Transaction summary and bulk recategorization
`GET /api/transactions/summary` and the list, CSV and PDF endpoints all build their query through the one `Filtered` method in `TransactionService`, which takes `TransactionFilterRequest`; both request types derive from it, so a filter cannot mean different things in the totals and in the rows. The `unusual` filter added on 2026-09-26 is a property of that base class for that reason, and it is honoured by all four without a line of their own; so is `uncategorized`, added with month-end close, which keeps a row without a category or a split with at least one line without one, and which the month-end checklist counts through the same summary. A split transaction that matches a category filter through one of its lines counts with its whole amount, exactly as the list shows it, not with the matching line's share.

`POST /api/transactions/bulk-tags` replaces the whole tag set of every listed transaction and is all-or-nothing in the same way as the category operation, but it accepts split rows, because a tag belongs to the payment and not to a line, and it has no type rule.

`POST /api/transactions/bulk-category` is all-or-nothing: it loads every listed id through the visibility filter, fails with `not_found` if any is missing, and writes all changes in a single `SaveChanges`. Transactions have no edit rule beyond visibility, matching `PUT /api/transactions/{id}`, so `forbidden` never applies, and like that endpoint it takes no advisory lock because repeating it is harmless. Split transactions are rejected rather than having their lines rewritten, since a split's categories live on its lines. The category check is the same `ValidateCategoryAsync` used by create and update, run once per transaction type present in the batch.

## Ledger items and groups
Since 2026-10-01 the transactions page reads `GET /api/transactions/ledger` instead of `GET /api/transactions`, so that the members of a [transaction group](../features/transaction-groups.md) fold into one item. Members of one group can fall on two pages under any sort, so the folding has to happen in SQL before paging; a client-side collapse would show a group twice or with a partial net.

`LedgerKeys.Of` builds one `UNION ALL` of two projections to the same `LedgerKey` row (`Kind`, `Id`, `CreatedAt`, `Date`, `Amount`, `Name`) from the one `Filtered` query the list, summary and exports use. The first branch is the filtered transactions whose `GroupId` is null or names a group the caller cannot see (another member's, or one that was ungrouped). The second is the caller's groups with at least one filtered member, whose keys are correlated subqueries over the filtered members: `MAX(Date)` for the date sort and `ABS(SUM(income positive, expense negative))` for the amount sort, the group's name for the name sorts. Only the key the sort needs is computed; the others are constant parameters, so a date-sorted page runs no category or account subquery and no `SUM`. `LedgerKeys.Sorted` orders the union like the list (date then creation time in the direction asked, or the field descending or ascending then creation time descending), puts `Kind` first for the category and account sorts so groups follow every transaction, and ends with the id so that ties never move between pages. `ToPageAsync` counts and pages the union, and the page's transactions go through the same responder as the list while the page's groups get one query for `memberCount` (every live visible member), and `matchingCount`, first and last date and net (the filtered members). `LedgerKeysTests` captures the SQL of every sort through `SqlCapture` without a database: one statement, one `UNION ALL`, `LIMIT` and `OFFSET`, `max(` only for the date sort, `sum(` and `abs(` only for the amount sort, and `ORDER BY "Kind"` before the name for category and account.

A transaction response answers `groupId` only when the group is visible to the caller, so a housemate's responses never name it, and `enteredByMe` when the caller entered the row. Membership changes are one `ExecuteUpdateAsync` on `GroupId`, which leaves `UpdatedAt` and the change tracker alone; that is what keeps a closed month free of drift and the household activity log free of group names.
