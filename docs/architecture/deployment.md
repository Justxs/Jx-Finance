# Containers and the recovery command

## Containers
`docker compose up -d --build` runs PostgreSQL, API and frontend. The API healthcheck checks PostgreSQL connectivity and is defined only in `docker-compose.yml`, not in the Dockerfile, because every overlay includes that file and `depends_on` needs its timing; the port the API listens on (`ASPNETCORE_URLS`) is set only in the Dockerfile; the frontend healthcheck asks Caddy's admin endpoint inside the container (`http://127.0.0.1:2019/config/`), which answers the same way with the plain and the production Caddyfile, where a request to the site itself would need the certificate and the hostname. Services restart unless stopped. Every service logs through the `json-file` driver with five files of 10 MB (`x-logging` in `docker-compose.yml`), so container logs cannot fill the disk. The production overlay uses Caddy internal TLS, persistent Caddy state, and SITE_ADDRESS; install/trust its root certificate on authorized client devices and map the hostname to the private server address. Do not bypass browser certificate interstitials.

The API opens every database connection with `-c jit=off` added to the connection string's `Options`, whatever server it reaches, so the Compose database, an external PostgreSQL and the test databases all plan the same way. PostgreSQL's JIT compiler starts above a planner cost of 100,000, and the visibility filters on every query inflate the estimates of a large ledger past it: on 100,000 rows the ledger page spent about 1.2 seconds compiling a query that runs in 45 milliseconds. Options already in the configured connection string are kept. See [General decisions](../decisions/general.md).

The production overlay (`docker-compose.production.yml`) replaces port lists rather than adding to them. Compose merges `ports` from several files, so a plain `ports:` entry in the overlay left `8081:80` published next to 443; the overlay now uses `!override` for the frontend and `!reset` for the database and the API. With the overlay only `${BIND_ADDRESS}:${HTTPS_PORT:-443}` is published; PostgreSQL and the API are reachable only inside the Compose network. `Caddyfile.production` is copied into the frontend image next to the plain Caddyfile and the overlay selects it with the container command, so the overlay needs no bind mount and works where the Docker daemon cannot see the checkout (a CI job that talks to the host's Docker socket). After changing either Caddyfile, rebuild the image (`--build`).

The overlay also sets `AllowedHosts` to `${SITE_ADDRESS};localhost`. `appsettings.json` keeps `*`, which suits development; in production ASP.NET Core's host filtering then answers 400 to any other `Host` header. `localhost` stays in the list because the API healthcheck calls `http://localhost:8080/health` from inside the container. `SITE_ADDRESS` must therefore be a bare hostname, without scheme or port.

`SITE_ADDRESS` also fixes the relying party id of [passkeys](../features/passkeys.md): the overlay's `App__SiteUrl` (`https://${SITE_ADDRESS}`) makes its host the relying party and its origin the only one a passkey ceremony accepts. Changing `SITE_ADDRESS` later orphans every stored passkey, because an authenticator offers a passkey only to the name it was made for; members then sign in with their password and add their passkeys again. The origin carries no port, so passkeys, like the emailed links, assume the default `HTTPS_PORT` of 443. An installation opened by an IP address or over plain HTTP offers no passkeys at all, and one name per installation is supported: reaching it under a second name would need WebAuthn related origins, which the application does not serve.

The API image is published for the build's own architecture (`dotnet publish -a $TARGETARCH --self-contained false`; BuildKit sets `TARGETARCH`), because Magick.NET, which [receipt reading](../features/receipt-reading.md) uses to prepare photos, ships a native library per platform and would otherwise put all eight, about 240 MB, into the image; for one architecture it adds about 37 MB. The runtime stage also installs `tesseract-ocr` with the `tesseract-ocr-eng` and `tesseract-ocr-lit` language data from the base image's distribution, which receipt reading runs as a process; together they add about 66 MB to the image uncompressed (465 to 531 MB on 2026-09-29, 132 to 152 MB as pulled). Receipt reading adds no container, no port and no outbound call. The API finds `tesseract` on its `PATH` once; without it `receiptReadingReady` is false and a photo answers `receipt.engineUnavailable`, which is what a development machine without Tesseract sees. To check an image: `docker run --rm --entrypoint tesseract <image> --list-langs` lists `eng` and `lit`.

Since 2026-10-01 the runtime stage also installs `ghostscript` from the same distribution, without its recommended packages. Magick.NET runs its `gs` command, with `-dSAFER`, to render the pages of a [scanned receipt PDF](../features/receipt-reading.md#scanned-pdfs) at 300 dots per inch; it adds no container, port or outbound call, and its size in the image has not been measured yet. Nothing checks for it at start: where it is missing, as on a development machine, rendering fails and a scan answers `receipt.pdfWithoutText`, the answer from before scans were read, while photos and PDFs with text read as usual. Ghostscript is licensed under the AGPL and runs unmodified from the distribution's package. To check an image: `docker run --rm --entrypoint gs <image> --version` prints its version.

Base images are pinned as `name:patch-tag@sha256:digest` in `docker-compose.yml` and both Dockerfiles: a floating tag such as `postgres:16` gives a different image on each build host and makes a rebuild unreviewable. `just update-images` (`scripts/update-images.mjs`) asks the registries for the newest patch tag inside the same line (PostgreSQL 16, Caddy 2 alpine, Node 24 alpine, .NET 10.0, Aspire dashboard 13) and rewrites tag and digest; `just update-images --check` only reports and exits 1 when something is behind. It needs no Docker. A new PostgreSQL major is deliberately outside its range because the data directory needs a dump and restore.

`.dockerignore` keeps the build context to what the two images compile. It excludes, among the usual build output, `backend/JxFinance.Api/backups`, `backend/JxFinance.Api/attachments`, `*.json.gz`, `*.info.json`, `.local`, `*.user`, test results, coverage, Storybook output and the agent tool directories. The API Dockerfile copies the whole `backend/` directory, so without those lines a backup taken in development, which holds password hashes and two-factor secrets, would enter the build layers and the Web SDK would publish the `.info.json` files into the final image.

`just verify-production` (`scripts/verify-production.mjs`, also the CI job `production-overlay`) starts the overlay as a throwaway project `jx-verify` on `https://127.0.0.1:8443` with its own volumes and checks: only 443 is published, `auth_keys`, `backups`, `attachments` and `import_inbox` are mounted only into `api` and `maps` only into `frontend`, read-only, the API runs as a non-root user, HSTS and the other headers are present, the site's Content-Security-Policy is exactly the expected one, the `Permissions-Policy` allows geolocation to the site itself only, a missing map tile file answers 404 rather than the page, both sign-in cookies are `Secure` and `HttpOnly`, the access token still authenticates after the API container is recreated (which proves the signing key persists on `auth_keys`), and a foreign `Host` header gets 400. It removes the stack and its volumes afterwards; `--keep` leaves it running. It does not prove certificate trust on client devices.

The API container runs as the non-root `app` user and the image pre-creates `/keys`, `/backups`, `/attachments` and `/import-inbox` owned by it. Files attached to transactions live on the `attachments` volume at `App:AttachmentDirectory` (`/attachments`), each under its attachment id; see [Attachments](../features/attachments.md). An `auth_keys` volume created by an older root image keeps root ownership; fix it once with `docker compose run --rm --no-deps --user root --entrypoint chown api -R app:app /keys`, otherwise key persistence fails and sessions reset on restart.

Caddy sends `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin` and a `Permissions-Policy` that switches off camera, microphone, motion sensors, payment and USB on every response and allows geolocation for the site itself only (`geolocation=(self)`, since 2026-10-01, so that [Use my location](../features/transaction-locations.md#the-place-field) can ask; the browser still asks the person), and removes its `Server` header. The static site gets the full Content-Security-Policy; `/api/*` responses get `default-src 'none'; frame-ancestors 'none'` and `nosniff`, set with `defer` so they replace anything the upstream might send: an API response is data and must never be rendered as a document that can load anything. The production file adds `Strict-Transport-Security: max-age=31536000` without `includeSubDomains` and without `preload`. `SITE_ADDRESS` is chosen by the operator and may sit under a name whose other subdomains serve plain HTTP on the same private network; the application sets host-only cookies, so covering subdomains would protect nothing of its own while it could break those neighbours for a year. Scripts are limited to same-origin files, which is why the theme bootstrap lives in `public/theme-init.js` rather than inline in `index.html`. Inline styles stay allowed because the chart and toast libraries set style attributes.

Run a single API instance for this release. Configure the private interface deliberately when enabling remote access. Environment-specific secrets remain in the ignored .env.

## The map tile file

The [map of spending by place](../features/transaction-locations.md#the-map) is drawn from one PMTiles file, `lithuania.pmtiles`, that the administrator puts on the `maps` volume. `docker-compose.yml` mounts the volume read-only into the `frontend` container at `/srv/maps` (the production overlay repeats the mount), and both Caddyfiles serve it with `handle /maps/*` and `file_server`, which answers the range requests the PMTiles reader sends. The API never sees the file. Without it `HEAD /maps/lithuania.pmtiles` answers 404, the reports page offers no Map view and nothing else changes. The file is not in backups; it can always be made again.

To make it, on any machine with network access:

1. Download the `pmtiles` command-line tool for the platform from the [go-pmtiles releases](https://github.com/protomaps/go-pmtiles/releases).
2. Pick a daily Protomaps basemap build from the [builds page](https://maps.protomaps.com/builds/), for example `https://build.protomaps.com/20261001.pmtiles`. The map's style expects the Protomaps basemap layers (`earth`, `water`, `roads`, `boundaries` and `places`).
3. Extract Lithuania, which reads only the byte ranges it needs from the build:
   `pmtiles extract https://build.protomaps.com/20261001.pmtiles lithuania.pmtiles --bbox=20.93,53.89,26.84,56.45 --maxzoom=13`.
   A lower `--maxzoom` gives a smaller file with less street detail; the map stops zooming in where the tiles end.
4. Check it with `pmtiles verify lithuania.pmtiles` and look at its bounds and zooms with `pmtiles show lithuania.pmtiles`.
5. Copy it into the volume on the Docker host. The volume is named after the Compose project, `<project>_maps`, which `docker volume ls --filter name=maps` lists; then
   `docker run --rm -v <project>_maps:/maps -v "$PWD":/source alpine cp /source/lithuania.pmtiles /maps/lithuania.pmtiles`.
6. Reload the reports page. No container needs a restart, and replacing the file later works the same way.

`just e2e` does not use the volume: `docker-compose.e2e.yml` mounts `frontend/e2e/fixtures/maps` instead, which holds a 460-byte `lithuania.pmtiles` written by hand for the end-to-end check, one uncompressed zoom-0 tile with an `earth` polygon over the whole world and a `places` point named Vilnius.

## Import inbox folder

The [import inbox](../features/bank-statement-import.md#import-inbox) reads statement files from `App:ImportInbox`. `docker-compose.yml` sets `App__ImportInbox: /import-inbox` and mounts the named `import_inbox` volume there, read-write, into `api` only; the image pre-creates `/import-inbox` owned by `app`, because the job moves each file into `done/` or `failed/` beside it. An empty volume costs one directory listing every five minutes. To turn the inbox off, remove the variable; with no folder configured the job does nothing and Settings › Installation › Import inbox says so. Development (`just dev`) leaves it unset.

A bank's scheduled export or a sync client (Syncthing, Nextcloud, an SFTP drop) usually writes to a folder on the host, so replace the named volume with a bind mount in an override file, for example `- /srv/statements:/import-inbox`, and make the folder writable by the container's `app` user (`docker compose exec api id -u` prints its uid). Put camt.053, OFX and MT940 files anywhere in it, and each CSV export in a subfolder named after its account's IBAN. Files in `done/` and `failed/` are never deleted by the application. `just verify-production` checks that the `import_inbox` volume is mounted only into `api`. The volume is not in backups: the waiting reviews are left out of them too, and the files in `done/` are the bank's own exports.

## Recovery command
`docker compose run --rm --no-deps -it api --recover-admin admin@example.com`

This requires an existing administrator and interactive password entry. It resets the password, clears lockout and 2FA, invalidates recovery codes, and revokes sessions. It does not create users or change application records. The database must already be migrated. The host command was tested against a disposable administrator; the container invocation still requires validation on a working Docker host.

`docker compose run --rm --no-deps api --evaluate-categorizer member@example.com` prints how well a learned categorizer would have filled that member's last three months, in counts and percentages only, and writes nothing; see [Learned categories](../features/learned-categories.md#evaluating-on-a-ledger).
