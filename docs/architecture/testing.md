# Tests and Storybook

## Backend tests
`backend/JxFinance.Tests` holds `Unit` (pure logic, no database), `Architecture` (NetArchTest rules and checks over the mapped endpoints) and `Integration` (the whole API against PostgreSQL through FastEndpoints.Testing). `just test-unit` runs the first two without Docker in about 20 seconds, `just test-class <Name>` runs one class by its short name, and `just test` runs everything. Measured on 2026-10-03 on the 12-thread development machine, the full run took between 2 minutes 15 seconds and 2 minutes 50 seconds over five runs; before the integration classes were split into collections it took about 10 minutes 30 seconds.

Two checks that guard generated files need no database and run in `just test-unit`. `ModelMappingTests.Model_has_no_changes_without_a_migration` builds `AppDbContext` through `DesignTimeDbContextFactory`, the factory `just migrate-add` uses, and fails with "Run 'just migrate-add <Name>'" when `HasPendingModelChanges()` finds a model change without a migration. `OpenApiContractTests.OpenApi_document_matches_the_approved_contract` fetches `/openapi/v1.json` from the `FastEndpointsPipeline` application and fails with "Run 'just gen'" when it differs from `frontend/openapi.json`, ignoring `servers` and formatting.

Wiring mistakes are caught there too. `ServiceWiringTests` asks the service provider of `FastEndpointsPipeline` (`Services`, built but not started) through `IServiceProviderIsService` whether every constructor parameter of every endpoint, of every class with `[RegisterService]` and of every hosted service is registered, skipping parameters with a default value, and whether every service a background job resolves with `GetRequiredService<T>()` in `Infrastructure/BackgroundJobs` is. FastEndpoints creates each endpoint while it maps the routes, so a missing registration on an endpoint's path already stops the pipeline from starting and fails every test of that collection with the same exception; this test is the one that names the type, the parameter and the fix, and a job's lookup would otherwise fail only when the job next runs.
The same class requires every `[RegisterService]` class under `Endpoints/<Tag>` to register as an interface declared in `Endpoints/<Tag>/Interfaces` that it implements. A class that nothing injects (a static helper, a per-run object such as one statement import, an internal class a service creates) carries no `[RegisterService]` and needs no interface. `ScaffoldPlaceholderTests` fails while a summary keeps the text `just new-endpoint` writes (a `Summary` equal to the endpoint's name, "Describe what this does and when to call it.", "The id." or "Succeeded.") or an endpoint keeps the placeholder handler.

The approved-list tests (`AdminRouteTests`, `TokenReadableTests`, `TokenWritableTests`, `McpToolTests` and both lists of `QueryFilterTests`) compare through `ApprovedList.AssertMatches` in `Support`, which writes one line per difference: the entry, whether the code has it and the list does not or the other way round, the list and file to edit, and the change to make in the code instead. A list naming an entry twice or out of order fails with a message of its own. The leak checks beside them, the backup routes in `AdminRouteTests` and the anonymous routes in `AuthorizationTests` write their lines the same way, and a new check of this kind should too.

Warnings are errors only in Release (`TreatWarningsAsErrors` in `backend/Directory.Build.props` is conditioned on `$(Configuration)`), while the analyzers and `EnforceCodeStyleInBuild` stay on in every configuration. The Debug build that `dotnet watch` runs under `just dev` therefore shows an unused `using` as a warning instead of stopping, and `just check-fast`, `just test`, `just test-unit`, the pre-push build, CI, the contract export and the EF recipes all build Release, where it fails.

xUnit v3 runs test collections in parallel and the classes of one collection one after another. Nothing in the project changes that: there is no `CollectionBehavior` attribute and no `xunit.runner.json`, so collections run on as many threads as the machine has logical cores. The integration classes form nine collections, eight of them a group of feature folders, declared in `Support/Collections.cs`:

| Collection | Folders under `Integration` |
| --- | --- |
| `DataCollection` | Receipts, Backups, Data |
| `ImportsCollection` | Imports, RecurringBills, CategorizationRules, Contacts |
| `InvestmentsCollection` | Investments, Settings, Currencies, Conversions, Transfers, Accounts |
| `LedgerCollection` | Transactions, Tags, Categories, Payees |
| `NetWorthCollection` | NetWorth, Budgets, Goals, Trash |
| `NotificationsCollection` | Notifications, Email, Diagnostics |
| `PeopleCollection` | Households, Users, Auth |
| `ReportsCollection` | Reports, MonthCloses, Dashboard, TransactionGroups |
| `SetupCollection` | `Auth/DemoDataTests` alone, because removing demo data empties the ledger tables of its database |

The groups were balanced on the summed test time of each folder from a TRX report (`dotnet test --project backend/JxFinance.Tests -c Release --report-xunit-trx`), so the slowest collection, not the sum, sets the run time. On this machine six, seven and eight collections all finished in 2 to 3 minutes, with the spread coming from whatever else the machine was doing: the applications and PostgreSQL share six physical cores, so each collection added makes every test a little slower. More collections than eight are not worth it here. The architecture tests in `FastEndpointsPipeline` share an application of their own, the full API pipeline with `App:ApiDocs=true` on the in-memory `TestServer` and a connection string nothing opens, and are a collection with `DisableParallelization`, so they run alone. Its `Endpoints` are the FastEndpoints routes only, without the health, docs and MCP routes the pipeline also maps.

Each collection has its own fixture type, a sealed subclass of the abstract `ApiFixture`, because FastEndpoints.Testing caches one application per fixture type; a collection therefore gets its own application instance, with its own singletons, data protection keys, attachment and backup folders and database. `TestDatabases` starts one PostgreSQL 16 container for the whole run the first time a fixture asks for a database, migrates `jx_test_template` once, and gives each fixture `CREATE DATABASE jx_test_<fixture> TEMPLATE jx_test_template`, so migrations run once instead of once per collection and the application's own startup migration finds nothing pending. The template is migrated with an `AppDbContext` built the way the design-time factory builds it (Identity options from `DependencyInjection.ConfigureIdentity`), with service-provider caching off: unit tests build `AppDbContext` without those options, and EF would otherwise reuse their model and report pending model changes. `DesignTimeDbContextFactory` turns the caching off for the same reason, so the model check above sees the Identity schema the migrations were made with whichever unit test built a context first. Each fixture drops its database when its collection ends and the last one stops the container; Testcontainers' reaper removes it if the run crashes.
With `JX_TEST_POSTGRES` set, no container starts. Its database name must still begin with `jx_test_`, and that database is only the connection the setup works through: the template and the fixture databases are created beside it as `<name>_template` and `<name>_<fixture>`, so the login needs the `CREATEDB` right, and all of them are dropped at the end of the run.

Instance settings (feature switches, enabled currencies, the reporting currency, the time zone) are one `InstanceSettings` row per database, cached by the `IInstanceSettingsStore` singleton of each application. A test that changes them, through `OverrideSettingsAsync`, `FeatureOffAsync`, `OnlyCurrenciesAsync`, the `*OnAsync` helpers or `PUT /api/settings`, changes the database and the application of its own collection only, and inside a collection no other test runs until it has restored them. The same holds for everything else that is installation-wide: a backup restore, the sign-in throttle counters, the fake email, Discord and receipt services, stored exchange rates and securities.

A few things stay shared by every application in the process, and the setup deals with each:
- FastEndpoints keeps the JWT signing key that validates tokens in a static resolver, so the last application to start would decide which tokens every other one accepts. Every fixture and `FastEndpointsPipeline` set the same `App:Jwt:SigningKey` (`ApiFixture.JwtSigningKey`).
- FastEndpoints configures the serializer once per process under a lock, with the same options for every application, and its static service resolver points at the last application started. The only service a validator resolves itself is `IClock`, the same system clock in every application, and no validator takes constructor arguments.
- FluentValidation's global property-name resolver is set to camel case by the first application to start, so the unit tests that check a validator's property name compare it ignoring case.
- PdfSharp's font resolver is a static set once with `??=`; `TestDatabases` sets it before any application builds, so two applications starting together cannot both set it.
- Serilog's static `Log.Logger` is replaced by every application; that only decides which logger writes a line.

A new integration class goes in its feature folder with that folder's collection and fixture, for example `[Collection<LedgerCollection>]` and `(LedgerFixture fixture) : IntegrationTestBase(fixture)`; xUnit hands a collection fixture only to a constructor that asks for its exact type. A new feature folder joins the collection closest in subject, and a collection that grows past the others is split by moving a folder, or by adding a fixture and collection pair to `Support/Collections.cs`.
Tests isolate themselves with fresh users and data (`Support/IntegrationTestBase.cs`), but installation-wide rows are seen by every class of the collection, in an order that changes between runs. Find what the test made by the id it got back rather than by a search; give a security an ISIN of its own unless it is meant to meet the sample broker report's (`MarketPriceSettingsTests` uses `IE00B4L5Y983`, the reports use `IE00BK5BQT80`); store the ECB rate a test expects instead of relying on an earlier on-demand fetch (`ManualExchangeRateTests`); and remove a goal stored at the largest amount, because a change of reporting currency multiplies every goal and overflows it (`GoalIsolationTests`, `GoalProgressTests`). A backup restore ends every session, so `BackupEndpointTests` signs the shared administrator client back in with a login of its own `X-Forwarded-For`, since sign-in is throttled to ten calls per five minutes per client.

A full update of a transaction, an account, a budget or a goal needs the row's `version`. `PutVersionedAsync(client, url, body)` reads it from the database for the record the URL names and adds it to the body, unless the body already carries one or a version is passed; `AssertStaleUpdateRefusedAsync(url, edit)` drives the conflict case for any of the four: no version answers 400, two updates from the same version leave the first written and refuse the second with 409 `conflict.stale`, and an update from the fresh version succeeds. A test that wants an unknown id to answer 404 sends any non-zero `version` itself, because a missing one is refused before the lookup.

`RetentionJobTests` proves that one failing step does not stop the rest by making the database refuse it: a statement trigger that raises on `DELETE FROM "AuditEvents"` breaks the first step, and the test asserts that a backdated deleted transaction and its trash entry, removed by two later steps, are gone; it checks the trigger fires before running the job and drops it in a `finally`. A real failure needs no seam in `RetentionJob`, and the trigger lives only in that collection's database.

`global.json` selects Microsoft.Testing.Platform as the `dotnet test` runner and `xunit.v3` brings its adapter, so the project references neither `Microsoft.NET.Test.Sdk` nor `xunit.runner.visualstudio`, which exist for VSTest. `Microsoft.AspNetCore.Mvc.Testing` arrives through `FastEndpoints.Testing`, whose `buildTransitive` targets still copy the API's `.deps.json` next to the tests. `SSH.NET` is referenced directly only to lift the version Testcontainers would bring in to 2026.0.0, which fixes GHSA-q939-rpr3-3284; drop the reference once Testcontainers depends on a fixed version itself.

## Frontend tests
Vitest has three projects. `unit` (node) and `dom` (jsdom) are what `nub run test` runs. `stories` (jsdom) runs every Storybook story, including its `play` function and an axe scan, and is what `nub run test:stories` and `just test-stories` run; a story is therefore a test, and a selector that no longer matches fails CI instead of rotting. It is a project of its own because it takes about three minutes against about two and a half for the other two, so `nub run test` stays the quicker loop; `just check` runs both and CI runs all three under coverage with `test:coverage`. No browser is involved. Storybook itself is for looking at the interface; until 2026-09-20 the stories also ran in headless Chromium, which the [development decisions](../decisions/development.md) record as superseded.

The story runner lives in `src/test/stories`. `story-runner.ts` lists every `src/**/*.stories.tsx` with Node's `globSync` when the run starts and imports each file by its path, sorts the paths and deals them round-robin to six shard files (`shard-1.test.ts` to `shard-6.test.ts`), because Vitest runs test files in parallel and a single file would use a single core. It used `import.meta.glob` until 2026-10-04, but that list is fixed when Vite transforms the runner, and `fsModuleCache` (below) kept the transformed runner between runs, so a new story file was skipped without an error until the cache was cleared; listing at run time keeps the cache for every other module. Each shard imports its story files once, which matters: importing the preview pulls in the whole route tree, and paying that per story file instead of per shard would multiply the run time. `story-session.ts` composes each file with `composeStories` after `setProjectAnnotations` has been given the real `.storybook/preview.tsx`, so decorators, providers, i18n, theme, router and the five-second `findBy*` timeout are the ones Storybook uses. Every story becomes one test named after its file and its story, for example `components/ui/button/button.stories.tsx > Default`, and the test awaits `Story.run()` (loaders, `beforeEach`, mount, `play`) and then the axe scan.

The only thing the runner swaps is the mock transport. `.storybook/mock-worker.ts` holds the service worker start-up (`startMockWorker`, up to three attempts, because `worker.start()` occasionally never resolved in a fresh iframe) and exports it as `mockWorkerLoader`; the runner replaces that one loader with the same `mswLoader` from `msw-storybook-addon`, pointed at a `setupServer()` from `msw/node`. Handlers therefore resolve exactly as in Storybook: the merged `parameters.msw`, as an array or as an object of arrays, with a story's own list replacing the preview default. An unhandled request prints a warning and is not an error, which is what the worker does as well. Relative URLs such as `/api/accounts` work because MSW resolves them against the jsdom location.

Storybook's portable stories keep their pending clean-ups (unmount, hook clean-up, container removal, `beforeEach` returns) in one module-level list that only `run()` and `load()` flush, and there is no public call that flushes it alone. Calling the finished story's own `load()` would run its loaders and `beforeEach` a second time, so the runner composes an empty `teardownStory` with `composeStory` from `storybook/preview-api` and no project annotations: its `load()` flushes the list and then has no loaders or `beforeEach` of its own to run. The runner calls it after every story and once more in `afterAll`, so the last story of a shard is torn down too. After that it resets the MSW handlers and deletes the preferences row from the TanStack DB collection, while `disposeStoryState` clears the saved filters and transaction templates the same way, and `src/test/setup.ts` clears `localStorage`, the theme attributes and the language as it does for DOM tests. The preview has a `beforeEach` whose clean-up (`disposeStoryState` in `src/storybook/decorators.tsx`) clears every query client a story created and dismisses toasts, in Storybook as well as in the runner. Measured on 2026-09-20 over a shard of 222 stories with garbage collection forced before each sample, the heap went from 127 MB to 192 MB, in steps that coincide with lazily loaded modules such as Recharts; without forced collection a worker's resident memory ended between 0.5 and 1 GB.

jsdom lacks a few things the stories need, and `src/test/polyfills.ts`, loaded by `src/test/setup.ts`, supplies only these. `Blob`, `File`, `FormData` and `Request` are replaced by Node's own classes: jsdom's `FormData` cannot be sent by Node's `fetch`, and the conversion Vitest 5.0.1 ships for it reads a private field that jsdom 30 renamed, so every upload failed with `Cannot read properties of undefined (reading '_buffer')`. Remove the replacement when Vitest and jsdom agree again. `scrollTo` is an empty function because the router calls it on every navigation and jsdom only prints "Not implemented". `matchMedia` was already stubbed. Nothing else is stubbed: Base UI popups, dialogs and the lazy charts pass without `ResizeObserver` or `IntersectionObserver`, and `chooseOption` and `openedDialog` in `src/storybook/interactions.ts` needed no change, since they wait on the DOM (the listbox leaving, the dialog being visible) and not on a transition event.

jsdom applies no stylesheet and computes no layout, so an assertion that needs real CSS or geometry cannot run there. Such a story carries `tags: ["browser-only"]`; the runner registers it as skipped, Vitest reports the count in its summary, and its `play` function still runs in Storybook's Interactions panel. Today the list has two entries: `ClosedPositionsOpen` in `features/investments/positions-section`, which checks `offsetParent` to prove that a row inside an opened disclosure is laid out, and `Default` in `features/reports/place-map`, which finds the labelled region of MapLibre's canvas, drawn only with WebGL; in jsdom the map shows its could-not-be-drawn sentence instead. Do not loosen an assertion to get it through jsdom; tag the story instead, and keep the list short.

Accessibility is part of the run. After the `play` function the runner scans `document.body` with `axe-core`, portalled popups included, and any violation fails the test with the rule, the help text and the offending markup. `region` is off as in Storybook's own accessibility addon, because a component in isolation has no landmarks. Five rules are off because they need paint or layout that jsdom does not have: `color-contrast` and `color-contrast-enhanced` (computed colours), `link-in-text-block` (colour and underline comparison), `target-size` (element geometry) and `scrollable-region-focusable` (overflow measurement). Without CSS the mobile and desktop variants of a layout are both in the tree, which made the two navigation landmarks of the root layout collide; the scan therefore leaves out elements with a `sm:hidden`, `md:hidden`, `lg:hidden` or `xl:hidden` class, matching the 1280 pixel desktop width the stories were written for. A rule is switched off for a single story with `parameters.a11y.config.rules`, which both the runner and Storybook honour, and no story does so today; there are no exemptions for vendored primitives. Beyond the theme tokens, which `src/theme-contrast.test.ts` checks, colour contrast is a manual check: `.storybook/preview.tsx` keeps `a11y: { test: "error" }`, so the Accessibility panel of `nub run storybook` shows violations, contrast included, as errors, and a change to colours or a new surface is reviewed there in both themes. A play function that picks from a select uses `chooseOption`, which waits for the listbox to leave the DOM; axe otherwise inspects the popup while it closes and reports Base UI's focus guards and the half-closed listbox.

To run the stories of one file, set `STORY_FILE` to any part of its path; shards with no matching file skip without importing anything. From `frontend` in PowerShell: `$env:STORY_FILE = "button.stories"; node_modules\.bin\vitest.cmd run --project stories; Remove-Item Env:STORY_FILE`. Add `-t "Default"` to narrow it to one story by name. `nub run test:stories -- <path>` does not work for this, because nub does not pass the filter on; `node_modules\.bin\vitest.cmd run --project stories src/test/stories/shard-1.test.ts` runs one shard. Even a single story takes about a minute, nearly all of it transforming the application that the preview imports.

`just e2e` starts a throwaway Compose project (`docker-compose.e2e.yml`: project `jx-e2e`, port 8089, own volumes, no database or API ports published), runs the Playwright smoke tests in `frontend/e2e` against it (first-run setup, closed setup, refused login, account form, ledger and balance, sign out) and removes it; it never touches the dev database. The Playwright config has three projects that run in order: `smoke` (`smoke.spec.ts`, which performs the first-run setup), `setup` (`auth.setup.ts`, one administrator sign-in saved to `e2e/.auth/admin.json`, ignored by git) and `chromium` (every other spec, started with that stored state).
Each of those specs creates what it needs through the API under unique names and does not depend on another spec: statement import with a matched transfer, cross-currency transfer create and edit, recurring bill create and confirm, a feature switched off and on, the member lifecycle with a password reset, two-factor enrolment with a code from `otpauth` and a recovery code, a passkey added and used to sign in through Chromium's virtual authenticator (CDP `WebAuthn.addVirtualAuthenticator`, which works because the stack is served on `localhost`), backup and restore, the language switch in the account menu, the phone navigation, and the map of spending by place drawn from the fixture tile file in `e2e/fixtures/maps`, which `docker-compose.e2e.yml` mounts where the `maps` volume would be, with every request on the page's origin.
Since 2026-10-01 they also cover the newest flows, written while Docker was not running and first run on 2026-10-02: settle-up of a split expense between two household members and a shared asset seen by the second member (`households.spec.ts`), Record refund on a purchase (`refunds.spec.ts`), a payment spread over three months and its slice in a later month's report, a bill paid in arrears counted in the months up to its date, a spread split counting each line's share, a spread refund taking a slice off each month and a statement row spread from the import review (`spreading.spec.ts`), a debt's recorded balance added, corrected and deleted on its page with the last one refused (`debt-balances.spec.ts`), a reconciliation against a statement balance (`reconciliation.spec.ts`), the month-end close of the previous month (`month-close.spec.ts`), the member download imported into an empty member (`member-export.spec.ts`), a write through a read-and-write API token replayed with the same `Idempotency-Key` (`api-tokens.spec.ts`, through Playwright's request context), a transaction group made, expanded, ungrouped and brought back with undo (`transaction-groups.spec.ts`), a learned category suggestion with the `LearnedCategories` switch on (`learned-categories.spec.ts`) and the bills calendar (`recurring-bills.spec.ts`). Anything per-user and sticky, such as a closed month or a reconciliation, runs as a fresh member from `signedInMember`, so the administrator's months stay open for the other specs. Receipt reading has no spec, because no receipt image or text PDF is committed as a fixture.
Three things in `e2e/support.ts` are not obvious. The refresh token rotates, so a stored state goes stale as soon as one test refreshes; the automatic `keepAdminState` fixture therefore checks `/api/auth/me` before each test (refreshing, or signing in again when a restore ended every session) and writes the cookies back afterwards, without local storage, so a language chosen in one test does not leak into the next. `browser.newContext()` inherits the project's stored state, so `newVisitor` passes an empty one for a second person.
Sign-in is throttled to ten calls per five minutes per client, which the suite exceeds, and FastEndpoints identifies the client by `X-Forwarded-For`; `frontend/Caddyfile` has `trusted_proxies static {$TRUSTED_PROXIES:127.0.0.1/32}`, `docker-compose.e2e.yml` sets it to `private_ranges` for the throwaway stack only, and every test sends its own address derived from its title. Everywhere else the default trusts only loopback, so a client still cannot choose its own throttle bucket. A known backend defect is written as a test marked `test.fail` with the reason, so the suite stays green and turns red when the defect is fixed and the mark has to go. `just e2e-install` downloads the Chromium build they need.

Translation keys are typed: `src/i18next.d.ts` registers `locales/en/common.json` as the resource type, so `t("…")` only accepts existing keys and a key held in a variable is typed `TranslationKey`. `src/locales/locale-keys.ts` makes `tsc` fail when Lithuanian lacks a key English has or has one English lacks, naming the key; an English plural (`_one` and `_other`) is expected in Lithuanian as `_one`, `_few`, `_many` and `_other`. `locales.test.ts` fails when the placeholders of a text differ, or when a Lithuanian plural lacks one of the forms `Intl.PluralRules("lt")` names (`one`, `few`, `many`, `other`), because i18next falls back to English for a missing form.

Token contrast is checked without a browser. `src/theme-contrast.test.ts` (unit project) reads `src/global.css`, builds the tokens of every `[data-palette]` in light and dark the way the cascade does (ledger light, the palette's light block, ledger dark, the palette's dark block) and checks each pair as its own case, named after palette, theme and pair. Text (`foreground`, `muted-foreground`, `income`, `expense`, `primary`) needs 4.5:1 on background, sidebar, card, popover, the section panel, muted, the input fill and accent; each `*-foreground` needs 4.5:1 on its fill, and the primary and destructive button text on their hover fills too. The focus ring needs 3:1 on all of those surfaces, the input stroke on the outer ones (not on its own fill, which is 2.4:1 in dark), and `chart-1` to `chart-3` on background, card and panel. Composites use the opacities the components use: the test reads them from `section.tsx`, `input.tsx` and `button.tsx`, and the ring's from a `ring-ring/<n>` in `global.css` when there is one, otherwise from `input.tsx`, so it fails when a class it relies on goes away. Tokens must be `#rgb` or `#rrggbb`; any other format fails with the token's name. The ratio maths is in `src/test/contrast.ts`. Other colours and new surfaces stay with the Accessibility panel review described above.

Vitest runs the frontend tests; `nub run --cwd frontend test` runs them once, `test:watch` watches and `test:coverage` writes a V8 coverage report. Tests sit beside the file they cover. `vitest.config.ts` is separate from `vite.config.ts` so a test run never regenerates the route tree, and it keeps the React Compiler preset so components are tested as they ship. `just test-fe <path>` runs the unit and DOM tests of one file or folder.

Three settings keep repeated runs short. `reactPlugins()` in `vite.shared.ts` gives the Babel plugin an `exclude` for `node_modules`, `src/api/generated` and `src/api/schemas`: generated code has no components worth compiling, but its hook names matched the React Compiler preset's filter, so every test that imported the client paid for running Babel over hundreds of generated files. `fsModuleCache: true` in `vitest.config.ts` keeps transformed modules in `node_modules/.vitest-cache` between runs and processes; Vitest keys the cache on the file contents and the config, and `vitest --clearCache` empties it. The cache cannot see what a transform read from elsewhere, which is why the story runner lists its files at run time; anything else built with `import.meta.glob` would go stale the same way. Measured back to back on 2026-10-04 with the machine busy: `login-page.test.tsx` went from 36 to 41 seconds to 19 seconds on a warm cache and `src/lib/budgets.test.ts` from 7 to 9 seconds to 2.5 seconds.
The `unit` project runs with `isolate: false`: its files share a worker and its module registry instead of each getting a fresh one. Measured back to back on 2026-10-04, alternating the setting, the project took 17.7 to 23.1 seconds isolated and 11.6 to 12.3 seconds without, with all 2118 tests passing in each of six runs. A unit test therefore must not leave module state behind: globals and environment variables are unstubbed and spies restored by the config, fake timers are put back in an `afterEach`, and a test that needs a module's load-time state fresh takes it from `freshModuleLoader`. The `dom` and `stories` projects stay isolated.
`tsconfig.base.json` has no `incremental`. It was on briefly on 2026-10-04 and made a `tsc -b` with nothing changed take under 2 seconds instead of 7 to 24, but TypeScript 7 then reused the diagnostics of a file whose imported JSON had changed: a key removed from `locales/lt/common.json` passed, and putting it back still failed, until `tsc -b --force`.

Of the unit and DOM projects, `*.test.ts` runs in plain Node and is for pure logic (validation, calendar, cash effect, import preview rows, report presets). `*.test.tsx` and `*.dom.test.ts` run in jsdom with `src/test/setup.ts`, which loads the jest-dom matchers, stubs `matchMedia`, and after each test unmounts, restores the spies, clears `localStorage`, resets the theme attributes and returns i18n to English. The `vi.restoreAllMocks()` there looks redundant next to `restoreMocks: true` in the config but is not: the config restores spies before the next test, which is after this hook, and the blocked-storage tests (`browser-storage`, `preferences`, `privacy-store`, `sidebar-store`, `theme-init`, `theme-store`, `transaction-views`) replace `localStorage` with one that throws, so `localStorage.clear()` here fails with `SecurityError: The operation is insecure` unless the spies are restored first. Anything touching `window`, `document`, `localStorage` or a React hook belongs in the jsdom project; the split exists because creating a jsdom environment per file is the slowest part of a run.

The preferences collection reads storage when its module loads, so store tests seed storage with `seedPreferences` from `src/test/preferences.ts` (which writes the collection's stored format) and take a fresh copy of the store for each test from a loader made by `freshModuleLoader` in `src/test/fresh-module.ts`, which calls `vi.resetModules()` and imports the module again; `storedPreferences` reads the row back and `blockStorage` makes the `localStorage` property throw, which is how the blocked-storage path is tested. `src/test/query.tsx` gives hooks and components a fresh `QueryClient` seeded with settings and currencies and a `fetch` that never resolves, so a test states the loaded data it needs and nothing reaches the network. Text from `Intl` goes through `plain()` before comparison because locales use non-breaking spaces. Time zone tests set `TZ` through `vi.stubEnv` and build their dates inside the test. Exit animations do not run in jsdom, so behaviour that only exists while a dialog closes stays a Storybook concern.

A test's own time is limited to 5 seconds, and whatever a test body imports for the first time is counted in it. A full run keeps one worker per CPU thread but one busy (eleven on a 12-thread laptop), and because DOM files are isolated every one gets a fresh worker, each loading jsdom and its packages from disk while the single main process transforms every source file through Babel and the React Compiler, and Vitest starts the slowest files first, so the first seconds are the busiest. A module loaded inside a test in that window waited behind all of it: the first test of `transaction-views.dom.test.ts` took up to 24 seconds (the store pulls in the generated model barrel of about 200 files), the other store tests 2 to 3 seconds, and the command palette test up to 6 seconds while React loaded the two lazy net worth charts. Both run alone in well under a second, which is why they only failed in the full run. So module loading happens before the tests: `freshModuleLoader` imports the module once at the top of the file, where the time counts towards collection and not a test, and later copies reuse the transformed code; the palette test imports the two chart modules at the top as well. Keep new tests that way: import heavy or lazy modules at the top of the file, not inside a test.

`src/test/app-router.tsx` mounts the real route tree for `route-prefetch.test.tsx` and `command-palette.test.tsx`: the whole shell with a page, several suspense queries in a row and, for the palette, the palette on top. That work is real and takes 0.5 to 2.3 seconds per test in a full run, against a Testing Library default of 1 second for `findBy` and `waitFor`, so these two files wait up to 15 seconds (`appWait`) and allow 30 seconds per test (`APP_TEST_TIMEOUT`). The first test of `route-prefetch.test.tsx` also compiles the code-split transactions route on a cold worker, and on 2026-10-03, with the machine busy, that alone passed the earlier 5-second wait in every full run while the file passed alone; a longer wait costs nothing when the page is fast, because `findBy` returns as soon as the heading appears; apart from the files that use `src/test/api.tsx`, described below, nothing else raises a timeout. The query client there has an infinite `staleTime` because both files count requests. With the default of 0, a suspense query treats data older than one second as stale when its component mounts, so on a slow run the transactions page asked for `/api/transactions/ledger` again after the loader had fetched it and the "asked once" assertion failed; the tests check that loader and page build the same keys, which an infinite `staleTime` still catches, and not how quickly the machine renders.

Every test query client comes from `testQueryClient(options?)` in `src/test/query-client.ts`: queries do not retry and never go stale unless `staleTime` is passed, and `mutationCache` takes the app's `createMutationCache()` where toasts and invalidation should behave as in the app. Which helper to use:

| Helper | Use it for | Query client |
| --- | --- | --- |
| `renderWithQuery`, `createQueryWrapper` (`src/test/query.tsx`) | a hook or component given its data up front, with no network | default; mutations without the app's cache, since its invalidation would wait on a `fetch` that never answers |
| `renderInApp` with `mockApi` (`src/test/api.tsx`) | a form or section talking to the Storybook handlers: request bodies, errors, navigation | with the app's mutation cache |
| `mountApp` (`src/test/app-router.tsx`) | the real route tree: loaders, prefetching, the command palette | default; the infinite `staleTime` is what keeps the request counts stable |
| Storybook decorators (`src/storybook/decorators.tsx`) | stories and the story runner | with the app's mutation cache |

Paged lists show the new page number as soon as the button is pressed and keep the previous rows until the next page arrives, so a test or story that pages waits for a row of the new page before it counts rows; the `Paged` story of `HouseholdActivity` counted after the page number alone and failed whenever the response was slow.

`vitest.config.ts` sets coverage thresholds per folder for the three areas that are tested directly, a little under what `test:coverage` measured on 2026-09-19 (statements, branches, functions, lines): `src/hooks/**` 83/79/63/88, `src/lib/**` 85/83/90/91, `src/stores/**` 95/92/95/96. There is deliberately no global threshold: pages, forms and tables are covered by stories, which the V8 report of the unit and DOM projects does not see, so the overall figure (about 20%) says nothing. Raise a folder's numbers when its coverage rises.

Covered: `src/lib`, `src/api/client.ts` (money normalization, session refresh, problem details), stores, the settings and formatter hooks, the pure feature helpers, and the shared components with behaviour of their own (pagination, error state, query boundary, confirm delete, money field, meter, the theme, language and palette controls, sidebar visibility). Pages, forms and tables are exercised through Storybook stories and their play functions, and since 2026-10-03 the forms and sections of settings, users, auth, categories and tags also have DOM tests that check what a story does not: the request body that was sent, nothing sent when validation refuses, the server's error on its field or in the `FormError`, a confirmation that cancels without a request, and what a role, a feature switch or a missing mail server hides.

Those tests use `src/test/api.tsx`. `const api = mockApi()` at the top of a file starts an MSW server in Node with the default Storybook handlers, resets them, clears every query client and dismisses toasts after each test; `api.use(...)` overrides a handler for one test (`failWith`, `failWithStatus` and `pending` from `@/storybook/handlers`), `api.sent(method, pathname)` lists the requests made and `api.lastBody(method, pathname)` parses the last JSON body. `renderInApp(ui, { path, validateSearch })` renders the component inside a `QueryBoundary`, with a fresh query client that carries the real mutation cache (so toasts and invalidation behave as in the app), a `TooltipProvider`, the `Toaster`, and a memory router whose root renders the component and which registers one route at `path` with the search schema the component reads through `useSearch({ from })`; it returns `router`, so a test asserts a navigation through `router.state.location`. It does not load the route tree or the Storybook decorators, which would double a file's run time. Importing the helper also raises that file's `findBy` and `waitFor` wait to 3 seconds and its test timeout to 10 seconds: in a full run the first test of such a file renders a component for the first time behind suspense queries answered by MSW, and on the 12-thread machine that took between 1 and 6 seconds while the same test alone took well under one. `settings-page.test.tsx` renders the whole settings page, whose sections ask one after another, and waits up to 8 seconds for its first element.

## Storybook
Every component file has a colocated `*.stories.tsx`, and `src/storybook/pages.stories.tsx` renders the real route tree at each path, so the whole app can be reviewed with `nub run storybook` (port 6006) without the API, a database or a login. CI runs `nub run build-storybook`, which fails when a story no longer compiles. A new component ships with its story.

`src/storybook/fixtures/<tag>.ts` holds typed, deterministic mock data (fixed ids, dates around `FIXTURE_TODAY`, 2026-09-18) and `src/storybook/handlers/<tag>.ts` mocks that tag's endpoints with MSW; both folders mirror `src/api/generated/<tag>` and their `index.ts` re-exports every module (`export *` for fixtures, investments included), so stories keep importing `@/storybook/fixtures` and `@/storybook/handlers`. `fixtures.contract.test.ts` parses every response fixture through the generated zod response schema, which catches what the TypeScript types cannot (uuid, date and enum formats, length limits), and fails when a new fixture export is neither checked nor listed as exempt. An export is matched to its schema by name: the explicit `contracts` map first, then the name's ending through `contractsBySuffix` (`…Problem`, `…Notification`, `…Bill`, `…Goal`, `…Budget`, `…Transaction` and a few more), so a new fixture that follows the naming needs no entry. A fixture whose ending names another type gets an explicit entry.
A response type with several fixtures has one factory in its fixtures file, named after the type (`goal`, `budget`, `account`, `transaction`, `bill`, `security`, and `userProfile` for users), with a `…Defaults` object for every field most fixtures share; `Seed<T, typeof defaults>` from `fixtures/base.ts` makes those fields optional and the rest required. A new required response field is then one line in the defaults object, and the create handlers and the unit tests that need a whole response build it with the same factory.
Handlers mock every API endpoint, building each handler from the generated factory in `src/api/generated/<tag>/<tag>.msw.ts` so path, method, success status and response type come from the spec; error responses throw a `Response` from the override (`failWith`, `failWithStatus`, `found`), pending states pass the never-resolving `pending` override, and the few responses the factories cannot express (CSV and PDF export, the blanket error and loading sets) reuse the generated method and path through `onRouteOf`. It also exports `emptyHandlers`, `errorHandlers` and `loadingHandlers`; a story picks one with `parameters: { msw: { handlers: emptyHandlers } }`, and a one-off override goes in front of the defaults with `parameters: withHandlers(getMeMockHandler(failWith(unauthorizedProblem)))`. `handlers.coverage.test.ts` fails for every operation in `openapi.json` that no default handler serves, naming the operation, the factory to add and the handler file; `withoutHandler` lists the few that deliberately have none: the session refresh `client.ts` sends with plain `fetch`, the backup and tax summary downloads the browser opens as links, the goal progress update and the ping, which nothing in the app calls. `settingsWith(patch)` in `fixtures/settings.ts` returns the settings fixture with a patch applied, merging `features` flag by flag; `src/test/settings.ts` builds the unit-test settings on it.
When an endpoint is added or its shape changes, update both files. The worker script lives in `.storybook/public`, not in `public`, so it never reaches the production bundle.

Stories never see the real date. `.storybook/preview.tsx` calls `pinClockToFixtureToday` from `src/storybook/clock.ts` when it loads, which replaces the global `Date` with a proxy whose `new Date()`, `Date()` and `Date.now()` start at noon UTC on `FIXTURE_TODAY` and then advance with real time; `Date` with arguments, `Date.parse`, `Date.UTC` and `instanceof Date` are untouched, and `performance.now()` is not patched. Noon UTC is the same calendar day in every time zone from UTC−11 to UTC+11, including the fixture settings' `Europe/Vilnius`, so `useToday`, "the last ended month" and report presets land on September 2026 whatever the machine date. The runner uses the same preview, and story files are imported after it, so a module-level `new Date()` in a story file is pinned as well. Fixtures and stories that describe "today" use `FIXTURE_TODAY`, `FIXTURE_MONTH` and the month-close constants; moving the fixture date means moving those together. Unit and DOM tests do not load the preview and keep the real clock; they build their dates inside the test.

`src/storybook/decorators.tsx` wraps each story in a fresh query client, a toaster and an in-memory TanStack router that registers the real paths with their search schemas, so components calling `useSearch({ from: "/transactions" })` work; `parameters: { route: "/transactions?type=expense" }` sets the starting URL. The same file exports the layout decorators: `withWidth(size)` constrains a story to a named width (`field`, `card`, `form`, `panel`, `wide`) or to an explicit Tailwind class for a one-off, and `withPageFrame` gives feature page stories the route's centred frame and a `QueryBoundary` with the `RoutePending` fallback. Fixture helpers live in `fixtures/base.ts`: `uid(prefix, n)` builds the deterministic UUIDs, `cycle` repeats a list and `many(items, count, prefix?)` produces the long lists used by overflow stories; money conversion comes from `@/lib/money`. Page stories opt out with `parameters.providers = "none"` and use `AppAt`, which mounts the generated route tree and presets the auth gate. The toolbar switches light and dark theme and English and Lithuanian. `.storybook/main.ts` drops the TanStack Router Vite plugin so Storybook never regenerates the route tree. Stories that need an interaction to reach a state use a `play` function; on TanStack Form fields use `fireEvent.change`, because `userEvent.type` followed by submit clears the value.
