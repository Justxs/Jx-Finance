# Authentication

Sign-in creates a `UserSessions` row with a 1-day or 30-day absolute expiry and issues two HttpOnly, SameSite=Strict cookies: `jx_access`, a 10-minute JWT built with FastEndpoints.Security (`JwtBearer.CreateToken`), and `jx_refresh`, an opaque token scoped to `/api/auth/refresh` whose SHA-256 hash is all the database keeps. The bearer handler reads the JWT from the cookie, so no token is ever reachable from JavaScript. `POST /api/auth/refresh` rotates the refresh token and issues a new access token without extending the session's expiry; the frontend fetch client calls it once on a 401 and retries the request.

Rotation tolerates two tabs. The session row keeps the hash of the previous refresh token and the time of the rotation. The rotation itself is one conditional `UPDATE … WHERE TokenHash = <the hash that was read>`, so of several simultaneous refreshes exactly one rotates and answers with both cookies. A request that loses that race, or that presents the previous token within 30 seconds of the rotation, answers 204 with a fresh access cookie only and leaves the refresh cookie alone: the browser keeps the refresh cookie the winning response set, whichever response arrives first, and the losing tab can retry its request at once instead of waiting for the other tab's cookies. Nothing is cleared on that path. The previous token presented after those 30 seconds is treated as a stolen copy: the session row is deleted and the cookies are cleared, so the legitimate browser has to sign in again. A token that matches neither hash answers 401 and clears the cookies without touching the session, because anyone can send a well-formed cookie for a known session id. `SignInAsync` and `RenewAsync` forget the previous hash, so a token from before a password change has no grace.

Deactivation and the failed-attempt lockout share Identity's lockout columns but mean different things. Deactivating a user sets `LockoutEnd` to `AppUser.DeactivatedUntil` (`DateTimeOffset.MaxValue`) and `AppUser.IsDeactivated` tests exactly that; it is what `isActive`, the bearer handler, the refresh endpoint and the background jobs look at. The temporary lockout is Identity's own (`Lockout.MaxFailedAccessAttempts` 5, `DefaultLockoutTimeSpan` 15 minutes, set in `DependencyInjection`) and is consulted only where a secret is verified, all of which goes through `AuthService.AttemptAsync`: the sign-in password, the authenticator or recovery code (an authenticator code through `AuthenticatorCode.ConsumeAsync`, which refuses a code already accepted in the last three minutes, see [Two-factor authentication](../features/two-factor-authentication.md#a-code-works-once)), the password that confirms 2FA setup and disable, the current password of a password change and the password that confirms a restore. A failure calls `AccessFailedAsync`; a locked account answers 429 `credentials.lockedOut` without checking the secret. The counter resets only when a sign-in completes, so the password step of a 2FA sign-in does not reset it and an attacker who knows the password cannot try codes without limit. A temporary lockout deliberately does not end the sessions the user already has: otherwise anyone who knows an email address could sign its owner out every 15 minutes. A deactivated user always gets `credentials.invalid`. The per-client throttle on the endpoints stays in place. `--recover-admin` clears both the lockout end and the counter.

`POST /api/users/{id}/reactivate` is the inverse of deactivation: it clears `LockoutEnd` and the failed-attempt counter and changes the security stamp. Deactivation had already changed the stamp, so no session from before it can come back; the second change only keeps the rule that every change of account state moves the stamp. For a user who is not deactivated it does nothing and answers 204, which makes it safe to repeat and means it cannot be used to lift a temporary lockout. It has no self rule because a deactivated administrator cannot be signed in to call it.

An installation always keeps one active administrator. Because nobody may demote or deactivate themselves, a single request can never remove the last one; two administrators removing each other at the same moment could. `UserService.ChangeRoleAsync` and `DeactivateAsync` therefore run in a transaction that first takes the advisory lock `AppLock.AdministratorChange` (`738192437`), and under it count the administrators who are not deactivated. If the target is the only one, the change answers 403 `user.lastAdministrator`. The second of two crossing requests waits for the lock, sees the first one's result and is refused. Reactivation and password reset only ever add an active administrator, so they do not take the lock. The tests remove the other administrators' role rows for the duration of a test, because the shared fixture administrator would otherwise always be the one that remains.

`POST /api/users/{id}/reset-password` is the administrator's way to let a member back in; since 2026-09-20 a member who has a working mailbox can also do it themselves through `POST /api/auth/forgot-password`, and both ways stay. The administrator sends the new password and their own current password. The confirmation goes through `ConfirmPasswordAsync`, so it counts toward the administrator's lockout, answers 400 `password.incorrect` for the same reason restore does, and is checked before the target is looked up, so a wrong password learns nothing about user ids. The password is set through Identity's reset token inside one database transaction, which applies the configured password validators (`password.tooWeak`) and changes the stamp, so every session of the target ends; the failed-attempt counter and a temporary lockout are cleared, a deactivation is left in place. `resetTwoFactor` also disables the authenticator, replaces its key and invalidates the recovery codes, the same three steps as `--recover-admin`. The target may be another administrator, never the caller (`user.selfChange`, 403): changing your own password belongs to the profile, where the session is renewed instead of revoked. The endpoint is throttled to 10 calls per five minutes per client. There is no forced change at next sign-in; see the [user management decisions](../decisions/user-management.md).

Each request still validates the security stamp and that the user is not deactivated (`JwtCookieAuthentication`), then checks that the `UserSessions` row named by the token's `sid` claim exists for that user and has not expired, so deleting a row (sign out, a revocation from the profile's list of signed-in browsers, a restore) ends that browser on its next request instead of when its 10-minute access token runs out. The check is one more lookup by primary key next to the user lookup that was already there. It runs without the request's cancellation token. `JwtBearerHandler` logs any exception from `OnTokenValidated` as an Error before an event can intervene, so a browser that aborts a request, as TanStack Query does when a query is cancelled, would otherwise leave an Error log and a failed Npgsql `CONNECT` span for every dropped request. The lookup takes milliseconds, and the endpoint's own queries still stop on the abort. A token whose user id claim is missing or not a GUID fails authentication with 401 rather than reaching the ownership filters as an empty user. Role changes/deactivation therefore invalidate access and refresh tokens at once. Own-password and 2FA changes re-issue the initiating session's tokens with the new stamp (`ISessionService.RenewAsync`). FastEndpoints' `RefreshTokenService` is not used: it carries tokens in the request and response body and slides the refresh expiry, which contradicts both the cookie transport and the absolute session lifetime. First-run setup is serialized. 2FA setup/disable requires the current password, and setup refuses to expose a key for an already-enabled authenticator.

The Compose API persists Data Protection keys and the JWT signing key (`jwt-signing.key`, generated on first start unless `App:Jwt:SigningKey` is configured) in `auth_keys`. A key file that exists but is blank, as a crash during the first write can leave it, is replaced by a new key; a key file that cannot be read or written stops the start instead of falling back to a key that would change on every restart. Both are plain files there and only the `api` service mounts the volume; protect it as sensitive deployment data, see "Secrets at rest" in [quality requirements](../quality-requirements.md). The production overlay enables secure cookies. API/database development ports bind only to loopback; the frontend bind address is configurable.

A record prints every public property in its compiler-generated `ToString`, so a record that carries a secret would put it into any log line or exception message that formats the object. Every record that holds a password, a token, a two-factor code or key, passkey credential JSON or ceremony state, the JWT signing key, the SMTP delivery settings or a Discord webhook URL therefore replaces that output: it declares `private bool PrintMembers(StringBuilder builder)` and prints the other members with the secret shown as `SecretText.Hidden` (`***`), or overrides `ToString` when there is nothing else worth printing. `SecretRedactionTests` in the unit tests finds every record in the API assembly whose string properties are named like a secret (`Password`, `Token` except `ViaToken`, which holds a token's name, `Secret`, `SharedKey`, `AuthenticatorUri`, `TwoFactorCode`, `Webhook`, `Credential`, or any property of a `…SigningKey` record or of `PasskeyState`), fills them with markers and fails when `ToString` shows one, so a new request record with a `Password` field cannot slip through. `UpdateDiscordSettingsRequest` prints `WebhookUrl = ***`, and `DiscordTarget`, the parsed webhook id and token, prints `Token = ***`. Name a new secret property so the test recognizes it, or extend the pattern.

## Passkeys

[Passkeys](../features/passkeys.md) use the passkey support in ASP.NET Core Identity 10 without `SignInManager`. `DependencyInjection.ConfigureIdentity` sets `Stores.SchemaVersion` to `IdentitySchemaVersions.Version3`, which maps `AspNetUserPasskeys`, and `AddInfrastructure` registers Identity's `PasskeyHandler<AppUser>` as `IPasskeyHandler<AppUser>` by hand, because `AddIdentityCore` does not. `SignInManager` would keep the ceremony state in, and sign in through, Identity's own cookie schemes, which this application does not have. A passkey sign-in ends in `ISessionService.SignInAsync` like a password sign-in, so the session row, the two cookies, the stamp check and every rule above apply to a passkey session unchanged.

Identity reads the schema version from the application's `IOptions<IdentityOptions>` while it builds the model, and falls back to version 1 when the context has no application service provider. An `AppDbContext` created outside dependency injection must therefore be given one that carries `ConfigureIdentity`: `DesignTimeDbContextFactory` builds a small service provider for it, and `MigrationBackfillTests` starts from the application's own `DbContextOptions`. Without it the model lacks the passkey table and EF reports pending model changes. The store was on version 1 before, not 2. Moving to 3 therefore also gave `AspNetUsers.PhoneNumber` a 256-character limit and the login and token keys a 128-character limit, which the `AddPasskeys` migration applies; the stored values (the authenticator key and recovery code rows) fit.

`IdentityPasskeyOptions` is configured by `PasskeySite.Configure` from `App:SiteUrl`: user verification and a discoverable credential are required, attestation is `none`, and the browser timeout is two minutes. When the site address is set, its host is `ServerDomain` and `ValidateOrigin` accepts that one origin, never a cross-origin frame. Without a site address the handler takes the relying party from the host header and compares the client's origin with the request's `Origin` header. `PasskeySite.IsAvailable` is the rule the public settings report as `passkeysAvailable`.

The handler hands back a state with each set of options. `PasskeyStateCookie` keeps it in `jx_passkey`: the `PasskeyState` record (ceremony kind, the handler's state, and for a registration the user id and session id) serialized as JSON and protected with Data Protection under the purpose `JxFinance.Passkeys.State.v1`. The cookie uses the options of the session cookies (`AuthCookies.Options`: HttpOnly, SameSite=Strict, Secure under `App:SecureCookies` or HTTPS), the path `/api/auth/passkeys` and a five-minute expiry. The protected value repeats the expiry, so a copy replayed after the browser dropped the cookie is refused too. The finishing call always deletes the cookie before it checks anything, so each state is used once. A value that does not unprotect (tampered, another purpose, another key ring), of the wrong kind or past its expiry reads as no state and answers `passkey.stateInvalid`. No table and no clean-up job are needed.

A failed passkey sign-in never touches the failed-attempt counter and a successful one resets it; a temporary lockout does not block it. A deactivated user, or one without a password (setup not finished), gets `credentials.invalid`. The reason Identity gives for a refused ceremony (origin, relying party hash, signature, sign count) is logged at Information, never the credential.

## Personal API tokens

[Personal API tokens](../features/personal-api-tokens.md) are a second authentication scheme beside the JWT cookie, and the cookie path is unchanged by them. `AddJwtCookieAuthentication` registers FastEndpoints' JWT bearer scheme as before, then the `PersonalApiToken` scheme (`PersonalApiTokenAuthenticationHandler`) and a policy scheme named `Credentials`, which becomes the default authenticate, challenge and forbid scheme. Its `ForwardDefaultSelector` sends a request whose `Authorization` header starts with `Bearer jxp_` to the token scheme and every other request to the JWT scheme, so a request that carries a token is authenticated by the token alone and its cookies are never read. `JwtBearerHandler` still falls back to the `Authorization` header when there is no cookie, exactly as it did before, because a JWT there does not start with the marker.

A token is `jxp_`, an 8-character public prefix of letters and digits, `_`, and 32 random bytes in base64url (`PersonalApiTokenFormat`). The `PersonalApiTokens` row keeps the prefix in clear under a unique index and the SHA-256 hash of the secret part as 64 hex characters. The handler parses the header strictly (length, marker, separator, alphabet, and a secret that decodes to exactly 32 bytes and encodes back to itself), puts the prefix into Serilog's diagnostic context as `TokenPrefix` so the request log names the token without its secret, looks the row up by prefix together with its expiry and whether the user is deactivated, and compares the hash with `CryptographicOperations.FixedTimeEquals`, as `SessionService` compares refresh tokens. A fast hash is enough because 256 random bits cannot be guessed, and a slow one would cost every request. The lookup and the `LastUsedAt` update run with `CancellationToken.None` for the reason the session check does. `LastUsedAt` is written by one `ExecuteUpdateAsync … WHERE LastUsedAt IS NULL OR LastUsedAt < now - 1 minute`, and only when the row read shows it is older than that. The principal carries `ClaimTypes.NameIdentifier`, so `HttpCurrentUser`, the ownership filters and the active household work unchanged, a `jx.token` claim with the token id, `jx.token.name` with its name and `jx.access` with its `TokenAccess` (`Read` or `ReadWrite`). `HttpCurrentUser.TokenName` reads the name; `ICurrentUser.TokenName` is a default interface member that answers null, so `FixedUser` and the jobs' `JobUser` never carry one. It carries no `sid`, no `stamp` and never a role claim, so `Roles(AppRoles.Admin)` refuses it by construction and nothing that reads the session id can act on it. A failed token answers the challenge itself: 401 `token.invalid` with `WWW-Authenticate: Bearer error="invalid_token"`.

`PersonalApiTokenGateMiddleware` sits between `UseAuthentication` and `UseAuthorization`, after `UseRateLimiter`, and acts only on requests whose header carries the marker. A request that the handler did not authenticate gets the challenge, on anonymous routes too, which is why `GET /api/ping` tells a script whether its token is good. While `Feature.ApiTokens` is off it answers 404 `feature.disabled`. A `GET` passes only on an endpoint whose metadata says `TokenReadable`; any other method passes only when the `jx.access` claim is `ReadWrite` and the endpoint carries `TokenWritable`. Every refusal answers 403 `token.notAllowed`, with one of three messages: a `GET` outside the readable list, a read-only token on a writable route ("create a read-and-write token"), or a route that is not writable ("it needs a browser session"). `PersonalApiTokenGateMiddleware.Refusal` is that decision as a pure function. The nine writable endpoints add `Options(b => b.WithMetadata(TokenWritable.Yes))` themselves, as the two opted-out readers add `TokenReadable.No`; a group never makes its writes writable. `ApiGroup` attaches `TokenReadable.Yes` to every endpoint of a group built with `tokenReadable: true`, in the same `Options` call as `RequiresFeature`; an endpoint that must stay out adds `TokenReadable.No` (the broker connections and the dashboard layout), and `TokenReadable.Allows` needs at least one mark and no refusal. The gate runs before authorization so that a token never reaches an authorization policy, an endpoint filter or a handler outside the list. The OpenAPI document shows the same lists: `TokenSecurity.MarkReadable` marks the readable `GET` operations, `TokenSecurity.MarkWritable` the writable ones, and the document transformer adds the `PersonalApiToken` bearer scheme to their `security`, beside `Cookie`; orval ignores `security`, so the generated client is unchanged.

The rate limit is ASP.NET Core's rate limiter with a global limiter partitioned by the `jx.token` claim: a fixed window of 60 requests a minute per token, no queue, and `RateLimitPartition.GetNoLimiter` for every request without the claim, so browsers are not limited as before. `OnRejected` writes 429 `token.rateLimited` through `ProblemResponses.WriteAsync` with `Retry-After` from the lease. FastEndpoints' `Throttle` stays on the endpoints that use it; it counts per endpoint and per client address, which cannot give a script one budget across all routes.

No antiforgery is added. A browser never adds an `Authorization` header to a cross-site request by itself, and without a CORS policy a cross-origin page cannot send one, while the cookies stay SameSite=Strict. `UserService.DeactivateAsync`, both password resets (the administrator's `UserService.ResetPasswordAsync` and the emailed link's `AccountEmailService.ResetPasswordAsync`, through `PasswordReset.CompleteAsync`) and `RecoveryCommand.RecoverAsync` delete the user's tokens inside the change they already make; an own password change, two-factor and passkeys leave them alone, because a token is not tied to the security stamp. `Retention.PruneApiTokensAsync` deletes tokens 30 days after they expired, in `RetentionJob` after the sessions step.

`IdempotencyMiddleware` runs after `ActiveHouseholdMiddleware`, so the household is resolved and the gate has already let the request through, and before FastEndpoints. It acts only on a `POST` or `PATCH` that carries `Idempotency-Key` and a `jx.token` claim, so the browser never reaches it. It buffers the request body with `EnableBuffering` and hashes method, path, query string, the raw `X-Active-Household` header and body with SHA-256, each part followed by a zero byte (`IdempotencyMiddleware.RequestHash`). It then claims the key with one `INSERT INTO "ApiIdempotencyKeys" … ON CONFLICT DO NOTHING` on the scoped `AppDbContext`, outside any transaction, so the claim commits before the endpoint runs and the services' own transactions (`RecurringBillService.ConfirmAsync` opens one) never nest inside it; the claim time is cut to whole microseconds so the later guards compare equal to what PostgreSQL stored. When the insert finds a row, a different hash answers 409 `idempotency.keyReused`, a stored answer is replayed with `Idempotency-Replayed: true` (the content type follows from the status), a claim without an answer younger than 60 seconds answers 409 `conflict.busy`, and an older claim, or any row older than 24 hours, is taken over with one conditional `UPDATE … WHERE CreatedAt = <the time read>`. A claimed request writes into a `MemoryStream` swapped in for `Response.Body`; afterwards one `ExecuteUpdate` guarded by the claim time stores status, body and `Location`, or, for a 5xx or an exception, one `ExecuteDelete` releases the claim, and the buffer is copied to the real body. Both run with `CancellationToken.None`. The table is transient: `BackupDatabase.ReadShapes` lists it with the sessions and outboxes, `UserExportTables` excludes it, and `Retention.PruneIdempotencyKeysAsync` deletes rows older than 24 hours in `RetentionJob` after the tokens step.

A write through a token is attributed like a browser write, plus two marks: `TransactionService.CreateAsync` sets `TransactionSource.Api` when `ICurrentUser.TokenName` is set, and `AppDbContext` hands the name to `AuditCollector`, whose `NewEvent` writes it to `AuditEvent.ViaToken` on every event of the save, the bulk summaries included.
