# Authentication

Sign-in creates a `UserSessions` row with a 1-day or 30-day absolute expiry and issues two HttpOnly, SameSite=Strict cookies: `jx_access`, a 10-minute JWT built with FastEndpoints.Security (`JwtBearer.CreateToken`), and `jx_refresh`, an opaque token scoped to `/api/auth/refresh` whose SHA-256 hash is all the database keeps. The bearer handler reads the JWT from the cookie, so no token is ever reachable from JavaScript. `POST /api/auth/refresh` rotates the refresh token and issues a new access token without extending the session's expiry; the frontend fetch client calls it once on a 401 and retries the request.

Rotation tolerates two tabs. The session row keeps the hash of the previous refresh token and the time of the rotation. The rotation itself is one conditional `UPDATE … WHERE TokenHash = <the hash that was read>`, so of several simultaneous refreshes exactly one rotates and answers with both cookies. A request that loses that race, or that presents the previous token within 30 seconds of the rotation, answers 204 with a fresh access cookie only and leaves the refresh cookie alone: the browser keeps the refresh cookie the winning response set, whichever response arrives first, and the losing tab can retry its request at once instead of waiting for the other tab's cookies. Nothing is cleared on that path. The previous token presented after those 30 seconds is treated as a stolen copy: the session row is deleted and the cookies are cleared, so the legitimate browser has to sign in again. A token that matches neither hash answers 401 and clears the cookies without touching the session, because anyone can send a well-formed cookie for a known session id. `SignInAsync` and `RenewAsync` forget the previous hash, so a token from before a password change has no grace.

Deactivation and the failed-attempt lockout share Identity's lockout columns but mean different things. Deactivating a user sets `LockoutEnd` to `AppUser.DeactivatedUntil` (`DateTimeOffset.MaxValue`) and `AppUser.IsDeactivated` tests exactly that; it is what `isActive`, the bearer handler, the refresh endpoint and the background jobs look at. The temporary lockout is Identity's own (`Lockout.MaxFailedAccessAttempts` 5, `DefaultLockoutTimeSpan` 15 minutes, set in `DependencyInjection`) and is consulted only where a secret is verified, all of which goes through `AuthService.AttemptAsync`: the sign-in password, the authenticator or recovery code, the password that confirms 2FA setup and disable, the current password of a password change and the password that confirms a restore. A failure calls `AccessFailedAsync`; a locked account answers 429 `credentials.lockedOut` without checking the secret. The counter resets only when a sign-in completes, so the password step of a 2FA sign-in does not reset it and an attacker who knows the password cannot try codes without limit. A temporary lockout deliberately does not end the sessions the user already has: otherwise anyone who knows an email address could sign its owner out every 15 minutes. A deactivated user always gets `credentials.invalid`. The per-client throttle on the endpoints stays in place. `--recover-admin` clears both the lockout end and the counter.

`POST /api/users/{id}/reactivate` is the inverse of deactivation: it clears `LockoutEnd` and the failed-attempt counter and changes the security stamp. Deactivation had already changed the stamp, so no session from before it can come back; the second change only keeps the rule that every change of account state moves the stamp. For a user who is not deactivated it does nothing and answers 204, which makes it safe to repeat and means it cannot be used to lift a temporary lockout. It has no self rule because a deactivated administrator cannot be signed in to call it.

An installation always keeps one active administrator. Because nobody may demote or deactivate themselves, a single request can never remove the last one; two administrators removing each other at the same moment could. `UserService.ChangeRoleAsync` and `DeactivateAsync` therefore run in a transaction that first takes the advisory lock `AppLock.AdministratorChange` (`738192437`), and under it count the administrators who are not deactivated. If the target is the only one, the change answers 403 `user.lastAdministrator`. The second of two crossing requests waits for the lock, sees the first one's result and is refused. Reactivation and password reset only ever add an active administrator, so they do not take the lock. The tests remove the other administrators' role rows for the duration of a test, because the shared fixture administrator would otherwise always be the one that remains.

`POST /api/users/{id}/reset-password` is the administrator's way to let a member back in; since 2026-09-20 a member who has a working mailbox can also do it themselves through `POST /api/auth/forgot-password`, and both ways stay. The administrator sends the new password and their own current password. The confirmation goes through `ConfirmPasswordAsync`, so it counts toward the administrator's lockout, answers 400 `password.incorrect` for the same reason restore does, and is checked before the target is looked up, so a wrong password learns nothing about user ids. The password is set through Identity's reset token inside one database transaction, which applies the configured password validators (`password.tooWeak`) and changes the stamp, so every session of the target ends; the failed-attempt counter and a temporary lockout are cleared, a deactivation is left in place. `resetTwoFactor` also disables the authenticator, replaces its key and invalidates the recovery codes, the same three steps as `--recover-admin`. The target may be another administrator, never the caller (`user.selfChange`, 403): changing your own password belongs to the profile, where the session is renewed instead of revoked. The endpoint is throttled to 10 calls per five minutes per client. There is no forced change at next sign-in; see the [user management decisions](../decisions/user-management.md).

Each request still validates the security stamp and that the user is not deactivated (`JwtCookieAuthentication`), then checks that the `UserSessions` row named by the token's `sid` claim exists for that user and has not expired, so deleting a row (sign out, a revocation from the profile's list of signed-in browsers, a restore) ends that browser on its next request instead of when its 10-minute access token runs out. The check is one more lookup by primary key next to the user lookup that was already there. A token whose user id claim is missing or not a GUID fails authentication with 401 rather than reaching the ownership filters as an empty user. Role changes/deactivation therefore invalidate access and refresh tokens at once. Own-password and 2FA changes re-issue the initiating session's tokens with the new stamp (`ISessionService.RenewAsync`). FastEndpoints' `RefreshTokenService` is not used: it carries tokens in the request and response body and slides the refresh expiry, which contradicts both the cookie transport and the absolute session lifetime. First-run setup is serialized. 2FA setup/disable requires the current password, and setup refuses to expose a key for an already-enabled authenticator.

The Compose API persists Data Protection keys and the JWT signing key (`jwt-signing.key`, generated on first start unless `App:Jwt:SigningKey` is configured) in `auth_keys`. A key file that exists but is blank, as a crash during the first write can leave it, is replaced by a new key; a key file that cannot be read or written stops the start instead of falling back to a key that would change on every restart. Both are plain files there and only the `api` service mounts the volume; protect it as sensitive deployment data, see "Secrets at rest" in [quality requirements](../quality-requirements.md). The production overlay enables secure cookies. API/database development ports bind only to loopback; the frontend bind address is configurable.

A record prints every public property in its compiler-generated `ToString`, so a record that carries a secret would put it into any log line or exception message that formats the object. Every record that holds a password, a token, a two-factor code or key, the JWT signing key, the SMTP delivery settings or a Discord webhook URL therefore replaces that output: it declares `private bool PrintMembers(StringBuilder builder)` and prints the other members with the secret shown as `SecretText.Hidden` (`***`), or overrides `ToString` when there is nothing else worth printing. `SecretRedactionTests` in the unit tests finds every record in the API assembly whose string properties are named like a secret (`Password`, `Token`, `Secret`, `SharedKey`, `AuthenticatorUri`, `TwoFactorCode`, `Webhook`, or any property of a `…SigningKey` record), fills them with markers and fails when `ToString` shows one, so a new request record with a `Password` field cannot slip through. `UpdateMyDiscordRequest` prints `WebhookUrl = ***`, and `DiscordTarget`, the parsed webhook id and token, prints `Token = ***`. Name a new secret property so the test recognizes it, or extend the pattern.
