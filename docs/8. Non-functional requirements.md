# 8. Non-functional requirements

The qualities the app should hold to, beyond features. Scoped realistically for a self-hosted, mostly single-user tool — see [[1. Overview]] and [[7. Architecture notes]].

## Performance
- Adding a transaction feels instant (optimistic UI; sub-200 ms server response on a local network).
- Dashboard and transaction list load quickly for a personal-scale dataset (tens of thousands of rows). Index `Transaction` on `UserId`, `Date`, `AccountId`, `CategoryId`.

## Security
- Passwords hashed by [[4. Tech Stack#Back-end|ASP.NET Core Identity]]; never stored in plain text.
- **2FA (authenticator TOTP) + recovery codes** — **optional** per user ([[9. Open questions & decisions|D52]]); reasonable to leave off behind a WireGuard tunnel. **Email verification** for new accounts is **deferred** ([[9. Open questions & decisions|D53]]).
- Accounts are **admin-created** — no open self-registration ([[9. Open questions & decisions|D35]]).
- Every API route requires authentication and enforces per-user data isolation (`UserId` scoping, [[9. Open questions & decisions|D50]]). See [[6. API surface#Conventions]].
- Secrets (DB connection string, keys) live in a git-ignored `.env`, never in source control.
- HTTPS in transit via Caddy; remote access through WireGuard rather than public port exposure.
- **Rate limiting** on `/auth/*` (built-in .NET rate limiter) to blunt brute-force attempts ([[7. Architecture notes#Backend conventions]]).

## Reliability & backups
- Scheduled `pg_dump` to a file so data can be restored after loss; a dump also runs **before migrations apply** ([[9. Open questions & decisions|D54]]).
- Test the restore path at least once — a backup that hasn't been restored isn't proven.
- Database migrations (EF Core) are versioned and applied automatically on API startup, after that pre-migration backup ([[9. Open questions & decisions|D39]], [[9. Open questions & decisions|D54]]).

## Usability
- Fast entry is the top priority — the add-transaction flow is the core action ([[3. User flows#Flow: Add a transaction (core action)]]).
- Sensible defaults: date defaults to today; starter categories seeded.
- Numbers are always clear and exact; consistent currency formatting.

## Maintainability
- TypeScript on the front-end, C# on the back-end — type safety on both sides, sharpened by strongly-typed IDs and a `Money` value object ([[7. Architecture notes#Backend conventions]]).
- Consistent formatting/linting (Oxc; .NET analyzers).
- Single-command local run via Docker Compose, and a task runner for dev/codegen/test ([[7. Architecture notes#Developer experience & CI]]).
- **Testing:** backend integration tests on a real Postgres (Testcontainers) + architecture tests (NetArchTest). No end-to-end suite — deliberate ([[7. Architecture notes#Testing]]).

## Observability
- Structured logging (Serilog) on the API for errors and slow requests.
- Health-check endpoint for the API and database, wired to the Docker healthcheck.

## Privacy
- Self-hosted: data never leaves the owner's machine/network. No third-party analytics or tracking.

## Localization (i18n)
- The UI ships in **English** (default) from the first release with the **i18n structure in place**; **Lithuanian** translations follow (an MVP feature, [[2. Features#Must-have (MVP)]], [[9. Open questions & decisions|D21]]). Language is user-selectable and remembered.
- All user-facing strings come from translation files (no hard-coded text); the structure allows adding more languages later without code changes.
- **Locale-aware formatting** of dates, numbers, and currency (€) follows the selected language, via shared `Intl`-based formatters bound to the active locale ([[7. Architecture notes#Frontend conventions]]); money values themselves stay exact `decimal` — only their display is formatted.
- **Lithuanian plural forms** (one / few / many) are handled through i18next/ICU plurals — don't assume English's one/other.
- Server-originated messages (e.g. validation/error text in [[7. Architecture notes#Global error handling|ProblemDetails]]) should be localizable too, or kept generic so the client can map them to translated copy.

## Accessibility & compatibility
- Keyboard-navigable forms; reasonable contrast (Tailwind; dark mode is a later enhancement, see [[2. Features#Nice-to-have (later)]]).
- Targets current evergreen browsers; responsive layout for phone use.
