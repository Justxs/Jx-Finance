# Quality requirements

- Exact ledger values: canonical decimal-string API contract, validated numeric range, transfers excluded from spending, split allocation consistency.
- Isolation: verify personal/shared reads and mutations, member removal, account re-scoping, mixed-scope transfers, role changes and deactivated sessions.
- Reliability: migrations on fresh and existing databases, repeat-safe imports and bill confirmations, unique daily snapshots, repeat-safe reminder scans.
- Usability: preserve failed form submissions; expose edits and pagination; visible labels and keyboard focus; responsive desktop/phone layouts; meaningful empty and error states.
- Localization: EN/LT dictionary parity, translated controls and new bill reminders, locale-aware currency/date display, dot/comma decimal entry. Existing user-authored category names are data and are not automatically translated.
- Privacy: private deployment, no analytics, fonts bundled with the frontend rather than loaded from an external host. Application records never move funds.
- Observability: structured API logs, correlation IDs and database healthcheck. Production logs must not include passwords, recovery codes or bank upload contents. OpenTelemetry is off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set. When set, the API exports traces (ASP.NET Core requests except `/health`, outgoing HTTP calls, Npgsql commands), metrics (ASP.NET Core, HttpClient, .NET runtime, Npgsql) and Serilog logs with trace and span ids to that OTLP collector. The service name defaults to `jxfinance-api` and follows `OTEL_SERVICE_NAME`; the other standard `OTEL_EXPORTER_OTLP_*` variables (protocol, headers) apply. The collector must stay inside the private deployment, because telemetry carries request paths and SQL statement text. Wiring lives in `Extensions/TelemetryExtensions.cs`. The `aspire` Compose service is the standalone .NET Aspire dashboard and acts as that collector. It sits behind the `telemetry` profile, so a plain `docker compose up` does not start it. `scripts/dev.ps1` starts it and points the API at `http://localhost:4317`; the UI is at http://localhost:18888. For the containerized API, set `OTEL_EXPORTER_OTLP_ENDPOINT=http://aspire:18889` in `.env` and add `--profile telemetry`. The dashboard runs without authentication and keeps telemetry in memory only, so its ports bind to loopback and a restart clears it.
- Performance: paginated transaction/transfer lists; import capped at 10,000 entries; measure personal-scale data before adding caching. The frontend's bundle warning is a diagnostic, not evidence of unacceptable runtime performance.
- Secrets at rest: the application does not encrypt what it writes to its volumes. `auth_keys` holds the JWT signing key (`jwt-signing.key`) and the ASP.NET Core Data Protection key ring as plain files; whoever reads them can forge a session for any user and decrypt the stored broker tokens. `backups` holds gzip-compressed JSON of every table, including password hashes and two-factor secrets, and `db_data` holds the same data live. Encrypting these needs a key that lives somewhere other than the same disk, and where that is (a host secret store, a hardware token, a passphrase typed at start) is the operator's decision, so the application does not pretend to solve it. What the deployment does: both volumes are mounted only into the `api` service, the API runs as the non-root `app` user, PostgreSQL and the API publish no port under the production overlay, and development backups stay out of the image build context. What the operator must do: encrypt the host disk or the Docker data root (BitLocker, LUKS), keep `/var/lib/docker/volumes` readable by root only and keep other accounts out of the `docker` group (membership equals root), treat a downloaded backup like a password database, download backups and then delete them from the server instead of letting them accumulate, and after a suspected leak of `auth_keys` stop the API, delete `jwt-signing.key` and the key ring and start again, which invalidates every access token issued so far and makes stored broker tokens unreadable until re-entered (refresh tokens are random values checked against the database, so they are not forgeable from those files and keep working). `App:Jwt:SigningKey` can supply the signing key from the environment instead of the file, which moves the secret into `.env` rather than removing it.
- Supply chain: base images are pinned by digest and CI actions by commit SHA; CI fails on a NuGet package or a shipped frontend package with a known vulnerability (moderate and above). Advisories in development-only frontend packages are reported but do not fail the build, because they do not reach the browser bundle and would otherwise block every unrelated change until upstream tooling releases a fix. Updates arrive through the weekly pull request, never directly on `master`.
- Container hygiene: every service has a health check and bounded `json-file` logs (5 × 10 MB). The API image runs as a non-root user. `AllowedHosts` is restricted to the site hostname under the production overlay.

Passing static checks does not establish visual correctness. Keep exact test commands, results and any unverified deployment steps in Verification. Do not repeat historical claims of browser passes as current evidence.
