# 9. Open questions & decisions

A lightweight log: decisions already made (so they're not re-litigated) and questions still open. Link back to wherever each one bites.

> [!info] **Log convention.** This log was established **2026-05-30**; entries are append-only and treated as **Accepted** unless a later entry supersedes them. When a decision changes, add a *new* `D…` row and note `supersedes Dx` in it (and mark the old one `↩︎ superseded by Dy`) rather than editing history. First supersessions: **D50–D56** (the 2026-05-30 scope & sequencing reset — defer households, ledger before auth, optional 2FA, email decoupled, safer migrations).

## Open questions
Grouped by area. ⚠️ marks a gap or tension between existing decisions that needs resolving before/while building.

### Auth & users
*Resolved — admin-created users (D35); **2FA now optional** + 1-day cookie / remember-me (D36 → [[9. Open questions & decisions|D52]]); **email decoupled from onboarding & deferred** (D34/D44 → [[9. Open questions & decisions|D53]]); first admin via first-run setup page (D44).* Still open:
- **When to require 2FA:** keep it optional, or require it only if/when the app is exposed beyond the WireGuard tunnel? → [[9. Open questions & decisions|D52]]
- **Lost-authenticator recovery (only matters if you enable 2FA):** recovery codes only, or also an admin-triggered reset? → [[9. Open questions & decisions|D52]]
- **Remember-me duration:** how much longer than the 1-day default, and sliding or absolute expiry? → [[9. Open questions & decisions|D36]]

### Money & data
*Resolved — EUR + currency-aware (D40), 2 decimal places (D41), UTC storage / frontend formatting (D42), loans as `Debt` & credit cards deferred (D43), **period boundaries in one configured timezone** ([[9. Open questions & decisions|D56]]).* Still open:
- **Rounding policy for derived figures:** how are computed values (e.g. budget remaining, net worth) rounded for display vs. storage? → [[5. Data model#Conventions]]

### Import & categorization
*Resolved — format mapped from a real export and dedup keyed on the bank entry number (D47).* Still open:
- **Transfer/cash detection accuracy:** the heuristic that flags own-account transfers and cash withdrawals is best-effort — how aggressive, and is a manual "this is a transfer" toggle enough? → [[6. API surface#Import (v1.2)]]
- **Auto-categorization design (later):** rule format (keyword/merchant match)? Which ML approach, and when is there enough data for it to help? The import data is rich in repeating payees (Lidl, Maxima, Spotify…) — good rule fodder. → [[2. Features#Nice-to-have (later)]]

### Recurring bills & notifications
- **Reminder scheduling:** is a daily job frequent enough? (The client picks up new notifications via refetch-on-focus, D38.) → [[7. Architecture notes#Background jobs]]
- **Unconfirmed bills:** if a due bill is never confirmed, do reminders repeat, and does `NextDueDate` advance anyway or wait? Avoid reminders piling up. → [[5. Data model#RecurringBill]]
- **Bill end conditions:** do recurring bills need an end date / occurrence count (e.g. a 12-month loan)? Currently open-ended.
- **Notification types beyond bills:** reuse the `Notification` model for budget-exceeded / goal-reached? → [[5. Data model#Notification]]

### Net worth
- **Asset valuation cadence:** manual updates only, or live pricing pulled in later? → [[5. Data model#Net worth (v1.2)]]
- **Snapshot frequency:** monthly automatic, on-demand, or both? → [[5. Data model#NetWorthSnapshot]]

### Households & sharing (deferred — D50)
*Deferred out of the MVP ([[9. Open questions & decisions|D50]]); these are **parked** until the sharing milestone ([[11. Milestones & tasks#M6 — Households & sharing]]) and don't affect the single-user build. Recorded so the thinking isn't lost:*
- **Re-scoping an account:** can an account flip Personal ↔ Shared after it has history, and what happens to its past transactions' visibility? (Leaning: allowed, and history follows the account.)
- **Shared reference data:** do Categories (and Budgets/Goals) get their own Personal/Shared scope, or are categories always personal even on shared accounts? (Leaning: same scope model; shared accounts use the household's shared categories.)
- **Leaving / removing a member:** what happens to records they created in a household — stay shared (owned by the household) or revert?
- **Default active scope:** on login, default to Personal or the last-used household?

### Frontend & realtime
*Resolved: optimistic list-only updates + loading states for server-computed values (D30), refetch-on-focus (D38), pagination on large lists (D37).* Still open:
- **Pagination style:** offset vs. cursor paging, and the default page size? → [[6. API surface#Conventions]]
- **Localized number input:** Lithuanian uses a comma decimal separator — parse and format inputs per locale. → [[8. Non-functional requirements#Localization (i18n)]]

### Ops & deployment
- **Backups:** pg_dump cadence, retention (how many kept), and stored *off* the app's own disk? Is a restore drill scheduled? → [[8. Non-functional requirements#Reliability & backups]]
- **Seed data:** which starter categories ship, and are their names localized (EN/LT)? Seeded per user when the admin creates them. → [[5. Data model#Category]]
- **SMTP provider:** self-hosted SMTP relay vs. a transactional provider (and the from-address/domain) for the email features. → [[4. Tech Stack#Back-end]]
- **HTTPS inside WireGuard:** is Caddy TLS needed within the tunnel, or is plain HTTP acceptable there? → [[7. Architecture notes#Deployment topology]]

### Tooling
- **CI platform:** GitHub Actions vs. Azure DevOps (your EnergyKlik repo uses Azure Pipelines) — pick one for build + the client-drift check. → [[7. Architecture notes#Developer experience & CI]]

## Risks & mitigations
Things that could hurt later, and the planned response. Not blockers — watch items.

| Risk | Impact | Likelihood | Mitigation / trigger to act |
|------|--------|-----------|------------------------------|
| **Computed balances slow down** as transactions grow | Dashboard/list latency | Low at personal scale | Indexes already planned (D2); if it bites, add a cached/materialised balance or rolling snapshot. Revisit only when measured |
| **Migrations-on-startup** misbehave (a bad migration, or two instances racing) | Corrupt/locked financial data on a deploy | Low (single instance now) | **A `pg_dump` runs before migrations apply ([[9. Open questions & decisions\|D54]])** so a bad one is recoverable; fine for single-instance Docker (D39); if scaling out, gate migrations behind a one-shot job / advisory lock |
| **SMTP deliverability** (verification, reset, reminders land in spam or fail) | Users can't verify / reset; reminders silently lost | Medium | Use a real relay or transactional provider (open question), set SPF/DKIM, log send failures, surface "resend" |
| **Backups never actually restore** | Total data loss despite "having backups" | Medium | Schedule a real restore drill (NFR); store dumps off the app's disk; alert on backup-job failure |
| **Lost authenticator with no recovery path** (only if you enable optional 2FA, [[9. Open questions & decisions\|D52]]) | User fully locked out | Low (2FA optional) | Recovery codes at enrolment; admin-triggered 2FA reset; or simply leave 2FA off behind WireGuard |
| **CSV format drift** (Swedbank changes columns/encoding) | Importer breaks or mis-maps | Low–Medium | Parsing is row-type + header driven (D47); fail loudly on unexpected shape rather than importing garbage; keep a sample fixture in tests |
| **Transfer/cash auto-detection mis-flags** rows on import | Wrong reclassification, skewed spending | Medium | Best-effort flag only; the user confirms per row (D9); never auto-commit a reclassification |
| **Per-user data leakage** (the `UserId` filter is the isolation boundary) | A user sees or edits another user's rows | Low (single user now) | One central `UserId` filter on *every* query; never trust a client-supplied id; cover with integration tests once a second user exists. Household/scope sharing is deferred ([[9. Open questions & decisions\|D50]]), so there's no cross-scope surface in the MVP |

## Parking lot
Ideas to revisit but not decide now: multi-currency base + FX, tags vs. categories overlap, PWA/offline scope, real-time multi-device sync (WebSockets), and live investment pricing. Also the heavier .NET-API patterns scoped out for now — **CQRS/MediatR, API versioning, distributed caching (Redis), message brokers / durable schedulers (Hangfire/Quartz), and an OpenTelemetry observability stack** — each to be added only when a real need appears ([[7. Architecture notes#Backend conventions]]).
