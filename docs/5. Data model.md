# Data model

Money uses C# decimal and PostgreSQL numeric(18,2). API money is a canonical dot-decimal string; currency is EUR. Amounts exceeding the column's range or using grouping separators are rejected. Money rounds to two places with .NET's default midpoint-to-even policy. Browser numbers are used for display/charts; persisted values go through validated decimal strings.

Accounts have a starting balance. Current balance is computed from transactions and both transfer directions; it is not a stored running total. Transactions carry account, date, flow type, amount, description, source and optional bank reference. Split transactions use TransactionLine rows; editing replaces the lines, and deleting removes them physically. Other owned entities normally use soft deletion and timestamps.

Transactions have a unique account/import-reference index, including soft-deleted rows. TransferImports retains immutable bank-entry receipts for imported/matched transfers and a unique account/reference. Normal transaction import history and transfer receipts are checked together. Imports serialize per target account with a PostgreSQL transaction advisory lock.

Accounts and Categories carry owner, Personal/Shared scope and optional household. HouseholdMembership assigns Owner/Member independently from application Admin/Member roles. Transaction visibility follows the account. Transfer visibility follows either endpoint; mutation requires both. Budgets, goals, assets, debts, bills, notifications and net-worth snapshots remain personal.

Deleting a category unsets category references in transactions, split lines and bills, and retires dependent budgets. Archiving an account hides its transactions through the account visibility filter. A transfer's visible side continues to contribute to the balance of its remaining visible account.

A net-worth snapshot is unique per user/local date. Reads and the hourly job update today's value under a per-user lock. The reliability migration retains the latest row if older concurrent reads created duplicate daily snapshots. Historical points represent observations on those dates, not a reconstruction of days when the application was off.

RecurringBill stores kind, optional amount/account/category, cadence, NextDueDate, reminder lead days and active state. Confirmation carries ExpectedDueDate; a per-bill database lock and date concurrency token prevent duplicate occurrence posting. In-app bill notifications store the bill name and ISO due date so the client can localize the sentence.
