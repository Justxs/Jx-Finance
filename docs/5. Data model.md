# Data model

Money uses C# decimal and PostgreSQL numeric(18,2). API money is a canonical dot-decimal string with the currency in a sibling field, as a lowercase ISO 4217 code such as `eur`. Amounts exceeding the column's range or using grouping separators are rejected. Money rounds to two places with midpoints away from zero (`Money.Round`), so 0.125 becomes 0.13 and -0.125 becomes -0.13. Browser numbers are used for display/charts; persisted values go through validated decimal strings.

Accounts have a starting balance in their main currency. Balances are computed per currency from the starting balance, transactions, both transfer directions and both sides of currency conversions; nothing is a stored running total. `currentBalance` is those balances valued in the account's main currency at the newest rate, and `reportingBalance` is the same in the reporting currency. Transactions carry account, date, flow type, amount, description, source and optional bank reference. Split transactions use TransactionLine rows; editing replaces the lines physically, because the new set is what takes their place, while deleting the transaction leaves them alone so that restoring it brings its categories back. Other owned entities normally use soft deletion and timestamps.

Soft deletion is now reversible for the records whose delete touches nothing else. `DeletionEntry` is the trash row: an `OwnableEntity` holding the `Kind` (stored as its name), the `EntityId` of the deleted record, the `Description` it read by at the time (at most 200 characters), `DeletedAt`, a nullable `RestoredAt` and a nullable `CompanionId` for the fee transaction a currency conversion takes with it. Indexes on (UserId, DeletedAt) and (Kind, EntityId) serve the list and the restore lookup. Each feature's `DeleteAsync` writes the entry through `IDeletionRecorder` in the same `SaveChanges` as the soft delete, so one cannot exist without the other, and a cascade such as a conversion's fee gets no entry of its own. Restoring flips `IsDeleted` back and stamps `RestoredAt`, again in one save. Fourteen kinds are covered — transaction, transfer, conversion, budget, goal, asset, debt, recurring entry, investment entry, category, tag, categorization rule, household and attachment. The last four also clear foreign keys, remove join rows or un-share records, so their delete writes one `DeletionChange` row per row it rewrote: the entry id, a `Kind` naming what was done (`TransactionCategory`, `LineCategory`, `RecurringBillCategory`, `Budget`, `TransactionTag`, `RuleTag`, `AccountShare`, `CategoryShare`, `TagShare`, stored as its name) and the `RowId`, with (DeletionEntryId, Kind, RowId) as the primary key and a cascading foreign key to the entry. The previous value is implied by the entry, so it is not stored. A restore puts back only the recorded rows that are still in the state the delete left them in. Archiving an account stays its own named operation. The 30-day retention window is a read filter and nothing purges the rows, for the reasons in [Trash and undo](<features/29. Trash and undo.md>); the one exception is an attachment, whose row and file are removed 30 days after it or its transaction was deleted.

`AuditEvent` is the household activity log: one row per thing a person did to a record shared into a household, written from the `SaveChangesAsync` override of `AppDbContext` out of the change tracker, in the same save as the change. It is a plain class — no owner column, no soft delete, no query filter — holding the `HouseholdId` (cascading foreign key), the `ActorUserId` (restricting foreign key to the user), `OccurredAt`, the `Action` and `EntityKind` stored as their names, a nullable `EntityId`, the `Description` it read by at the time (at most 200 characters), a nullable `Count` for an import or bulk edit, and `Changes`, a `jsonb` list of at most 12 `{field, from, to}` display strings, each value cut to 120 characters. Indexes on (HouseholdId, OccurredAt) and OccurredAt serve the read and the prune. A transfer between two households writes a row in each; personal records write none; an import or bulk edit writes one summarising row per household. `AuditRetentionJob` deletes rows older than 400 days (`AuditEvent.RetentionDays`). Details in [Audit log](<features/30. Audit log.md>).

Transactions have a unique account/import-reference index, including soft-deleted rows, an account/date index that serves the account filter of the ledger and the balance queries, and the `TransactionTags` index on (TagId, TransactionId) that serves the tag filter, which becomes one `EXISTS` subquery per chosen tag rather than a lookup per row; investment entries have the same pair, and transfers are read by user and date or through their two account foreign keys, so they need no further index. TransferImports retains immutable bank-entry receipts for imported/matched transfers and a unique account/reference. A transfer takes at most one receipt per account: a second bank entry of the same account that points at an already matched transfer is refused with `import.transferAlreadyMatched`, while the entry of the other account still matches it. A receipt also fixes part of its transfer against later edits: the date, the receipt's account staying on its side of the transfer, and the amount on that side; the description, the other account and, between currencies, the other amount stay editable. Broker deposits and withdrawals carry the same receipt on the brokerage account. Normal transaction import history and transfer receipts are checked together. Imports serialize per target account with a PostgreSQL transaction advisory lock.

A `Tag` is the second way to classify a transaction and is built from the same pieces as a `Category`: it is an `OwnableEntity` that implements `IShareable`, so it gets the owner column, its restricting foreign key and the shareable query filter with the active-household narrowing without any code of its own. It stores a name of at most 50 characters, the scope and the optional household, and nothing else — no icon and no flow type, because a tag answers "what was this payment for" rather than "what kind of spending was it", and the same tag is meaningful on income and on an expense. The name is unique per owner ignoring case, checked in `TagService` with a case-insensitive comparison and answered with 409 `conflict.duplicate`, and backed by a unique index on (UserId, Name) filtered to `IsDeleted = false`, so the exact duplicate of a race is refused by the database and a deleted name becomes free again.

`TransactionAttachment` is a file attached to a transaction: an `OwnableEntity` whose `UserId` is the uploader and whose `CreatedAt` is the upload time, holding the `TransactionId` (restricting foreign key), the sanitized `FileName` (at most 120 characters, shown only, never a path), the `ContentType` detected from the file's first bytes (at most 60), `SizeBytes` and the lowercase hex `Sha256` (`character(64)`). The bytes live in the attachment directory under the row's id, not in the database. Its query filter is its own rather than the owner filter: an attachment is visible when it is not deleted and its transaction is, so it follows the account's sharing and the active household, a household member sees the files another member uploaded, and deleting or archiving hides the files with the transaction without touching them. One index on (TransactionId, CreatedAt) serves the list and the ledger's count. A transaction holds at most ten files of at most 10 MB. Details in [Attachments](<features/31. Attachments.md>).

A `Debt` can carry its repayment terms in five columns added on 2026-09-21: `LoanAmount` (numeric(18,2)), `FirstPaymentDate` (date), `TermMonths` (integer, 1 to 600), `MonthlyPayment` (numeric(18,2)) and `AmortizationType` (integer, `Annuity` = 0 by default, `Linear` = 1). The first four are nullable, so a debt stored before has no terms and no schedule; `TermMonths` and `MonthlyPayment` are never both set. The repayment schedule is computed from them on request by `Common/Amortization/AmortizationCalculator` and is not stored, and `OutstandingAmount` stays the recorded balance that net worth subtracts. See [Debt amortization](<features/32. Debt amortization.md>).

`TransactionTag` is the many-to-many row between `Transaction` and `Tag`: the two ids are its primary key and there is a second index on (TagId, TransactionId) for the ledger filter and the report breakdown. Like `TransactionLine` it is a plain class rather than an `EntityBase`, so it has no timestamps, no soft deletion and no query filter; it is only ever reached through a transaction or a tag, and both of those are filtered. Split lines carry no tags: a tag describes the payment, the split divides it between categories, and putting tags on both would let one amount count twice under the same tag. A transaction carries at most ten tags, which is also the cap on the ledger's tag filter.

A `CategorizationRule` is an `OwnableEntity` and deliberately not an `IShareable`: it is a personal habit rather than a household fact, so the plain owner filter is its whole visibility story and nobody but the owner can list, edit, reorder, delete or run it. It stores a name, a 0-based `Position` that is kept dense per owner, the condition (`Match` of `Contains`, `StartsWith` or `Exact`, plus a `Pattern` of at most 200 characters), the optional narrowings (`AccountId`, `MinAmount`, `MaxAmount`) and the optional `CategoryId` it sets; the tags it adds live in `CategorizationRuleTags`, a plain join row of (RuleId, TagId) built exactly like `TransactionTag`, cascading from the rule and restricted on the tag. A rule has to set a category, a tag, or both, and at most 100 rules belong to one user. Positions are renumbered 0, 1, 2 inside the same database transaction whenever a rule is moved or deleted, so a gap or a tie is not representable. The index on (UserId, Position) serves the only read there is, the ordered list. What a rule reaches is a separate question from who owns it: a run evaluates through the account-filtered transaction query, so a rule of one member does touch a shared account's rows, the same way that member could have set the category by hand.

Accounts, Categories and Tags carry owner, Personal/Shared scope and optional household. HouseholdMembership assigns Owner/Member independently from application Admin/Member roles. Transaction visibility follows the account. Transfer visibility follows either endpoint; mutation requires both, and an update that changes an account requires the new account as well. Budgets, goals, assets, debts, bills, notifications and net-worth snapshots remain personal.

A request can narrow that visibility to one household. No column stores the choice: `ICurrentUser` gained an `ActiveHouseholdId` that the HTTP implementation reads from the validated `X-Active-Household` header, defaults to "no household" everywhere else, and that the shareable query filter appends to as "the record is personal, or its household is the active one". Everything that hangs off an account — transactions, transfers, conversions, investment entries — narrows with it, because those filters already ask whether the account is visible. The filter narrows and never widens: the membership condition that was there before still has to hold, so a household the caller is not a member of stays invisible whatever the header says.

Deleting a categorization rule takes its `CategorizationRuleTags` rows with it and renumbers the rules below it; the transactions it filled in earlier keep their category and their tags, because a rule writes once and owns nothing afterwards. Deleting a category unsets category references in transactions, split lines and bills, and retires dependent budgets. Those two, a tag delete and deleting a household are the deletes that rewrite other rows; each records the ids it rewrote as `DeletionChanges`, which is what makes them restorable. Deleting a tag is the same rule applied to the join table: its `TransactionTags` rows are deleted outright inside one database transaction and the tag is then soft-deleted, while the transactions themselves — their amounts, categories, split lines and dates — are untouched. The join rows are deleted rather than soft-deleted because the pair of ids is the whole record and a retired pair would only add a condition to every filter query. Archiving an account hides its transactions through the account visibility filter, and nothing else: no foreign key is cleared and no row is rewritten, so restoring it only sets `IsDeleted` back and everything hanging off it is visible again. The one column that can change while it is archived is its sharing, because removing its owner from the household or deleting the household makes it personal exactly as it does an active account. A transfer's visible side continues to contribute to the balance of its remaining visible account.

A net-worth snapshot is unique per user/local date. Reads and the hourly job update today's value under a per-user lock. The reliability migration retains the latest row if older concurrent reads created duplicate daily snapshots. Historical points represent observations on those dates, not a reconstruction of days when the application was off. Snapshot columns are numeric(18,2) like every money column; when a total of the day does not fit, the totals are still answered and no snapshot is written for that read. Goal amounts are never negative: the target is above zero and the current amount is zero or more.

A goal also stores where its progress comes from: `Funding` (manual or account), a nullable `FundingAccountId` pointing at an account with delete behaviour Restrict, and `FundingSharePercent`, a whole percentage from 1 to 100 that defaults to 100. A manual goal keeps the account empty and reports the stored `CurrentAmount`. A funded goal keeps the account set and reports that share of the account's reporting balance, computed while the request is answered from the same balance service the accounts endpoints use, clamped at zero and never written to a column; its `CurrentAmount` stays as it was and is ignored, which is what lets an edit move a goal between the two modes without losing the typed amount. Because archiving an account is a soft delete and the row stays, the foreign key never blocks it: the account simply drops out of the query filter, and the goal answers a null progress instead.

A budget stores its category, its limit, a `Period` (`Monthly`, `Weekly`, `Quarterly` or `Yearly`, held as the integer the enum declares, with `Monthly` pinned at 0 so rows written before periods existed keep their meaning) and `RolloverEnabled`, added with a default of false so those same rows behave exactly as before. It stores no dates: the window it is read against is derived from the period and from today in the installation time zone, and for a weekly budget from `InstanceSettings.FirstDayOfWeek`, by `BudgetWindow` in the domain. A category may hold one budget per period, checked in the service rather than by a unique index, and the carry a rollover budget shows is recomputed on each read by walking back at most twelve windows, never past the window that holds the budget's `CreatedAt`. `CategoryAttribution` carries the transaction date for this, so one query over the whole walked span is bucketed per window in memory.

RecurringBill stores what a confirmation writes, kind, optional amount/account/category, cadence, NextDueDate, reminder lead days and active state. `Shape` (`Expense`, `Income` or `Transfer`) is an integer with `Expense` pinned at 0, so every row written before shapes existed still means what it meant. `ToAccountId` is a second nullable account with delete behaviour Restrict, set only by a transfer, where `AccountId` is the account the money leaves and `ToAccountId` the account it arrives in; an expense or an income leaves it empty and a transfer leaves `CategoryId` empty. The table keeps its name: renaming it would mean a migration that no backup taken by an older version could be restored into, since a backup file names the tables it carries. Confirmation carries ExpectedDueDate; a per-entry database lock and date concurrency token prevent duplicate occurrence posting.

`SubscriptionDismissal` is the only row subscription detection writes. It is an `OwnableEntity` and not an `IShareable`, so the plain owner filter is its whole visibility story: a dismissal is one person's judgement about one group, and two members of a household may disagree about a payment on the account they share. It stores nothing but the group — `AccountId` with delete behaviour Restrict, and `Description`, the normalized description at most 200 characters long — and never the transactions that produced the group, which is what makes a dismissal survive a new payment arriving in it. A filtered unique index on (UserId, AccountId, Description) where `IsDeleted = false` keeps one row per group per person and lets a group be dismissed again after a row is deleted; the service looks for the row first, so dismissing twice is a no-op rather than a conflict. Nothing else references the table and detection itself writes nothing at all. Backups need no change: `BackupDatabase.ReadShapes` enumerates the tables from the EF model rather than from a list, so a new table is carried the moment it is mapped.

Notification is the shared row every producer writes: owner, `Type` (`BillDue`, `BudgetWarning`, `BudgetExceeded`), a `Title` that names the thing the notification is about, a plain-text `Message`, `RelatedType` and `RelatedId` pointing at the row that caused it, the channel and the read flag. It also stores `Payload`, a nullable `jsonb` column holding a `NotificationPayload` record — `DueDate`, `ThresholdPercent`, `Period` and `Shape`, each optional and each filled only by the kinds that need it — so the client localizes the sentence from typed values instead of parsing text. The column is nullable because bill reminders written before it existed carry the ISO due date in `Message`; `NotificationMapper` reads that date back into the payload for those rows, which is why the migration adds a column and rewrites nothing. `RelatedId` is a bare `Guid?` with no foreign key, so a notification outlives the bill or budget it came from.

UserSessions holds one row per signed-in browser: the user, the SHA-256 hash of the current refresh token, the hash of the token it replaced together with the time of that rotation, the security stamp the session was issued under, whether the cookies persist, an absolute expiry, the first 256 characters of the `User-Agent` header sent at sign-in (null when there was none) and `LastSeenAt`, which is set at sign-in and on every refresh token rotation. The user agent and the three times are what the profile's list of signed-in browsers shows; the hashes and the stamp are never returned by the API. The previous hash is accepted for 30 seconds after the rotation so that two tabs refreshing at once both succeed; presented later it counts as a stolen token and the row is deleted. Rows are also hard-deleted on logout, when the user signs another browser out or signs out everywhere else on the profile, on a renewal that finds the session expired, the stamp changed or the user deactivated, and when the user next signs in after they expire or their stamp changes; deleting a user cascades. The table is not owner-filtered because it is read before a request is authenticated: the refresh endpoint finds the row from the cookie, and the bearer handler checks on every request that the row behind the access token still exists. It is left out of backups, so the new columns need nothing there.

## Currency

`Money` is an amount plus a `Currency`. On `Account.StartingBalance`, `Transaction.Amount`, `Transfer.Amount`, `Transfer.ReceivedAmount`, `CurrencyConversion.FromAmount` and `CurrencyConversion.ToAmount` it is mapped as an EF Core complex property onto two columns, the numeric amount and a three-letter uppercase code. Budgets, goals, assets, debts, recurring bills and net worth snapshots keep a bare amount and are always in the reporting currency. Split lines share their transaction's currency.

`Transaction.ReportingAmount` is the amount in the reporting currency, fixed when the transaction is created or edited using the rate for its date. Every income, expense, budget, trend and breakdown total sums this column, so past periods do not move when rates change. Split lines take a proportional share of it. Account totals, the dashboard balance and net worth are different: they value what is held today, so they use the newest rate.

`CurrencyConversion` belongs to one account and records the amount sold, the amount bought, the date and an optional `FeeTransactionId` pointing at the expense transaction created for the fee. It is visible to anyone who can see the account. An update keeps the account and rewrites the rest; the fee transaction is created, updated or soft-deleted in the same save, and its `ReportingAmount` is taken again at the rate for the new date. A conversion with `ImportRef` set came from a broker and is read-only.

`ExchangeRate` has the key (Date, Currency) and stores units of that currency per one euro, as published by the European Central Bank. Any pair is derived by crossing through the euro. The reporting currency is part of the installation settings. It is one value for the whole installation because shared budgets and categories would otherwise have no single meaning. Changing it revalues every stored `ReportingAmount`, soft-deleted transactions included, at the rate for each transaction's date, inside the same database transaction as the settings update.

## Installation settings

`InstanceSettings` is a single row with Id 1: installation name, the feature switches as a `FeatureFlags` complex property (one boolean column each), reporting currency, the enabled currency codes as a comma-separated string, exchange-rate sync flag, default language, IANA time zone, first day of the week, default account id and default page size. Until the row exists, values come from `App:ReportingCurrency`, `App:ExchangeRates:Enabled`, `App:DefaultCulture` and `App:TimeZone`, so an upgraded installation behaves as before. An empty currency list means every currency.

The same row also holds the mail server: `SmtpEnabled`, `SmtpHost`, `SmtpPort` (default 587), `SmtpEncryption` (`None`, `StartTls` or `SslOnConnect`, stored as its name), `SmtpUserName`, `SmtpProtectedPassword`, `SmtpFromAddress` and `SmtpFromName`. The migration gives existing installations `SmtpEnabled` false, port 587 and `StartTls`, so the enum column never reads back an empty string. `SmtpProtectedPassword` holds ciphertext from `IDataProtectionProvider.CreateProtector("JxFinance.Smtp.Password")`, exactly like `BrokerConnection.ProtectedToken`: it is stored, it travels inside a backup and it is readable only where the data protection keys are the same, and no API response ever carries it — `SmtpSettingsResponse` answers `hasPassword` instead. `InstanceSettingsSnapshot` exposes all of it as an `SmtpSettingsSnapshot` whose `IsConfigured` is what decides whether anything is queued at all.

## Email

`EmailMessages` is the outbox: `Id`, `Kind` (`PasswordReset`, `EmailVerification` or `BillReminder`, stored as its name), the recipient address and name, the subject and the plain-text body, an optional `DedupeKey` with a unique index filtered to non-null values, `CreatedAt`, `NextAttemptAt`, a nullable `SentAt`, an `Attempts` counter and the last error. There is a second index on (`SentAt`, `NextAttemptAt`), which is how `EmailOutboxJob` finds what is due. The row is a plain entity, not an `OwnableEntity`: it carries no owner, no soft deletion and no query filter, because it is written by background jobs and by anonymous requests where there is no current user, exactly like `UserSession`. It is also the second table left out of backups, for the reason in the decision log. A message is given up on after five attempts and removed a week later, together with sent rows.

`AspNetUsers` gains `BillReminderEmails`, a boolean defaulting to false — the per-user preference for a reminder email beside the in-app notification — and Identity's own `EmailConfirmed` starts to mean something: a user created by an administrator now starts unconfirmed and is confirmed through an emailed link. Only the reminder email looks at it.

`AspNetUsers` also carries `DashboardLayout` since 2026-09-21, a nullable `jsonb` value `{ "order": [...], "hidden": [...] }` of dashboard card ids stored as strings; null means the default layout. Unknown ids are ignored on read so a layout survives a version that adds or removes a card, and the column travels with the user row through backups. See [Dashboard](<features/17. Dashboard.md>).

## Investments

`Security` is installation-wide reference data with no owner: symbol, name, ISIN, exchange, type, currency, the broker's contract id, and the last known price with its date. Symbol plus currency is unique. Because the row is shared, writes are split by who may make them: any signed-in user can add a security, only an administrator can change symbol, name, ISIN, exchange, type, currency or the broker contract id, and the last price with its date can be set by an administrator or by a user who has an open position in that security on an account visible to them. A broker import writes securities and prices under its own rules and is not subject to this.

`SecurityPrice` is the price history of a security: security id, date and price to eight decimals, with the security id and the date as the primary key, so there is one price per security and date. Like `Security` it has no owner and is installation-wide; it is a plain row without soft delete, removed with its security. Every write of a price goes through `SecurityPriceBook`: the set-price operation, a security created or updated with a price, and the mark price of each open position in an Interactive Brokers report. Writing a date that already has a row replaces its price. `Security.LastPrice` and `LastPriceDate` stay as the denormalized newest point: they move only when the written date is the same as or later than the current one, and deleting a point sets them to the newest remaining point or to empty. Trade prices are never recorded as prices of the day. The migration that added the table copied every existing last price into one row per security. There is no market data feed, so dates between points have no row and a valuation uses the latest point on or before its date. The portfolio value over time is computed from this table and the ledger on request and is not stored; net worth snapshots remain the only stored value series.

`InvestmentTransaction` belongs to an account and is visible to whoever can see that account. It holds the type (buy, sell, dividend, withholding tax, interest, fee, split), date, quantity and price to eight decimals, the fee, a signed `CashAmount` in its own currency (negative when cash left the account, fees included), `ReportingAmount` frozen at the rate for the date like `Transaction.ReportingAmount`, a source, and the broker's id in `ExternalId`, unique per account. A split stores the ratio in `Quantity`, as new shares per old share, and moves no cash; a split imported from Interactive Brokers has `ExternalId` `ibkr:ca:<action id>`. Within one day the replay applies splits first, then buys, then sells, because trades on the day a split takes effect are already in new shares. Holdings, cost basis and gains are never stored: `Portfolio.Positions` replays the entries first in, first out.

Account balances add the sum of `CashAmount` per currency to the existing movements. `AccountResponse.HoldingsValue` is the market value of open positions at the newest exchange rate, and `ReportingBalance` includes it, which is how the dashboard total and net worth pick up investments with no change to the snapshot table. Changing the reporting currency revalues `InvestmentTransaction.ReportingAmount` together with transactions. Reports and the dashboard sum that `ReportingAmount` for dividend, interest, withholding tax and fee entries while the `Investments` feature is on; no table or column was added for it, and the entries still have no category.

`BrokerConnection` is owned by one user and unique per account: Flex Query id, the token protected with ASP.NET Data Protection, an optional funding account, an enabled flag, and the time and error of the last sync. `CurrencyConversion.ImportRef` and the existing `TransferImport` receipts deduplicate imported currency trades and deposits.

## Model configuration and migrations

`AppDbContext.ConfigureConventions` maps the value types once: every `IStronglyTypedId<TSelf>` struct is stored as a uuid through `StronglyTypedIdConverter<TId>`, `Money` properties that are not complex properties are stored as numeric(18,2) through `MoneyConverter`, and `Currency` is stored as its three-letter code. A nullable id or amount needs nothing extra. Other decimal columns keep explicit precisions because they differ (prices and quantities use eight decimals, the interest rate uses 5,2). Each entity has an `IEntityTypeConfiguration<T>` class under `Infrastructure/Data/Configurations`, loaded with `ApplyConfigurationsFromAssembly`; the context adds the restricting `UserId` foreign key to every `OwnableEntity` and the query filters, where an entity that implements `IAccountScoped` is visible through its account.

Migrations are never squashed or renamed. A backup records the id of the last applied migration and `BackupService` compares it with the running application, so rewriting history would make existing backups unrestorable. To keep the folder small instead, the `*.Designer.cs` file of every migration except the newest has an empty `BuildTargetModel`; the attributes that carry the migration id remain. The generated idempotent script was identical before and after that trim. The cost concerns `dotnet ef migrations remove`, which rebuilds the model snapshot from the designer of the migration before the one it removes. A freshly added migration can still be removed, because the newest committed migration keeps its full designer, but removing further back would produce an empty snapshot; an old migration is never removed anyway because deployed databases have applied it. Once a new migration has shipped, the designer of the one before it can be emptied the same way.
