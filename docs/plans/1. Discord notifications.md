# Plan: Discord notifications

Status: planned 2026-09-25. Size M. Build this first of the three plans, because the other two add notification kinds that should arrive on Discord without extra work.

## Outcome

A member pastes a Discord webhook URL into their profile, picks which notification kinds go there, and from then on every in-app notification of those kinds is also posted to that Discord channel. An administrator decides whether the installation may talk to Discord at all, because it is outbound traffic and the product promises that nothing leaves the server unless an administrator switched it on.

Nobody sees anyone else's notifications: the webhook is personal, like the bill reminder email preference.

## Decisions

| Topic | Decision | Rejected | Why |
| --- | --- | --- | --- |
| Ownership | One webhook per user, set on the profile; an installation switch in Settings allows or stops all Discord traffic | One installation webhook; both | Budget and bill alerts are personal. One shared channel would show them to everyone in it |
| Installation switch | A setting with its own enabled flag, like SMTP, not a feature switch | A `Feature.Discord` flag | Email set the precedent: delivery channels are settings, feature switches hide screens |
| Delivery | A `DiscordMessages` outbox table drained by a background job, like `EmailMessages` | Posting from the job that raised the notification | No job or request may wait for an outside service; retries and rate limits need a row to live on |
| Where fan-out happens | One `INotificationPublisher.Publish(notification)` that every producer calls; it adds the in-app row, the email (where one exists) and the Discord message to the same context | A change-tracker hook in `AppDbContext` like the audit log; separate calls in each job | Explicit, testable, and it moves the bill reminder's email enqueue out of the job. An architecture test keeps `db.Notifications.Add` inside the publisher |
| Message text | Built server-side at enqueue time in the installation language by a new `NotificationTexts` (en/lt), stored in the outbox row | Reusing `Notification.Title`/`Message` | `Message` is raw data (an ISO date, a percentage), not a sentence |
| Webhook URL at rest | Encrypted with Data Protection (purpose `JxFinance.Discord.Webhook`), never returned; the response carries `HasWebhook` | Plain column | The URL is a bearer credential: anyone holding it can post to the channel |
| URL looked up at send time | The outbox row stores the user id, not the URL | Copying the URL into the row | Changing or removing the webhook takes effect for messages still queued, and the secret lives in one place |

## Security

- **Allowed destinations only.** The server posts to a URL the user typed, so it must never become a way to reach internal hosts. The validator accepts only `https://` URLs whose host is `discord.com`, `discordapp.com`, `ptb.discord.com` or `canary.discord.com`, with the path `/api/webhooks/{numeric id}/{token}` and no query or fragment. The typed client builds the request from the parsed id and token against a fixed base address. It does not reuse the user's string. Error code `discord.invalidWebhook`.
- **No mentions.** Category, bill and payee names are user text and could contain `@everyone`. Every post sends `allowed_mentions: { "parse": [] }` and escapes Discord markdown in names.
- **No token in logs or traces.** The client is registered with `.RemoveAllLoggers()` like `FlexClient`. `TelemetryExtensions` redacts the path for Discord hosts in the HTTP client instrumentation. `SecretRedactionTests` gains `Webhook` in its name pattern, so `UpdateDiscordRequest.WebhookUrl` and the snapshot must print `SecretText.Hidden`.
- **Backups.** The encrypted URL travels in a backup as ciphertext. Under another key ring it cannot be read: the profile then shows `discord.webhookUnreadable` and asks for the URL again, the same way SMTP handles `email.passwordUnreadable`.

## Backend steps

1. **Publisher.** Add `Common/Notifications/INotificationPublisher` (scoped) with `Publish(Notification notification, NotificationDelivery? email = null)`. It adds the notification. If the installation switch is on and the owner has an enabled webhook subscribed to the type, it also adds a `DiscordMessage` with the text from `NotificationTexts` and a dedupe key derived from the notification (`{type}:{relatedId}:{local date}`). Where the caller passes an email, it also enqueues that through `IEmailOutbox`. Webhook rows are loaded once per job pass through `PreloadAsync(userIds)` so a job over many users does not query per notification.
2. **Move producers onto it.** `RecurringBillReminderJob` (its email enqueue moves into the publisher call) and `BudgetAlertJob`. Add an architecture test: only `NotificationPublisher` may call `Notifications.Add`.
3. **Texts.** Add `Common/Notifications/NotificationTexts.cs` with one en/lt sentence per `NotificationType`, mirroring `describe()` in `notification-bell.tsx`, plus a link line `App:SiteUrl` + the page path when `SiteUrl` is set. A unit test fails when a `NotificationType` value has no text.
4. **Client.** `Infrastructure/Discord/DiscordWebhookClient` implements `IDiscordWebhookClient.SendAsync(DiscordTarget, DiscordPost, ct)` and returns `Result`. It is registered with `AddHttpClient`: 10 s timeout, `.RemoveAllLoggers()`, UserAgent `JxFinance/1.0`. The body is `{ content, username: <installation name>, allowed_mentions: { parse: [] } }`. Responses map as follows:
   - 2xx: success.
   - 429: `discord.rateLimited`, carrying `retry_after`.
   - 401, 403 or 404: `discord.webhookGone`.
   - Other 4xx: `discord.rejected`, with Discord's message clipped.
   - 5xx, a timeout or a network error: `discord.sendFailed`.
5. **Outbox job.** `DiscordOutboxJob : PeriodicJob`, every 30 s, follows `EmailOutboxJob`: prune sent or given-up rows after 7 days, claim a batch under `AppLock.DiscordOutbox`, and commit before any socket opens. It then sends each message in its own try/catch and saves once. Retry handling:
   - `rateLimited` sets `NextAttemptAt` from `retry_after` without counting an attempt.
   - `webhookGone` gives up the row and every pending row for that user. It also sets `DisabledByDiscordAt` and `LastError` on the webhook, which the profile shows as "Discord says this webhook no longer exists".
   - Other failures back off like email: `min(4^attempts, 240)` minutes, 5 attempts.
   - Messages to one user are sent in `CreatedAt` order, at most 5 per user per pass, to stay under Discord's per-webhook limit.
6. **Admin endpoints** (`Endpoints/Settings`, admin role): `GET /api/settings/discord` → `{ enabled }` and `PUT /api/settings/discord` `{ enabled }`, then `store.Set` after commit. Switching it off leaves user webhooks in place and stops the job from claiming. Rows queued meanwhile are pruned after 7 days rather than sent late.
7. **User endpoints** (new `Endpoints/Users/…Discord…` under `/api/users/me/discord`):
   - `GET` → `{ hasWebhook, isEnabled, types, lastDeliveredAt, lastError, disabledByDiscord, unreadable }`.
   - `PUT` `{ webhookUrl?, isEnabled, types }`. An empty URL keeps the stored one, and a new URL clears `DisabledByDiscordAt`. `types` must be known values; an empty list is allowed.
   - `DELETE` removes the webhook and its pending messages.
   - `POST /test` sends synchronously, `Throttle(10, 300)`, and reports Discord's own words like the SMTP test. It is refused with `discord.disabled` while the installation switch is off.
8. **Error codes** in `ErrorCodes.cs`: `discord.disabled`, `discord.invalidWebhook`, `discord.webhookUnreadable`, `discord.webhookGone`, `discord.rateLimited`, `discord.rejected`, `discord.sendFailed`.

## Frontend steps

1. `just gen`, then list the four new mutations in `src/api/invalidation.ts` and add `serverErrors.discord.*` in both locales.
2. **Settings**: a `discord` entry in `settings-nav.tsx` and a `features/settings/discord-section/` with the switch and a sentence on what it sends and where. It is a small `useServerForm` form, plus a story (default, off, pending, `failWith`).
3. **Profile**: `features/profile/discord-form/` with:
   - the URL field as a password-type input, with a placeholder that says a URL is saved;
   - a checkbox per notification type, with labels from the bell's texts;
   - the enabled switch, a Test button, Remove, and the last error or last delivery time.
   When the installation switch is off, the section stays visible, disabled, with the reason. Stories cover empty, configured, disabled by Discord, unreadable, installation off, and a `play` for saving and testing.
4. `useDiscordEnabled()` next to `useEmailEnabled()` in `hooks/use-settings.ts`.
5. Command palette: add the profile's Discord section to `pageSections`.

## Tests

- **Unit:**
  - the webhook URL validator (accepted hosts, `http`, userinfo, other hosts, IP literals, extra path, query);
  - `NotificationTexts` covers every type in both languages;
  - message escaping and the 2000-character clip;
  - redaction of the new request and snapshot.
- **Integration, with a `FakeDiscordWebhookClient` replacing the real one in `ApiFixture`:**
  - a bill reminder reaches Discord only when the installation switch, the webhook and the type are all on;
  - a budget alert does too;
  - running a job twice queues one message;
  - 429 reschedules without counting an attempt;
  - 404 disables the webhook and gives up its pending rows;
  - changing the URL applies to queued messages;
  - the test endpoint refuses when the switch is off;
  - `GET` never contains the URL;
  - a backup round-trip keeps `DiscordWebhook` and drops `DiscordMessage`.
- **Architecture:** only the publisher adds notifications.

## Later, not in this plan

- Discord embeds with colour and fields instead of plain content.
- An installation-level channel for administrator events such as a failed broker sync or a backup.
- The same outbox shape for ntfy or Gotify. If a second webhook channel arrives, extract the claim-send-retry loop the two outbox jobs share into one helper.
