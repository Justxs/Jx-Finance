# Plans

A plan is written before a feature is built: the outcome, the design, the steps and the docs it will touch. Once the feature ships, its page under [features](../features/README.md) describes what exists; delete the plan then, because the feature page, the decisions log and the code are the record. Ideas without a plan stay in the [backlog](../backlog.md).

The table is in the suggested build order. Each plan's `Status:` line names what it must follow.

## Changes to shared code

Several plans touch the same code. Whichever lands second adapts to the first:

- `ImportPreviewService.PreviewAsync`, which picks one of five parsers (Swedbank CSV, camt.053, a mapped CSV, OFX and MT940) and shares everything after parsing (duplicates, rule suggestions, the [learned guess](../features/learned-categories.md#in-the-import-review) since 2026-10-01, unusual amounts, hand-entered matches, refund candidates, transfer hints and the closing balance): a plan that adds something per row adds it to that shared part, so every format gets it.
- `Common/Statistics.cs` (the median and spread moved out of `UnusualAmountRule`, shipped with [budget limits from history](../features/budgets.md#limits-from-history)), reused by the [cash-flow forecast](../features/cash-flow-forecast.md) since it shipped on 2026-09-29.
- `Transaction.PayeeKey`, shipped with [spending by payee](../features/reports.md#expense-by-payee) and read by `SuggestedRuleService` and, since 2026-10-01, by `LearnedCategoryService` for its training rows. The cash-flow forecast's usual spending groups by it too. Since 2026-09-30 the forecast's and the [bills calendar](../features/recurring-bills.md#calendar)'s matching rows read it in SQL through `RecurringHistory.LoadAsync`. Since 2026-10-01 unusual amounts, subscription detection and price rises (through `PriceRiseMatcher.LoadChargesAsync`) read it too, so no stored transaction description is normalized in memory any more except the learned suggestions for the ledger's uncategorized rows. `SubscriptionDescription.Normalize` remains for text that is not a stored transaction: typed match keys, payee names and filters, import rows before they are saved and transfer descriptions.
- The month-close checklist's `checklist.accounts`, which replaced `checklist.imports` when [reconciliation](../features/reconciliation.md#in-the-month-end-close) shipped: the [monthly digest](../features/monthly-digest.md), shipped on 2026-09-29, counts its `differs` and `behind` lines as accounts not reconciled, so a change to the states changes the digest too. The `duplicates` count added on 2026-10-01 is an open item of the review but is not in the digest's payload, so a plan that adds it there adds it to `MonthlyDigestPayload` and `NotificationTexts`.
- `AccountMovements`, which gained `LedgerBalanceOnAsync` and `ListAsync` with [reconciliation](../features/reconciliation.md); `ListAsync` has its own union of the five sources beside the summing one, so a plan that changes how a movement is signed adapts both. Refunds needed neither, because `-Amount` of a negative expense already raises the balance.
- `ICurrentUser`, which since the [monthly digest](../features/monthly-digest.md) shipped on 2026-09-29 resolves to a scoped `JobUser` inside `PeriodicJob.RunAsUserAsync` and to `HttpCurrentUser` everywhere else: a plan whose background work needs a service as one member sees it uses that scope rather than composing the service by hand.
- The Security section of Settings, which since [passkeys](../features/passkeys.md) and [personal API tokens](../features/personal-api-tokens.md) shipped on 2026-09-29 holds two-factor authentication, the passkey list and the token list under the nav label Security; `PasswordPrompt` (`features/profile/password-prompt`) is the shared password confirmation to reuse.
- `ApiGroup`, which since [personal API tokens](../features/personal-api-tokens.md) shipped on 2026-09-29 takes `tokenReadable`: a plan that adds a `GET` route to a readable group (Accounts, Transactions, Transaction groups, Transfers, Conversions, Categories, Tags, Reports, Dashboard, Budgets, Goals, Net worth, Investments, Recurring entries, Currencies, Households) either adds it to the list in `TokenReadableTests` or opts it out with `TokenReadable.No`; a new group is not readable unless it says so. The [data export per user](../features/data-export-per-user.md), shipped on 2026-09-29, stays out of reach through `UsersGroup`.
- `AppDbContext.OwnerFilter`, which since [household settle-up](../features/household-settle-up.md) shipped on 2026-09-29 has an `IHouseholdScoped` branch for records that belong to a household rather than to an account or a person: a plan that adds such a record implements the marker instead of checking membership per read path, and gives it an `AuditCollector` entry routed by the row's household. The same change added `ownerId` to `AccountResponse`, which account pickers that need "whose account is this" can read.
- `UserExportTables`, which since the [data export per user](../features/data-export-per-user.md) shipped on 2026-09-29 classifies every table of the EF model for the member export: a plan that adds a table gives it a rule there, as [household settle-up](../features/household-settle-up.md) did for its three on 2026-09-29, or `UserExportTablesTests` fails. `BackupDatabase.WriteTableAsync` is the one writer of the backup's table format, shared by the backup and that export.
- `TransactionCsvWriter.Header`, shared by the ledger export and the member export's `transactions.csv`. Since [spreading](../features/transactions.md#spreading-over-months) shipped on 2026-09-30 and [transaction locations](../features/transaction-locations.md) and [transaction groups](../features/transaction-groups.md) on 2026-10-01 it ends in `Note,Spread months,Place,Group`. A plan that adds a column appends it after `Group` and updates the header expectations in `TransactionExportTests`, `TransactionTagEndpointTests`, `TransactionLocationTests`, `TransactionNoteTests` and `TransactionGroupTests`, and the row endings in `TransactionEndpointTests`, `TransactionNoteTests`, `TransactionExportTests` and `TransactionLocationTests`.
- `TransactionResponse`, `ITransactionInput` and `TransactionFilterRequest`, which spreading extended on 2026-09-30 (`spreadMonths`, `spreadUntil`, `spreadOverlap`) and transaction locations on 2026-10-01 (`place`, `latitude`, `longitude` and the `place` filter, the fields read and written only while the `Locations` switch is on through `ApplyPlaceTo` and `WithoutPlace`), and [transaction groups](../features/transaction-groups.md) the same day (`groupId`, answered only when the group is the caller's, and `enteredByMe`, both set in `TransactionService`'s responder rather than the mapper). `SpreadSlice` carries the place since then, for the report's place breakdown. A new field also goes into the optimistic row builder in `transactions-page/use-transaction-mutations.ts`, the transaction fixtures in `storybook/fixtures/transactions.ts`, the draft in `transaction-draft.ts` and the phone list, as the transaction note did (commit `86ab390f`).
- The spending aggregates, which since [spreading](../features/transactions.md#spreading-over-months) shipped on 2026-09-30 take the visible query before the date filter, leave out `SpreadMonths != null` rows in SQL and append the slices of `Common/Spreads/SpreadRows.SlicesAsync`: `DatedFlows.DailyFlowsAsync` (now with the windows as parameters), `CategoryAttributionService`, `BudgetUsageCalculator.TagSpendAsync` and the report's tag and payee breakdowns. A plan that adds a spending figure by period starts from the same loader, and one that adds a whole-row reader leaves the slices out, as the member export's [double-entry journal](../features/data-export-per-user.md#double-entry-journal) does; [architecture](../architecture/transactions.md#spread-rows) lists which does which.
- `Common/RecurringBills/` (`RecurringOccurrences`, `RecurringEstimate`, `RecurringHistory`, `RecurringMatch`), which since the [bills calendar](../features/recurring-bills.md#calendar) shipped on 2026-09-30 holds the schedule, the estimate, the row loader and the paid tolerance that the cash-flow forecast and the calendar share. A plan that changes how the forecast finds a paid occurrence changes the calendar too.
- `SecurityPriceBook`, which since [live security prices](../features/live-prices.md#which-price-wins) shipped on 2026-09-30 takes a `PriceSourceKind` and refuses a fetched price over any other source's: every new price writer passes its source.
- `AuditCollector`, whose Shareable pass since [shared assets and debts](../features/households-and-sharing.md#shared-assets-and-debts) shipped on 2026-09-30 also takes the asset or debt of every valuation or payment link changed in the save and reports them as its `valuations` and `payments` fields. Since 2026-10-01 it also takes the name of the [personal API token](../features/personal-api-tokens.md#marks-in-the-ledger-and-the-activity-log) a change came through and writes it to every event as `ViaToken`; a plan that changes the pass keeps both.
- The transactions page, which since [transaction groups](../features/transaction-groups.md) shipped on 2026-10-01 reads `GET /api/transactions/ledger`, items of a transaction or a group, paged over the SQL union of `LedgerKeys`: a plan that adds a sort field adds its key to both branches there, and one that changes what the page shows per row reads `LedgerItemResponse` and the optimistic helpers in `transactions-page/ledger-page.ts`. `GET /api/transactions` stays the plain list.
- `ReceiptReading.Result`, whose `items[].name` keys the [ledger search](../features/receipt-reading.md#finding-a-purchase-by-item) reads in raw SQL through `ReceiptItemSearch.MatchingFiles` since 2026-10-01, beside the converter that writes them: a plan that renames or reshapes the stored JSON adapts that query, and `ReceiptItemSearchTests` fails when the keys move. The same search added `receiptItem` to `TransactionResponse`, optional and filled only by a search, so the optimistic row, the draft and the templates leave it out.
- `MemberImport`, which since 2026-10-02 imports a member export taken at any earlier migration by leaving out the columns the file lacks, so they take their migration's default, and running the startup backfills afterwards. A plan whose migration renames or drops a column of an imported table adds its mapping there, and one that fills a new column at startup rather than with a default runs that step from `MemberImport` too; see [Data export per user](../features/data-export-per-user.md#a-download-from-an-older-version).

A new plan is a kebab-case file here, starting with `# Plan: <name>` and a `Status:` line, and gets a row in this table.
