# Plans

A plan is written before a feature is built: the outcome, the design, the steps and the docs it will touch. Once the feature ships, its page under [features](../features/README.md) describes what exists; delete the plan then, because the feature page, the decisions log and the code are the record. Ideas without a plan stay in the [backlog](../backlog.md).

The table is in the suggested build order. Each plan's `Status:` line names what it must follow.

| Plan | Size | Where it lives | Build after |
| --- | --- | --- | --- |
| [Transaction locations](transaction-locations.md) | M for places; L and gated for the map | Transaction form, receipt reading, ledger filters, Reports | Nothing for places, since attachment metadata stripping shipped on 2026-09-30; two months of places for the map |
| [Write access for API tokens](api-write-access.md) | M; the MCP server S and gated | Settings › Personal › Security, the token gate | Nothing; the MCP server only when the owner asks |
| [Transaction groups](transaction-groups.md) | M to L, gated | Ledger, through a new ledger endpoint | The daily-use trial showing that tags and splits do not cover it |
| [Machine-learned categorization](machine-learned-categorization.md) | L, gated; model and `--evaluate-categorizer` built, gate not measured yet | Import review, transaction form, ledger | Six months of real data, then running the evaluation on the owner's ledger |

## Changes to shared code

Several plans touch the same code. Whichever lands second adapts to the first:

- `ImportPreviewService.PreviewAsync`, which since the [generic CSV import](../features/bank-statement-import.md#generic-csv) shipped on 2026-09-29 picks one of three parsers and shares everything after parsing (duplicates, rule and recall suggestions, unusual amounts, hand-entered matches, refund candidates, transfer hints and the closing balance): machine-learned categorization adds its guess to that shared part, so every format gets it.
- `Common/Statistics.cs` (the median and spread moved out of `UnusualAmountRule`, shipped with [budget limits from history](../features/budgets.md#limits-from-history)), reused by the [cash-flow forecast](../features/cash-flow-forecast.md) since it shipped on 2026-09-29.
- `Transaction.PayeeKey`, shipped with [spending by payee](../features/reports.md#expense-by-payee) and already read by `SuggestedRuleService`: machine-learned categorization reads it too. The cash-flow forecast's usual spending groups by it too. Since 2026-09-30 the forecast's and the [bills calendar](../features/recurring-bills.md#calendar)'s matching rows read it in SQL through `RecurringHistory.LoadAsync`. Unusual amounts, subscription detection and price rises (through `PriceRiseMatcher.LoadChargesAsync`) still normalize in memory; moving them to the column is a follow-up that only removes code.
- The month-close checklist's `checklist.accounts`, which replaced `checklist.imports` when [reconciliation](../features/reconciliation.md#in-the-month-end-close) shipped: the [monthly digest](../features/monthly-digest.md), shipped on 2026-09-29, counts its `differs` and `behind` lines as accounts not reconciled, so a change to the states changes the digest too.
- `AccountMovements`, which gained `LedgerBalanceOnAsync` and `ListAsync` with [reconciliation](../features/reconciliation.md); `ListAsync` has its own union of the five sources beside the summing one, so a plan that changes how a movement is signed adapts both. Refunds needed neither, because `-Amount` of a negative expense already raises the balance.
- `ICurrentUser`, which since the [monthly digest](../features/monthly-digest.md) shipped on 2026-09-29 resolves to a scoped `JobUser` inside `PeriodicJob.RunAsUserAsync` and to `HttpCurrentUser` everywhere else: a plan whose background work needs a service as one member sees it uses that scope rather than composing the service by hand.
- The Security section of Settings, which since [passkeys](../features/passkeys.md) and [personal API tokens](../features/personal-api-tokens.md) shipped on 2026-09-29 holds two-factor authentication, the passkey list and the token list under the nav label Security; `PasswordPrompt` (`features/profile/password-prompt`) is the shared password confirmation to reuse.
- `ApiGroup`, which since [personal API tokens](../features/personal-api-tokens.md) shipped on 2026-09-29 takes `tokenReadable`: a plan that adds a `GET` route to a readable group (Accounts, Transactions, Transfers, Conversions, Categories, Tags, Reports, Dashboard, Budgets, Goals, Net worth, Investments, Recurring entries, Currencies, Households) either adds it to the list in `TokenReadableTests` or opts it out with `TokenReadable.No`; a new group is not readable unless it says so. The [data export per user](../features/data-export-per-user.md), shipped on 2026-09-29, stays out of reach through `UsersGroup`.
- `AppDbContext.OwnerFilter`, which since [household settle-up](../features/household-settle-up.md) shipped on 2026-09-29 has an `IHouseholdScoped` branch for records that belong to a household rather than to an account or a person: a plan that adds such a record implements the marker instead of checking membership per read path, and gives it an `AuditCollector` entry routed by the row's household. The same change added `ownerId` to `AccountResponse`, which account pickers that need "whose account is this" can read.
- `UserExportTables`, which since the [data export per user](../features/data-export-per-user.md) shipped on 2026-09-29 classifies every table of the EF model for the member export: a plan that adds a table gives it a rule there, as [household settle-up](../features/household-settle-up.md) did for its three on 2026-09-29, or `UserExportTablesTests` fails. `BackupDatabase.WriteTableAsync` is the one writer of the backup's table format, shared by the backup and that export.
- `TransactionCsvWriter.Header`, shared by the ledger export and the member export's `transactions.csv`. Since [spreading](../features/transactions.md#spreading-over-months) shipped on 2026-09-30 it ends in `Note,Spread months`. [Transaction groups](transaction-groups.md) and [locations](transaction-locations.md) each append one column (`Group`, `Place`) after `Spread months`, in the order they land. Each updates the header expectations in `TransactionExportTests` and `TransactionTagEndpointTests`, and the row endings in `TransactionEndpointTests` and `TransactionNoteTests`.
- `TransactionResponse`, `ITransactionInput` and `TransactionFilterRequest`, which spreading extended on 2026-09-30 (`spreadMonths`, `spreadUntil`, `spreadOverlap`) and groups and locations extend. A new field also goes into the optimistic row builder in `transactions-page/use-transaction-mutations.ts`, the transaction fixtures in `storybook/fixtures/transactions.ts`, the draft in `transaction-draft.ts` and the phone list, as the transaction note did (commit `86ab390f`).
- The spending aggregates, which since [spreading](../features/transactions.md#spreading-over-months) shipped on 2026-09-30 take the visible query before the date filter, leave out `SpreadMonths != null` rows in SQL and append the slices of `Common/Spreads/SpreadRows.SlicesAsync`: `DatedFlows.DailyFlowsAsync` (now with the windows as parameters), `CategoryAttributionService`, `BudgetUsageCalculator.TagSpendAsync` and the report's tag and payee breakdowns. A plan that adds a spending figure by period starts from the same loader, and one that adds a whole-row reader leaves the slices out, as the member export's [double-entry journal](../features/data-export-per-user.md#double-entry-journal) does; [architecture](../architecture/transactions.md#spread-rows) lists which does which.
- `Common/RecurringBills/` (`RecurringOccurrences`, `RecurringEstimate`, `RecurringHistory`, `RecurringMatch`), which since the [bills calendar](../features/recurring-bills.md#calendar) shipped on 2026-09-30 holds the schedule, the estimate, the row loader and the paid tolerance that the cash-flow forecast and the calendar share. A plan that changes how the forecast finds a paid occurrence changes the calendar too.
- `SecurityPriceBook`, which since [live security prices](../features/live-prices.md#which-price-wins) shipped on 2026-09-30 takes a `PriceSourceKind` and refuses a fetched price over any other source's: every new price writer passes its source.
- `AuditCollector`, whose Shareable pass since [shared assets and debts](../features/households-and-sharing.md#shared-assets-and-debts) shipped on 2026-09-30 also takes the asset or debt of every valuation or payment link changed in the save and reports them as its `valuations` and `payments` fields: [write access for API tokens](api-write-access.md) adds the token name and keeps those lookups.
- `MemberImport.BeginAsync` refuses an export taken at another migration. Every plan with a migration therefore makes older member exports unimportable, and its docs step adds that sentence to `docs/features/data-export-per-user.md`.

A new plan is a kebab-case file here, starting with `# Plan: <name>` and a `Status:` line, and gets a row in this table.
