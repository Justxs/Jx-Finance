# Categorization rules: decisions

Related: feature page [Categorization rules](../features/categorization-rules.md).

## Current

Personal, never shared, ordered by a dense integer position and evaluated first-match-wins; the condition is contains, starts with or equals on the description, ignoring case, optionally narrowed by account and by an amount range in the transaction's own currency, and the action sets a category, adds tags, or both; they suggest in the import preview and write to the ledger only through an explicit run that by default touches only rows with no category and never touches split rows; recategorizing rows that already carry a category is a separate labelled option; a payee filed by hand at least three times in twelve months with one category, and never with another of the same flow type, is offered as a suggested rule once in a toast and on the Rules tab until it is created or dismissed; behind the `CategorizationRules` feature switch

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

- **2026-09-29.** Two open questions of the rule-suggestions plan, decided while the owner was away and to be reviewed: a suggestion keeps needing three rows in twelve months, and an import confirm says nothing about the suggestions it created
  - Rejected: Asking more rows of a payee that appears once a month; a "2 rule suggestions" line with a link to the Rules tab after an import confirm
  - Why: Both were the plan's conservative defaults. Three rows are what the toast's "you filed this three times" promises, and the other-category check already stops a payee whose history disagrees; raising the bar can wait for the daily-use trial to show noise. The Rules tab already lists every open suggestion, and a second message in a dialog that already reports duplicates, transfers and matches would compete with them. Review both once real months of use exist
- **2026-09-29.** A row counts as categorized by hand when none of the caller's current rules matches it, and a suggestion needs three such rows with one category and no row of the same key in another category of the same flow type
  - Rejected: A new `CategorySource` column set by every write path; a majority vote among the categories a payee got; counting a housemate's rows on a shared account
  - Why: Nothing records how a category was set, and old rows could never be told apart, so a source column would only work for rows written after it. A row a rule already matches needs no new rule, and because the first matching rule decides a row, a rule suggested behind an earlier one that already matches could never fire anyway. "Always" is only honest when the history never disagreed. Rules are personal, so the evidence is the caller's own rows
- **2026-09-29.** A suggested rule is offered once by answering `GET /api/categorization-rules/suggested?transactionId=` only when that row's group has exactly three rows, and a dismissal is a server row of key and category
  - Rejected: A toast after every save past the third; remembering "already offered" per browser; dismissals in a TanStack DB local-storage collection; a table of suggestions filled by a job
  - Why: Exactly at the threshold gives "once" with no state at all, and a missed toast is not lost because the Rules tab lists the suggestion. The list is computed on the server on every read, so it must agree on every device, which a browser-local dismissal would break; the subscription dismissal already has the server-row shape. Computing on read is cheap for a household and leaves nothing to keep in step

- **2026-09-20.** The first matching categorization rule decides a row, and no later rule sees it
  - Rejected: Letting every matching rule contribute, with the category from the first that sets one and the tags from all of them; a per-rule "stop here" flag
  - Why: Two rules that set different categories still need an order to settle it, so "all match" only hides the order in the half where it is visible. One rule per row is what lets the import preview name the rule that filled it, which is the label that makes a suggestion reviewable, and what makes the run preview's per-rule counts disjoint, so they sum to the total instead of overlapping. A stop flag is the same decision taken once per rule instead of once, with a default that would be wrong for somebody
- **2026-09-20.** Rule order is a dense 0-based `Position` per owner, changed one step at a time by `POST /api/categorization-rules/{id}/move`, which answers the whole list in its new order
  - Rejected: Sparse positions with gaps (10, 20, 30) and no renumbering; a fractional or lexicographic rank; sending the whole ordered list of ids in one `PUT`
  - Why: Nothing in the product was ordered before this, so there was no convention to follow and no reason to buy the complexity of a rank that never renumbers: a household has a handful of rules, the renumber is one `UPDATE` per rule inside the transaction that already exists, and a dense list is the one a person can read back as 1, 2, 3 on the screen. Gaps are only useful for inserting between two items, which the screen never offers. A whole-list `PUT` would make the client the authority on an order the server has to validate anyway, and would turn a mis-sent list into a silent reshuffle
- **2026-09-20.** Categorization rules get their own `CategorizationRules` switch in `Feature`, `FeatureFlags` and `FeatureGateMiddleware`, while tags got none
  - Rejected: Leaving rules unswitched like tags; folding them into the `Import` switch
  - Why: The reasoning that kept tags unswitched is the reasoning that gives rules a switch. A tag is an attribute rows already carry, so hiding it would have meant a second shape for the ledger, both exports and the report, and a household that turned it off would have lost a dimension from data it had already sorted. A rule is a screen and a route of its own that writes ordinary values: with the switch off the page and the routes disappear, the import preview simply stops suggesting, and every category and tag a rule ever set stays exactly where it is. Folding it into `Import` was rejected because the run over the existing ledger has nothing to do with importing, and an installation that imports nothing may still want the run
- **2026-09-20.** A rule is an `OwnableEntity` and never shareable, but a run reaches every transaction its owner can see, including rows on a shared account entered by somebody else
  - Rejected: Making rules `IShareable` like categories and tags; narrowing a run to the caller's own transactions
  - Why: Two people who share an account want different words for the same shop, and a shared rule that rewrote a housemate's rows overnight is the worst kind of surprise; keeping rules personal also keeps the evaluation order personal, which is half of what a rule means. Narrowing the run to rows the caller entered was rejected because the ledger has no such concept anywhere else: what a member may change is what a member can see, and the same person could set that category by hand in the ledger in two clicks
- **2026-09-20.** A run touches only transactions with no category at all, unless `recategorize` is sent; split transactions are never touched, and tags are added and never removed
  - Rejected: Replacing any category the rules disagree with; asking for a confirmation dialog instead of a request flag; replacing the row's tag set the way `bulk-tags` does
  - Why: A category somebody chose is a decision, and a tool that quietly overrules decisions stops being trusted after the first time; the option exists because re-running rules over a badly imported year is a real need, so it is a flag on the request, echoed back on the response, with its own sentence on the screen — a dialog alone would leave the API able to do the destructive thing by default. Splits are excluded because their categories live on their lines and a category on the parent means nothing the rest of the product respects. Tags are added rather than replaced because a rule has an opinion about one theme, not about everything a row was ever marked with
- **2026-09-20.** Matching over the ledger is a `WHERE` clause with `EF.Functions.ILike`, while the import preview matches the parsed CSV rows in memory; both halves live in `RuleMatcher`
  - Rejected: One in-memory matcher used everywhere, after loading the candidate transactions; one SQL matcher used everywhere, by writing the CSV rows to a temporary table first
  - Why: Loading the ledger to match it is the per-row work the paged list has always refused to do, and the run has to scale with the size of its answer rather than the size of the history. The CSV rows, on the other hand, are not in the database and the preview writes nothing, so there is nothing to run SQL against without inventing a temporary table for a read-only call. Keeping `LikePatternFor` and `Matches` in one file is what keeps the two definitions of "contains, ignoring case" readable together, and the test endpoint uses the in-memory half so the form cannot drift from the preview
- **2026-09-20.** A rule's amount range is compared with the transaction's own `Amount`, not its `ReportingAmount`
  - Rejected: Comparing in the reporting currency so one range covers every currency
  - Why: The number a person types is the number they read on the statement, and the import preview has no reporting amount at all before a row is confirmed — it is computed during confirm from the rate of that date. Comparing the row's own amount is the only rule that makes the preview and the run answer the same question, and a household whose accounts are all in one currency, which is the common case, cannot tell the difference
