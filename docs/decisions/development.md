# Development and testing: decisions

Related: architecture [API contract and generated client](../architecture/api-contract.md), [Tests and Storybook](../architecture/testing.md), [Developer tooling and package updates](../architecture/developer-tooling.md).

## Current

Warnings are errors in Release builds, analyzers run at `latest-recommended` with a short list switched off in `.editorconfig`, and every NuGet version sits in `Directory.Packages.props`. One committed API contract, `frontend/openapi.json`, compared semantically by a backend test; OpenAPI and Scalar are served only in Development, with `App:ApiDocs=true` as the explicit override the tests use. `DevDataSeeder` runs only in Development, first-run setup creates the administrator and its starter categories itself, and demo data is the host command `--seed-demo <email>` for an existing empty user. Stories run in jsdom as portable stories with the real preview, MSW and `axe-core`, and Storybook is for review by hand, where colour contrast is checked in the Accessibility panel; end-to-end tests run against a Compose project of their own with its own volumes. Shared frontend code (`src/components`, `src/lib`, `src/hooks`, `src/stores`) never imports a feature, feature folders have no `index.ts` barrels, and imports across folders use `@/` paths. The pre-push hook type-checks and builds without running tests, which run on demand from `just test-fe` up to `just check` Stories see a clock pinned to noon UTC on `FIXTURE_TODAY`. Docs describe behaviour and name code only where a reader needs an entry point; `just check-docs` fails on a backticked path or type name the code no longer has, and the route list in `docs/api-routes.md` is generated from the contract; no docs section runs past 16,000 characters without a heading. The React Compiler runs through Oxc (`oxc-transform-react`, via the `compiler` option of `@vitejs/plugin-react`) rather than Babel. The API runs on the FastEndpoints 9 beta line, and PDFsharp-MigraDoc stays on 6.2, the last MIT release.

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

Older entries are in the git history of this file (`git log -p -- docs/decisions/development.md`).

- **2026-10-26.** The backend moves to FastEndpoints 9.0.0-beta.6 and `FastEndpoints.Mcp` 1.0.0-beta.8, and PDFsharp-MigraDoc stays on 6.2.4. FastEndpoints 9 leaves rules with a `When` condition out of the OpenAPI schema, writes `minLength: 1` for a required string, and marks a list checked with `NotNull` as required instead of giving it `minItems: 1`. The `When` guards on the debt interest rate and term and on the new profile password only repeated FluentValidation's own null handling, so they were removed and their limits stay in the contract; the SMTP sender's length rule moved off its guard for the same reason. The ISIN, broker token and sender email patterns stay guarded, because an empty string is allowed there, and are now only checked by the API. The weekly update workflow excludes PDFsharp.
  - Rejected: Staying on 8.4.0-beta.18, as the 2026-10-13 update did, because the 8.4 line ended at beta.26 and `FastEndpoints.Mcp` now requires 9; PDFsharp 6.5.0, which is licensed AGPL-3.0-only instead of MIT and refuses to create a document without a valid license.
  - Why: The schema changes are corrections, apart from the guarded patterns, and each lost limit that a form imported is back after removing a redundant guard. An AGPL dependency would change the terms the MIT-licensed project can be shipped under, which is the owner's call, not a package update's.

- **2026-10-26.** The React Compiler runs through the `compiler` option of `@vitejs/plugin-react`, which uses `oxc-transform-react`, the Rust port of the compiler, in the same pass as the JSX and Fast Refresh transform. `@babel/core`, `@rolldown/plugin-babel` and `babel-plugin-react-compiler` were removed. `oxc-transform-react` is on 0.155, the Oxc release Vite+ 1.4 bundles, with a `peerDependencyRules` entry in `pnpm-workspace.yaml`, because `@vitejs/plugin-react` 6.1.2 still declares `^0.152.0`; its `transform` declaration is the same in both releases.
  - Rejected: Keeping the Babel preset, which is the stable path; holding `oxc-transform-react` at 0.152, which would keep a second Oxc version beside the one Vite+ ships.
  - Why: The production bundle step went from about 20 to 5 seconds (measured on 2026-10-26 against the same commit with Babel), and every Vitest run and Storybook start transforms each component once instead of through Oxc and then Babel. The Oxc integration is marked experimental, so a regression is reverted by restoring the three Babel packages and the Babel plugin in `reactPlugins()`.

- **2026-10-06.** The frontend uses Vite+ as its toolchain and command line, over pnpm 12 as the package manager: every frontend command is a `vp` command (`vp install`, `vp add`, `vp update`, `vp run`, `vp exec`, `vp dev`, `vp build`, `vp test`, `vp check`, `vp pm audit`), with the Oxlint and Oxfmt settings moved from `.oxlintrc.json` and `.oxfmtrc.json` into the `lint` and `fmt` blocks of `vite.config.ts`, and tests importing from `vite-plus/test`. `vitest.config.ts` stays separate, `tsc -b` stays the type check, and lefthook keeps running the staged-file jobs, now through `vp fmt` and `vp lint`.
  - Rejected: Keeping nub; calling pnpm directly with `vp` only as a project dependency; the `lint.options.typeCheck` option `vp migrate` adds, in place of `tsc -b`; `vp staged` in place of the lefthook jobs; a plain `vp update --latest` in the package-update job
  - Why: The owner asked for pnpm and Vite+ in place of nub, which also could not run in Git Bash, and for `vp` commands over pnpm ones because `vp` drives pnpm itself. `vp` fetches the pnpm version in `packageManager` on its own, while a bare `pnpm` started from the repository root went through corepack's global pnpm, which refused the pinned version. `tsc -b` already runs in the build and the pre-push hook, and lefthook also runs the backend and docs jobs. `vp migrate` dropped every rule of the `shadcn`, `jx` and `jx-code` JS plugins when it merged `.oxlintrc.json`, so the `lint` block was rebuilt from the old file. An update with `--latest` moved `vitest` to 5.0.3 while vite-plus 1.0.0 bundles 5.0.1, so `scripts/update-frontend.mjs` sets those versions from vite-plus instead.

- **2026-10-04.** Agents read docs by section: `just check-docs` fails on more than 16,000 characters between two headings outside Done and Log sections, the route list moved from `docs/api.md` to the generated `docs/api-routes.md`, and the read-first table in `AGENTS.md` links sections rather than whole pages. `just check-changed` runs the frontend tests in the folder of each changed file plus the contract tests of locales, the API client and Storybook fixtures. Claude Code hooks refuse edits to generated files and format each edited file with the pre-commit formatter.
  - Rejected: A cap on page size, which would split pages such as the data model that are fine to read by section; `vitest related` in `check-changed`, which ran 69 test files for 146 seconds after a change to `src/lib/money.ts`; a `Stop` hook running `check-changed`, which would add about a minute to every answer.
  - Why: Following the read-first table for an endpoint loaded about 28,000 tokens of `docs/api.md`, and `testing.md` had 45 KB under three headings, so an agent could not read only what it needed. `check-changed` passed while a DOM test beside the edited component failed. Agents spent turns fixing format checks on their own edits and occasionally edited generated files by hand.

- **2026-10-04.** Docs describe behaviour, not code layout: a page names a class or file only where a reader needs an entry point, a feature's folders are named once in the `docs/features/README.md` table, and docs change with behaviour, not with renames. `just check-docs` fails on a backticked repository path or PascalCase type name in `docs/` (decision logs and plans aside) and `AGENTS.md` that the code no longer has, and the Routes section of `docs/api.md` is generated from `frontend/openapi.json` by `just gen`
  - Rejected: Keeping the rule that every change updates every page naming the code it touches; checking camelCase names too; checking every backticked span against the whole repository text; a CI job that lists docs untouched by a code change; keeping the hand-written route table
  - Why: A refactor that split services touched 87 doc files, and commits averaged 5.7 doc edits, mostly renamed paths in pages whose behaviour had not changed. camelCase spans are mostly React, TanStack, DOM and config names that live only in packages (about 20 against 2 stale ones on 2026-10-04), and a whole-repository text search accepts any word that appears in a comment or string. Restricted to spans that look like paths into this repository and PascalCase names with two capitals, and checked against source identifiers, the check found 7 stale references in about 5,100 and 6 deliberate mentions of things that do not exist, and adds about 1.5 seconds. The 277-row route table duplicated the contract by hand

- **2026-10-04.** The pre-push hook only type-checks the frontend and builds the backend; frontend tests run when asked for, on a ladder from narrow to wide: `just test-fe <path>`, `just test-class` or `just test-method`, `just check-changed` for the files changed against HEAD, `just check-fast`, then `just test` and `just check`. The pre-commit hook keeps `stage_fixed: true`
  - Rejected: `vitest related` on the pushed files, as before; running `just test-unit` or the full frontend suite before every push; dropping `stage_fixed` so the format jobs only check and point to `just fix`
  - Why: `vitest related` follows imports through the shared barrels and the route tree, so a change with one importer still ran 44 test files, close to the full two-minute run, on every push. Type-checking with `tsc -b` (about 7 seconds) and an up-to-date Release build catch most breakage in seconds, and CI runs every test anyway. The `stage_fixed` worry was that formatting a partially staged file would commit its unstaged hunks, but lefthook 2 hides unstaged hunks before the jobs run and restores them after; tried in a scratch repository, only the staged hunks were committed, and when the formatter touched a line the unstaged hunk also changed the commit stopped with a message and both versions were kept

- **2026-10-04.** `TreatWarningsAsErrors` applies only when `$(Configuration)` is Release; analyzers and `EnforceCodeStyleInBuild` stay on in Debug, where findings are warnings
  - Rejected: Warnings as errors in every configuration, as before; switching IDE0005 and other style rules down to suggestions; a separate strict build step
  - Why: The Debug build that `dotnet watch` runs under `just dev` stopped on an unused `using` in the middle of an edit. Every gate that must stay strict already builds Release (`just check-fast`, `just test`, `just test-unit`, the pre-push build, CI, the contract export and the EF recipes), so the rule loses nothing there, and Debug still shows each finding. Lowering rule severities would have weakened those gates too, and another step would only repeat what the Release build does

- **2026-10-03.** The 89 EF migrations were squashed into one `InitialCreate` before the first release, and from that release on migrations are never squashed or renamed. The startup fills `PayeeKeyBackfill`, `DebtBalanceBackfill` and `SpreadFromBackfill`, their call in the member import and the `IX_Transactions_PayeeKeyPending` index went with them, along with the one-off data rewrites inside the old migrations; an existing development database is moved over by the one-off SQL in [Developer tooling](../architecture/developer-tooling.md#the-squashed-migration-history), and backups and member downloads taken before are refused
  - Rejected: Keeping the full history; squashing after the first release
  - Why: Nothing outside development has applied a migration, so the history protected no installation, while it cost a migration folder of about 180 files, three startup steps and an import step that only filled rows written before their columns existed, and data rewrites that only ever applied to development data. After a release every installation has applied the history and a backup names its last migration, so a squash then would strand real installations and their backups behind a manual history rewrite; before the release the only cost is the development database and its backups, which the one-off SQL and a new backup cover

- **2026-10-03.** A mutation stays pending until the queries it changed have refetched: the mutation cache awaits the invalidation in its `onSuccess`, before the mutation's own `onSuccess`, the success toast and the `mutateAsync` promise, and after a failure in `onSettled`, after the mutation's own rollback
  - Rejected: Firing the invalidation and forgetting it in `onSettled`, as before; returning it from `onSettled` alone; optimistic updates on every list
  - Why: Fired and forgotten, a form dialog closed and the toast showed while the list behind it still held the old rows, for one round trip, on every screen without an optimistic update. Returning the promise from `onSettled` keeps `isPending` true, but TanStack Query runs the mutation's own `onSuccess`, which is where the dialogs close, before the cache's `onSettled`, so the dialog still closed early; and on a failure the refetch must come after the mutation's `onError`, or a rollback would overwrite the fresh data. Optimistic updates for every list would be a second copy of each server rule. Only queries on screen are refetched and awaited, so the wait is usually one page of the ledger or one small list

- **2026-10-03.** Feature components get DOM tests through `src/test/api.tsx`: `mockApi()` runs the Storybook MSW handlers in Node and records the requests, and `renderInApp` renders one component with the real mutation cache, a toaster and a memory router that registers only the path and search schema the component reads
  - Rejected: Rendering through the Storybook decorators; mounting the whole route tree as `src/test/app-router.tsx` does; mocking the generated hooks
  - Why: The decorators and the route tree import every route and page, which doubled a single file's run time, while one route with its schema is all a section or form needs. The handlers are already the typed, contract-checked mock of the API, and mocking hooks would test neither the request body nor the error mapping
