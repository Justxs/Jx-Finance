# Receipt reading: decisions

Related: feature page [Receipt reading](../features/receipt-reading.md); [Attachments](attachments.md); [Transactions](transactions.md); [Categorization rules](categorization-rules.md).

## Current

Since 2026-09-29 receipts are read inside the installation and nothing is sent anywhere. The owner decided that receipt reading must not use any external API, so the hosted Anthropic reader implemented the same morning was replaced. A person reads one receipt photo or PDF at a time from the transaction form behind `Feature.ReceiptReading`, which now starts on like every other switch. A photo is turned upright, stripped of metadata, turned grey, scaled to 1600 pixels wide and put through a local adaptive threshold, then read by the Tesseract command line (`tesseract-ocr` with `lit` and `eng` data in the API image) through `IReceiptReader`, one process at a time with a 60 second limit; a PDF is read from its text with PdfPig, and since 2026-10-01 a PDF without text has its first three pages rendered by Ghostscript at 300 dots per inch and read like a photo, answering `receipt.pdfWithoutText` when rendering fails or every page is blank. `ReceiptTextParser` turns the text into merchant, date, currency, total, items and adjustments, and keeps every line it cannot read for the review. Each item takes the category remembered for its name, else the person's first matching categorization rule without an account, else none; item names are compared without diacritics, and OCR confusions are folded only where the parser looks for words such as totals and discounts.
There is no monthly limit and no usage table: one Tesseract process at a time, a per-file busy check under the advisory lock and the endpoint throttle are the limits. The API image is published for the build's architecture only. The action is offered only when the switch is on and `tesseract` is on the API's `PATH`. The browser shares the payment over the categories by weight so the lines add up exactly; readings are kept per person and file hash as a cache and deleted a day after their file is gone, and remembered categories are a personal dictionary of normalized item names. A reading is visible only to its reader, is stored as `jsonb` with no item table, and is kept while any attachment row of anyone, trashed or not, has its hash; "Read again" removes the earlier reading only after the new one succeeds. The read answers the reading and the candidates, matched to a hand-entered row for a receipt read first and offered as candidates for a bank row read first; the browser computes the totals and states differences in words without ever blocking the save. Readings and remembered item categories travel in backups

Since 2026-10-01 the ledger search also matches the item names of the caller's own readings of a row's attached files, read from `Result` in SQL with nothing copied and only while `ReceiptReading` is on; a trashed file stops matching, and a found row shows the item and its file's warranty date under the description.

Since 2026-10-01 a prepared image taller than 4000 pixels is cut after the threshold into parts of 2000 pixels overlapping by 150, each read by its own Tesseract process, and the texts are joined with the lines repeated across a seam removed; the prepared height may reach Magick.NET's 16000 pixel limit.

Since 2026-10-01 a receipt e-mail, saved as an HTML page or as an `.eml` message, is read in the API from its visible text with MimeKit, a message's HTML part first and its text part otherwise, and handed to the parser like a PDF's text; such a file is read for filling only and never attached.

Since 2026-10-01 a return receipt fills the form as a refund in the category of its largest returned amount, linked to the latest purchase from the same merchant that the reading finds; it is no longer refused.

Since 2026-10-03 an invoice is read by the same parser in an invoice mode: reading starts after the item table's header, rows lose their number and trailing columns, the seller comes from its label, the VAT becomes an adjustment when it balances, the issue date fills the form and the invoice number an empty note, and no address is taken.

Since 2026-10-01 the remembered item categories are listed at the end of the Categories page, by their normalized key with the category and the last use, searched on the server and shown 100 at a time, and each can be forgotten for good after a confirmation, through two routes under `/api/receipts` that tokens cannot use.

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

Older entries are in the git history of this file (`git log -p -- docs/decisions/receipt-reading.md`).

- **2026-10-03.** "Fill from receipt" also reads an invoice, through the same `ReceiptTextParser` in an invoice mode that a title line such as `PVM sąskaita faktūra` or `Invoice` turns on. The form takes the issue date, the owner's choice, and the invoice number goes into an empty note; the due date only widens the "Already in the ledger?" window and is shown in the review. Nothing beyond the form is offered
  - Rejected: A second parser for invoices; the due date as the transaction's date; offering a recurring entry from the review; filling Place from the invoice's address
  - Why: An invoice differs from a till receipt only in where reading starts, how a row and the seller are named and where the VAT sits, so one parser with a mode keeps one set of word lists and one result. The owner wants the date the invoice was issued, accepting that a payment weeks later is not linked by the import's three-day window; the wider candidate window covers a payment already imported. A recurring entry was left out to keep the change to the form. An invoice's head holds the buyer's address as well as the seller's, and Place must not get the person's home
- **2026-10-03.** The VAT printed under an invoice's rows becomes an adjustment of kind `vat` only when the rows, the other adjustments and the VAT add up to the printed total within a cent; otherwise it is dropped
  - Rejected: Always adding it; never reading it and letting the review report the gap; storing net and gross per row
  - Why: Some invoices print rows without VAT and some with it, and the text alone does not say which; checking the sum tells them apart without counting VAT twice. The lines are shared by weight anyway, so the VAT only has to explain the gap, not be split by rate
- **2026-10-03.** The parser was tuned on the owner's own receipts (a Maxima e-receipt printed from Gmail, a Maxima paper receipt, a Lidl e-receipt with deposits and two IKI app screenshots), each kept as an anonymised fixture: a name wrapped onto a lowercase line or after a line of 40 characters or more is joined, an amount alone on a line is read together with the line before it so a wrapped discount stays a discount, a row of numbers under a name is that item's price with a discount column when the header names one, lines holding several "label: amount" pairs are split, and mail header lines and article codes are dropped
  - Rejected: A layout per shop chosen by the merchant; leaving the samples as a manual check only
  - Why: The same few shapes (a wrapped name, a number row, a summary line) recur across shops, so rules on shapes cover new shops that print the same way, while a layout per shop breaks on the first unknown one. A fixture per real receipt keeps every later change honest against what the owner actually buys

- **2026-10-01.** The remembered item categories are listed in a section at the end of the Categories page, shown while `ReceiptReading` is on, one row per entry with its normalized key, the category or "Deleted or unshared category", and `UpdatedAt` as the last use. Decided while the owner was away, to be reviewed
  - Rejected: The Tags page beside Payee names and Places; a tab or a page of its own; storing and showing the printed item name, which needs a new column, a migration and a name for every entry written before
  - Why: An entry says which category an item goes to, so it belongs where categories are managed, and the product direction puts it on a page that exists. The key is what the dictionary matches on and is readable enough (`pienas`, `dantu pasta colgate`); a printed name would be one spelling among the many the key folds together, so it could mislead about what the entry matches
- **2026-10-01.** `GET /api/receipts/item-categories` searches on the server with the key's normalization and answers the 100 most recently used matches with a `total`; `DELETE /api/receipts/item-categories/{id}` hard-deletes one entry after a confirmation dialog, with no undo and no "forget all for this category". Both stay under `/api/receipts`, so a personal API token can use neither. Decided while the owner was away, to be reviewed
  - Rejected: Sending all up to 5000 entries to the browser; paging; a soft delete with an undo toast through the trash; a bulk forget per category; making the `GET` token-readable
  - Why: A search box finds any entry and the most recent hundred are the ones a person is likely to fix, so paging would add controls for little; the whole dictionary could be half a megabyte. Forgetting must hard-delete because the key is unique per person and the next choice of that name inserts it again, as forgetting through the review already does, so a trash entry would need a restore path for a row that is cheap to recreate by filing one item. Deleting or unsharing a category already makes its entries inactive, so a bulk forget would serve only a tidy-up. The receipts prefix is closed to tokens because readings reveal purchases item by item, and this list is the same kind of data

- **2026-10-01.** A return receipt fills the transaction form as a refund, with the category of the heaviest group of its items by the split's weight, the first group on a tie. This reverses the "return receipts refused" part of the 2026-09-29 plan entry below. Decided while the owner was away, to be reviewed
  - Rejected: Keeping returns refused; a refund per category, which would be several transactions from one form; leaving the category empty; taking the linked purchase's category
  - Why: A refund cannot be split, so one category has to stand for the receipt, and the largest share is the one the refund mostly corrects; a typical return is a single item, where every choice agrees. Several transactions would need a new save path for one receipt. The items' own categories are what the person just confirmed in the review, while a split purchase has no single category to take
- **2026-10-01.** The purchase a return belongs to is looked up on the server and answered as `refundOf` on the reading: the latest visible expense, not a refund, whose payee key equals the merchant's normalized name or starts with it and a space, of at least the returned total, in the receipt's currency, dated up to 90 days before the receipt and without this file attached; none when nothing matches. The refund takes its description in the create dialog. Decided while the owner was away, to be reviewed
  - Rejected: The import proposal's exact key only; matching the amount exactly; a list of purchases to choose from; looking it up in the browser
  - Why: A purchase filled from its receipt has the merchant as its key, but one from the bank has the merchant followed by the city or card text, so an exact key would miss the bank row; a prefix on whole words finds both without matching another shop whose name merely begins the same. A return is often part of a purchase, so the purchase is at least the total, as in the import's proposal, whose 90 days are reused. One proposal with the form's existing unlink button is the least to read, and the server already holds the query filters that decide what the person can see. Excluding the transactions with this file attached keeps an expense whose edit dialog read the return from linking to itself. The purchase's description gives the refund the shop's payee key, as "Record refund" does

- **2026-10-01.** An HTML page or e-mail receipt is turned into text with MimeKit, which MailKit already references: `MimeMessage` takes an `.eml` apart and `HtmlTokenizer` walks the HTML, keeping visible text only, starting a line at each block element and joining a table row's cells with a space. `.eml` is accepted beside `.html` and `.htm`, its HTML part first and its text part otherwise, and a file is known by its declared type or, when none is declared, its extension. Decided while the owner was away, to be reviewed
  - Rejected: AngleSharp or HtmlAgilityPack as a new package; stripping tags with a regular expression; rendering the page in a headless browser and reading the picture with Tesseract; HTML only, without `.eml`; reading a PDF or image attached to the message
  - Why: A receipt needs text in reading order, not a DOM, and MimeKit's tokenizer, maintained with MailKit, already decodes entities and knows script and raw-text content, so a second parser would be a new dependency for nothing this uses. A regular expression trips over comments, scripts and entities, and a browser would be a heavy process to recover text that is already text. Mail programs save a message as `.eml` more readily than as HTML, and MimeKit parses it in a few lines. A receipt sent as a PDF attachment is better saved and read as a PDF, which already works, than unpacked by a second path
- **2026-10-01.** HTML and e-mail files are read for filling only and never stored: attachments keep JPEG, PNG, WebP, HEIC and PDF, the create dialog does not attach such a file on save, "Split that payment instead" attaches nothing, and the edit dialog reads it without attaching it first. Decided while the owner was away, to be reviewed
  - Rejected: Allowing `text/html` and `message/rfc822` as attachment types
  - Why: An attachment is served back for preview and download, and an HTML file served from the API's origin could run script in the person's session, so storing it would need a sandboxed origin or a conversion to PDF; an `.eml` also keeps the sender's and recipient's addresses and every header, which the photo path strips. The price is that such a reading goes after a day with its file never attached, so its items count neither in the spending per item report nor in the item search; a person who wants the receipt kept can print the e-mail to PDF, which attaches and reads from its text

- **2026-10-01.** A PDF without text is rendered page by page with Magick.NET through Ghostscript, which the API image installs as the distribution's `ghostscript` package, at a fixed 300 dots per inch, and each page then goes through the photo's preparation and Tesseract. This reverses the 2026-09-29 entry below on the backlog's request. Decided while the owner was away, to be reviewed
  - Rejected: Poppler's `pdftoppm` as a second process; PDFium through a NuGet wrapper; `libgs10` alone; a density chosen per page so the page comes out 1600 pixels wide; 200 dots per inch
  - Why: Magick.NET already reads the images and calls Ghostscript itself, so the code is one read setting and the page joins the photo path; `pdftoppm` would be a second renderer and a second process call to maintain, and a PDFium wrapper brings native libraries per platform, which the image already pays for once with Magick.NET. On Linux Magick.NET runs the `gs` command rather than loading the library, so the library package alone would not do; `ghostscript` with `--no-install-recommends` is the smallest package that provides it, its size in the image not yet measured. The page is scaled to 1600 pixels wide afterwards anyway, so a per-page density buys little for the code; 300 is the usual scanning resolution, gives a till roll 80 millimetres wide 945 pixels and an A4 page 2480, and keeps pages up to about 1350 millimetres long under the 16000 pixel limit. Ghostscript is licensed under the AGPL; it runs unmodified as a separate program from the distribution's package, whose source the distribution publishes, which is the arrangement the image already has with every other package. Rendering untrusted PDFs is Ghostscript's riskiest use, so it runs with `-dSAFER`, on at most three pages of a file of at most 10 MB, inside the non-root API container
