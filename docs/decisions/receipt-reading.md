# Receipt reading: decisions

Related: feature page [Receipt reading](../features/receipt-reading.md); [Attachments](attachments.md); [Transactions](transactions.md); [Categorization rules](categorization-rules.md).

## Current

Since 2026-09-29 receipts are read inside the installation and nothing is sent anywhere. The owner decided that receipt reading must not use any external API, so the hosted Anthropic reader implemented the same morning was replaced. A person reads one receipt photo or PDF at a time from the transaction form behind `Feature.ReceiptReading`, which now starts on like every other switch. A photo is turned upright, stripped of metadata, turned grey, scaled to 1600 pixels wide and put through a local adaptive threshold, then read by the Tesseract command line (`tesseract-ocr` with `lit` and `eng` data in the API image) through `IReceiptReader`, one process at a time with a 60 second limit; a PDF is read from its text with PdfPig, and since 2026-10-01 a PDF without text has its first three pages rendered by Ghostscript at 300 dots per inch and read like a photo, answering `receipt.pdfWithoutText` when rendering fails or every page is blank. `ReceiptTextParser` turns the text into merchant, date, currency, total, items and adjustments, and keeps every line it cannot read for the review. Each item takes the category remembered for its name, else the person's first matching categorization rule, else none. The action is offered only when the switch is on and `tesseract` is on the API's `PATH`. The browser shares the payment over the categories by weight so the lines add up exactly; readings are kept per person and file hash as a cache and deleted a day after their file is gone, and remembered categories are a personal dictionary of normalized item names

Since 2026-10-01 the ledger search also matches the item names of the caller's own readings of a row's attached files, read from `Result` in SQL with nothing copied, and a found row shows the item and its file's warranty date under the description.

Since 2026-10-01 a prepared image taller than 4000 pixels is cut after the threshold into parts of 2000 pixels overlapping by 150, each read by its own Tesseract process, and the texts are joined with the lines repeated across a seam removed; the prepared height may reach Magick.NET's 16000 pixel limit.

Since 2026-10-01 a receipt e-mail, saved as an HTML page or as an `.eml` message, is read in the API from its visible text with MimeKit, a message's HTML part first and its text part otherwise, and handed to the parser like a PDF's text; such a file is read for filling only and never attached.

Since 2026-10-01 a return receipt fills the form as a refund in the category of its largest returned amount, linked to the latest purchase from the same merchant that the reading finds; it is no longer refused.

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

- **2026-10-01.** A return receipt fills the transaction form as a refund, with the category of the heaviest group of its items by the split's weight, the first group on a tie. This reverses the "return receipts refused" part of the 2026-09-29 plan entry below. Decided while the owner was away, to be reviewed
  - Rejected: Keeping returns refused; a refund per category, which would be several transactions from one form; leaving the category empty; taking the linked purchase's category
  - Why: A refund cannot be split, so one category has to stand for the receipt, and the largest share is the one the refund mostly corrects; a typical return is a single item, where every choice agrees. Several transactions would need a new save path for one receipt. The items' own categories are what the person just confirmed in the review, while a split purchase has no single category to take
- **2026-10-01.** The purchase a return belongs to is looked up on the server and answered as `refundOf` on the reading: the latest visible expense, not a refund, whose payee key equals the merchant's normalized name or starts with it and a space, of at least the returned total, in the receipt's currency, dated up to 90 days before the receipt and without this file attached; none when nothing matches. The refund takes its description in the create dialog. Decided while the owner was away, to be reviewed
  - Rejected: The import proposal's exact key only; matching the amount exactly; a list of purchases to choose from; looking it up in the browser
  - Why: A purchase filled from its receipt has the merchant as its key, but one from the bank has the merchant followed by the city or card text, so an exact key would miss the bank row; a prefix on whole words finds both without matching another shop whose name merely begins the same. A return is often part of a purchase, so the purchase is at least the total, as in the import's proposal, whose 90 days are reused. One proposal with the form's existing unlink button is the least to read, and the server already holds the query filters that decide what the person can see. Excluding the transactions with this file attached keeps an expense whose edit dialog read the return from linking to itself. The purchase's description gives the refund the shop's payee key, as "Record refund" does

- **2026-10-01.** An HTML page or e-mail receipt is turned into text with MimeKit, which MailKit already references: `MimeMessage` takes an `.eml` apart and `HtmlTokenizer` walks the HTML, keeping visible text only, starting a line at each block element and joining a table row's cells with a space. `.eml` is accepted beside `.html` and `.htm`, its HTML part first and its text part otherwise, and a file is known by its declared type or, when none is declared, its extension. Decided while the owner was away, to be reviewed
  - Rejected: AngleSharp or HtmlAgilityPack as a new package; stripping tags with a regular expression; rendering the page in a headless browser and reading the picture with Tesseract; HTML only, without `.eml`; reading a PDF or image attached to the message
  - Why: A receipt needs text in reading order, not a DOM, and MimeKit's tokenizer, maintained with MailKit, already decodes entities and knows script and raw-text content, so a second parser would be a new dependency for nothing this uses. A regular expression trips over comments, scripts and entities, and a browser would be a heavy process to recover text that is already text. Mail programs save a message as `.eml` more readily than as HTML, and MimeKit parses it in a few lines. A receipt sent as a PDF attachment is better saved and read as a PDF, which already works, than unpacked by a second path
- **2026-10-01.** HTML and e-mail files are read for filling only and never stored: attachments keep JPEG, PNG, WebP, HEIC and PDF, the create dialog does not attach such a file on save, "Split that payment instead" attaches nothing, and the edit dialog reads it without attaching it first. Decided while the owner was away, to be reviewed
  - Rejected: Allowing `text/html` and `message/rfc822` as attachment types
  - Why: An attachment is served back for preview and download, and an HTML file served from the API's origin could run script in the person's session, so storing it would need a sandboxed origin or a conversion to PDF; an `.eml` also keeps the sender's and recipient's addresses and every header, which the photo path strips. The price is that such a reading goes after a day with its file never attached, so its items count neither in the spending per item report nor in the item search; a person who wants the receipt kept can print the e-mail to PDF, which attaches and reads from its text

- **2026-10-01.** A PDF without text is rendered page by page with Magick.NET through Ghostscript, which the API image installs as the distribution's `ghostscript` package, at a fixed 300 dots per inch, and each page then goes through the photo's preparation and Tesseract. This reverses the 2026-09-29 entry below on the backlog's request. Decided while the owner was away, to be reviewed
  - Rejected: Poppler's `pdftoppm` as a second process; PDFium through a NuGet wrapper; `libgs10` alone; a density chosen per page so the page comes out 1600 pixels wide; 200 dots per inch
  - Why: Magick.NET already reads the images and calls Ghostscript itself, so the code is one read setting and the page joins the photo path; `pdftoppm` would be a second renderer and a second process call to maintain, and a PDFium wrapper brings native libraries per platform, which the image already pays for once with Magick.NET. On Linux Magick.NET runs the `gs` command rather than loading the library, so the library package alone would not do; `ghostscript` with `--no-install-recommends` is the smallest package that provides it, its size in the image not yet measured. The page is scaled to 1600 pixels wide afterwards anyway, so a per-page density buys little for the code; 300 is the usual scanning resolution, gives a till roll 80 millimetres wide 945 pixels and an A4 page 2480, and keeps pages up to about 1350 millimetres long under the 16000 pixel limit. Ghostscript is licensed under the AGPL; it runs unmodified as a separate program from the distribution's package, whose source the distribution publishes, which is the arrangement the image already has with every other package. Rendering untrusted PDFs is Ghostscript's riskiest use, so it runs with `-dSAFER`, on at most three pages of a file of at most 10 MB, inside the non-root API container
- **2026-10-01.** Whether rendering works is found out on each scan: a Magick.NET error while rendering, such as Ghostscript missing, answers `receipt.pdfWithoutText`, the answer before this change, and a scan whose pages all render white answers the same. Decided while the owner was away, to be reviewed
  - Rejected: Probing Ghostscript once at start and reporting it in `GET /api/settings`; a new error code for a missing renderer; answering `receipt.unsupportedFile`
  - Why: A scan is rare and the failure is quick, so a probe and a second readiness flag would add code for no visible gain; the action stays offered on Tesseract alone, because a photo and a text PDF still read. The existing message already tells the person what to do, take a photo or save the page as an image, and with no new code there is no new text to translate. Skipping white pages keeps an empty PDF on the same answer whether Ghostscript is installed or not, so the existing tests hold on both

- **2026-10-01.** A prepared image taller than 4000 pixels is cut, after the threshold, into parts of 2000 pixels that overlap by 150, fixed in pixels of the prepared image; each part is a separate Tesseract call through the unchanged `IReceiptReader`, and the height cap rises from 12000 to the 16000 pixel limit. Decided while the owner was away, to be reviewed
  - Rejected: Reading the whole tall image in one call, as before; parts without overlap; part sizes as a ratio of the width; cutting before the threshold; one Tesseract process over a multi-page TIFF of the parts
  - Why: Before, a long screenshot was shrunk to fit 12000 pixels and read as one block, so its print got smaller the longer it was. Without an overlap a line cut by the edge is lost in both parts. The prepared image is already 1600 pixels wide whenever the height allows, and Tesseract cares about the height of the print in pixels, so fixed pixels say what they mean; 4000 keeps every photo up to 2.5 times as tall as wide in one piece, so ordinary receipt photos read exactly as before. Thresholding first gives both parts the same pixels in the overlap. One process per part keeps the reader a one-image, one-text call that the 60 second limit, cancellation and the test fake already cover; a tall receipt is rare, so the extra process starts do not matter
- **2026-10-01.** Parts are joined by dropping the next part's lines up to the last of its first six that equals, ignoring case and extra spaces, one of the previous part's last six lines of at least four characters, and the previous part's lines after that copy; with no such line the texts follow each other. Decided while the owner was away, to be reviewed
  - Rejected: Matching only a whole run of trailing lines against leading lines; similarity matching with an edit distance; keeping both copies and letting the parser cope
  - Why: The lines cut by the two edges are read as fragments, so a whole run rarely matches exactly, while the full lines inside the overlap come from identical pixels and are read the same. Dropping the previous part's lines after the copy removes its cut-off fragment, which the next part has whole. Edit distance would also merge two neighbouring items whose names differ by a letter. Keeping both copies would count the overlapping items twice. The four-character floor keeps lone prices and VAT letters from being taken for the seam; a repeated short line near a seam can still be, and the review then shows the gap to the printed total

- **2026-10-01.** The ledger search finds item names in the stored readings themselves: one more alternative of the shared `search` filter reads the caller's own `Read` readings of the row's attached files in SQL, `jsonb_array_elements` over `Result -> 'items'` with the same `ILIKE` as the description, while the `ReceiptReading` switch is on. No column, table, migration or backfill. Decided while the owner was away, to be reviewed
  - Rejected: Storing the confirmed item names on the transaction or in a `TransactionReceiptItems` child table when "Use these lines" applies a split; a stored generated column of the names on `ReceiptReadings`; mapping `Result` as an EF JSON type so LINQ could reach the items; finding items without diacritics through the normalized key
  - Why: The names are already durable per transaction: a `Read` reading lives as long as any attachment row with its hash, trashed included, which is exactly as long as the file and its warranty date, so a copy would add a table to the trash, retention, backup and member export and import for no data that is not already kept. "Use these lines" runs before the transaction exists in the create dialog, so a copy would also need the save to carry the names, and it would miss every receipt read but not split. A generated column breaks restoring a backup, which copies every mapped column, and remapping `Result` would change the stored JSON. Folding diacritics would make this one search part behave unlike the description, note, payee and place beside it
- **2026-10-01.** Only the caller's own readings count, a trashed file stops matching, and a found row answers `receiptItem` with the first matching item of its oldest matching file and that file's warranty date, shown as a muted line under the description without an amount. Decided while the owner was away, to be reviewed
  - Rejected: Matching a household member's readings of a shared purchase; a ledger column for the item; showing the item's amount; answering the match on `LedgerItemResponse` only; leaving the warranty date out
  - Why: Readings are personal, as in the spending per item report, and their categories are one person's choices; a partner finds the purchase once they read the receipt too. A line under the description is where the note already sits, so the table keeps its columns, and with no amount there is nothing for hidden amounts to mask. The field on `TransactionResponse` reaches the list, the ledger and the group members alike. The backlog asks for the purchase and its warranty date, and the date is on the file that matched

- **2026-09-29.** The owner's decision: receipt reading uses no external API. Tesseract runs inside the API image and reads the receipt; the hosted reader, its key, model, monthly limit and consent texts are removed
  - Rejected: The hosted Anthropic reader implemented earlier the same day; a local vision model under Ollama; PaddleOCR
  - Why: A receipt shows what was bought, where and when, and the owner wants that to stay in the installation, with no account, key or bill to manage. A vision model would read receipts better, but it needs a model of several gigabytes, a second container and a GPU or tens of seconds of CPU per receipt on the small home servers this runs on, which is too heavy for a household ledger. PaddleOCR would bring a Python runtime into a .NET image. Tesseract is packaged by the distribution, has Lithuanian data, reads a receipt photo in about a second and adds about 66 MB to the image; its weakness, text instead of items, is covered by a parser tested on real layouts and by showing every line it cannot read
- **2026-09-29.** Tesseract is called as a command-line process with the image on standard input and the text on standard output
  - Rejected: A .NET wrapper around the Tesseract library
  - Why: The process call is about fifty lines with a timeout, cancellation and one process at a time, and it uses the binary and language data the distribution maintains. The wrappers on NuGet lag behind Tesseract 5, ship native libraries for some platforms only and would pin the image to their Leptonica build
- **2026-09-29.** A photo is prepared with grey, a 1600 pixel width and a local adaptive threshold, and read with page segmentation mode 6
  - Rejected: Sending the photo as it is; a global contrast stretch; page segmentation mode 4; deskewing
  - Why: Measured on receipts rendered, blurred and lit from one side: the raw photo gave 1 of 13 checked values, a global stretch lost the darker half, the local threshold gave 13 of 13 and changed nothing on a clean scan. Mode 4 split some printed lines in two and separated names from prices; mode 6 kept them. Tesseract handled the small rotation of a hand-held photo without deskewing
- **2026-09-29.** A PDF is read only from its text, with PdfPig; a PDF without text answers `receipt.pdfWithoutText`
  - Rejected: Rendering PDF pages to images with Ghostscript for Magick.NET, or with Poppler's `pdftoppm`, and reading them with Tesseract
  - Why: The PDFs people get for a purchase (e-shop and e-receipt PDFs) carry text, which is exact where OCR guesses. Ghostscript is licensed under the AGPL and, like Poppler, would add a second native renderer and its fonts to the image for the rare scan saved as PDF, which the person can photograph instead. PDFsharp, already used for exports, cannot extract text. Revisit when a real receipt PDF without text turns up often
- **2026-09-29.** An item's category is the one remembered for its name, else the category of the person's first matching categorization rule without an account, else none
  - Rejected: A built-in keyword list of shop items per category; asking the rules with the transaction's account
  - Why: A built-in list would guess in categories the person does not have and need a translation per language; the person's own rules and remembered names already say how they file things. The read request carries no account and a receipt item is not a bank line, so only rules that apply to every account are used. The `CategorizationRules` switch turns the rule step off with the rules page
- **2026-09-29.** The `ReceiptReading` switch starts on in a new installation, and the migration that removes the hosted settings leaves an installation's current value alone; the action is offered only while `tesseract` is found on the API's `PATH`
  - Rejected: Keeping the switch off by default; switching it on in existing installations with the migration
  - Why: It started off only because reading sent receipts out. Now nothing leaves, and readiness follows the engine, so a development machine without Tesseract hides the action instead of failing. An administrator who switched it off chose that, and the only existing installation is the development database, so the migration only changes the column default
- **2026-09-29.** No monthly limit and no usage table; one Tesseract process at a time, the per-file busy check and the endpoint throttle stay
  - Rejected: Keeping the monthly limit as a cap on CPU
  - Why: The limit existed to cap a bill. A read costs about a second of one core, one process at a time keeps a burst from taking every core, and the throttle of 30 calls per five minutes per client stays
- **2026-09-29.** Item names are compared without diacritics, and OCR confusions are folded only when the parser looks for words such as totals and discounts
  - Rejected: Keeping diacritics in the remembered key; folding `0`, `1` and `l` in the key too
  - Why: OCR often loses Lithuanian diacritics, so `SURIS DZIUGAS` has to find `Sūris DŽIUGAS`. Keys written before this change keep their diacritics and simply stop matching, which only the development database has. Digits are dropped from the key anyway, and folding `l` into `i` in stored names would merge different products
- **2026-09-29.** Open questions of the plan, decided while the owner was away and to be reviewed: the default model is Claude Sonnet 5; an administrator's consent for the installation plus the sentence beside every read is the consent, without a per-member opt-in; the bottle deposit stays with its drink; the monthly limit is 100 reads for the whole installation, with no per-member limit; HEIC stays in v1
  - Rejected: Haiku 4.5 or Opus 5.5 as the default; a one-time agreement per member; the deposit on its own line in a category chosen once; a per-member limit; JPEG, PNG, WebP and PDF only
  - Why: Each is the plan's recommended or most conservative answer. Sonnet 5 reads at the high-resolution tier, which matters for small receipt print, at a third of Opus's estimated cost; the choice is revisited after the 20-receipt check before release. The per-click sentence already tells every member where the file goes, and a second agreement would add a setting without adding information. Keeping the deposit with the drink needs no extra category and no extra step. A limit per installation caps the bill that a leaked session could run up, and per-member limits can follow if a household asks. HEIC was the one open question with a condition: the spike showed Magick.NET decodes HEIC in the `aspnet:10.0` image, so it stays
- **2026-09-29.** The API image is published for the build's architecture only (`dotnet publish -a $TARGETARCH --self-contained false`)
  - Rejected: Publishing without a runtime identifier, as before
  - Why: Without one, Magick.NET copies its native library for eight platforms into the image, about 240 MB. For one architecture it adds a single native library of about 37 MB. BuildKit sets `TARGETARCH`, so an arm64 host still gets its own library
- **2026-09-29.** The service unprotects the API key and hands it to the reader, and the reader creates the SDK client per call with the fixed base address
  - Rejected: The reader unprotecting the key itself, as the plan put it
  - Why: With the key read in the service, the integration tests exercise `receipt.keyUnreadable` and `receipt.notConfigured` through the fake reader, and the reader stays a transport that is unit-tested against a stub HTTP handler. `ReceiptRequest` prints the key as `***`
- **2026-09-29.** The image is prepared, and refused when unsupported, before the read is counted
  - Rejected: Preparing it inside the reader after the count
  - Why: A HEIC that cannot be decoded or a password-protected PDF costs the provider nothing, so it should not use up one of the month's reads
- **2026-09-29.** Readings have a plain index on (UserId, Sha256) and the busy check runs under the advisory lock; "Read again" inserts a new reading and removes the earlier one only after it succeeds
  - Rejected: A unique index on (UserId, Sha256) filtered to `Pending` and `Read`, as the plan proposed
  - Why: With that index a forced read could not insert its `Pending` row while the `Read` one exists, so it would have to overwrite the old reading first and lose it when the new call fails. The lock already serializes the busy check and the count
- **2026-09-29.** The purge keeps a reading while any attachment row, of any user and trashed or not, has its hash
  - Rejected: Only attachment rows uploaded by the reading's own user, as the plan put it
  - Why: A household partner reads a file the owner attached; the plan's rule would delete the partner's reading a day later although the file is still there. The reading's lifetime follows the file, which is what the plan's outcome asks for
- **2026-09-29.** The read answers the reading and the candidates only; the browser computes the three totals
  - Rejected: Answering the totals from the server as well
  - Why: The totals change with the transaction amount the person types, so the browser computes them in `receipt-split.ts` anyway; a second copy on the server could only disagree
- **2026-09-29.** As planned, and not reopened: a hosted vision model through `IReceiptReader` with one implementation and a fake for tests; one Messages API call with structured outputs and category numbers constrained by an enum; receipt text treated as data; three consent gates; a fixed provider address; a synchronous read with a 60 second timeout, one retry and Cancel; the count before the call under `AppLock.ReceiptReadings`; a cache per person and file hash; Magick.NET for orientation, metadata, size and HEIC, and PDFsharp for the first three pages; the action inside `TransactionForm` beside the split switch; the proportional largest-remainder split in the browser; differences stated in words and never blocking; the result as `jsonb` without a `ReceiptItem` table; a personal dictionary applied after the model and never sent to it; manual-entry matching for the receipt-first order and candidates for the bank-first order; readings visible only to their reader; readings deleted with their file; the three tables in backups; return receipts refused
  - Rejected: Tesseract or PaddleOCR with a hand-written parser; a local vision model; a forced tool call or free text; a configurable base URL; a queue drained by a job; no limit or a per-user limit; no cache; SkiaSharp or ImageSharp; resizing in the browser; rendering PDF pages to images; a header button, a route or a page; distributing each adjustment separately or a negative discount line; a server endpoint for the lines; a `ReceiptItem` table; sending corrections to the model; a separate receipt inbox; readings shared through the attachment's visibility; keeping readings forever; leaving readings out of backups; recording a return as income or a negative split
  - Why: The reasons are the plan's and are summarized on the [feature page](../features/receipt-reading.md): classic OCR gives text, not items, and would need a parser per shop layout; a local model costs every household a GPU or minutes per receipt; the enum keeps unknown categories out and the checks keep unknown numbers out; a person waits for the answer, so a queue would only add polling; one proportional rule covers discounts, vouchers, rounding, foreign receipts and misread cents and always adds up to the payment the validator demands
