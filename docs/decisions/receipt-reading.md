# Receipt reading: decisions

Related: feature page [Receipt reading](../features/receipt-reading.md); [Attachments](attachments.md); [Transactions](transactions.md); [Email](email.md) for how a stored secret is handled.

## Current

Implemented 2026-09-29 behind `Feature.ReceiptReading`, the first switch that starts off. A person reads one receipt photo or PDF at a time from the transaction form with a hosted model, Anthropic Claude, called by the API server through `IReceiptReader`; the model picks a category number per item from the person's own expense categories, and the browser shares the payment over the categories by weight so the lines add up exactly. Reading needs the switch, an administrator's key and consent in Settings, and a click next to the sentence that says where the file goes. The default model is `claude-sonnet-5`, chosen from a fixed list; each read counts against an installation-wide monthly limit of 100 before the call. Readings are kept per person and file hash as a cache and for a later per-item report, deleted a day after their file is gone, and remembered categories are a personal dictionary of normalized item names.

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

- **2026-09-29.** Open questions of the plan, decided while the owner was away and to be reviewed: the default model is Claude Sonnet 5; an administrator's consent for the installation plus the sentence beside every read is the consent, without a per-member opt-in; the bottle deposit stays with its drink; the monthly limit is 100 reads for the whole installation, with no per-member limit; HEIC stays in v1
  - Rejected: Haiku 4.5 or Opus 5.5 as the default; a one-time agreement per member; the deposit on its own line in a category chosen once; a per-member limit; JPEG, PNG, WebP and PDF only
  - Why: Each is the plan's recommended or most conservative answer. Sonnet 5 reads at the high-resolution tier, which matters for small receipt print, at a third of Opus's estimated cost; the choice is revisited after the 20-receipt check before release. The per-click sentence already tells every member where the file goes, and a second agreement would add a setting without adding information. Keeping the deposit with the drink needs no extra category and no extra step. A limit per installation caps the bill that a leaked session could run up, and per-member limits can follow if a household asks. HEIC was the one open question with a condition: the spike showed Magick.NET decodes HEIC in the `aspnet:10.0` image, so it stays
- **2026-09-29.** The API image is published for the build's architecture only (`dotnet publish -a $TARGETARCH --self-contained false`)
  - Rejected: Publishing without a runtime identifier, as before
  - Why: Without one, Magick.NET copies its native library for eight platforms into the image, about 240 MB. For one architecture it adds a single native library of about 37 MB. BuildKit sets `TARGETARCH`, so an arm64 host still gets its own library
- **2026-09-29.** The service unprotects the API key and hands it to the reader, and the reader creates the SDK client per call with the fixed base address
  - Rejected: The reader unprotecting the key itself, as the plan put it
  - Why: With the key read in the service, the integration tests exercise `receipt.keyUnreadable` and `receipt.notConfigured` through the fake reader, and the reader stays a transport that is unit-tested against a stub HTTP handler. `ReceiptRequest` prints the key as `***`
- **2026-09-29.** The image is prepared, and refused when unsupported, before the read is counted
  - Rejected: Preparing it inside the reader after the count
  - Why: A HEIC that cannot be decoded or a password-protected PDF costs the provider nothing, so it should not use up one of the month's reads
- **2026-09-29.** Readings have a plain index on (UserId, Sha256) and the busy check runs under the advisory lock; "Read again" inserts a new reading and removes the earlier one only after it succeeds
  - Rejected: A unique index on (UserId, Sha256) filtered to `Pending` and `Read`, as the plan proposed
  - Why: With that index a forced read could not insert its `Pending` row while the `Read` one exists, so it would have to overwrite the old reading first and lose it when the new call fails. The lock already serializes the busy check and the count
- **2026-09-29.** The purge keeps a reading while any attachment row, of any user and trashed or not, has its hash
  - Rejected: Only attachment rows uploaded by the reading's own user, as the plan put it
  - Why: A household partner reads a file the owner attached; the plan's rule would delete the partner's reading a day later although the file is still there. The reading's lifetime follows the file, which is what the plan's outcome asks for
- **2026-09-29.** The read answers the reading and the candidates only; the browser computes the three totals
  - Rejected: Answering the totals from the server as well
  - Why: The totals change with the transaction amount the person types, so the browser computes them in `receipt-split.ts` anyway; a second copy on the server could only disagree
- **2026-09-29.** As planned, and not reopened: a hosted vision model through `IReceiptReader` with one implementation and a fake for tests; one Messages API call with structured outputs and category numbers constrained by an enum; receipt text treated as data; three consent gates; a fixed provider address; a synchronous read with a 60 second timeout, one retry and Cancel; the count before the call under `AppLock.ReceiptReadings`; a cache per person and file hash; Magick.NET for orientation, metadata, size and HEIC, and PDFsharp for the first three pages; the action inside `TransactionForm` beside the split switch; the proportional largest-remainder split in the browser; differences stated in words and never blocking; the result as `jsonb` without a `ReceiptItem` table; a personal dictionary applied after the model and never sent to it; manual-entry matching for the receipt-first order and candidates for the bank-first order; readings visible only to their reader; readings deleted with their file; the three tables in backups; return receipts refused
  - Rejected: Tesseract or PaddleOCR with a hand-written parser; a local vision model; a forced tool call or free text; a configurable base URL; a queue drained by a job; no limit or a per-user limit; no cache; SkiaSharp or ImageSharp; resizing in the browser; rendering PDF pages to images; a header button, a route or a page; distributing each adjustment separately or a negative discount line; a server endpoint for the lines; a `ReceiptItem` table; sending corrections to the model; a separate receipt inbox; readings shared through the attachment's visibility; keeping readings forever; leaving readings out of backups; recording a return as income or a negative split
  - Why: The reasons are the plan's and are summarized on the [feature page](../features/receipt-reading.md): classic OCR gives text, not items, and would need a parser per shop layout; a local model costs every household a GPU or minutes per receipt; the enum keeps unknown categories out and the checks keep unknown numbers out; a person waits for the answer, so a queue would only add polling; one proportional rule covers discounts, vouchers, rounding, foreign receipts and misread cents and always adds up to the payment the validator demands
