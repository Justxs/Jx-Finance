# Email: decisions

Related: feature page [Email](../features/email.md).

## Current

Implemented 2026-09-20. One SMTP server per installation, configured by an administrator in Settings, with its own enabled switch and a data-protected password that no response carries; a single-use, one-hour reset link from the sign-in screen beside the administrator reset, recovery codes and host-side admin recovery, which all stay; address confirmation with a resend, consumed by a button click rather than on page load, blocking nothing except unsolicited mail to that address; since 2026-09-27 an email beside any notification kind the user ticks, none by default, sent through the notification publisher like Discord. Everything but the administrator's test message leaves through an outbox table drained by a background job, so no request and no other job waits for a mail server. Message texts are plain, held in the backend in English and Lithuanian, and since 2026-09-29 sent in the member's own language, `AspNetUsers.Language`, saved when they pick one in the interface, and in the installation language while they have none

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

Older entries are in the git history of this file (`git log -p -- docs/decisions/email.md`).

- **2026-10-01.** Reset and confirmation links are built only from `App:SiteUrl`; while it is empty no such message is queued, `forgot-password` still answers 204 and logs a warning, and a resend answers `email.notConfigured`
  - Rejected: Keeping the request's scheme and host as the fallback; refusing to start without `App:SiteUrl`; accepting the request host only when it matches `AllowedHosts`
  - Why: With `AllowedHosts` at `*` the host is whatever the caller sends, so a forged `Host` mailed a valid reset token to an address the attacker controls. The mail server is configured at runtime in Settings, so a startup check cannot know whether links will ever be needed, and it would stop development and installations that never send mail. Matching `AllowedHosts` still trusts the request and does nothing while the list is `*`. The production overlay always sets `App:SiteUrl`, so only an installation without it loses the links, and the warning says why
- **2026-09-29.** Each member's language is stored as a nullable `AspNetUsers.Language`, saved by `PUT /api/users/me/language` whenever a signed-in member picks a language, and used for every email and Discord message the server writes to that member, falling back to the installation's `DefaultLanguage` while it is null
  - Rejected: Keeping the installation language for every message; a language per notification kind; a language field in the profile form separate from the interface picker; making the server the source of the interface language
  - Why: The monthly digest is long enough that the wrong language matters, and the backlog already named the gap before a second member relies on mail or Discord. The interface picker is where a member says which language they read, so saving that choice asks nothing new of them, and a null keeps today's behaviour for everyone who never picks. A language per kind answers a question nobody asked. The interface language stays per browser, as decided on 2026-09-19 in the [Interface](interface.md) log, so a failed save changes nothing visible; the root route sends a choice made before the column existed once, when the profile has none
- **2026-09-27.** Email follows Discord: each user ticks, per `NotificationType`, whether a notification is also emailed, stored as `AspNetUsers.EmailNotificationTypes` (a `jsonb` list like `DiscordWebhooks.Types`) and sent by `NotificationPublisher` for every producer; the choice has its own endpoint, `PUT /api/users/me/email-notifications`, and `BillReminderEmails` is dropped without carrying a `true` over
  - Rejected: Keeping the one `BillReminderEmails` boolean for bill reminders only; one combined endpoint that saves the email kinds and the Discord settings together; migrating a `true` to `["billDue"]`
  - Why: The boolean made email the only channel that a producer had to wire itself, so budget alerts, unusual amounts and the month-end reminder could reach Discord but never a mailbox, and every new kind would have needed another column and another branch in its job. Moving the send into the publisher gives every producer, current and future, both channels from one place, under the producer's own transaction and lock. A combined endpoint was rejected because the two halves have different lives: Discord needs a webhook URL that is encrypted, validated against Discord's hosts, kept when left empty and may be refused with its own errors, while the email choice is a plain list that every user can save without any of that; one body would make a user who only wants email send Discord fields, and a Discord failure would block the email choice. The profile table still shows both columns side by side; it simply saves through two calls. The application is not released, so dropping the column costs nobody a setting
- **2026-09-20.** Every message except the administrator's test send is written to an `EmailMessages` outbox table and sent by `EmailOutboxJob` once a minute, in batches of 20, with five attempts at 4, 16, 64 and 240 minutes and a 20-second cap on one connect-authenticate-send
  - Rejected: Sending inline from the request or the reminder job; sending inline with a fire-and-forget `Task.Run`; a queue library
  - Why: A mail server that is slow or dead would otherwise hold an HTTP request open, or stall the reminder scan while it holds `AppLock.RecurringBillReminders`, which would delay every other user's reminder. Fire-and-forget loses the message on a restart and hides every failure, and it still runs in the request's scope, so a disposed `AppDbContext` follows. A queue library is a second piece of infrastructure to deploy in a household application that already has PostgreSQL. The outbox also makes the reminder email exactly as deduplicated as the notification, because both rows are written in one transaction. The test send stays inline on purpose: its answer is the mail server's answer, and it stores nothing
- **2026-09-20.** `EmailMessages` is excluded from backup and restore, the way `UserSessions` already is, while the data-protected SMTP password inside `InstanceSettings` travels with the backup exactly as the broker's Flex token does
  - Rejected: Exporting the outbox like every other table; leaving the password out of the backup and asking for it after a restore
  - Why: A queued message is work in flight, not a fact about the household; restoring a month-old backup should not resend its mail, and a half-sent outbox in a file that gets copied around is a liability. The password is different: it is a setting the installation needs to keep working, it is already ciphertext that only this key ring can read, and the backup holds password hashes anyway. Leaving it out would mean a restore silently stops sending until somebody notices; carrying it means a restore onto different data protection keys answers `email.passwordUnreadable` when tested, which is a clear instruction instead of silence
- **2026-09-20.** The reset and confirmation links carry ASP.NET Identity's own `DataProtectorTokenProvider` tokens, with nothing stored; single use comes from the security stamp the reset changes
  - Rejected: A `PasswordResetTokens` table with a hash, an expiry and a used flag; a token signed with the JWT key
  - Why: A stored token needs an insert, an index, a sweep, backup coverage and a restore story, and it can still be replayed if the used flag is written after the password. The stamp is already the mechanism that ends sessions on a password change, so reusing it makes the link dead at exactly the moment the password changed, with no second source of truth. The reset token keeps the default provider at a one-hour lifetime; confirmation gets its own provider at one day, since a mailbox read the next morning should still work
- **2026-09-20.** Asking for a reset link and presenting a bad one are throttled per client (5 and 10 calls per five minutes) but neither counts toward the five-failure account lockout; a completed reset clears the counter and any temporary lockout and leaves a deactivation in place
  - Rejected: Counting a bad token as a failed attempt; throttling only per client without an answer that hides whether the address exists
  - Why: Counting would let anyone who knows an address lock its owner out on demand, the same objection that kept the lockout from ending open sessions on 2026-09-19. The token is a 32-byte protected payload, so a five-try counter defends against nothing here. Clearing on success is the point of the flow: the person proved control of the mailbox, so the door that the lockout closed should open. A deactivation is an administrator's decision and is not a lockout
- **2026-09-20.** An unconfirmed address blocks only unsolicited mail to it — the bill reminder — and nothing else; the reset link and the confirmation message itself are still sent to it
  - Rejected: Blocking sign-in until the address is confirmed; blocking nothing at all, reminders included
  - Why: Accounts are created by an administrator who typed the address, so there is no self-registration to defend against and locking people out of their own ledger over an unread mailbox would be pure cost. Sending reminders to an unconfirmed address is the one real risk: a typo turns a household's bill names into somebody else's mail, repeatedly, with no way for them to stop it. Refusing the reset link as well would make a wrong-but-unconfirmed address a trap with no way out
- **2026-09-20.** Message texts live in `Common/Email/EmailTexts.cs` in English and Lithuanian side by side, and a message is composed in the installation's `DefaultLanguage`
  - Rejected: .NET resource files with satellite assemblies; sending the language from the client; keeping the texts in the frontend locale files
  - Why: The backend has no translation mechanism at all: every other piece of server text a user reads is an `ErrorCodes` constant that the client turns into a sentence, and that path cannot reach something that leaves the application. Resource files are more machinery than the four messages justify, and two files drift apart more easily than two branches of one function. The client cannot supply the language for a reminder composed by a background job, and there is no per-user language in the data model — the toggle is a per-browser preference that never reaches the server — so the installation default is the only honest answer today
- **2026-09-20.** The mail server is one installation setting with its own `enabled` flag, read and written through `settings/smtp`, and not a `FeatureFlags` entry
  - Rejected: Adding `Email` to `FeatureFlags` and `FeatureGateMiddleware`; putting the fields into the existing `PUT /api/settings` body
  - Why: A feature switch hides routes, and `forgot-password`, `reset-password` and `verify-email` must stay reachable: a link mailed yesterday should not 404 because an administrator turned a switch off this morning. Folding the fields into the main settings body would have put a credential behind `GET /api/settings`, which every signed-in user reads, and would have made one save either send the password again or lose it. A separate admin-only pair keeps the secret where only administrators can see that it exists
