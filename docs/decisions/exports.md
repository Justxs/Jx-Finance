# Exports: decisions

Related: feature pages [Exports](../features/exports.md) and [Data export per user](../features/data-export-per-user.md); architecture [Transactions, imports and receipts](../architecture/transactions.md) and [Backup and restore](../architecture/backup-and-restore.md#the-member-export).

## Current

**Data export per user.** A member downloads their own records from Settings › Personal › Import and export as one zip streamed to the browser: `data.json` in the backup's table format (`jx-finance-user-export`, version 1) and three CSVs, with attached files only when asked. "Their own" is what they own plus everything on their own accounts, the transfers touching them and the rows those point at; secrets, sessions, household rows and other members' accounts never leave this way. The same zip imports into an empty member of this or another installation, where every record becomes the member's own and personal, also when it was taken on an older version from after the migration squash of 2026-10-03: the old table shapes map onto the current schema column by column, and a download from a newer version is refused. The zip also holds `ledger.beancount`, the member's own accounts, assets and debts as a balanced Beancount double-entry journal whose balance assertions are the app's figures, while the database stays single-sided. Taking it sends no notification; that and the import rules were decided while the owner was away and should be reviewed.
It is a plain `GET` link streamed as it is written, with attachments optional and off, no size cap and no password, limited to three an hour per client and one at a time per member, and read through explicit ownership predicates rather than the query filters. `data.json` holds soft-deleted rows too. The Import and export section is always listed, while the bank statement import inside it follows the `Import` switch.

**Ledger exports.** The transaction CSV streams rows from the database into the response, with the tag map of the filtered set loaded once before the first row. The PDF refuses more than `App:PdfExportMaxRows` rows (5000) with `export.tooManyRows`.

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

Older entries are in the git history of this file (`git log -p -- docs/decisions/exports.md`).

- **2026-10-02.** A member download taken on an older version imports into a newer one by column-level mapping: `MemberImport` accepts any migration EF lists for this application, inserts only the columns the file holds so later columns take the defaults their migrations gave existing rows, and then runs the startup backfills (`PayeeKeyBackfill`, `DebtBalanceBackfill`, `SpreadFromBackfill`) in the import's transaction; a migration it does not list answers `import.newerVersion` when its id sorts after the current one and `import.unknownVersion` otherwise. Decided while the owner was away, to be reviewed
  - Rejected: Importing into a temporary schema created at the file's migration and running the migration chain on it before copying the rows over; keeping the single accepted migration and telling the member to import with the version that wrote the file, as a restore does; scoping the backfills to the member's rows by a new parameter; one shared `backup.schemaMismatch` for a newer and an unknown file
  - Why: Every migration since the export appeared on 2026-09-29 only adds tables, nullable columns or columns with a default, and none renames or drops a column of an imported table, so the generated migrations already say what an old row becomes and the insert needs no per-version code. A migration chain at import time would need a schema per import, EF migrations run against another schema, its own locks and cleanup, and would still need the startup backfills, which live outside the migrations. Running the old version is reasonable for an administrator restoring a whole installation, not for a member moving their data. The backfills select only rows still missing their value, which after startup are the imported ones, so reusing them unchanged keeps one definition of each fill. A member who took the file on a newer version can fix it by upgrading, which an unknown version cannot, so the two get their own codes and texts. A future migration that renames or drops an imported column adds an explicit mapping in `MemberImport`; until then such a column fails the import as `import.invalidFile`
- **2026-10-01.** The double-entry journal opens each debt at its earliest recorded balance against `Equity:Opening-Balances` and posts every later recorded balance, narrated "Recorded balance" with its note, against `Equity:Revaluation`, as it already did for asset valuations; tracked payments still count only after the newest balance, as in the app. Decided while the owner was away, to be reviewed
  - Rejected: Keeping the opening at the current record; posting a lower recorded balance as principal repaid from `Equity:Outside-Accounts` or as interest under `Expenses`
  - Why: The current record hid every manual change before it, and the history now exists. A recorded balance says what was owed, not how it came about, so it cannot be split into payments or interest without inventing figures; a revaluation keeps the income statement equal to the app's reports
- **2026-10-01.** The transaction CSV and the member export's `transactions.csv` gain a `Group` column after `Place`, holding the name of the caller's own group and empty for a row in someone else's; the member export carries `TransactionGroups` as an owned table, and older exports could not be imported after the `AddTransactionGroups` migration until imports from an older version arrived on 2026-10-02
  - Rejected: Leaving groups out of the exports; the group id instead of its name; naming a housemate's group
  - Why: A group is something the member made, so it belongs in what they take with them, and a spreadsheet reads a name, not an id. A housemate's group is personal to them and would leak into this member's file. The column goes at the end like `Note`, `Spread months` and `Place`, so a spreadsheet that reads the older columns by position keeps working. See [Transaction groups](transaction-groups.md)
- **2026-09-30.** The member export adds `ledger.beancount`, a Beancount v3 double-entry journal of the member's own accounts, assets and debts, while the database stays single-sided; a C# `JournalChecker` checks it in the tests
  - Rejected: Replacing `Transaction`, `Transfer`, `CurrencyConversion` and `InvestmentTransaction` with journal entries and postings; an hledger or ledger-cli journal; a JSON of postings; exporting the exchange-rate and security-price tables; a per-household journal for an administrator; running Python `bean-check` in CI
  - Why: Every feature reads the current shapes: the six arms of `AccountMovements`, `CategoryAttributionService`, splits and refunds, trash restores, the audit log, settle-up, debt payments, the month-close snapshot and the member export and import. A rewrite buys no figure the app does not already compute exactly. Transfers and conversions are already two-sided and a transaction's other side is its category, so the model is double-entry in all but storage, and the journal makes that explicit and checkable. Beancount is the strictest of the three formats, refusing an unbalanced transaction and a failed assertion, and Fava gives a complete browser interface on top of it; a JSON of postings has no tool to check it. The price rule keeps installation-wide market data out, as the export already did, except one `LastPrice` per held security, without which Fava cannot value holdings the way the app does. Household data belongs to every member, so there is one journal per member. The C# checker catches the same errors without a Python toolchain in the runner
  - Adaptations to the code found while building it: an oversold account books `NONE` but posts only the quantity the app's replay found in lots, because Beancount under `NONE` would otherwise hold a negative quantity the app does not; the app tracks only unsplit expenses on a debt, so a split payment linked to one counts wholly as spending rather than being prorated; and `inferred_tolerance_default` `*:0.005` lets a stock split, which posts only security units, balance to the rounding of 28-digit lot costs
- **2026-09-30.** The member export is re-importable, into an empty member only, with the ids kept, references outside the file cleared or dropped, and everything made personal. Decided while the owner was away; review it
  - Rejected: Merging into a member who already has data; giving every row a new id; importing households and shares; inserting table by table in dependency order without deferring foreign keys
  - Why: Merging needs a rule for every duplicate account, category and rule, and new ids need a rewrite of every reference column; keeping the ids and refusing a member with data answers the one real case, moving to another installation, with no mapping. A collision then means the records are already here, which `import.alreadyPresent` says. Households belong to several members, so the importer cannot rebuild them, and a shared row without its household would be invisible; personal is the only scope that holds. Deferring foreign keys reuses the restore's inserter and copes with self-references such as category parents, at the cost of briefly locking the tables the way a restore does; lock_timeout keeps that bounded
- **2026-09-29.** Export links are built by the generated `getExport…Url` builders, and the ledger passes the list's own parameters, so the CSV and PDF follow the list's sort; `useExportUrl` only appends the active household
  - Rejected: Keeping hand-written paths in `lib/export-url.ts`; passing only the filters with a made-up page
  - Why: The paths had to be kept in step with the contract by hand. The export endpoints bind the list request, so the contract marks `page` and `pageSize` required although the export ignores them; the list's parameters satisfy that without inventing values and give the file the order on screen. Giving the export endpoints a request without paging would drop the two parameters and is left to the backend
- **2026-09-29.** The two open questions of the member export plan: the file is not re-importable in version 1, and taking it leaves no notification. Decided while the owner was away; review both
  - Rejected: Declaring `jx-finance-user-export` a public contract now and shipping or promising an importer; a "Your data was downloaded on …" notification
  - Why: Nobody has asked to move a member between installations, and an importer has to decide what to do with references to rows it does not have. The format already carries `format` and `version` and `BackupReader` reads it, so declaring it a contract later costs a version bump rather than a redesign; until then the feature page says the file is not re-importable. A notification would be the only trace of a stolen session taking the data, but the same session can already read every one of these records through the API and the CSV export without any trace, so it would protect nothing new and add a notification kind. The download is logged with the member's id. This is the conservative answer to both and is easy to reverse
- **2026-09-29.** The member export writes its zip through `DeferredWriteStream`, which holds synchronous writes in memory until the next asynchronous write or flush
  - Rejected: `AllowSynchronousIO` for this one request; building the archive in a temporary file and streaming the file
  - Why: .NET 10's async zip API still writes an entry's trailer and the central directory synchronously, which Kestrel refuses. Allowing synchronous IO would block a thread on the response and break the rule the rest of the API keeps; a temporary file would leave personal data on the server, which the streamed design exists to avoid. Only those small trailers are ever buffered
- **2026-09-29.** "Their own" in the member export is four kinds of row: what the member owns; everything on their own accounts, whoever entered it; every transfer with a side on their accounts; and the categories, tags and securities their rows point at
  - Rejected: Everything the member can see; only what the member created
  - Why: "Everything visible" would take the history of a partner's shared accounts, which is the household's and is what the administrator's backup is for. "What I created" would split one account's history between two files and leave out of the member's own account what their partner entered on it. The referenced rows are few and already visible to the member, and without them the ids in the file would mean nothing
- **2026-09-29.** The member export never includes password hashes, stamps, two-factor secrets, passkeys, API token hashes, sessions, the broker token, Discord webhooks, households, memberships, the activity log, outboxes, installation settings or market data
  - Rejected: Including the encrypted secrets, as the backup does
  - Why: An encrypted secret is unreadable on any other installation and useless to a person. Household rows belong to all members, not to one. `UserExportTablesTests` fails when a table of the model is left unclassified or an exported column is named like a secret
