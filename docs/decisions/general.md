# General: decisions

Related: architecture [Architecture](../architecture/README.md).

## Current

### Architecture

One API project, feature services use EF directly, thin endpoints, architecture tests. Every feature service sits behind its own interface in `Endpoints/<Tag>/Interfaces`, even with a single implementation, and endpoints, jobs and other services depend on the narrowest interface they need; a service that outgrows one concern is split along its seams, each part with its own interface. A tag reaches another only through its `Interfaces`, `Shared` or request and response namespaces, never its `Services`, and `Common` never depends on `Endpoints`; helpers two tags need live in `Common` or the owning tag's `Shared` folder

### Release scope

Ledger, planning, reporting, multi-currency, investments, tags on transactions, description-based categorization rules and administrator backups are in, and since 2026-09-30 daily closing prices of held securities from a market data provider, off until an administrator switches it on; since 2026-10-01 machine-learned category suggestions are in too, off until an administrator switches them on, see [Learned categories](learned-categories.md); offline and wider sharing stay deferred

### Database lifecycle

Apply EF migrations directly on startup; every connection the API opens turns PostgreSQL's JIT compiler off; the `pg_dump` based dump, the backup scheduler and offsite copies removed on 2026-09-05 stay removed. Backups exist again in a different form, see [Backup and restore](backup-and-restore.md)

### Concurrent edits

The full update of a transaction, an account, a budget or a goal requires the `version` the client read, which is PostgreSQL's `xmin`, and answers 409 `conflict.stale` when the row changed since; bulk endpoints, imports, jobs and progress deltas stay last-write-wins. See [Concurrent edits](../architecture/api-contract.md#concurrent-edits)

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

- **2026-10-07.** The API turns PostgreSQL's JIT compiler off for its own connections by appending `-c jit=off` to the `Options` of the configured connection string in `ConfigKeys.DefaultConnectionString`. Timing a ledger of 100,000 rows over ten years for two members showed every ledger page at about 2 seconds and a ledger search at 5, of which about 1.2 seconds per query was JIT compilation of plans whose estimated cost the visibility filters had pushed over `jit_above_cost`; with JIT off the same page takes about 100 milliseconds end to end
  - Rejected: `command: postgres -c jit=off` in `docker-compose.yml`; `ALTER DATABASE ... SET jit = off` in a migration; raising `jit_above_cost`; rewriting the visibility filters until the estimates drop
  - Why: Compose reaches only the bundled database, not an external server, Testcontainers or `JX_TEST_POSTGRES`, so the tests would keep planning differently from production. A database setting needs the right to alter the database, is lost when a backup is restored into a fresh one, and would be the first migration that changes server settings. A higher threshold only moves the cliff to a larger ledger. The filters are correct and shared by every query; their estimates are far off because PostgreSQL cannot see through the nested `EXISTS`, and household-sized queries gain nothing from JIT at any size
- **2026-10-04.** The next three largest classes are split along their seams with no change in behaviour or contract. The recurring entry service becomes `RecurringBillService` (list, read, create, update, delete), `RecurringBillOccurrenceService` (confirm and skip) and `RecurringBillScheduleService` (calendar and totals), each behind its own interface, sharing an internal `RecurringBillLookup`. `StatementImport` and `TrashRestorers`, which nothing injects, are split into internal classes in the same folder without interfaces. Architecture tests now check the wiring without a database: every constructor parameter of an endpoint, a registered service or a hosted service, and every service a job resolves with `GetRequiredService`, is registered; every `[RegisterService]` class under a tag registers as an interface from that tag's `Interfaces`; no endpoint keeps the scaffold text. Approved-list tests name each added or missing entry, the list to edit and the alternative
  - Rejected: `ValidateOnBuild` on the application's service provider; relying on the startup failure FastEndpoints already gives when it creates an endpoint it cannot resolve; partial classes for the long files; interfaces for the internal parts; keeping one interface for every recurring entry operation
  - Why: `ValidateOnBuild` sees only registered services, not the endpoints FastEndpoints creates itself nor what a job resolves from its scope, and the startup failure stops every architecture test with one exception without saying which registration is missing. Partial classes would only spread one class with all its state over more files. The internal parts are created per run or per call and are never injected, so an interface would describe nothing a caller chooses. The calendar and totals read the ledger and rates while confirming writes it, and each endpoint now depends only on what it calls
- **2026-10-03.** Optimistic concurrency for the four records household members edit together: transactions, accounts, budgets and goals map PostgreSQL's `xmin` system column as a row version (`uint Version` with `IsRowVersion()`), every response carries it as `version`, and each `PUT` requires it. The update service sets it as the original value and forces the row update, so a mismatch answers 409 with the existing `conflict.stale` code rather than a new one, and writes nothing. The edit forms send it, show the message in the form on a 409 and pick up the fresh version so that saving again works. Bulk endpoints, imports, background jobs, `ExecuteUpdate` paths and the goal progress `PATCH` take no version
  - Rejected: Keeping last write wins; comparing an `UpdatedAt` the client sends; an explicit version column the application increments; `ETag` and `If-Match` headers; an optional version; a new `conflict.edited` code
  - Why: Last write wins let one member silently undo another's edit of a shared record. `UpdatedAt` is set by the application only for tracked saves, and several `ExecuteUpdate` writes leave it alone on purpose (place renames, group membership), so a timestamp check would miss real changes. An explicit column needs a migration, a backfill and an increment in every write path, raw SQL and `ExecuteUpdate` included, while PostgreSQL maintains `xmin` on every write for free and the migration runs no SQL; the price is that unrelated writes such as a revaluation or the unusual-amount stamp also move it, which costs one extra save. A header is not part of the generated hooks' request types, which is why `Idempotency-Key` stays out of the OpenAPI document too, so the forms would have to pass it by hand. There are no outside clients and the app is unreleased, so a required version costs nothing, while an optional one would leave token scripts silently last-write-wins. `conflict.stale` already means "this changed in the meantime" for recurring confirmations, and one translated message covers both
- **2026-10-03.** The three largest services are split along their existing seams, each part behind its own interface, and endpoints inject the narrowest one: `TransactionService` into `TransactionQueryService` and `TransactionWriteService`, `NetWorthService` into `AssetService`, `DebtService` and a `NetWorthService` for totals and history, and `SettingsService` into `SettingsService` (installation settings with the reporting-currency revaluation), `SmtpSettingsService`, `MarketPriceSettingsService`, `DiscordSettingsService` and `ExchangeRateSyncService`. Behaviour and the API contract are unchanged. A private helper two parts share became an internal static class in the tag's `Services` folder (`TransactionResponses`, `DebtTracker`, `OwnerDeletion`, `StoredSettings`), and helpers another tag used moved out of `Services`: the backup reader, archive, JSON names and database plumbing to `Backups/Shared`, `ContactSplitMarks` to `Contacts/Shared`, `PriceSyncRules` with the EODHD key purpose to `Common/MarketPrices`, and `MonthlyDigest` from `Common/Notifications` to `MonthCloses/Shared`. New architecture tests hold the result: no type reaches another tag's `Services`, `Common` never depends on `Endpoints`, every entity has an owner filter or is listed as global or child, the admin routes and the files calling a bare `IgnoreQueryFilters()` match approved lists. Bulk soft deletes go through `SoftDeleteAsync`
  - Rejected: Keeping one service per tag and splitting only by regions of the file; one combined interface implemented by several classes; a shared base class or an injected helper service for the response builder; duplicating the small helpers in each part; moving the backup helpers to `Infrastructure` or `MonthlyDigest` to `Infrastructure/BackgroundJobs`; a denylist of forbidden filter bypasses
  - Why: The transaction service had passed a thousand lines and the net-worth service eleven dependencies, so every endpoint pulled in everything; a narrow interface states what an endpoint or job can do. A static helper keeps the shared code in one place without another registration or a hierarchy. The backup reader depends on `IBackupVisitor`, so `Infrastructure` would have depended on `Endpoints`, and the digest builder reads a month-close response, so its home is that tag. Allowlists fail on the new case the day it appears, the way the token and anonymous route lists already do. `UpdatedAt` stays untouched by place renames and group membership changes, as their own decisions record

- **2026-10-02.** A job declares a `JobSchedule`: a fixed interval, or a cron expression parsed by Cronos and read in the installation time zone. `RetentionJob` runs at 03:00, `MonthCloseReminderJob` and `MonthlyDigestJob` at 08:00, the rest keep their intervals, and every job still makes one pass at startup
  - Rejected: Hangfire, Quartz.NET, TickerQ or Coravel; computing the next local time by hand from `IClock.StartOfDay`; a cron expression for every job; no startup pass for cron jobs
  - Why: The outbox tables and advisory locks already give the durability and the single run a job library sells, while each library brings its own tables, dashboard or job activation beside `CreateUserScope`. A local time of day computed by hand has to get daylight saving right twice a year, which Cronos already does. Cron cannot express an interval in seconds that a setting chooses, such as the email outbox's. Without the startup pass, a server that is off every night would never run the retention
