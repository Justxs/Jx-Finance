# Imports: decisions

Related: feature page [Bank statement import](../features/bank-statement-import.md); architecture [Transactions, imports and receipts](../architecture/transactions.md).

## Current

Three statement formats, Swedbank CSV, ISO 20022 camt.053 XML and any CSV read through a personal column mapping saved once per bank and listed as its own provider, chosen explicitly from the provider list and sharing one preview and one confirm; a mapped CSV names columns by header, or by position from 1 when it is saved as having no header row, reads one of four amount styles, skips non-booked rows, counts unreadable ones and records its latest balance like a camt.053 closing balance; a credit card is an account of type `CreditCard`, with no limit or due date stored, whose new mapping starts on the card amount style; duplicate references skipped, including deleted imports, with camt.053 references stored unprefixed; a row matching a hand-entered transaction of the same signed money and currency within three days is proposed as a link that stamps the bank reference on that transaction and adds nothing; strict Swedbank columns with any supported currency; tolerant camt.053 reading that counts unreadable entries; an IBAN mismatch is a warning, not a refusal; explicit transfer matching; no automatic money movement; counted review views and a search that only change what is shown; review rows that show the purpose text under the payee and their marks in the description cell, with tags, spread and "Mark as transfer" behind one "More options" popover; a confirmed import that ends on a result panel linking to the next steps; an edited review asks before it is discarded and is not resumable; an incoming row with a refund candidate from the same payee in the last 90 days, or a camt.053 reversal, starts as a refund for review; a statement file dropped into the import inbox folder (`App:ImportInbox`) becomes a review waiting for the owner of the one account whose IBAN the file or its subfolder names, read again through the ordinary preview when the owner opens it, and is never imported without that review

One pair of routes, `POST /api/import/preview` and `POST /api/import/confirm`, each taking `format`, and a mapped CSV also `mappingId`. A mapping is a personal record that stores the encoding, delimiter, lines above the header, decimal mark and one of eight date formats, which the inspect call only proposes, and it fits a file when every column it names is there; a row's currency is the currency column, else the mapping's, else the account's, and its reference is the reference cell up to 64 characters, else a hash of the row shared with camt.053. A camt.053 entry whose details add up to it becomes one row per detail; a file with several statements reads the one for the chosen account and refuses with `import.noStatementForAccount` when none matches, and an IBAN of another visible account offers to switch to it. A refund candidate is an expense on the same account and currency, dated on the row's day or up to 90 days before, at least the row's amount, whose `PayeeKey` matches the row's payee or description, the most recent winning; a hand-entered refund matches the bank's incoming row by signed money. A link to a hand-entered row keeps its date, category, tags and description. Review rows can carry tags

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

Older entries are in the git history of this file (`git log -p -- docs/decisions/swedbank-csv-import.md`).

- **2026-10-02.** After a design critique, the review row shows the bank's purpose text under the payee, its marks move into the description cell, the Tags, Status and Record as columns go, and a row's tags, spread and "Mark as transfer" sit behind one "More options" popover; the category cell carries "Record as" when the row needs it. A confirmed import ends on a result panel in the dialog with zero-free counts, the statement check and links to categorize the new rows, view them and open the month close. Decided while the owner was away, to be reviewed
  - Rejected: Keeping one column per control with a wider minimum width; showing the per-row controls on hover or focus only; a menu whose items open further popovers; closing the dialog on confirm and leaving only the toast
  - Why: At laptop width the old 1072px table pushed the status column out of view and left the description about 150px, the part a person reads to decide. Controls that appear on hover cannot be found by touch and shift the row as they appear, while one popover per row keeps every setting one click and one tab stop away and the values that were set stay visible as marks. A toast disappears before the next step is clear, and the ledger filter for the uncategorized rows of that account and period is exactly what the member does next

- **2026-10-01.** The owner asked for a card account type, which supersedes the 2026-09-29 entry that kept cards as type Other. `AccountType.CreditCard` (`creditCard`) is added at the end of the enum, stored as an integer like the others, so no migration. Its balance stays signed and is normally negative; the accounts table reads it as "Owed €450.20" in the ordinary colour; net worth and the totals count it as before; the mapping form starts a new mapping on the "Card statement" style when the chosen account is a card; the cash-flow forecast gives a card no below-zero warning; the journal opens it under `Liabilities:CreditCards`; paying it is an ordinary transfer. Decided while the owner was away, to be reviewed: the type only, with no credit limit, statement date or due date, and the wording and forecast choices above
  - Rejected: Storing a credit limit and a due date; showing the debt as a positive balance with its own sign rule; leaving a card out of net worth or moving it to the debts of the net-worth page; a dedicated card payment entry instead of a transfer; keeping the forecast's below-zero warning for cards
  - Why: A limit and a due date would each need a field, validation, a column and a screen that uses them, and nothing reads them yet, so they wait for a feature that does (an available-credit line or a due reminder). Keeping balances signed means every sum, report and reconciliation stays as it is, and only the words change where a person reads the balance. A card is an account with its own transactions, not a debt record with a schedule, so it stays in the accounts and counts once. A payment from the bank is money moving between two of the member's accounts, which is what a transfer is. Below zero is a card's normal state, so the forecast warning would fire for every card every day
- **2026-10-01.** The owner asked for CSV files without a header row, which supersedes the 2026-09-29 entry that required one. A mapping gains `NoHeaderRow`; when it is set, the existing `Columns` names hold 1-based positions (`"1"`, `"4"`), the parser names the cells of the first line by position and reads that line as an entry, and the form offers "The file has no header row" beside the other reading options, which re-reads the file and shows the columns as "Column 1", "Column 2" over the sample rows it already showed. Inspect proposes no header when the line it found holds a date. Decided while the owner was away, to be reviewed: positions stored as text in the same column map, a date in the first line as the only detection, and a missing position answered like a missing column
  - Rejected: A second column map of integers beside the names; 0-based positions; detecting a missing header by numbers as well as dates; letting a no-header mapping fit a file inspected with a header
  - Why: Positions as text keep one `jsonb` shape, one validator, one `import.missingColumns` path and the same form selects, so the change is a flag rather than a parallel mapping; positions from 1 are what a person counts in a spreadsheet. A date is what every statement line has and no header cell does, while a numeric header such as a year would misfire. The 2026-09-29 worry stands for these files: a bank that reorders its columns makes a position read the wrong cell where a name would have failed, which is why a header stays the default and the saved choice is explicit. A file whose header holds an IBAN-like number or no date is still read with a header unless the member ticks the box
- **2026-10-01.** Decided while the owner was away, to be reviewed. The import inbox is a folder named by `App:ImportInbox`, off when unset, read by `ImportInboxJob`, a `PeriodicJob` every five minutes under the `Import` switch, with the database work of each file under `AppLock.ImportInbox`; `docker-compose.yml` sets it to `/import-inbox` on a named `import_inbox` volume
  - Rejected: A `FileSystemWatcher`; a folder chosen in Settings; a bind mount to a host folder in the default compose file
  - Why: Every other job is a periodic pass, and a watcher misses events on network and container mounts and fires before a copy finishes; a pass that skips files written in the last minute needs neither. A path typed in the browser would let an administrator point the API at any folder it can read. A named volume works on every host without a path, and an empty folder costs one directory listing per pass; an owner who wants a sync client replaces it with a bind mount, as the deployment page says
- **2026-10-01.** Decided while the owner was away, to be reviewed. A file belongs to the one account, among active members' accounts, whose IBAN the file names, or whose IBAN is the name of the subfolder it sits in; a CSV file must sit in such a subfolder and is read with the account owner's saved mappings, exactly one of which must read it, falling back to Swedbank CSV when none does
  - Rejected: A subfolder per member; a file name convention; a subfolder per mapping; guessing between two mappings that both read the file; giving a joint IBAN recorded by two members to one of them
  - Why: camt.053, OFX and MT940 files already carry the IBAN, and the preview already uses it to choose a statement and warn about a mismatch, so the root of the folder needs no convention at all. A CSV carries no account, and an IBAN folder name is the one fact that names both the account and its owner without a second lookup table; the mapping then follows from the fit test the mapping form already uses. A wrong guess would put a statement in someone else's review, so anything ambiguous goes to `failed/` with the reason
- **2026-10-01.** Decided while the owner was away, to be reviewed. A waiting review is the stored file, an `ImportInboxFile` row with the bytes, the account, the format and the mapping, and Review downloads it and runs the ordinary `POST /api/import/preview`; the dialog removes the row with `DELETE /api/import/inbox/{id}` once the confirm succeeds
  - Rejected: Storing the preview result; keeping the file in a pending folder on disk; importing straight away; a confirm that takes the inbox id and removes the row in its own transaction
  - Why: A stored preview goes stale: duplicates, hand-entered matches and refund candidates depend on the ledger at the time of review, as the 2026-09-28 entry on resumable reviews found. Bytes in a row commit together with the notification, survive the file being moved or deleted, and need no second store to keep in step. The dialog's preview, review and confirm stay exactly as they are; a removal that fails after a confirm only leaves a file whose rows are all duplicates now, which Dismiss clears
- **2026-10-01.** Decided while the owner was away, to be reviewed. A file the inbox cannot use moves to `failed/` with a `<name>.reason.txt` beside it, and Settings › Installation › Import inbox lists the latest 20 by reading that folder; accepted and repeated files move to `done/`; nothing deletes either folder's files
  - Rejected: A failures table in the database; deleting processed files
  - Why: The reason is next to the file for whoever fixes it on the host, and the folder is the list, so there is nothing to keep in step or to prune. The files are the household's statements, and the application does not delete what it did not create
- **2026-10-01.** Decided while the owner was away, to be reviewed. A file whose SHA-256 the inbox received in the last 90 days is ignored; removing a file from the list deletes its bytes at once and keeps the row as the fingerprint; `RetentionJob` deletes every inbox row 90 days after it arrived, reviewed or not
  - Rejected: Keeping fingerprints for ever; keeping a waiting file until it is reviewed however long that takes
  - Why: A one-way sync client copies an export again after the inbox moved it, and without a fingerprint each copy would become a new review. Ninety days outlasts any statement period and bounds the table, and the original stays in `done/` to drop in again; the review's own duplicate check still protects the ledger after that
- **2026-10-01.** Decided while the owner was away, to be reviewed. The inbox table is left out of backups and of the member download
  - Rejected: Backing up the waiting files like attachments
  - Why: They are copies of files the folder keeps, up to 20 MB each, and a restored waiting review would point at a ledger that has moved on
- **2026-10-01.** Decided while the owner was away, to be reviewed. Each accepted file raises one `importWaiting` notification for the account's owner, through `INotificationPublisher`, linking to Settings › Personal › Import and export
  - Rejected: One summary notification per pass; no notification
  - Why: A statement arrives rarely, a few a month, and the file name in the title is what the member needs to recognise it; going through the publisher lets a member choose email or Discord for it like any other kind
