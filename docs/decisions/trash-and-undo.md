# Trash and undo: decisions

Related: feature page [Trash and undo](../features/trash-and-undo.md).

## Current

Deleting a transaction, transfer, conversion, budget, goal, asset, debt, recurring entry, investment entry, category, tag, categorization rule or household writes a `DeletionEntry` beside the soft delete, which feeds a toast with Undo and a 30-day Trash section on the profile (Settings › Personal › Trash); the last four also write one `DeletionChange` per row they rewrote. Restoring is one `POST /api/trash/restore` keyed by kind and record id, idempotent, and refused with a published code when the account is archived, the category is gone, a conversion's fee was deleted separately, a split's lines are missing, a budget's category and period were taken again, a tag's name was taken again, the rule limit is reached or the restorer is no longer a household owner; recorded rows that have moved on since are skipped rather than refused. Archiving an account stays its own operation. Past the window `RetentionJob` sweeps: it hard-deletes the entries, their changes and the records ten of the fourteen kinds point at, from the same cutoff the read filter uses

## Log

Newest first. Each entry is a choice between real alternatives: what was chosen, what was rejected, and why.

- **2026-10-01.** Ungrouping a [transaction group](transaction-groups.md) is a trash kind, `transactionGroup`, that records each member as a `GroupMember` change; a restore regroups the recorded members still live and in no other live group, and the kind is purged after 30 days, after the transactions
  - Rejected: Ungroup as a hard delete without undo; leaving `GroupId` on the members and only soft-deleting the group
  - Why: Ungroup loses a name and a set of rows the person chose, which is what the trash exists for. Clearing `GroupId` on the members leaves no row pointing at a deleted group, and the recorded ids put the members back unless they have joined another group since
- **2026-09-23.** There is a purge job after all: `RetentionJob` (the former `AuditRetentionJob`) runs the audit prune, a session sweep, a record purge and a trash-entry prune as four steps of one daily pass, from one cutoff helper, and the ten purged trash kinds and the four kept ones are two lists a test forces a new kind into
  - Rejected: Leaving the 2026-09-21 decision that nothing purges; a separate job per step; purging all fourteen kinds; a configurable retention setting per step
  - Why: The earlier decision priced the purge against a 120-byte trash entry, which was the wrong number: the record behind it carries split lines, tag links and up to ten files, and an imported-into installation grows rows no query can reach again. The reasons it gave against a purge were an order to delete in and a failure mode, and both are answered by writing the order down once — conversions before transactions, imports before transfers, attachments before their transaction — rather than by not doing it. Separate jobs would have to agree on an order they cannot see; one pass makes the order a line of code. Categories, tags and households stay out because restricting foreign keys point at them from rows the purge does not touch, so taking them would need a second pass of rewrites for a hundred bytes. A setting per step would be four numbers an administrator has no basis to choose, when the windows the product already promises — 30 days of trash, 400 days of log — are the only honest ones
- **2026-09-23.** `RetentionJob` takes its trash cutoff from `DeletionEntry.WindowStart`, the same helper `TrashService` reads for the list and for `restore.expired`, and `AppDbContext` stamps `CreatedAt`/`UpdatedAt` from the injected `IClock` rather than `DateTimeOffset.UtcNow`
  - Rejected: A second constant or a job-local `now.AddDays(-30)`; purging by the trash entry's `DeletedAt` and joining to the record
  - Why: One cutoff in two places is the only thing that makes "the job never deletes what the UI still offers" checkable rather than hopeful, and a unit test now compares them at the boundary instant. The stamps have to come from the same clock for that to hold, because a record's `UpdatedAt` and its entry's `DeletedAt` are written in one save and compared against one cutoff; reading the ambient clock in the context also made the rule untestable with frozen time. Joining to the entry would miss every soft-deleted row that never had one — a conversion's fee, a household's memberships — which is exactly the set nothing else would ever remove
- **2026-09-21.** A category, tag, categorization rule or household delete records what it rewrote as rows of a `DeletionChanges` child table — (entry, kind, row id) — and a restore applies each recorded row only where it is still sound, skipping the rest rather than refusing
  - Rejected: A JSON payload column on `DeletionEntry` per kind; storing the previous value beside each row id; refusing the whole restore when any recorded row has moved on; keeping the four deletes final (the decision below, which this replaces)
  - Why: The payload is a set of ids that a restore feeds straight back into set-based `UPDATE ... WHERE id = ANY(...)` statements, which a table does with typed columns, a primary key that deduplicates for free and a cascade from the entry, while a JSON column would have to be parsed in memory and would still be one unbounded value per row — a category can touch a year of transactions, and a table row per id is the shape PostgreSQL stores and backs up best. The table is picked up by `BackupService` from the EF model with no code, as a JSON column would be too, so backup coverage did not decide it. The previous value is not stored because it is always the deleted record itself. Skipping instead of refusing follows from what the person asked for: they want the category back, and one transaction that has since been filed elsewhere is their later decision, not a reason to keep the category deleted; the checks that concern the record itself — a tag name taken again, the rule limit, the household owner — still refuse the whole restore with a published code
- **2026-09-21.** Undo and the trash are built on one `DeletionEntries` table written beside each soft delete, not on a `DeletedAt` column added to `EntityBase`
  - Rejected: Adding `DeletedAt` to every soft-deleted table and answering the trash as a union over ten of them; writing the entry automatically from the `AppDbContext` soft-delete interceptor
  - Why: A union of ten paged, differently filtered queries would have had no stable sort or count and would grow a branch per new entity, while the column would have been a migration across roughly twenty tables to learn one timestamp. One table also stores what the union cannot: the description as the row read at the moment it was deleted, which is what a trash entry has to show when the record itself is now invisible, and the id of the fee transaction a conversion took with it. Writing it from the interceptor was rejected because a cascade would then get its own row — deleting a conversion would list the conversion and its fee as two separate things to undo — and because the description is feature knowledge that the interceptor would have to carry a registry for
- **2026-09-21.** Eight kinds are restorable; categories, tags, categorization rules and households are not, and archiving an account stays its own operation (replaced later on 2026-09-21 by the `DeletionChanges` decision above; archiving an account still stays its own operation)
  - Rejected: Restoring them partially and saying so; recording the ids each of those deletes rewrites so they could be undone too
  - Why: Deleting a category clears `CategoryId` on every transaction, split line and recurring entry and retires its budgets; deleting a tag removes its `TransactionTags` rows; deleting a rule removes its tag rows and renumbers its siblings; deleting a household un-shares every account, category and tag in it. A restore that gives the name back without the rows is not an undo, it is a second, quieter surprise, and the brief for this feature says to refuse rather than restore something broken. Recording the rewritten ids means an unbounded list per delete — a category can touch a year of transactions — for four operations that a household performs rarely and deliberately. An account is different again: its delete is called archive, it is already reversible in intent, and un-archiving belongs on the accounts screen where the archived accounts are, not in a list of things deleted in the last 30 days
- **2026-09-21.** `TransactionService.DeleteAsync` and `ConversionService.DeleteAsync` stop hard-deleting split lines; editing a split still replaces them
  - Rejected: Keeping the hard delete and refusing to restore any split transaction; soft-deleting `TransactionLine` with its own `IsDeleted` column and query filter
  - Why: Without the lines a restored split comes back with `IsSplit` true and no categories, which is the broken row the refusals exist to prevent, and refusing every split would have excluded the transactions most worth undoing. A line has no identity a user refers to, so the asymmetry is the honest one: an edit has a new set to put in their place, a delete does not. A soft-deleted line would need a filter on a table that is only ever reached through an already-filtered transaction, and `CategoryAttributionService` selects lines only for transactions its own filtered query returned, so orphaned lines are invisible to every reader. Rows deleted by an older version still have no lines and are refused with `restore.detailsLost`
- **2026-09-21.** Restore is `POST /api/trash/restore` with a body of `kind` and `entityId`, and answers 204 again for a record that is already back
  - Rejected: `POST /api/trash/{id}/restore` keyed by the trash row; making every `DELETE` answer 200 with the new trash row id; answering 409 on a second restore
  - Why: The undo toast fires in the moment after a delete and knows the kind and the id it deleted, never the id of a trash row it has not read; keying on the record lets the toast and the Restore button call one operation instead of two. Changing seventeen delete endpoints from 204 to a body to carry that id would have been a contract change across the whole product for one screen. Idempotence is what makes Undo safe when it is clicked twice, or clicked in the toast and then again in the trash, which is exactly the moment a conflict would be least welcome
- **2026-09-21.** There is no purge job; the 30-day window is a filter on the list and a refusal on restore (replaced on 2026-09-23 by the `RetentionJob` decision above)
  - Rejected: A nightly job that hard-deletes rows past the window; a shorter window with a purge; no window at all
  - Why: A purge would be the first destructive background job in this installation and the first code that hard-deletes ledger rows, with foreign keys from transfers, conversions, budgets and goals pointing at them, an order to delete in, and a restore-from-backup story to invent — all to save a row of about 120 bytes per delete, on top of rows the product has kept forever since its first release anyway. Without a window at all the list would grow without bound and would promise a restore for a row whose account, category and household context is years stale, which is the promise `restore.expired` exists to refuse
- **2026-09-21.** The trash is a section of `/profile`, and `/api/trash` is not in `FeatureGateMiddleware` — the service filters each row by the feature its kind belongs to
  - Rejected: A top-level `/trash` page with a sidebar entry; a section of `/settings`; gating the prefix on one feature; ignoring feature switches in the trash
  - Why: Settings is administrators only and the trash is every user's own records, while the profile already holds what belongs to the person rather than to a feature and already has the section navigation and a list section of the same shape; a top-level page would have needed a permanent navigation entry for a screen that is empty most of the time. The gate is by URL prefix, so a cross-cutting route cannot be gated at all without picking one feature arbitrarily; filtering per kind is what makes an installation with budgets switched off stop listing and stop restoring budgets, while transactions and transfers, which belong to no switch, keep working
- **2026-09-21.** The undo lives in the shared `useConfirmedDelete`, which takes an optional kind and also swaps the confirm dialog's wording
  - Rejected: A toast per screen beside each existing `toast.success`; always showing the undo wording in `ConfirmDeleteDialog`
  - Why: Seventeen screens use that hook and eight of them needed the undo; doing it per screen would have been eight copies of the same mutation, the same toast and the same action handler, and the ninth screen added later would have forgotten it. Making the dialog always say "you can undo this" would make it lie on categories, tags, rules, households and archiving an account, where the delete really is final — the optional kind is what lets one dialog tell the truth in both cases
