# 11. Milestones & tasks

A build order front-loaded on **developer experience** and on **getting something you actually use early**. Scaffolding, codegen, and feedback loops come first; then the **core ledger** (so the app is useful and validated by real use); then the **auth spine** before the app is ever exposed; then the rest. Milestones are roughly sequential; tick tasks as you go.

> [!tip] Each milestone ends with a **Definition of done** — don't move on until it's true. Decisions referenced as `D…` live in [[9. Open questions & decisions]].

> [!info] **2026-05-30 reset.** Build order changed: **ledger before auth** ([[9. Open questions & decisions|D51]]), **households & sharing deferred** to M6 ([[9. Open questions & decisions|D50]]), **2FA optional** ([[9. Open questions & decisions|D52]]), and **email decoupled from onboarding** ([[9. Open questions & decisions|D53]]). M0 is trimmed to "just enough to ship feature 1," with heavier tooling added as it earns its place.

> [!info] **2026-06-11 restructure.** The backend collapsed from 3 projects to a **single project** following the [minimal clean architecture](https://ardalis.github.io/CleanArchitecture/minimal-clean-architecture/) shape ([[9. Open questions & decisions|D59]]): `Domain/`, `Infrastructure/`, and `Endpoints/` (was `Features/`) are now top-level folders in `JxFinance.Api`; `Persistence/` became `Infrastructure/Data/`. Layering is unchanged and moves to namespace-based architecture tests (M0.5). The frontend moved to **actual file-based routing** (`@tanstack/router-plugin`, `routes/__root.tsx` + `routes/index.tsx` → generated `route-tree.gen.ts`) and gained its first `features/` folder, matching [[7. Architecture notes#Frontend structure]].

## M0.5 — Backend tidy & data-access seam (pre-M1)
A small, deliberate reorganization **before** the ledger lands — so M1 features are built on the intended shape rather than retrofitted. Keeps the **single-project vertical-slice** layout ([[9. Open questions & decisions|D45]], [[9. Open questions & decisions|D59]]), pins down the **data-access rules on the `DbContext`** ([[9. Open questions & decisions|D60]]), and adds a few cross-cutting wins. ([[7. Architecture notes#Backend structure]], [[7. Architecture notes#Data access]])

> [!info] **2026-06-11 revision.** The repository / unit-of-work seam originally planned here (D57) was built, then **removed the same day in favour of using `AppDbContext` directly** in feature services ([[9. Open questions & decisions|D60]]) — EF Core already provides both patterns, and the wrappers added indirection without value. The guardrail moved up a level: *endpoint classes* must not touch the context; services own data access.

> [!note] Informed by general .NET-API best-practices; the heavy patterns (**CQRS/MediatR, distributed caching, API versioning, message brokers**) are explicitly **deferred** — see [[7. Architecture notes#Backend conventions]].

**Target `JxFinance.Api` layout (tidied):**
```
JxFinance.Api/
  Program.cs                reads top-down: builder → AddApiServices()/AddInfrastructure() → pipeline → Run
  Extensions/               grouped DI + pipeline registration (AddApiServices, UseApiPipeline)
  Common/
    Errors/                 ProblemDetails mapping, Result→HTTP
    Middleware/             CorrelationIdMiddleware
    Processors/             FastEndpoints pre/post processors
  Domain/
    Common/                 EntityBase, OwnableEntity, Result<T>, IClock, DateRange
  Infrastructure/
    Auth/  Configuration/  Time/
    Data/                   AppDbContext, EF configurations, Migrations/
    DependencyInjection.cs
  Endpoints/
    Ping/
      IPingService.cs  PingService.cs
      GetPing/ { GetPingEndpoint, GetPingResponse }
```

### Data access ([[9. Open questions & decisions|D60]], supersedes D57)
- [x] Feature services inject **`AppDbContext` directly** — no `IRepository<T>` / `IUnitOfWork` wrappers; EF Core's `DbSet`/`SaveChangesAsync` are the repository + unit of work
- [x] Confirm soft-delete + (future) `UserId` query filters stay on the `DbContext`, so every query inherits them ([[9. Open questions & decisions|D24]], [[9. Open questions & decisions|D50]])
- [x] `DbContext` converts hard deletes of `EntityBase` rows into soft deletes, so `Remove` can't bypass D24 (audit stamps applied there too)

### Cross-cutting & tidy
- [x] `CorrelationIdMiddleware` — assign/honour `X-Correlation-ID`, enrich Serilog via `LogContext` ([[9. Open questions & decisions|D58]])
- [x] Group registration into `AddApiServices()` / `UseApiPipeline()` extension methods; slim `Program.cs`
- [x] Move error-handling + `Result`→ProblemDetails mapping under `Common/Errors/` (`ErrorCodes` + `ToProblemDetails`; first real consumer is M1)
- [x] Typed, startup-validated `AppOptions` *(already in place from M0; `ValidateOnStart()` added)*

### Guardrails
- [x] **Architecture test (NetArchTest), namespace-based** ([[9. Open questions & decisions|D59]]): endpoint classes must not reference `AppDbContext`/EF Core (data access lives in feature services, [[9. Open questions & decisions|D60]]); `JxFinance.Domain.*` depends on nothing ([[9. Open questions & decisions|D26]]) — *via `NetArchTest.eNhancedEdition` (the maintained fork; the original `NetArchTest.Rules` is frozen at 1.3.2)*
- [x] `just test` and the client-drift check stay green

> [!success] **Done:** the backend matches the documented shape — thin endpoint → feature service → `AppDbContext` (EF Core); correlation IDs in logs; `Program.cs` reads as a table of contents; an architecture test fails if an endpoint class reaches for `AppDbContext`. *(Ping doesn't hit the DB; the first real data access is M1's Accounts.)*

## M2 — Auth & hardening
The security spine — finish this **before the app is reachable** over WireGuard ([[9. Open questions & decisions|D51]]). It slots onto the `UserId` seam already in place. ([[3. User flows#Flow: Sign in]], [[6. API surface#Auth (MVP)]])

- [x] ASP.NET Core **Identity** + cookie auth, **1-day** session ([[9. Open questions & decisions|D36]]) — *cookie auth via `IdentityConstants.ApplicationScheme`; `rememberMe` issues a 30-day persistent cookie instead of the 1-day default*
- [x] `User` entity: `Role` (Admin/Member), `EmailConfirmed`, `TwoFactorEnabled` ([[5. Data model#User]]) — *`Role` via ASP.NET Identity roles rather than a scalar column; `EmailConfirmed`/`TwoFactorEnabled` come from `IdentityUser`; added `DisplayName`*
- [x] **First-run setup page** + `POST /api/setup` — admin sets a password **directly**, no email step ([[9. Open questions & decisions|D44]], [[9. Open questions & decisions|D53]]) — *reuses the existing seeded dev user row if present (no password set yet) so pre-M2 dev data isn't orphaned; `GET /api/setup/status` added for the frontend gate*
- [x] Login / logout / `me`; **"remember me"** longer cookie; swap the seeded user for the real session
- [x] **Optional 2FA (TOTP)** enrolment + recovery codes — offered, not required ([[9. Open questions & decisions|D52]]) — *`/api/auth/2fa/{setup,enable,disable}`; login accepts `twoFactorCode` (TOTP or a one-time recovery code) when enabled; verified end-to-end with a real RFC 6238 TOTP generator in both the backend test suite and a Playwright pass*
- [x] **Admin user management**: create a user with a password set directly, list, change role, deactivate ([[6. API surface#Users (MVP)]]) — *`GET/POST /api/users`, `PUT /api/users/{id}/role`, `POST /api/users/{id}/deactivate` (soft, via Identity lockout), `PUT /api/users/me`; an admin can't change their own role or deactivate themselves*
- [x] **Rate limiting** on `/auth/*` ([[9. Open questions & decisions|D27]]) — *FastEndpoints `Throttle()` on `/api/auth/login` (10/5min) and `/api/setup` (5/5min), per client IP*
- [x] Frontend: auth pages, route guards, optional-2FA + setup screens — *`/setup`, `/login` (two-step when 2FA is enabled), `/users` (admin-only, role-gated route + hidden nav item), `/profile` (display name/password, 2FA enrolment with QR + recovery codes)*

> [!success] **Done:** a fresh install walks first-run setup → admin signs in (2FA only if they enabled it) → can create another user who signs in and sees only their own data. Safe to expose over WireGuard.

> [!note] **Email features are deferred ([[9. Open questions & decisions|D53]]).** Email verification, password-reset-by-email, and notification email land later (set up in M5, or pulled earlier if you want them). The `IEmailSender` seam goes in here so they slot in cleanly.

## M6 — Households & sharing
Built ([[9. Open questions & decisions|D61]]) — scoped to Accounts + Categories rather than the full original D49 model. It adds onto the `UserId` already on every row as an *additive* migration, exactly as D50 anticipated. ([[5. Data model#Ownership]])

- [x] **Resolved the parked questions** ([[9. Open questions & decisions#Households & sharing — resolved for M6 (D50 → D61)|Households & sharing — resolved for M6]]): account re-scoping (allowed, history follows the account, free via the join), shared categories (yes, same scope model), member-leaves (falls out of the visibility rule, no special-case code), default scope (moot — no global switcher; Personal + Shared rows are listed together with a badge)
- [x] Added `Household` + `HouseholdMembership` tables; added `Scope` (`Personal`/`Shared`) + `HouseholdId` columns to `Account` and `Category` only (`IShareable`) — not to Budget/Goal/Asset/Debt/RecurringBill/Notification, which stay personal-only for now
- [x] **Account is the scope anchor** — chose the **join** over a denormalised copy: `Transaction`/`Transfer` have no `Scope` of their own, so re-scoping an account instantly re-scopes its whole history with a single-row update
- [x] Expanded the central filter: `ShareableFilter<T>` for `Account`/`Category` (`UserId = me OR (Scope = Shared AND HouseholdId ∈ my memberships)`), hand-written filters for `Transaction`/`Transfer` (join to `Accounts`), and for `Household`/`HouseholdMembership` (member-visible, not owner-visible) — **cross-scope leakage covered by an integration test**: a household member sees a shared account/transaction/household; a non-member gets 404s and empty lists on the exact same rows
- [x] **Households** + **member management** endpoints (household **Owner** role, independent of the app-wide Admin/Member role; a household always keeps ≥1 Owner) ([[6. API surface#Households (M6)]])
- [x] Frontend: Households page (create/rename/delete, add member by email, change role, remove member); Account/Category forms gain a Scope + Household picker (hidden entirely if you belong to no household); shared rows show a "Shared · household name" badge in the Accounts/Categories lists
- [ ] *Not built this pass, deferred to a future additive migration:* a dedicated Personal/household **active-scope selector** in the header — skipped because Personal + Shared rows already list together for just two shareable entity types, so a global switcher wasn't yet worth the added state; widening `Scope`/`HouseholdId` to Budgets/Goals/Net worth/Recurring bills

> [!success] **Done:** create a household, add an existing user by email, mark an account Shared; every household member sees and can edit it (including its transactions); a non-member sees nothing; personal accounts stay private.
